## Critical

### C1. virt の RAM は `0x40000000` から（direct map と LMA が virt で成り立たない）

- 所: design §3.2（direct map `0x80000000`〜 → PA `0x00000000`〜）、§3.12（`hal_pmem_to_kernel(p) = p + 0x80000000`）、§2.2（link VA `0x80100000`、PA `0x00100000`）、§4.6（ELF の `e_entry` = 物理 `_start`、LMA `0x00100000`）、boot-test 案（`-kernel build/armv7-virt/vmunix`）。
- 根拠: QEMU v10.0.11 `hw/arm/virt.c` 163 行 `[VIRT_FLASH] = { 0, 0x08000000 }`、194 行 `[VIRT_MEM] = { GiB, LEGACY_RAMLIMIT_BYTES }`（RAM は `0x40000000`）。
- 起こる事: virt では PA `0x00100000` は pflash。QEMU は ELF の segment を ROM blob として flash の上に置くので、命令は読めても `.data`・`.bss`・stack への store は flash の command になり、p004 の最初の C の関数で壊れる。仮に別の所に置いても、virt の RAM `0x40000000`〜`0x5FFFFFFF` に `+0x80000000` をすると `0xC0000000`〜 = device 窓と重なる。
- 修正案: BSP ごとの `ARMV7_PHYS_BASE`（zybo 0、virt `0x40000000`）を持ち、direct map を「VA `0x80000000` ↔ PA `PHYS_BASE`」、`hal_pmem_to_kernel(p) = p - PHYS_BASE + 0x80000000`、範囲の判定も `PHYS_BASE` 起点にする。`armv7-virt` の vmunix の LMA は `PHYS_BASE + 0x00100000`（C2 で raw の image にするなら QEMU の置き場所 `0x40010000`、下を見よ）。§7.1 の `readelf -h` の `e_entry` の期待値も platform ごとに。pte の host 試験に「PHYS_BASE ≠ 0」の場合を足す。

### C2. QEMU は ELF の kernel に DTB の pointer も initrd も渡さない

- 所: design §1.3「DTB を `r2` で渡す（`-kernel` の ELF でも `dtb_start = loader_start` に置く）」、§4.6「QEMU は DTB を `r2` で渡し、`-initrd` を `/chosen` に書く」、§7.2 p007 の `INITRD=root.img`、D3 の `armv7.initrd`（virt）、boot-test 案の hunk 3・5（`-initrd "$INITRD"`）。
- 根拠: QEMU v10.0.11 `hw/arm/boot.c`:
  - 956 行「Assume that raw images are linux kernels, and ELF images are not」。ELF の時 `is_linux = 0`。
  - 692〜721 行: `!info->is_linux` の reset は `cpu_set_pc(cs, entry)` だけで、`r0`〜`r2` を設定しない。
  - 1042〜1076 行: initrd の読み込みは `if (is_linux)` の中だけ。`initrd_size` が 0 なので 640 行の `/chosen/linux,initrd-start` も書かれない。
  - 957〜976 行: ELF の時、DTB は image が `loader_start` を覆わなければ `loader_start`（virt は `0x40000000`）に置かれる。`-append` は 630 行で DTB の `bootargs` に入る（これは働く）。
- 起こる事: virt の HAL は `r2` から DTB を見つけられない（`r2` は reset の値）。`-initrd` は黙って無視され、p007 の virt の `login:` は ramdisk 無しの `VFS initialization failed` で止まる。設計の「riscv32-virt と同じ」は riscv の boot の約束で、arm では違う。
- 修正案（どちらか、p004 の前に設計で決める）:
  - (a 勧め) virt は **Linux の起動の約束**で入る: `-kernel vmunix.bin`（raw）にすると QEMU は `is_linux = 1` で `0x40010000`（`KERNEL_LOAD_ADDR`、36 行）に置き、小さな loader で `r0=0`・`r1`=board id・`r2`=DTB として入り、initrd も読んで `/chosen` に書く。JTAG（§4.1 の 6）・後の U-Boot `bootm` と同じ「`r2` = DTB」の約束で 1 本にできる。kernel の入口は image の先頭、armv7-virt の LMA は `0x40010000`（あるいは入口の数命令を位置独立にして実際の pc から PHYS_BASE を求める）。boot-test 案の image の既定を `vmunix.bin` に。
  - (b) ELF のまま: DTB は「RAM の先頭 `0x40000000`」と決め打ち、ramdisk は `-device loader,file=root.img,addr=…` で置き、範囲は `-append` の boot parameter で渡す。D3 の `armv7.initrd` の出所が `/chosen` でなくなる。boot-test 案の `INITRD` の hunk も書き直し。
  - どちらでも §1.3・§4.6・§7.2 の文と boot-test 案の注を直す。最初の T1 の起動の前に、host で `qemu-system-arm -M virt … -S` と QMP の `pmemsave`／gdbstub で `r2` と DTB の `/chosen` を確かめる手順を p004 に入れる（log を読まずに判定できる）。

## High

### H1. QEMU zynq と実機の判別が逆になる

- 所: design §1.4「`-M xilinx-zynq-a9` に PL310 の model は無い」「`0xF8F02000` の CACHE_ID を読み、ARM の ID でなければ QEMU」「`PSS_IDCODE` は両方で読めるので使えない」、§3.6（QEMU なら 100 MHz）、§3.11・§3.14 `bsp_l2_present`。
- 根拠: QEMU `hw/arm/xilinx_zynq.c` 271 行 `sysbus_create_varargs("l2x0", MPCORE_PERIPHBASE + 0x2000, NULL);`、`hw/misc/arm_l2x0.c` 30 行 `#define CACHE_ID 0x410000c8`（75 行で返す）。同 `xilinx_zynq.c` 58 行 `ZYNQ_BOARD_MIDR 0x413FC090`（r3p0 と同じ値、223 行で設定）。一方 `hw/misc/zynq_slcr.c` は `PSS_IDCODE`（135 行）を read only にするだけで reset の値を設定しない（325〜378 行の reset に無い）→ QEMU では 0 を読む見込み（実測は未）。実機の PS の IDCODE は 7z010 の値（0 でない）。
- 起こる事: QEMU が「実機」と判定され、timer の周波数を QEMU の SLCR の reset 値から計算する（QEMU の `ARM_CLK_CTRL` reset `0x1F000400` で DIVISOR 4、ARM PLL FDIV 26 を PS_CLK 50 MHz で計算すると periphclk 162.5 MHz。実際の QEMU の timer は `arm_mptimer.c` 64 行で 10 ns/tick = 100 MHz）。tick が 1.625 ms 毎になるが `TIMER TICK` の文字は出るので、p005 の QEMU の受け入れは通ってしまい誤りが隠れる。
- 修正案: 判別を `PSS_IDCODE == 0` → QEMU にする（MIDR・PL310 は使えない）。jtag-boot の DTB と qemu-zynq.sh の DTB に区別の property（例 `/chosen/zedbsd,platform = "qemu"`）を入れて主にし、IDCODE を DTB 無しの時の予備にする案も良い。QEMU の受け入れにも速さの確かめ（QMP の `query-…` ではなく、guest の `TIMER 10S` の行の到着を host の時計で測る、実機と同じ方法）を足す。§1.4・§3.11 の「QEMU に L2 は無い」の文を直す（QEMU の l2x0 は register の箱だけで cache の振る舞いは無い）。

### H2. 短い descriptor に software の状態の置き場所が無い

- 所: design §3.2「L2 の table は 256 entry = 1 KiB、4 つを 1 page にまとめて割る」、§3.3「`HAL_SPACE_PAGE_DIRTY` は writable の page を AP で read-only に置き、最初の write の permission fault で dirty を立てて write を許す」、§7.1 `pte-host-test.c`、§7.6 (2)〜(4)。
- 根拠: `include/hal/hal.h` 720〜723 行（PRESENT・ACCESSED・DIRTY）、810〜822 行 `hal_space_prot_query`（古い translation 経由の store の観測を要求）。ARMv7 の small page descriptor の bit は XN・type・B・C・AP[1:0]（AFE=1 では AP[0] = AF）・TEX[2:0]・AP[2]・S・nG・PA で全部 hardware が使う（ARM ARM は読んでいない。この配置は一般の知識）。
- 起こる事: 「論理では writable で、dirty を取るために今 RO」の page と「本当に RO」の page を entry だけからは区別できない。DIRTY の値自体も持つ所が無い。permission fault を HAL の中で解決する（§3.3）時に誤って書き込みを許すか、本当の RO を dirty にする。pte の host 試験は descriptor の組み立てしか見ないので検出しない。
- 修正案: Linux の arm と同じ影の table を採る: 1 page（4 KiB）に hardware の L2 table を 2 つ（2 KiB、L1 の 2 entry 分）と同じ形の software の table を 2 つ（2 KiB）置き、software の側に writable・dirty・accessed・device の印を持つ。§3.2 の「4 つを 1 page」を「2 つ + 影 2 つ」に直し、`hal_space_destroy` の解放の単位も合わせる。TEX remap（SCTLR.TRE=1、PRRR/NMRR）で TEX[2:1] を OS に空ける案は、ARM ARM の該当の記述を確かめてから（推測なので今は採らない）。pte の host 試験に「論理 W・RO 中 → write fault → dirty・W」「本当の RO → write fault → `PAGE_FAULT` を kernel へ」の状態遷移を足す。

### H3. 1 CPU でも ACTLR.SMP と SCU の扱いが要る

- 所: design §3.5「二次 CPU の起動前に `ACTLR.SMP` を立てる」、§3.7「SCU: CPU0 が `SCU_CTRL` を立てる」（どちらも WS286 の外とされた SMP の節）、§3.2（Normal WBWA・Shareable、TTBR の S=1）、§3.2「entry を書いた後は `dsb` だけで足りる（A9 は walk が L1 を見る）」。
- 根拠: Linux v6.12 `arch/arm/mm/proc-v7.S` 295〜299 行 `__v7_ca9mp_setup` は L1 を invalidate し、broadcast と SMP bit の設定へ進む（SMP の kernel の時）。UP の kernel では Linux は shareable を付けず（`proc-v7-2level.S` 47 行 `ALT_UP(orr r0, r0, #TTB_FLAGS_UP)`）、page table の更新を clean する。Cortex-A9 TRM の ACTLR.SMP の記述（「SMP=0 の時、Inner Shareable な Normal memory を cache しない」趣旨）は読んでいない: **推測**。Zynq の DDR・OCM が global monitor（cache しない memory への ldrex/strex）を持つかも **未確認**。
- 起こる事（推測）: SMP=0 のまま Shareable で張ると L1 D-cache が効かず遅いか、ldrex/strex が global monitor に行き `strex` が成功しない spin lock の hang。また SMP=0 では page table の walk が L1 を見る保証が無く、§3.2 の「clean 不要」が成り立たない。
- 修正案: locore の MMU on の前に、A9 では SCU を有効にし（`SCU_CTRL` bit0。bit1 の address filtering など BootROM の値を保つ RMW）、`ACTLR.SMP=1` を立ててから D-cache と MMU を有効にする（FW は SMP の WS で）。あるいは WS286 の間は Shareable を全部外す（UP の Linux と同じ）。どちらを採るかを §3.2・§3.5 に書き、boot の self-test に (a) ldrex/strex の成功、(b) ID_MMFR3[23:20]（coherent walk）の値の表示、を足す。virt の A15 は QEMU なので差が出ない事も書いておく（実機の p005 で初めて分かる）。

### H4. userland の移植の範囲が足りない（rtld・libc の arch の file・TLS）

- 所: design §2.3（crt0/crt1/setjmp、elf.c、stat.h だけ）、§8 p007（16 LW）、§7.2・§7.4 p007 の `uname -m` → `armv7`。
- 根拠:
  - `toolchain/llvm/patches/0001-add-zedbsd-x86-target.patch` 305〜306 行: 既定は `IsPIE`（`-pie`）、366〜367 行 `-dynamic-linker /lib/ld.so`。userland は既定で rtld を通る。
  - `src/rtld/rtld.c` 27〜47 行の arch ごとの `RTLD_MACHINE`・`RTLD_RELATIVE`、351・379・524・530・648・651 行などの arch の枝、`src/rtld/entry-{aarch64,amd64,i386,riscv64,sparcv9}.S`、`src/rtld/elf.h` の relocation の番号（ARM の `R_ARM_*` は無い）。2103〜2114 行: variant I の arch では static TLS を作らず全部 dynamic（ARM も variant I）。
  - libc の arch の file: `userland/base/libc/syscall-aarch64.S`（設計は `__syscall6` を crt0 に置くと書くが tree では別 file）、`src/libc/setjmp-aarch64.S`、`userland/base/libc/static-tls.c` 229〜239 行（thread pointer の読み、arm の枝が無く 0 になる）、`userland/base/libc/posix.c` の `uname`（`#elif defined(__aarch64__)` の並びに arm が無く `"unknown"`）、`pthread.c` 3735 行付近の spin の hint。
- 起こる事: p007 で最初の program が `/lib/ld.so` を要求して起動しないか、`-static` に逃げても TLS（variant I、TCB 8 byte）の置き方が決まっていない。`uname -m` の受け入れは今の posix.c では `unknown` を返して落ちる。16 LW の見積もりは rtld の arm 版（relocation、PLT/GOT、TLS、entry）を含まない。
- 修正案: §2.3 に (1) rtld の arm 版（`entry-armv7.S`、`R_ARM_RELATIVE`・`ABS32`・`GLOB_DAT`・`JUMP_SLOT`・`TLS_DTPMOD32`・`TLS_DTPOFF32`・`TLS_TPOFF32`、`__tls_get_addr` か TLSDESC のどちらか）、(2) `syscall-armv7.S`・`setjmp-armv7.S`・static-tls.c・posix.c（`"armv7"` か `"armv7l"` を決める）・pthread.c の枝、(3) TLS の variant I の TCB 8 byte の約束（clang/lld の local-exec の offset と合わせる）を足す。あるいは WS286 は全部 `-static` で link すると決め、static の時の TLS の初期化の道を書く。p007 を rtld の Phase と最小の userland の Phase に分けるか、見積もりを見直す（rtld の arm 版だけで 8〜12 LW の増と推測）。

### H5. kernel の build に `KERN_USER_ABI_ARMV7` が無い

- 所: design §2.2（kernel の flag の列に `-DKERN_USER_ABI_ARMV7` が無い）、§2.3（sysroot の呼び出しにだけ有る）。
- 根拠: `platform/riscv32/vmunix.mk` 13〜15 行は kernel にも `-DKERN_USER_ABI_RISCV32` を渡す。`include/uapi/stat.h` 91〜98 行: 定義が有れば `struct stat` 92 byte（8 byte 揃え）、無ければ 80 byte（packed、aligned 4）。各側の `_Static_assert` は自分の側の値しか見ない。
- 起こる事: kernel は 80 byte、user は 92 byte の stat を使い、build は両方通る。p007 で `stat`/`fstat` の結果が壊れ、`ls`・`login` が謎の挙動をする。
- 修正案: `platform/armv7/vmunix.mk` の CPPFLAGS に `-DKERN_USER_ABI_ARMV7`（riscv32 と同じ形）を明記し、§2.2 の列にも足す。stat.h の枝に `KERN_USER_ABI_ARMV7` を足す時、kernel の build で「armv7 の HAL なら `KERN_USER_ABI_ARMV7` が定義されている」事を `#error` で確かめる 1 行を HAL 側に置くと再発を防げる。

## Medium

### M1. EABI の helper の表が足りない（32 bit の除算と `__aeabi_mem*`）

- 所: design §2.2（64 bit の helper だけ）、§2.3（「`aeabi_*` の list は p009 で確定」）。
- 根拠: Cortex-A9 は ARM mode の `sdiv`/`udiv` を持たない（一般の知識。A15 は持つ。virt の A15 で走らせても kernel は `-mcpu=cortex-a9` で build するので呼び出しは出る）。LLVM の ARM の AAPCS 向けの codegen は `memcpy`・`memset` の libcall を `__aeabi_memcpy`/`4`/`8`・`__aeabi_memset`・`__aeabi_memclr` に落とす（LLVM の source は読んでいない: 推測。p004 の `llvm-nm -u` で確かめられる）。`src/libc/int64.c` は 64 bit の C の関数だけを持つ。
- 起こる事: 全部の 32 bit の `/`・`%` で link が落ちる（`__aeabi_uidiv`・`__aeabi_idiv`、商と余りを r0:r1 で返す `__aeabi_uidivmod`・`__aeabi_idivmod` は asm が要る）。`__aeabi_memset(dest, n, c)` は `memset(dest, c, n)` と引数の順が違い、写し間違えると黙って壊れる。
- 修正案: §2.2 に必要な symbol の表を書く（`__aeabi_uidiv`・`idiv`・`uidivmod`・`idivmod`・`uldivmod`・`ldivmod`・`llsl`・`llsr`・`lasr`・`memcpy{,4,8}`・`memmove{,4,8}`・`memset{,4,8}`・`memclr{,4,8}`）。compiler-rt の `lib/builtins/arm/*.S` を使うなら license（Apache-2.0 WITH LLVM-exception）の扱いを Guardrail と照らす。int64.c の host 試験に `__aeabi_memset` の引数の順と divmod の両方の戻り値を足す。§2.3 の「p009 で確定」は p007 の誤記と思われる。

### M2. virt の PSCI は HVC

- 所: design §1.3・§3.7（`smc #0`、`CPU_ON`）、§3.13（`hal_reset` = PSCI `SYSTEM_RESET`、`hal_poweroff` = `SYSTEM_OFF`）。
- 根拠: QEMU `hw/arm/virt.c` 2186〜2192 行: `vms->virt`（virtualization=on）の時だけ SMC、既定は HVC。
- 起こる事: `reboot`/poweroff が A15 の EL3 の無い CPU で `smc` を未定義命令にし、kernel の panic か fault。
- 修正案: DTB の `/psci` の `method`（`"hvc"`/`"smc"`）を読んで選ぶ。boot-test の既定の `-machine virt` では HVC。

### M3. `hal_cpu_idle` の不可分性

- 所: design §3.6「`hal_cpu_idle` = `wfi`（IRQ を enable して）」。
- 根拠: `include/hal/hal.h` 194〜197 行「Atomically enable interrupts and halt, then return with IRQs disabled.」
- 起こる事: `cpsie i` の後・`wfi` の前に来た割り込みは処理され、その後の `wfi` が次の tick（最大 1 ms）まで眠る。kernel の wake の取りこぼし。
- 修正案: IRQ を mask したまま `wfi`（ARMv7 は mask 中でも pending の割り込みで起きる）、続けて `cpsie i`・`cpsid i` で handler を走らせて戻る。§3.6 にこの順を書く。

### M4. devcfg/PCAP の手順の抜け

- 所: design §5.6 の 1〜8、「PL の有効化」、§5.6.1。
- 根拠: Linux v6.12 `drivers/fpga/zynq-fpga.c`:
  - 420・439 行: DMA の前後で `INT_STS` に `IXR_ALL_MASK` を書いて消す。
  - 166〜170 行: `STATUS_DMA_Q_F` を見て queue が満杯なら止め、`DMA_DONE` の割り込み（225〜226 行）で続きを積む。
  - 397〜405 行: 各 chunk は 8 byte 揃え・4 の倍数（UG585 p.212 の引用）。
  - 497〜499 行: `PCFG_DONE` は `INT_STS` の bit 2（`IXR_PCFG_DONE_MASK`、89 行）を poll。597 行: probe で `INT_STS` を全部消す。
  - 354 行付近: `CTRL` は read-modify-write で `PCAP_PR | PCAP_MODE`（暗号化の時だけ `RATE_EN`）。
  - QEMU の model（`xlnx-zynq-devcfg.c` 220〜236 行）も UNLOCK に違う値を書くと device を閉じる。
- 起こる事: (a) BootROM・前回の program の `D_P_DONE` が残ったまま待つと、DMA の完了前に「済んだ」と判断する。(b)「buffer が複数なら最後だけ |1」で queue の深さを超えて積むと command を失う。(c) PCFG_DONE を STATUS で待つと永久に来ない。JTAG で PL を書いた後の `fpgaload --enable` は INT_STS の PCFG_DONE を見るが、attach で INT_STS を消すと（Linux の probe の形を写すと）見えなくなる。(d) `CTRL` を丸ごと書くと FORCE_RST・JTAG_CHAIN_DIS・DAP_EN などを壊し、PS の reset か JTAG（この WS の唯一の起動と回復の道）を POR まで失う（bit の位置は UG585 未読の記憶: 推測）。
- 修正案: 手順に「DMA の前に INT_STS を全部消す」「PCFG_DONE は INT_STS bit 2」「attach では INT_STS を消さない（PCFG_DONE を保つ）」を足す。buffer は 1 つの物理連続の coherent 領域（2.1 MB）にするか、Q_F を見て DMA_DONE で積み足す。8 byte 揃えを確かめる。CTRL の書き込みは許す bit（PROG_B・PCAP_PR・PCAP_MODE・PCAP_RATE_EN）だけを変える helper に閉じ込め、host 試験でその mask を確かめる。UNLOCK には `0x757BDF0D` 以外を決して書かない事を comment と試験で固定する。

### M5. QEMU の devcfg は PCFG_INIT・PCFG_DONE を立てない

- 所: design §5.6「手順の register の遷移は QEMU で確かめられる（PL は無いので PCFG_DONE は model が立てる）」、§7.3 p008、§8 p008 の到達点「devcfg の手順（QEMU zynq）」。
- 根拠: QEMU `hw/dma/xlnx-zynq-devcfg.c` 177〜178 行: DMA の完了で立てるのは `DMA_DONE | DMA_P_DONE` だけ。292〜294 行: STATUS の reset 値に `PCFG_INIT` が無い。PROG_B に反応して INIT を変える code も無い。
- 起こる事: 手順 4 の「INIT を待つ」が 2.5 s で timeout し、QEMU の p008 は必ず落ちる。
- 修正案: QEMU で確かめるのは `fpgaload --status`・UNLOCK・CTRL の mask・DMA の queue と `D_P_DONE` までと書き直す（PROG_B の手順は実機だけ）。DMA の部分を QEMU で通したいなら、試験用の boot parameter で PROG_B の待ちを飛ばす道を driver に明示して作る（既定では無効）。

### M6. lazy な VFP の欠落と試験の穴

- 所: design §3.10、§3.9（signal で VFP を `signal_fpregs` に保つ）、§7.2〜§7.4（p006 の到達点は `VFS initialization failed`、p007 は `login:`・`uname`）。
- 根拠: 同じ方式の `src/hal/mips/fpu.c` は `mips_fpu_sync`（201 行〜: 保存してから読む）と `mips_fpu_forget`（228 行〜: owner を捨てる）を持つ。設計 §3.10 は switch と undef の道しか書かない。
- 起こる事: (a) fork・signal の入口・debug の読み（`hal_fpregs`）で hardware の中の最新の値でなく古い保存値を写す。(b) exec の後に前の image の FP の値が残る。(c) task の破棄の後も per-CPU の owner が古い task を指し、次の undef でその解放済みの領域へ保存する（use-after-free）。(d) undef の判定を「VFP/NEON の命令」に限ると NEON の符号（`0xF2xxxxxx`〜`0xF4xxxxxx`）や Thumb を漏らす。(e) sh・login・ls は浮動小数点を使わない見込みで、WS286 の受け入れは lazy の道を一度も通さない。
- 修正案: §3.10 に sync（fork・signal_enter・get_fpregs・transfer の前）と forget（exec・destroy）を明記する。undef は「FPEXC.EN=0 で user から来たら EN=1 にして同じ命令をやり直す（本当の未定義なら EN=1 で再び undef → SIGILL）」の単純な形にし、lr の巻き戻しを書く。p007 の到達点に、2 つの process が d0〜d31 と FPSCR に違う値を置いて互いに switch しても保たれる、signal の handler が VFP を使っても戻った後の値が保たれる、を確かめる小さな試験の program を ramdisk に足す（virt の PNG で `VFP PASS`）。

### M7. 排他の monitor を閉じる

- 所: design §3.3・§3.1 dispatch.S（context switch・user への戻り）。
- 根拠: ARMv7 では例外の入口・戻りで local monitor が消える保証が無く、OS が switch で `clrex`（か dummy の `strex`）をする（ARM ARM は読んでいない: 推測。Linux arm の例外の戻りも同じ目的の命令を持つと記憶）。
- 起こる事: user の thread A が `ldrex` の後に横取りされ、別の thread が同じ番地を書いた後に A に戻ると、A の `strex` が成功し得る（A9 の local monitor は番地を見ない実装と推測）。user の lock が壊れる。
- 修正案: dispatch.S の switch と user への戻りの直前に `clrex` を置くと §3.3 に書く。

### M8. Cortex-A9 r3p0 の erratum

- 所: design §3.5（ASID の切り替えの順）、§3.3（abort の handler）。
- 根拠: Linux v6.12 `arch/arm/Kconfig` の `ARM_ERRATA_754322`（「Cortex-A9 (r2p*, r3p*)」、SMP の条件無し）と `ARM_ERRATA_775420`（「r2p2, r2p6, r2p8, r2p10, r3p0」、data cache の maintenance の abort で deadlock）。`arch/arm/mm/proc-v7-2level.S` 53〜55 行: 754322 は CONTEXTIDR を書く前の `dsb`。SMP の WS には 751472・764369 も要る。QEMU は erratum を再現しない（`ZYNQ_BOARD_MIDR` は r3p0 でも挙動は理想の CPU）。
- 起こる事: 実機だけで稀な誤った translation（ASID の切り替えの直後）や、user の範囲の cache maintenance（後の `cacheflush`）の abort での hang。
- 修正案: §3.5 の順の先頭に `dsb`（754322）、abort の入口に `dsb`（775420）を書き、SMP の WS の設計の注に 751472・764369 を残す。

### M9. direct map の最初の 1 MiB と async abort

- 所: design §3.2（direct map の section、Normal WBWA）、§3.12（PA `0x0`〜`0xFFFFF` を予約）、§4.1 の 6（`cpsr` = `0x1D3`、A を mask）、§3.3（external abort `0b10110` → `MACHINE_CHECK`）。
- 根拠: U-Boot v2025.07 `arch/arm/mach-zynq/cpu.c` 55〜66 行: `filter_start = 0` と `OCM_CFG = 0x1F` は U-Boot 本体（`#ifndef CONFIG_XPL_BUILD`）だけ → JTAG の流れでは PA `0x0`〜`0x2FFFF` は OCM、その上の 1 MiB 未満は SCU の filter の外（UG585 未読、DDR が見えない事は推測）。
- 起こる事（推測）: 予約しても、VA `0x80000000` の section が PA 0 の穴を Normal cacheable で張っているので、prefetch・投機の読みが穴に行くと imprecise external abort。入口の CPSR.A=1 のまま A を開けないと、その abort は保留されたまま、または後で原因と関係無い所で出る。
- 修正案: direct map の最初の 1 MiB の section は張らない（zybo）。kernel か jtag-boot が U-Boot 本体と同じ `OCM_CFG = 0x1F`・`filter_start = 0` を行って JTAG と後の SD の起動の memory の地図を揃える案も比べる（CPU1 の BootROM の loop は高位の OCM のままなので触れない、ただし実機で確かめる）。VBAR を設定した直後に `cpsie a` すると §3.3 に書く。

### M10. SwitchBot の記録の食い違い

- 所: [ws.md](../ws.md)「現在の状態・再開点」の 2 行目「電源は SwitchBot のプラグ AC276E42B252（VF2 から付け替え、ユーザー「AC276E42B252をプラグします。認識の通りです。」）」と、同じ節の 3 行目「ZYBO は USB 給電、SwitchBot は未接続」、design §12 D2・冒頭の引用「Switchbotは既存のもの」。
- 起こる事: どちらが今の事実か分からない。プラグが本当に ZYBO 側に移ったなら、VF2 の道具（memory の「VF2 board SSH deploy」のプラグと同じ ID）が ZYBO の電源を切るか、その逆。R15 の「DAP が戻らない時はユーザーが USB を抜き差し」も、プラグで代われるかが変わる。
- 修正案: Q1 がユーザーに今の配線を確かめ、ws.md の 2 行を 1 つの事実に直す（原文の引用は残す）。VF2 の道具の側の注にも反映する。

### M11. Phase の依存・受け入れ・見積もり

- 所: design §8・§10、[ws.md](../ws.md) の Phase の表。
- 指摘:
  1. U3（serial の対話で判定）は p005 だけの依存に書かれているが、p005〜p008 の実機と QEMU zynq の受け入れの全部が U3 に拠る。U3 が否なら p005 以降に受け入れの道が無い。p005 以降の全部の依存に U3 を書く。
  2. p006 の到達点 `VFS initialization failed` は task・syscall・signal・VFP・fork を何も確かめない（user の process がまだ無い）。p006 の受け入れに kernel の中の self-test（user mode への遷移、syscall の往復、signal の入口と戻り、VFP の lazy）を足すか、それらの受け入れを p007 に移して p006 の LW を見直す。
  3. p007 の 16 LW は H4 の rtld・libc の分を含まない。
  4. 「Q1: LLVM に ARM」は critical path の先頭で、memory の「LLVM patch level needs new cache」により rev-0 の cache asset の upload と digest の更新が要る（GitHub への公開 = ユーザーの指示が要る操作）。待ちの見積もりと誰が upload するかを §10 の依頼 1 に書く。
  5. C1・C2 の直しで boot-test 案（Q1 の適用）が変わるので、Q1 は今の案を適用しない方がよい。

## Low

- **L1 QEMU zynq の細部**（design §5.1・§5.6.2・§3.13・§7.3）:
  - `hw/arm/xilinx_zynq.c` 467 行 `ignore_memory_transaction_failures = true`: GP0 の読みは bus error でなく 0 を返す（§5.6 の最後の文の「bus の error」は誤り）。
  - `hw/char/cadence_uart.c` 519 行: CR の reset は `0x128`（TX・RX は無効）、340 行で TX が無効なら書いても出ない。QEMU には SPL が無いので、§5.1 の「U-Boot が設定した baud を保ち、CR の enable だけ確かめる」は「無効なら MR・BAUDGEN・BAUDDIV・CR を設定する」にする。
  - `hw/misc/zynq_slcr.c` 471 行: `PSS_RST_CTRL` は store だけで reset しない → QEMU zynq の `reboot` は何も起きない。`hal_reset` の後は park して止まる事を書く。
  - QEMU zynq も `-dtb` を受け、ELF の時は PA 0 に置き `bootargs` を `-append` から書く（`boot.c` 957〜976・630 行）。`-device loader` で `0x01F00000` に置く今の案でもよいが、`-append` が効かない事の理由は「DTB が無いから」で、`-dtb` を渡せば効く。
- **L2 例外の分類の表**（§3.3）: `bkpt` は ARMv7 では Prefetch Abort（IFSR の debug event）で、Undefined の行の「`bkpt` → BREAKPOINT」と矛盾する（Prefetch Abort の行の記述が正しい）。DFSR の符号に domain fault（`0b01001`/`0b01011`）、table walk の external abort（`0b01100`/`0b01110`）、icache maintenance（`0b00100`）が無い。DFSR.CM（bit 13）の扱いも書く。LLVM の `__builtin_trap` は `udf` 系の符号で `ILLEGAL_INSN` になる事も。
- **L3 例外の時の stack の揃え**（§3.3）: kernel の中で SVC の sp が 8 byte 揃えでない瞬間に例外が来ると、C の handler が AAPCS の 8 byte 揃え無しで走る。Linux の `svc_entry` のように sp の bit 2 を見て揃え、戻りで戻す。
- **L4 OpenOCD の細部**（§4.3・§7.5）:
  - OpenOCD 0.12 では `ftdi serial` は旧名で `adapter serial` が今の名前（旧名も動くが警告）。
  - upstream の `zynq_7000.cfg` に `0x03722093` が無く `-ignore-version` も無い事は確認した（設計どおり）。自分の宣言は `-ignore-version` か `-expected-id 0x03722093` のどちらかで足りる。
  - p003 の `mdw phys 0x43C00000` は止めた cortex_a の CPU に読ませるので、GP0 が応答しない時は CPU が debug の中で固まる。`zynq.ahb`（mem_ap）で読めば DP の ABORT で回復できる見込み（推測）。§7.5 の順も、Linux の手順（level shifter を閉じて書き、書けてから開ける）に合わせて `pl-jtag.sh` の後に `zybo_pl_enable` にする。
  - OpenOCD を timeout で kill すると DBGDSCR の halting debug の bit が残り、kernel・user の `bkpt` が Prefetch Abort でなく CPU の停止になり得る（推測）。jtag-boot は `shutdown` で終える事、kill した時は次に `jtag-reset.sh` を挟む事を書く。
- **L5 jtag-boot の入口と配置**（§4.1・§4.4）: 入口を `0x00100000` の決め打ちでなく ELF の `e_entry`（か `_start` の symbol）から取り、`_end`（BSS の終わり）が DTB の `0x01F00000` と ramdisk の `0x04000000` に届かない事を load の前に確かめる。`board_init_f` は `ps7_init()` の戻り値を見ない（U-Boot `mach-zynq/spl.c` 25〜31 行）ので、p002 の DDR の 4 MiB の verify は必須のまま残す。
- **L6 toolchain の文面**（§2.1・§2.4・§10）: 作り直しの時間が §2.4 は 20〜60 分、§10 は 30〜60 分。`-mtp=cp15` の既定は clang の `Driver/ToolChains/Arch/ARM.cpp` の側の判定で、`ZedBSD.cpp` に置けるかは patch を書く時に確かめる（patch の行数が 60〜80 より増え得る、推測）。TTBR の IRGN は Multiprocessing Extensions の時 bit 6 と bit 0 に分かれる事を §3.2 に書く。
- **L7 `FPGA_IRQ_WAIT` の意味**（§5.6.2・§7.7）: 「呼び出しの最初に unmask し、待つ間に来た数を返す」か「前回からの保留の数を返す」かを決める。§7.7 の 4 は `write 0x20 2` と `wait` が別の process なので、前者では最初の割り込みを失わない事（level のまま残る）に依存する。待ち手が 2 つの時の扱い（`EBUSY` か両方を起こすか）も。
