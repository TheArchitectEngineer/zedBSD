## 方法

道具は P2 の scratchpad の Python（tree に入れていない、`python3 -I` で実行）。ws218-p001 の `csim.py`・`cruns.py`・`ccom.py` を写し、識別子の接頭辞の除去だけを Venus 用（`vn_`・`vkr_`・`vulkan_`・`venus_`・`gpu_op_`・`vk_command_type_`・`i915_vk_` など）に変えた。名前の照合は新しく書いた `idx.py`（A と B に共通の識別子から、Khronos の Vulkan header の名前と C・POSIX の語を除く）。

- `csim.py`: token の k-gram の一致。**ident**（接頭辞を外し小文字、数は値のまま: 名前つきの写し）k=8・12、**norm**（識別子 → I、数 → N: 名前を付け替えた写し）k=20、低情報の gram を除く `MIND=10`。
- `cruns.py`: ident k=12 で 14 token 以上、norm k=20 で 28 token 以上続く一致を両側の file:行と本文で出し、目で分類した。
- `ccom.py`: comment（license の block を除く）の 5 語の一致。
- 目視: libvulkan の生成器 `tools/maintain-codec.noct` と Venus の生成器 `vn_protocol.py`・生成物（`vn_encode_VkBufferCreateInfo` など）、`wire.c` の primitive と `vn_protocol_driver_types.h`、reply の流れ（`context.c` と Mesa `vn_ring.c`・`vn_instance.c`）、capset の読み方（`context.c`・kernel `transport.c`）と `venus_hw.h`、i915 の `render/transport.c` と virglrenderer の `vkr_transport.c`。
- 値の照合: `include/uapi/gpu-op.h` の番号を `VK_EXT_command_serialization.xml` と機械で突き合わせた。MESA の構造体の型の値を `VK_MESA_venus_protocol.xml` の extension 番号（385）と offset から計算して突き合わせた。

### encoder・decoder の生成 code（目視、確かめた事実）

- **libvulkan の encoder・decoder は Venus の生成器も生成物も写していない。** `codec.c` は zedBSD の Noct の生成器 `tools/maintain-codec.noct`（249 行、Zlib）が zedBSD の公開 header（Khronos の宣言）を読んで作る。Venus の `vn_protocol.py`（Python＋Mako の templates）とは作りが違う: (1) Venus は struct ごとに `_pnext`・`_self`・本体と `vn_sizeof_*` の 4 関数に分け、pNext の chain を struct ごとの `switch` で辿る。zedBSD は 1 関数で、pNext は「core 1.0 では常に 0」か、2 つの私的な外部 memory の宣言（`wire.c:20-98`）だけ。(2) Venus は pointer が NULL でなければ配列を送る。zedBSD は `VK_SHARING_MODE_CONCURRENT` の時だけ queue family の配列を送り、immutable sampler は型で絞る（`maintain-codec.noct` の `pointerRule` の後の条件）。(3) zedBSD は書き込みの失敗を `writer->error` に保って後の field を読まない、Venus は先に大きさを測って encoder を確保する。配列の長さの規則（`pointerRule` の 52 行）は Vulkan の `vk.xml` の `len` 属性（Khronos の事実）と同じ値で、Venus の生成器も同じ所から読んでいる。
- 例: `VkBufferCreateInfo` の Venus（`vn_protocol_driver_buffer.h:184-236`、`_pnext`・`_self`・本体の 3 関数、`vn_encode_VkFlags(enc, &val->flags)` …）と zedBSD（`codec.c:2685-2727`、1 関数、`vulkan_write_u32(writer, record->flags)` …）。一致するのは field の順と幅（wire の layout の事実）だけ。
- **i915 の実行器の codec**（`src/drivers/gpu/i915/render/vulkan-codec.inc`）は `plan/ws031/handover/tools/gen_vk_server_codec.py` が zedBSD の `codec.c` から「文ごとの鏡」として作る。Venus の renderer の decoder（`vn_protocol_renderer_*.h` の `vn_decode_*_temp`・`vn_replace_*_handle`）とは ident k=12 で 0 の一致。BC（V3D）の decoder も 0。
- wire の primitive（`wire.c:205-385`）: little endian の 4・8 byte、float は bit をそのまま、byte 配列は 4 byte に詰めて padding を 0 にする、pointer は u64 の 0/1、文字列は NUL 込みの長さ。Venus（`vn_protocol_driver_types.h` の `vn_encode_blob_array`・`vn_encode_simple_pointer`・`vn_encode_array_size`）と同じ wire の形だが、書き方は別（zedBSD は byte ずつ組む、容量を倍で伸ばす、allocator の callback を使う）。
- reply の扱い: zedBSD は各 transaction の前に 178（reply の stream の指定）、後に 179（位置の移動）＋137（`vkEnumerateInstanceVersion`）の trailer を付け、最後の版の word が書かれるのを poll して完了を知る（`context.c:1096-1125`）。Mesa は ring（`vn_ring.c:623`）と roundtrip で、この trailer の作りは Mesa に無い。zedBSD 独自の設計。

## 結論（判断の材料）

### (A) Venus の著作権表示を外せるか

- 確かめた事実: Venus（Google）の著作権表示・SPDX・license の file は WS167 の p002（`cf0318f00`）で既に外れていて、今の tree と image の inventory に無い。今回の比較でも、zedBSD が Venus から使っているのは command の番号、MESA の構造体の型の値、wire の layout、capset の layout という interface の事実だけで、code の文・表の作り・comment・関数の分け方・生成器の写しは見つからなかった（機械比較は対照と同じ水準。LV の高い値は Khronos の公開 API の宣言の分）。
