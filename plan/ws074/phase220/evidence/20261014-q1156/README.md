# q1156-i01 — non-Grid vertical-rl geometry and paint diagnosis

The [minimal page](vertical-rl-inline.html) is q1144's non-Grid vertical-lr fixture with only `writing-mode:vertical-rl` changed. It contains a single ASCII run and two explicit-break lines in 100×100 content boxes. [Rectangles](summary.json): Chromium 153 places the single span at `(99,9,11,36)` and the two-line span at `(89,111,21,36)`, progressing from the right edge. The browser places them at `(9,9,36,10)` and `(9,111,36,20)`, horizontally from the left. The 10 versus 11 pixel line thickness is a font difference between the fixed browser font and Chromium's system monospace, so this comparison diagnoses axis and side, not exact font metrics.

[Layout dump](browser.layout.txt) retains horizontal text fragments and downward line stacking; [paint dump](browser.paint.txt) puts successive glyphs at x9, x15, x21. [Browser CPU](browser.png) and [Chromium](chromium.png) show the direction difference. Browser CPU and GPU PPM renders are byte-identical (`d6ad43d5bf04bc017352d48422e8370bbaf70af0a93ddbd6bf818225cfef328e`), so both currently paint the same horizontal result. Source confirms `layout/inline.c`'s simple vertical path and definite Grid room accept vertical-lr only; private paint rotation is gated on `vertical_inline`, which stays false here.

A bounded next implementation can extend the existing simple vertical text path to vertical-rl/LTR explicit-height blocks and fixed Grid children: measure physical inline advance, stack lines from right to left, preserve DOM bounds/hit and rotate sideways Latin glyphs through the existing CPU/GPU item path. Fixed Grid rows then need right-to-left physical placement separately; implicit auto tracks and margins/frames need another scope. This is a design hypothesis for the next Queue, not a verified change.
