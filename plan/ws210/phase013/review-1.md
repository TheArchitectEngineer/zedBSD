# WS210 p013 review-1（design-reviewer、3fdaa73c6）— 要点の写し（全文は Q1 の会話の記録）
結論: このままでは実装不可。H1 は人の判断、H2〜H4 を設計 1.1 で直す、Pi の baseline（TFU の on/off、hover・scroll の 1 frame）を先に。
H1 E1 は Guardrail「画像の処理は GPU で」（plan/guardrail.md:230-232）に反する: 部分の copy は kernel の CPU の行の copy（vulkan-buffer-copy.c:262-273、vulkan-native-job.c:197-224）、compositor の snapshot_update も CPU（native-storage.c:657-750、TFU 有効でも 256KB 以下は CPU :26・:710-712）。TFU が有効な機体（812bbb111、v3d-diagnostic.c:118-126）では今は CPU が画素を触らないので E1 で増える。案 (a) 例外の承認 (b) GPU だけ: kernel の buffer_image_whole（vulkan-native-image.c:653-722）を draw を覆う 64x64 の tile に限った tile pass に広げる（staging は常に frame 全体が正しいので tile 単位で丸ごと書いて正しい、P3・WS141）。
H2 kern_memcpy（src/kern/kcrt.c:114-145）は src・dst が 8B 揃いの時だけ word、他は 1B ずつ、-mgeneral-regs-only（platform/arm64/vmunix.mk:21）、native の memory は uncached（vulkan-memory.c:417）、offset y*pitch+x*4（vulkan-buffer-copy.c:533-536）で x 奇数なら 1B の uncached の load/store（推測 4〜8 倍遅い）、controller-protected の間（:203）に compositor の job も待つ（推測）。scroll など大きい部分は全部 CPU（whole でないと GPU の tile の経路に乗らない vulkan-native-image.c:690-701）。直し: draw の x と幅を 16px（64B）に揃える、面積がしきい値（25〜40%、Pi で決める）を超えたら全体の 1 region で GPU の tile の経路、P3 に kernel の uncached copy の高速化（ldp 64B 単位）か H1 (b)。
H3 acquire の semaphore を COLOR_ATTACHMENT_OUTPUT で待つ（present.c:280）、E1 は transfer だけ → wait の stage を TRANSFER（か ALL_COMMANDS）、最初の barrier を srcStage=TRANSFER・srcAccess=0、copy の後は TRANSFER→BOTTOM_OF_PIPE。
H4 staging の先書き（present.c:246-258）で acquire・submit の失敗時に part がどの stale にも入らず古い画素が残る。kernel は barrier の oldLayout を FIFO の実際の layout と照合（vulkan-barrier.c:158-161）、copy の時も（vulkan-buffer-copy.c:250）。直し: staging に写した時点で全部の j に stale[j] ∪= part、vkQueueSubmit 成功の後で stale[i] を空・whole[i]=0、submit より後の失敗では全部の whole を立てる、oldLayout は whole[i] なら UNDEFINED でなければ PRESENT_SRC。
M1 E3 はどの対象でも通らない（zedBSD の WSI は B8G8R8A8 と TRANSFER_DST を出す wsi-wayland.c:309-312・344-356、Linux の compositor は ARGB8888 だけ gpu-dmabuf.c:111）、bcm2711 は loadOp に関わらず tile を load（vulkan-native-pass.c:455-456）、i915 は renderArea を保持しない（command.c:1331・1353）→ E3 を削り、R8G8B8A8 だけの surface は staging へ写す時に R/B を入れ替え、TRANSFER_DST が無い surface は今の quad の全体の経路を残す。
M2 zedBSD の WSI は app の image を読むだけで保持（wsi-swapchain.c:2524-2660、1254-1340）。規格の明文は確認できない。present.c:562 の clipped=VK_TRUE は VK_FALSE に。libkeiland で OS の macro は使えないので、常に保持に頼り debug の環境変数で全体の copy を強制、自己検査の mode（present の後に読み戻して staging と比べる）。
M3 見積もりの 13ms は CPU の変換の値、TFU 有効の今の main では違う。incremental の TLB copy と snapshot は実機未確認（phase001 review-1 M8）→ baseline を取る、p013 が WS141 p016（TFU）と実機の確認に依存すると記録。
M4 stale が外接矩形 1 つに膨らむ（kernel の written_box も 1 つ vulkan-buffer-copy.c:656-686、snapshot の部分は 256KB まで）→ stale を少数（4 個まで）の矩形の list、複数 region（kernel の上限 64 vulkan-buffer-copy.h:14）、和がしきい値を超えたら全体の GPU の経路。
M5 試験: acquire の順は保証されない（wsi-swapchain.c:3057-3085）→ 任意の順・同じ image の連続・失敗の注入。i915 の揃っていない bufferOffset の部分の copy（command.c:2806-2935）は未検証。Linux・FreeBSD の guest は WS210 では許可が要る。T1 の PNG の比較の基準は M2 の強制全体と自己検査で。
M6 完了の条件と調べの上限が無い、ws.md の Resume point に p013 が無い。
L1 present_targets が 8 枚で切る（present.c:631-635）→ 先に枚数を問い合わせて確保。L2 staging の usage に TRANSFER_SRC（kernel が検査 vulkan-buffer-copy.c:389）、HOST→TRANSFER の barrier は不要。L3 B8G8R8A8 の swapchain は Pi で未通過だが code は byte を保つ（vulkan-native-image.c:522-526、native-pass.c:355、gpu-zedbsd.c:88-94、vulkan-native-draw.c:379-381）→ Pi の確かめに含める、switcher の縮小画像と screenshot も。L4 E2 の算法を純関数の module にして p005 で再利用。
Pi の見積もり（推測、hover 228x140、3 frame の和で 228x300）: staging への書き込み 0.1〜0.3ms、kernel の行の copy x 偶数 0.5〜1.5ms・奇数 3〜10ms、compositor の snapshot の部分の変換 0.6〜1.5ms、合計 1.5〜4ms（揃えた場合）。
