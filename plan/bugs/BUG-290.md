# BUG-290: Raspberry Pi 4 で Settings の窓を undock（dock の後の double click）すると Settings が必ず落ちる

- 状態: reproduced（Pi 4 の実機、ユーザー「Undockすると100%落ちるようです。」） / tracking（2026-10-12 から P2 が担当、2026-10-11 ユーザー「Bug は P2 が直す」。直しの候補と診断の行を入れた版の Pi での再現待ち）
- 発見: 2026-10-12 ユーザー、WS141 p013 の測定の時。
- 観察: Settings の窓を dock（最大化、1904x1020 への resize は成功）の後、double click で undock（1180x800 への resize）すると、`ZSETTINGS FAILED operation=kl_window_present_resize result=-3` の後に client が切れる。-3 は Settings の present.c が libkeiland の EIO を `VK_ERROR_INITIALIZATION_FAILED` に読み替えた値。
- 切り分け: libvulkan を lazy map（P3 の 3b0d9db5c）の前の main 8eb7c81 の物に戻しても落ちる（ユーザー「やはり落ちました。」）→ lazy map のせいではない。compositor は 0d7bbc1ed（P3 の damage の直し）、kernel は main 8eb7c81。
- 次: libkeiland の resize（vkDeviceWaitIdle・swapchain の作り直し・target・canvas の vkAllocateMemory/vkMapMemory）のどこが EIO かを log で特定。bcm2711 の resource の確保・memory の上限。i915・Venus での再現は T1-547。

## 2026-10-12 P2: source の解析、診断の行、直しの候補（branch agent/p2-bug290）

### 分かったこと（source から。実機では未確認）

- Settings の `-3` は EIO に限らない。`present.c` の `present_size` は `kl_window_present_resize` の 0 以外を全部 `VK_ERROR_INITIALIZATION_FAILED` にし、`kl_window_present_resize` は `keiui_present_resize` の失敗を全部 EIO にする。どの Vulkan の呼び出しが何を返したかは、今までどこにも出ていなかった（`keiui_present.operation` に残るだけ）。
- `keiui_present_resize`（`userland/desktop/libkeiland/ui/present.c`）の順: `vkDeviceWaitIdle` → target の解放 → 新しい swapchain を作る（`oldSwapchain` に古い物）→ 古い swapchain を壊す → target → 古い canvas を壊す → 新しい canvas。つまり新しい swapchain を作る間、古い swapchain と古い canvas が生きている。
- libvulkan の Wayland の swapchain は 1 枚ごとに app の image（optimal）と共有の image（compositor へ渡す物）の 2 つの VkDeviceMemory を持つ（`wsi-swapchain.c` の `swapchain_group_create`・`swapchain_native_images_create`）。3 枚で 6 個。
- bcm2711 の kernel は VkDeviceMemory の宣言を **device 全体で 256 MiB**（`src/drivers/gpu/bcm2711/vulkan-memory.c` の `VULKAN_MEMORY_BUDGET`、`controller->vulkan_memory_bytes`）に制限し、compositor が import した client の buffer も別に数える（同じ file の「conservative charges for imported aliases」）。超えると `VK_ERROR_OUT_OF_DEVICE_MEMORY`。compositor・壁紙・glass・全部の窓が同じ 256 MiB を使う。
- 1904x1020 と 1180x800 の 4 byte の pixel で概算（tile の余白は無視）: 大きい窓の swapchain は約 46.6 MB（6 個）、canvas 7.8 MB、compositor の import 23 MB。dock（小→大）の resize の途中の峰は Settings の分で約 84 MB（古い小 26.5 MB＋新しい大 46.6 MB＋compositor の古い import 11.3 MB）、undock（大→小）は約 100 MB（古い大 54.4 MB＋新しい小 22.7 MB＋compositor の古い import 23 MB）。**undock の峰が dock より約 16 MB 高い**。全体が上限の近くなら、dock は通り undock だけが毎回落ちる形に合う（仮説。実機の値は未確認）。
- 別の筋: compositor が client を protocol error で切っていると、次の libvulkan の呼び出し（swapchain の作り直しの capabilities など）が `VK_ERROR_SURFACE_LOST_KHR` を返し、同じ `operation=kl_window_present_resize result=-3` に見える。compositor の log の `KWL ERROR client=… reason=…` と `KWL CLIENT gone client=… reason=…` で分かる。

### 入れた物（libkeiland だけ。libvulkan・kernel・compositor は変えていない）

1. 診断の行（`userland/desktop/libkeiland/ui/window.c` の `window_present_tell`）: `kl_window_present_resize`・`kl_window_present` の Vulkan の失敗を、窓ごとに 1 回だけ stderr に出す。
   `KEILAND PRESENT_FAILED call=… operation=<失敗した Vulkan の呼び出し> result=<VkResult> errno=… width=… height=… extent=WxH maximized=… connection=<wl_display_get_error> protocol=<code> interface=<名前> object=<id>`
   読み方: `result=-2`（OUT_OF_DEVICE_MEMORY）なら memory の上限、`connection=71`（EPROTO）なら compositor が切った（interface・protocol が理由）、`result=-4` は device lost、`result=-1000000000` は surface lost。
2. 直しの候補（`present.c` の `keiui_present_resize`）: `vkDeviceWaitIdle` の後、古い target・canvas・swapchain を先に全部解放してから新しい物を作る（`oldSwapchain` は使わない）。解放と確保が重ならないので、undock の峰は新しい小さい物だけ（Settings の分は約 26.5 MB＋compositor の古い import）になる。窓の見え方は変わらない（今も新しい swapchain の最初の frame の前に古い swapchain を壊している）。失敗した resize の後は swapchain・canvas が無いので、`keiui_present_frame` は NULL を触らずに `VK_ERROR_INITIALIZATION_FAILED`（operation=keiui_present_frame）を返す。
