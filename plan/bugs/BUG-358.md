# BUG-358: 4096 byte の logical sector の disk で native UFS への書き込みが極端に遅い（小さな file の多い導入で 30〜40 KB/s）

- 状態: closed（2026-10-30 Q1 の判定、main ed93695ac。QEMU の flush の回数・crash 試験・14 platform の build で確かめた。実機は未実施、再発で reopen）。直し: 2026-10-30 P4、q1688-i01、commit 6387b82a0。登録: 2026-10-29 Q1（ユーザー「4096バイトセクタで遅いことはバグとして記録して、先に進んでほしい」）
- 発見: 2026-10-29 P4（q1665-i10、WS307 p011 の 4 回目 `p011.hfdv7fqg`、QEMU の 4096 の NVMe）。
- 観測: installer の全体の導入（既定の項目 165 MiB、小さな file の多い unit）が 22 分で約 50 MB（目算 30〜40 KB/s）。同じ導入は 512 の NVMe で約 9 分。
  WS307 p006 の測り（16 MiB の dd が 512 で 23 秒、4096 で 63 秒、約 2.7 倍）より差がずっと大きい。
- 見立て（未確認）: 512 byte の journal の record の read-modify-write（plan/ws307/ws.md の制限）、小さな file の metadata の書きが 4096 の read-modify-write になる。
- 関係: [BUG-355](BUG-355.md)（UFS の大きい書き込みが約 1 MB/s、512 でも遅い）。
- 回避: WS307 の試験は 4096 の導入を base・OpenSSH・OpenSSL（約 45 MB）だけ・timeout 3600 s に縮めた（ae125c7d4）。
- 未確認: 実機の 4Kn の disk、原因の切り分け（journal・metadata・buffer cache・driver）。

## 原因（2026-10-29 P4、q1688-i01）

- 1 つ目は [BUG-355](BUG-355.md) と同じ: `mkfs -t ufs --profile=native` の volume に tail journal があり、変更のたびに同期で書いて flush する。4096 の disk では 1 回の commit の書き込みが多く（512 byte の record が 4 KiB の block の read-modify-write になり、32 KiB の block の volume では allocation run が 32 KiB）、さらに遅い。測り（`ufs-speed.aeWMJv`、cache=unsafe）: 32 MiB の dd が 6.0 MB/s で、flush 25816 回・driver の書き込み 41326 回・394 MB（12 倍）。4 KiB の file 300 個は 312 KiB/s で、flush 18187 回・driver に 280 MB。
- 2 つ目（tail journal を外すと出る）: batched journal（v3）の道が 4096 の disk で壊れていた。`src/drivers/fs/ufs.c` は 512 byte の sector の番号のまま、`buf_write_pinned`・`buf_unpin`・`buf_writeback_range`・`buf_writeback_cached`・`buf_prefetch` を呼んでいた。これらは disk の block（4096 byte）の単位を取る。tail journal の locator を消した 4096 の volume では `mkdir` が EIO になり、volume は「the storage of a new inode could not be given back (error 5)」で書けなくなった（guest の dmesg）。大きい file の dd では、driver に 1.4 MB しか届かなかった。4096 の disk はこれまで tail journal の道しか通っていなかったので、この不具合は出ていなかった。

## 直し（commit 6387b82a0）

- 1 つ目は BUG-355 の直し（mkfs の native が tail journal を書かない）。
- 2 つ目: `ufs.c` に sector の単位の包みを足した（`ufs_buf_write_pinned`・`ufs_buf_unpin`・`ufs_buf_writeback_range`・`ufs_buf_writeback_cached`・`ufs_buf_prefetch`）。それぞれ、既にある `ufs_sector_blocks` で sector の範囲を覆う disk の block に直してから呼ぶ。pin する書き込みが block の途中で始まる・終わる時は、覆う block を cache から読み、その中に置いてから block ごと pin する。そのような block の持ち主は 1 つ: fragment は disk の block より小さくならない（`ufs_read_super` が拒む）。block を共有する metadata の書き込みは、呼ぶ側が持つ journal の lock（`j3->lock`）で順に並ぶ。512 の disk では、今までと同じ呼び出しになる。

## 確かめた事（2026-10-29〜30 P4、QEMU だけ）

- 直した後（`ufs-speed.6skEyw`、同じ条件）: 32 MiB の dd は flush 8 回・driver の書き込み 85 回・34.2 MB・36 MB/s（locator だけを消した回 `ufs-speed.cdKU6v` は 130 MB/s。時間は host の負荷で揺れる）。4 KiB の file 300 個は flush 3 回・52 回・11.7 MB・4.3 MB/s。もう一度 mount した後の読み戻し（`cksum`・`diff -r`）は一致した。
- crash（`ufs-crash.rtSJPR`）: 4096 の disk で 3 s と 20 s に切っても、fsync した file は同じ。replay の mount・名前に穴が無い・その後の書き込みと読み戻しも ok。前の mkfs の tail journal の volume も mount・書き込み・読み戻しが ok。
- host の検査（`check-volume.py`）は 4 KiB の fragment を読めないので、4096 は guest の中の読み戻しだけで確かめた。
- 未実施: 実機の 4Kn の disk、WS307 p011 の 4096 の導入（既定の項目に戻して流し直す）。
- 回避（ae125c7d4、WS307 の試験で 4096 の導入を減らした物）は p011 の流し直しの時に戻す。
