# BUG-210: 5330 の実機で LPSS I2C の BAR0 が 0（firmware が割り当てない）で I2C-HID の touchpad が付かない

Reproduction: reproduced（実機 5330、ユーザーの dmesg、2026-10-06）
Disposition: resolved（2026-10-06 ユーザーの実機の確認「タッチパッドがI2Cで使えるようになりました。2本指でスクロールができています。」）
Discovery: 2026-10-06 ユーザーの実機の dmesg（project root の `dmesg`）
Handling: [WS159](../ws159/ws.md)（native の touchpad）

## 観測

```
lpss-i2c: 0000:00:15.0 BAR0 type 3 at 0x0 size 0x1000 did not map (3)
lpss-i2c: attach failed while powering on (3)
lpss-i2c: 0000:00:15.1 BAR0 type 3 at 0x0 size 0x1000 did not map (3)
lpss-i2c: attach failed while powering on (3)
i2c-hid: \_SB_.PC00.I2C1.TPD0 not taken (13)
```
BAR0 は 64-bit の memory の 4 KiB、address が 0。`pci-pcat.c` の map が bus_address 0 を EINVAL で断る。controller が無いので i2c-hid は ENODEV。

## 解析（Q1、2026-10-06）

zedBSD の PCI の走査（`src/drivers/pci/pci.c`）は 64-bit の BAR の両半分を正しく読むので、走査の時に BAR0 は本当に 0。firmware は他の 64-bit の BAR を 4 GB の上に置いている（xHCI は 0x60_5528_0000・0x60_5526_0000）が、Linux では I2C の BAR0 は 0x40_1700_1000（`plan/ws159/tests/latitude5330-linux/lspci-lpss-i2c.txt`）で別の範囲。→ **firmware が LPSS I2C を未割り当てのまま残し、Linux の PCI core が host bridge の窓（`_CRS`）の空きから割り当てている**見込み（Linux の `dmesg | grep 00:15.0` の `BAR 0: assigned` で確かめられる、未確認）。

## 直し（方針）

x86 で memory の BAR が未割り当て（0）なら、PCI の root bridge の窓（`\_SB.PC00._CRS` の 64-bit・32-bit の memory の範囲）の中で、既に割り当てられた BAR（全 device の）と重ならない空きを、大きさに揃えた位置で選び、BAR に書く。PCI の attach は ACPI より前なので、未割り当ての BAR を持つ device（LPSS など）は ACPI の namespace の後に割り当てて attach する（遅らせるか、やり直す）。HAL の API は変えない。

## 原因（P1、2026-10-06）

firmware が LPSS I2C（00:15.0・00:15.1）の 64-bit の BAR0 を割り当てず 0 のまま残す。zedBSD は BAR を自分で割り当てる仕組みを持たず、`pci-pcat.c` の map は bus_address 0 を EINVAL で断る。PCI の走査と driver の attach は ACPI の namespace より前なので、attach の時点では host bridge の窓（`\_SB.PC00._CRS`）も読めない。

`\_SB.PC00._CRS` の 32-bit の窓（`_Y0E`）と 64-bit の窓（`_Y0F`）は、run time に GNVS（`OperationRegion (GNVS, SystemMemory, 0x6150C000, 0x0CE0)`）の M32B・M32L・M64B・M64L から作られる。tree の DSDT（`plan/ws049/tests/latitude5330/dsdt.dat`）を WS049 の AML の harness で評価すると（GNVS は 0 と読める）、32-bit の窓は base 0 長さ 0、64-bit の窓は base 0x10000 長さ 0 になり、実際の値は table には無い。実機の値は修正後の kernel が `pci: _CRS window ...` の行で出す。zedBSD の dmesg の `gmadr=0x4000000000`（i915 の aperture）と xHCI の 0x6055280000・0x6055260000 から、64-bit の窓は 0x4000000000 から始まると推定している（未観測）。

## 修正（P1、2026-10-06）

- PCI の core（`src/drivers/pci/pci.c`、`include/drivers/pci/pci.h`）: `struct drv_pci_bus_ops` に `defer_unassigned` を足した。それを立てた host の root bus では、memory の BAR が address 0・大きさ 0 でない function に合う driver があれば、attach を止めて待たせる（`probe_deferred`、`drv_pci_device_probe` は EAGAIN）。`drv_pci_probe_deferred()` が待ちを終えて待った function を probe する（BAR が割り当てられなかった function も probe するので、driver が今までどおり失敗を log する）。待つのは root bus の function だけで、bridge の下は今までどおり。
- ACPI（新 `src/drivers/acpi/acpi-pci-root.c`、`include/drivers/acpi/acpi.h`）: `drv_acpi_pci_root_resources_walk(segment, bus, ...)` は `_HID`/`_CID` が PNP0A03・PNP0A08 で `_SEG`・`_BBN`（無ければ 0）が合う device の `_CRS` を walk する。`drv_acpi_system_resources_walk()` は PNP0C01・PNP0C02 の device（`_STA` が present でも functioning でもない物だけ除く。5330 の `\_SB.PRRE` は `_STA` 0x08）の `_CRS` を walk する。
- 割り当て（新 `src/drivers/pci/pci-pcat-assign.c`、`src/drivers/pci/pci-window.c`、`include/drivers/pci/pci-window.h`）: `drv_pci_pcat_assign_deferred()` は、待つ function が無ければ何もしない（QEMU）。あれば segment 0 bus 0 の host bridge の `_CRS` の memory の窓（1 MiB より下の legacy は除く）を読み、使用中の範囲（全 function の address を持つ memory BAR、全 bridge の memory・prefetchable の窓、PNP0C01/02 の `_CRS`、segment 0 の ECAM、loader の memory map の全 range）を集め、各 BAR を `drv_pci_window_place()` で置く: 窓の中で大きさに揃えた最も低い、どの使用中の範囲とも重ならない address（4 KiB 未満の BAR も 1 page を取る）。64-bit の BAR は 4 GiB より上の窓を先に、32-bit の BAR は窓の 4 GiB より下の部分だけ。書き込みは既存の `drv_pci_device_assign_bar()`（decode を止め、上位を先・下位を最後に書き、読み戻して command を戻す）。log: `pci: _CRS window 0x...-0x...`、`pci: 0000:00:15.0 BAR0 assigned 0x... size 0x1000 from _CRS window 0x...-0x...`、置けない時は `... fits in no _CRS window (8)`。
- `src/drivers/pci/pci-pcat.c`: `CONFIG_DRIVER_ACPI` の build で `.defer_unassigned = 1`。`src/kern/platform/pcat.c`: `drv_acpi_attach()` が成功したら `drv_pci_pcat_assign_deferred()`、失敗したら `drv_pci_probe_deferred()`（待った function をそのまま attach）。LPSS の attach は i2c-hid の probe（`kern_platform_input_init`）より前に終わる。
- `platform/amd64/vmunix.mk`: ACPI の build に `pci-pcat-assign.c`・`pci-window.c` を足した。
- HAL: `include/hal/hal.h` も `src/hal/` も変えていない。ECAM と memory map は既存の bsp の `amd64_acpi_ecam_address()`・`bsp_mem_range_count()`・`bsp_mem_range()` を `extern` で使う（`pci-pcat.c` の ECAM と同じ形）。

## 確認（P1、2026-10-06）

- build: `make -j16 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug210/uat vmunix`（P1 の worktree）が warning 0、kernel include check・amd64 vmunix check PASS。i386・arm64 の build は未実施（`pci.c` の変更は arch に依らない C、pcat.c の呼び出しは `CONFIG_DRIVER_ACPI` の中）。
- style-check: 新しい file は 0 件。`pci.c` は `goto release_binding` 1 件が増えた（既存の後始末の label への前方 jump と同じ形）。`pcat.c`・`pci-pcat.c` は増えていない。
- host（`plan/ws159/tests/run-host-pci-window.sh`）: allocator の 21 件 PASS（ASan/UBSan でも）。5330 の `\_SB.PC00._CRS` を harness で評価した値（GNVS 0）では窓が無く ENOSPC。GNVS を推定値（M64B=0x4000000000・M64L=0x4000000000、M32B=0x80000000・M32L=0x40000000）にすると、dmesg の BAR（xHCI 2 つ、i915 の aperture、i915 の register は 0x6054000000 と仮定）・PRRE の `_CRS`・ECAM・低い RAM を避けて、00:15.0 → 0x4010000000、00:15.1 → 0x4010001000。Linux は 0x4017000000 台に置いた（Linux は firmware の後で bridge の窓を自分で割り当てるので、同じにはならない見込み）。
- host（`plan/ws159/tests/run-host-pci-root.sh`）: `acpi-pci-root.c` を WS049 の harness に入れて 5330 の DSDT・SSDT1〜15 で: root bridge（PC00）を見つけ memory の 16 範囲（GNVS の 2 つの窓は長さ 0）、無い bus は ENOENT、PNP0C02 の walk が PRRE（`_STA` 0x08）の 0xfe000000・0xff000000 を含む。PASS。
- QEMU・実機: 未実施（P1 は QEMU を起動しない）。

## 試験の依頼（実機 5330、ユーザー）

image: P1 の commit 以降の main で `make -j16 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/uat disk-image`。見る行と合否:

1. `pci: _CRS window 0x...-0x...`（実機の窓。64-bit の窓が 0x4000000000 台から出るはず）。
2. `pci: 0000:00:15.0 BAR0 assigned 0x... size 0x1000 from _CRS window ...` と 00:15.1 の同じ行。`fits in no _CRS window` や `could not be written` が出たら FAIL（その行と窓の行を BUG-210 に記録）。
3. `lpss-i2c: 00:15.0 ready, FIFO tx .. rx .., clock 133000 kHz`（00:15.1 も）。`did not map` が出ないこと。
4. `i2c-hid: ... not taken` が出ず、touchpad の input device が出て、touchpad で pointer が動くこと（tap・2 本指の scroll は WS159 の範囲）。
5. 他の device（xHCI・i915・hda・AX211）が今までどおり attach すること（attach の順が ACPI の後に動くのは BAR 0 を持つ function だけ）。

QEMU の回帰（未実施、依頼するなら T1）: 既存の boot-test の login prompt。QEMU には BAR 0 の function が無いので `pci: ... assigned` も `_CRS window` の行も出ないのが PASS。
