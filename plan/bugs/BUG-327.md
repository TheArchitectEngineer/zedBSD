# BUG-327: 5330 で zedBSD の USB の stick からの小さな読み込みが 1 回 30〜54 ms 待つ（起動が遅い）

- 状態: reproduced（5330 の実機の記録 1 回）/ tracking
- 発見: 2026-10-16 P2（WS253 起動の時間）、P1 が取った 5330 の記録（main 8666f25a6）の `hw.diskstats`: sda の read_ops=1693、read_bytes=33 MB、read_ns=92.2 s（平均 54 ms）。QEMU の USB の stick は平均 0.68 ms、NVMe は 0.40 ms。dd で 10 MB を続けて読むと 0.56 s で速いので、小さな読み込みを 1 回ずつ待つ所が遅い。
- 影響（推定、5330 での切り分けは T1 の測定の後）: compositor の glyphs-fonts 1.5 s、compositor が動き出すまでの約 2.5 s（page-in）、late の service、kernel→init の一部。
- 範囲: usb-storage・xHCI の driver の側。2026-10-16 ユーザー「USB driverが遅いのは、起動が遅い問題を解決しているサブエージェントで処理してくだしあ。」→ WS253 の範囲に入れ、P2 が直す（q1221-i04）。
- 関連: [WS253](../ws253/ws.md)
- 2026-10-16 ユーザーの見立て:「USB stickが古くてNANDフラッシュが劣化して遅くなっているかもしれないです。」→ 切り分け: 同じ stick を 5330 の Linux の側から小さな読み込み（4 KiB の direct I/O を散らして数百回、読むだけ）で測る。Linux でも 1 回数十 ms なら stick の劣化、Linux で速ければ zedBSD の usb-storage・xHCI の側。T1 の次の 5330 の回で相乗り。
- 2026-10-16 T1-703 の切り分け: stick は劣化していない。5330 の Linux から同じ stick（TransMemory 58.2G）を direct I/O で 4 KiB のランダム読み 300 回 = 平均 0.43 ms（image の範囲 0.36 ms）、連続 99〜196 MB/s。zedBSD の diskstats は 1 回あたり約 28〜34 ms（T1-703 の 2 回）。→ zedBSD の usb-storage・xHCI の側の待ち。出力 /home/awe/zedBSD-worktrees/t1/build/t1703-out/usb-read.txt。
- 2026-10-16 ユーザー「P2はQEMUでテストをお願いします。実機は他のチケットに回します。」→ P2 の確認は QEMU だけ、実機の確認は修正の後に別のチケット。

- 2026-10-16 P2（q1221-i04、WS253）: 1 command の時刻の内訳を出す計測を足した（既定は off）。`sysctl hw.usb.trace=1`（root、HW_USB_TRACE_STORAGE）で、usb-storage の command ごとに kernel の log に 1 行 `usb-storage-trace: sda op=28 lba=… blocks=… error=… queue_us=Q total_us=T xfer1=S/E/W xfer2=S/E/W xfer3=S/E/W`。xferN は BOT の CBW・data・CSW の順の各 transfer（data の無い command は 2 つ）、S は USB core が controller に渡してから xHCI が transfer event を取るまで（device と controller と割り込み）、E は event から USB core が終わりを出すまで（driver）、W は終わりから待つ thread が見るまで（起床）、queue_us は device の lock を待った時間、total_us は lock を取ってから終わりまで。時計は monotonic の counter（ns）。実装: `include/uapi/sysctl.h`（HW_USB_TRACE 10）、`src/kern/sysctl.c`（hw.usb.trace、`kern_usb_trace()`）、`src/drivers/usb/usb.c`（URB の時刻 submitted・event・completed、`drv_usb_trace_*`、`drv_usb_urb_trace_*`）、`src/drivers/pci/pci-xhci.c`（transfer_claim で event の時刻）、`src/drivers/usb/usb-storage.c`（command ごとの記録と 1 行）。
- 2026-10-16 P2 の QEMU の確認（USB の stick の boot、qemu-xhci）: MSI で 1 command 約 0.40〜0.52 ms（S は CBW 85〜205 µs・data 80〜270 µs・CSW 73〜88 µs、E 約 25 µs、W 0〜11 µs）、`-global qemu-xhci.msi=off -global qemu-xhci.msix=off` の INTx でも約 0.37〜0.50 ms。QEMU では 5330 の約 30 ms は再現しない（QEMU の usb-storage は即座に答え、throttle は 1 transfer の遅れを真似られない）。5330 での読み方: S が大きければ device・controller・割り込みの到着、E が大きければ完了の処理の遅れ（command の gate などで遅らされた drain）、W が大きければ待つ thread の起床、queue_us が大きければ command の取り合い。5330 の確認は別の ticket（2026-10-16 ユーザー「P2はQEMUでテストをお願いします。実機は他のチケットに回します。」）。5330 の dmesg では stick（30de:6545）は port 15 の SuperSpeed、xHCI（00:14.0）は MSI。USB3 の LPM（PORTPMSC）は zedBSD が設定しない（既定の無効）。

## 2026-10-16 原因解析（bug-analyzer、修正なし、code の読みと T1-703 の数値の再計算のみ。5330・QEMU は動かしていない）

### 前提の確認（経路に tick 待ち・worker 待ちは無い）

- usb-storage の 1 command = BOT の 3 段（CBW OUT → data → CSW IN）を順に同期で流す: `src/drivers/usb/usb-storage.c:750`・`:765`・`:794`（`bot_command_locked`）。各段は `storage_urb_transfer`（`:341-374`）が submit → `drv_usb_urb_wait_reusable` で待つ。
- 待ちは `drv_usb_urb_wait`（`src/drivers/usb/usb.c:2590-2662`）の `sched_yield()` の spin（`:2660`）。sleep も tick の丸めも無い（dd の `sys 0.50`/`real 0.56` は、この spin が CPU 時間として見えている物）。
- xHCI の submit は TRB を積んで即 doorbell（`src/drivers/pci/pci-xhci.c:4363`）。完了は hard IRQ の中で `xhci_irq`（`:3070`）→ `transfer_claim`（`:2698`）→ `xhci_completion_drain`（`:3182`）→ `drv_usb_hcd_complete`（`:2922`）まで直接進み、URB の status が立つ。retirement thread は UHCI/EHCI だけで xHCI には無い。
- IRQ は MSI-X/MSI/INTx の順で 1 本（`:6443-6447`）、HAL の MSI は BSP（CPU 0）宛て固定（`src/hal/amd64/irq.c:901`）、handler は `IRQ_MODE_REALTIME` で割り込み文脈から直接呼ぶ（`:894`、`:746`）。threaded IRQ は無い。
- link の省電力（U1/U2/U3）は system suspend の時だけ（`pci-xhci.c:7221-7244`、`:7400-7430`）。command 間に port を落とす code は無い。
- 1 command の最大は 64 KiB（`include/drivers/usb/usb.h:88`、xHCI は `DRV_USB_HCD_CAP_TRANSFER_RESERVE` を持つ `pci-xhci.c:6423` → `usb-storage.c:597`）。device ごとに `storage->lock` で 1 command ずつ直列（`usb-storage.c:1504`・`:1564`）、queue の深さ 1。
- `hw.diskstats` の read_ns は bio の admission（`src/kern/disk.c:4176-4197` `disk_stats_start`、`d_inflight++` の時）から完了までで、**`storage->lock` の待ち（他の read・write・flush が wire を使っている間）を含む**。busy_ns は inflight>0 の壁時計。

### 候補（確からしい順）

**1. xHCI の interrupt moderation `KERN_XHCI_IMOD 4000`（= 4000 × 250 ns = 1 ms、`pci-xhci.c:38-39`、書き込み `:5940`・`:6990`）。BOT の 3 段が各 1 ms の moderation を待つので、1 command ≈ 3 ms（大きさに依らない）。** 根拠:
- xHCI の IMODC は IP が落ちた時（MSI 送出時）に IMODI で再装填され、0 になるまで次の割り込みを出さない。BOT の次の段は前の段の完了 callback の後に submit するので、段ごとに最大 1 ms 待つ。定常では CBW 完了・data 完了・CSW 完了がそれぞれ 1 ms 境界に揃い、1 command ≈ 3 ms。
- 5330 の dd（`t1703-out/run1-time.txt`）: 10 MB を 0.56 s = 64 KiB × 約 160 command → **1 command ≈ 3.5 ms**。SuperSpeed の 64 KiB は wire で 0.2 ms 程度、Linux の 4 KiB は 0.43 ms なので、約 3 ms が host 側の固定費。
- QEMU で出ない理由: QEMU の xHCI は IMOD を register に保存するだけで（`/home/awe/qemu-pc98/hw/usb/hcd-xhci.c:3119-3120`）、`xhci_intr_raise`（`:575-598`）は event を書いた時点で即 MSI を上げる。→ QEMU の 0.68 ms は 3 段 × 0.2 ms 程度の純粋な往復。Linux の xhci は IMODI=160（40 µs）が既定。
- 以前の判断（`plan/history/queue-q255.md`・`q256`・`q277`、ws025-p030「IMOD 0/160/4000 で callback 率 71.5/s が同じ → 4000 を維持」）は HID の callback 率の比較で、HID の interrupt endpoint は polling 周期で決まり IMOD の影響を受けない。storage の BOT の往復時間は測っていないので、4000 の根拠にならない（QEMU で測った分は IMOD 自体が効かない）。

**2. 直列化と queue 待ち（1 の 3 ms が、同時に出る read と write・flush の後ろで何倍にも見える）。** 根拠:
- readahead の worker 4 本（`src/kern/readahead.c:30`）+ demand の read + 1 s ごとの flusher（`src/kern/buf.c:56` `BUF_FLUSH_INTERVAL`）が hook する UFS の journal commit（journal の書き込み → `bio_flush` = SYNCHRONIZE CACHE、`src/drivers/fs/ufs.c:16354`・`:20219`）が、全部 `storage->lock` に並ぶ。
- 数値: run2 は read_ns 41.8 s + write_ns 25.2 s に対し busy 25.6 s → 平均 inflight ≈ 2.6、busy/op = 25.6 s / 1860 op = 13.8 ms。run1 は busy 54.6 s / 2088 op = 26 ms/op。read が 3 ms/command なら run2 の read は 1483 × 3 ms ≈ 4.4 s で、残りの約 21 s は write 377 回と（ops に数えない）flush の wire 時間 → **write+flush が 1 回あたり 50〜90 ms** と推定（USB stick の小さな random write と SYNCHRONIZE CACHE はこの桁になる）。read の「28〜54 ms」は主にこの後ろで待つ時間（未確認、下の測定で分かる）。
- 影響する側の修正は BUG-327 の外（flush の頻度・writeback・page-in の readahead）。本 bug の修正は 1 で、2 は測定で切り分けてから別 ticket にする。

**3.（弱い）MSI が CPU 0 固定で、boot 中に CPU 0 が割り込み禁止で長く走る区間があると完了が遅れる**（`hal/amd64/irq.c:901`）。dd の 3.5 ms が 1 で説明できるので主因ではない。未確認。

**4.（可能性低、測定で除外する）stick が zedBSD では High Speed で繋がっている**（SS の link training に失敗して USB 2 側に落ちた場合）。64 KiB の wire が約 2 ms になり dd の 3.5 ms の一部を説明するが、4 KiB の read は 0.5 ms 程度のはずで、1 と区別できる（下の (c)）。

除外した物: tick 粒度の sleep（無い）、HCD の retirement worker（xHCI には無い）、doorbell の遅延（無い）、link の省電力（suspend 時だけ）、割り込みの取りこぼしの救済 poll（event ring を周期で読む物は無く、取りこぼせば 30 s の timeout になるはずで症状と合わない）。

### 確かめる方法（5330、T1、読むだけ。起動後に desktop が落ち着いてから ssh で）

(a) `lsusb -tv` → sda の stick の Speed（SuperSpeed なら 4 を除外）。`dmesg | grep xhci` → `irq=N MSI|MSI-X|INTx`（t1703 の dmesg には行が無いので取り直す）。
(b) 静止: `sysctl hw.diskstats; sysctl vfs.io.stats` を 30 s 空けて 2 回 → 何もしていない間の write・flush の数（io.stats の event 15 = WRITE10、16 = SYNC_CACHE、6 = DRIVER_FLUSH、14 = READ10、72/74 = XHCI_IRQ_ENTRY/EVENT。sysctl は `event=N calls= bytes=` で出る）。
(c) 純粋な read の 1 回: 前後で `hw.diskstats` と `vfs.io.stats` を取り、間に `dd if=/dev/sda of=/dev/null bs=4096 count=1 skip=<乱数 0..122019840/8>` を 300 回（zedBSD の dd は skip= を受ける）。Δread_ns/Δread_ops が **約 3 ms なら 1**、0.5 ms なら driver は速く boot の遅さは 2、30 ms なら未知の driver の停止。ΔIRQ_ENTRY(72)/ΔREAD10(14) は 1 なら 3 の近く（3 段 = 3 割り込み）。
(d) 同じ前後で `dd if=/dev/sda of=/dev/null bs=65536 count=160 skip=<固定>` → 64 KiB の 1 command。(c) と同じ約 3 ms なら大きさに依らない = 1（moderation）、(c) の数倍なら wire（4）。
(e) boot 直後の `vfs.io.stats` の 14〜17 と 6/9、40〜45（BUF_RUN/SINGLE）: boot 全体の READ10/WRITE10/SYNC_CACHE の数と、read が 4 KiB 単発（SINGLE）か run か。
(f) 1 の修正の確認（T1 の読むだけの枠の外、別の試験 build）: `KERN_XHCI_IMOD` は `#ifndef` なので config.mk の CFLAGS に `-DKERN_XHCI_IMOD=160` を足した image で (c)(d) を取り直し、約 3 ms → 0.5 ms 前後になること、dd の 10 MB が 0.56 s → 0.1〜0.2 s になること、`glyphs-fonts`・`wallpaper` の ms が下がること。QEMU は IMOD を無視するので QEMU での差は出ない（回帰の確認だけ）。

### 修正の方向（実装はしない）

1. `src/drivers/pci/pci-xhci.c:39` の `KERN_XHCI_IMOD` を 4000 → 160（40 µs、Linux の既定）か 0 にする。interrupter は controller で 1 本なので HID・isoch の割り込みも増えるが、以前の HID の比較（q256）で 0/160 は 4000 と同じ callback 率だった。suspend/resume の保存・復元（`:7291`・`:7346`）はそのまま。
2. （任意、効果は小）BOT の data 段と CSW 段を前の段の完了を待たずに IN ring へ先に積む（device は CBW を受けるまで NAK する）と、割り込みが 3 → 1〜2 回に減る。usb-storage と xHCI の ring の扱いの変更で、1 だけで十分なら不要。
3. 2 の queue 待ち（flush の頻度・write の直列化・page-in の readahead）は (b)(c)(e) の結果を見て別 ticket に分ける。

### 未確認の仮説

- 5330 で 1 command が本当に約 3 ms か（dd の換算だけ。(c)(d) で直接測る）。
- write+flush が 1 回 50〜90 ms という推定（(b)(e) の数で確かめる）。
- 5330 で MSI か INTx か、stick が SuperSpeed か（(a)）。
- QEMU での内訳の測定は行っていない: QEMU は IMOD を模さず（上）、P2 の 0.68 ms が既にあり、HW との差を説明する測定にならないため。
