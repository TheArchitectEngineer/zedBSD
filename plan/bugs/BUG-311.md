# BUG-311: Raspberry Pi 4 の onboard の WiFi と Bluetooth が立ち上がらない（firmware の tag 0x38041 not supported で WL_ON・BT_ON を操作できない）

- 状態: reproduced（実機、T1-628）/ scheduled — 直しは b6bbc3d7a（2026-10-14 P2、host と build だけ、実機の T1 待ち）。以前: scheduled（2026-10-14 Q1、P2。ユーザーの UAT「PiのイメージでWiFiとBluetoothが使えていないようなので、configやDTBの確認をお願いします。」）
- 観察（Pi 4、kernel 947617b 系の WS236 の試験の kernel、結果 plan/agents/T1/results-*-t1-628 と ledger の T1-628）:
  - WiFi: `rpi4-wifi: WL_ON was level 1 (0)` → GPIO 34〜39 を ALT3 → `rpi4-sdio: host specification 2, capabilities 00000000 (0 MHz)` → `rpi4-firmware: tag 38041 not supported` → `rpi4-wifi: WL_ON not driven low (21)` → `bcm43455: chip did not power up (21)` → `onboard Wi-Fi not published (21)`。wlan0 無し。
  - BT: `rpi4-bt: BT_ON was level 1` → GPIO 30〜33 → PL011 → `rpi4-firmware: tag 38041 not supported` → `BT_ON not driven low (21)` → `controller did not come up (21)`。`bt show` は no-controller。
  - firmware の file（brcm・cypress）と config.txt（disable-bt・enable_uart 無し）、DTB（ws232-p004 で確認）は揃っている。
- 推測（Q1）: WL_ON・BT_ON は Pi 4 の GPIO の expander にあり、firmware の mailbox の tag 0x00038041（GPIO の状態の設定）で操作する。firmware が「not supported」を返す（または driver が応答を誤って読む）ので電源の line を下げられない。GPIO の番号（expander の 128+N）、tag の引数の形、応答の code の読み方、firmware の版（start4.elf 3d301dd9）を確かめる。0x38041 の前に 0x38043（GPIO の設定）が要るかも。
- `rpi4-sdio: capabilities 00000000 (0 MHz)` も気になる（EMMC の capabilities が 0）。
- 関連: WS206（RPi4 の WiFi）、WS215（BT）、ws232-p004。

## 2026-10-14 P2: 原因と直し（commit b6bbc3d7a、未試験）

### 原因

- firmware は GPIO の expander の設定の tag（0x00038041 SET_GPIO_STATE と 0x00038043 SET_GPIO_CONFIG）を処理するが、答えの tag の code（value の長さの word）を
  request が書いたまま（0）にして、answered の bit 31 を立てない。driver（`rpi4-firmware.c` の `read_answer()`）はそれを「firmware が知らない tag」と読んで
  `tag 38041 not supported`・ENOTSUP（21）を返していた。→ `WL_ON not driven low (21)`・`BT_ON not driven low (21)`。取得の tag（0x30041・0x30043）は正しく答えるので
  `WL_ON was level 1` は読めていた。
- 出典（BSD-2-Clause の FreeBSD、事実だけ）: `sys/arm/broadcom/bcm2835/bcm2835_mbox.c` の注記「When setting the GPIO config or state the firmware doesn't set
  tag->val_len correctly」と、その時（val_len が 0）に response の bit と value の buffer の大きさを立てる回避。GPIO の番号（128 + N、BT_ON 128・WL_ON 129）と
  tag の値・value の並び（`bcm2835_firmware.h` の msg_get/set_gpio_state・config）、成功の時 firmware が先頭の word（GPIO）を 0 にすることも FreeBSD の
  `raspberrypi_gpio.c` と一致。Raspberry Pi の firmware の wiki（Mailbox property interface）は 0x30041/0x38041 を「onboard LED status」（pin 42・130）と書き、
  未知の tag は「response の bit が立たない」と書く。
- 版の 3d301dd9 の start4.elf が tag を持つかは、取得の tag が答えていることと、設定の tag が buffer の code 0x80000000 で返っていること（refused の行が無い）から、
  持っていると判断（実機では未確認）。
- `rpi4-sdio: capabilities 00000000 (0 MHz)` は原因ではない: BCM2711 の EMMC（Arasan の SDHCI）には capabilities の register が無く 0 を読む。driver は既に
  その値を log に出すだけで、base clock は firmware の clock の rate（同じ行の `firmware clock … Hz`）を使っている（`rpi4-sdio-host.c` の注記の通り）。

### 直し

- `src/drivers/platform/rpi4/rpi4-firmware.c`:
  - `read_answer()`: 設定の 2 つの tag で tag の code が 0 のまま返ったら、answered と value の buffer の大きさ（`message[PROPERTY_WORD_CAPACITY]`）を答えとして扱う。
    成否は従来通り先頭の status の word（成功で 0、firmware が処理しなければ GPIO の番号のまま）で判定するので、処理されなかった変更は EIO になる。
  - `drv_rpi4_firmware_set_gpio()`: まず GET_GPIO_CONFIG で方向を読み、input なら SET_GPIO_CONFIG（GPIO、方向 1 = 出力、元の polarity、termination 0・pull 0、
    level）で出力にして level を設定する（FreeBSD の `rpi_fw_gpio_pin_configure` と同じ field の並び）。既に output なら SET_GPIO_STATE。出力に変えた時は
    `rpi4-firmware: GPIO N made an output at level L` の行を出す。
  - `drv_rpi4_firmware_get_gpio_direction()` は同じ設定の読みの helper を使う（動作は同じ）。
- 試験の model（`plan/ws206/tests/gpio-host-test.c`）を実機の firmware の答えに合わせた: 設定の tag は tag の code 0 で返す、SET_GPIO_CONFIG を扱う、
  変更は 2 つの request（設定の読みと変更）、答えの bit を立てる firmware も受ける、処理されない変更は EIO で level が変わらない。

## 2026-10-14 P2: T1-630 の後の直し（commit ce45241dc、未試験）

T1-630（[結果](../agents/T1/results-20261014-t1-630.md)）: GPIO の直しは効いた（`not driven` が消えた）。その先で WiFi は `bcm43455: fast clock not available (42)`、
BT は reset の答え（7 byte）の後の Read Local Version に答えが無く `bt show` が `local-version Connection timed out`。

### WiFi: firmware の download を遅い（ALP）clock で行う

- 原因: driver は firmware の download の前に HT（fast）clock を要求していた（`bcm43455_chip_download()` の `request_fast_clock()`）。HT は firmware が NVRAM から
  PMU の resource を設定してから出るので、download の前には来ない。
- 出典（ISC の OpenBSD bwfm、事実だけ）: `if_bwfm_sdio.c` の `bwfm_sdio_preinit()` は `sc_alp_only = 1` で `bwfm_sdio_load_microcode()` を呼び、
  `bwfm_sdio_htclk()` は `sc_alp_only` の時 ALP_AVAIL_REQ を要求する。HT は download の後の `bwfm_sdio_clkctl(sc, CLK_AVAIL, 0)` で初めて要求する。
- 直し（`src/drivers/wifi/bcm43455/bcm43455-chip.c`）: download は ALP を要求して ALP_AVAIL を待つ（`request_clock()`、上限 5 s、bwfm と同じ）。HT は
  `bcm43455_chip_start()`（firmware の起動の後）でだけ要求する。log の語は `slow clock not available`・`fast clock not available` に分けた。
- 試験の model（`plan/ws206/tests/bcm43455-host-test.c`）: HT は firmware が走っている時だけ出す（実機の通り）、firmware の起動の前に HT を要求しないことを検査。

### BT: power の順の時間と、HCI reset の後の間

- 観察: 1 回の start の間に 8 byte を送り（HCI_Reset 4 と Read Local Version 4）7 byte を受けた（reset の Command Complete だけ）。電源の pulse は
  BT_ON の low が 10 ms、high にして CTS が 22 ms で立ってから 10 ms の静かな時間だけで command を送っていた。
- 出典（Apache-2.0 の Zephyr、事実だけ）: `drivers/bluetooth/hci/h4_ifx_cyw43xxx.c`（CYW43xxx）は BT_REG_ON を low にして 300 ms
  （BT_POWER_CBUCK_DISCHARGE_TIME_MS、core buck の放電）、high にして 500 ms（BT_POWER_ON_SETTLING_TIME_MS）待ってから HCI_Reset を送る。
- 直し:
  - `src/drivers/platform/rpi4/rpi4-bt.c`: BT_ON の low を 300 ms、high の後の CTS の待ちと合わせて 500 ms を待ってから（静かな時間・hunt に入る）。
  - `userland/base/bluetoothd/session.c`・`session.h`: UART の controller は HCI reset（ROM の reset、patch の後の reset、core の set-up の reset）の答えの後
    100 ms 待ってから次の command を送る（`timing.reset_settle_ms`、この daemon の選択）。
- この 2 つで直る確信は WiFi より低い（answer が来ない理由が電源の時間か reset の直後の取りこぼしかを実機で分けていない）。T1 の結果で直らなければ、
  PL011 の CTS（controller の RTS）が reset の後に落ちたままで送信が FIFO に止まっている可能性を次に調べる（kernel の `out` の数は FIFO に入れた数で、
  送り出した数ではない）。

### `rpi4-firmware: tag 30066 not supported`

- 0x00030066 は GPU の driver（`src/drivers/gpu/bcm2711/display-execute.c`、WS141）の display-done の通知。値の無い通知で、firmware は tag の答えの bit を
  立てないことがあり、driver は ENOTSUP を「通知は届いた」と扱って続ける（その file の注記の通り）。WiFi・BT とは関係が無く、害は無い（log の 1 行だけ）。

## 2026-10-14 P2: T1-632 の後（3 回目、commit は下）

T1-632（[結果](../agents/T1/results-20261014-t1-632.md)）: WiFi は firmware・NVRAM・CLM・country まで通り、`bcm43455: firmware version not read (42)`（ETIMEDOUT）で止まる。
BT は変わらず（reset の答え 7 byte の後、Read Local Version の答えが来ない）。

### WiFi: "ver" と "cap" を小さい buffer で読む

- 観察: 同じ control の道で `cur_etheraddr`（6 byte）・`country`・CLM の set（約 1.4 KiB）は通り、`ver` だけが答えを得ない。driver は get で「返して欲しい
  大きさ」の分の bytes を送る（Linux・bwfm と同じ）ので、`ver` は control の buffer のほぼ全部の 2047 byte を要求していた（frame は padding で 2560 byte）。
- 直し（`src/drivers/wifi/bcm43455/bcm43455.c`）: `ver` は 256 byte、`cap` は 768 byte を要求する（brcmfmac（ISC）の BRCMF_DCMD_SMLEN と
  MAX_CAPS_BUFFER_SIZE と同じ値。brcmfmac もこの大きさで読む）。原因が firmware の ioctl の大きさの上限か、SDIO の 5 block の書き込みかは分けていないが、
  どちらも 1〜2 block の要求で避けられる。
- 確信: 中。次に止まる所は `capabilities not read`、その次は radio の起動（`scan_ver`・escan）。

### BT: 送信が止まっているかを見る log と、Read Local Version の 1 回の再送

- 原因は分かっていない。reset の後 100 ms の間（前回の直し）でも同じ。分けるべき 2 つ: (a) 送信が FIFO に止まっている（controller の RTS = host の CTS が
  落ちたまま、PL011 の CTSEN の flow control で出ない）、(b) 送信は出たが controller が答えない。kernel の `out` の数は FIFO に入れた数なので区別できない。
- 直し:
  - `src/drivers/platform/rpi4/rpi4-bt.c`: program の reset（BT_IOC_RESET）の前に、その時の PL011 の FR を log に出す:
    `rpi4-bt: before the program's reset: FR xxx (CTS asserted|not asserted, send FIFO empty|holding bytes, busy|idle)`。2 回目以降の reset の行が、
    答えの来なかった command の後の線の状態を示す。
  - `userland/base/bluetoothd/session.c`: UART の controller で Read Local Version が時間切れなら、100 ms 待ってもう 1 回だけ送る。
- 次の判断: `send FIFO holding bytes` と `CTS not asserted` が出れば (a) — controller の RTS（GPIO 30 の CTS0）の扱い、または CTS の flow control を
  ROM の段だけ切る案。`empty` なら (b) — controller が答えない理由（DEV_WAKE、ROM の版、reset の直後の扱い）を調べる。
