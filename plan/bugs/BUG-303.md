# BUG-303: Core i5-13400F の desktop で Local APIC timer の較正が PIT の待ちで timeout し起動が止まる

- 状態: reproduced（実機、ユーザーの写真）/ scheduled（2026-10-14 Q1、bug-fixer）。修正 commit fc31f6ebe（2026-10-14、未検証: T1 の QEMU と実機の確かめ待ち）
- 発見: ユーザー（2026-10-14、Core i5-13400F の desktop、画面の写真 `build/review/bug303/screen.webp`、git に入れない）「これAPICのエラー、直せそう？」
- 観察（写真の文字）: `A64 TIMECOUNTER CANDIDATE policy=2 max=32 ratio=130/2 crystal=38400000 invariant=1 adjust=1` の後に `A64 TIMER CAL TIMEOUT stage=out-high port61=0D lapic-current=FF158E95 polls=1000000`、`fatal: src/hal/amd64/cmain.c:101: amd64 Local APIC timer initialization failed`。cpus=16、ACPI・IOAPIC は READY。
- 解析（Q1、source を読んだだけ）: `src/hal/amd64/bsp-pcat/lapic.c` の較正は TSC の周波数が CPUID 0x15 で分かっている時（policy=2 = READY）も、LAPIC の timer を PIT の channel 2 の 10 ms の窓（port 0x61 の OUT の bit）で測る。この機械では PIT の OUT が high から変わらない（Alder Lake・Raptor Lake の desktop の firmware は 8254 の clock を止めることがある、推測）。TSC は 38.4 MHz × 130/2 = 2.496 GHz と分かっている。
- 直し方の案: TSC の周波数が READY の時は、LAPIC の timer を TSC の 10 ms の busy-wait の窓で測る（PIT を使わない）。PIT は TSC の周波数が分からない時（KVM など）だけ。HAL の実装の直しで hal.h は変えない。
- 関連: 5320・5330（Alder Lake の laptop）は PIT が動き起動する。

## 修正（2026-10-14 bug-fixer、commit fc31f6ebe、未検証）

- 解析と code は一致した: `amd64_lapic_timer_start()` は policy に関係なく `pit_wait_10ms()` で窓を作っていた。AP（`smp.c` の `amd64_ap_entry`）と sleep の復帰（`idle-suspend.c`）は BSP が決めた `timer_initial` を書くだけで、較正は BSP の 1 回だけ（AP は `hal_cpu_start_others` で BSP の較正の後に起きる）。PIT を使うのは `lapic.c` だけ。
- 変更（`src/hal/` の実装だけ、`include/hal/hal.h` は不変）:
  - `src/hal/amd64/bsp-pcat/lapic.c`: 較正を `calibrate_timer()` に分けた。`amd64_timecounter_bsp_prepare()` が READY（CPUID 0x15 と invariant TSC）の時は、新しい `tsc_wait_window()` が TSC の 10 ms（`TIMER_CAL_WINDOWS_PER_SECOND` = 100）の窓で free-running の APIC の count を測る（3 窓で最短、今の形のまま）。NEEDS_PIT（KVM を含む）と UNAVAILABLE は今までどおり PIT（NEEDS_PIT は TSC の周波数も PIT で測る）。TSC が動かない時の上限 `TSC_POLL_LIMIT`（1 億回）で `A64 TIMER CAL TIMEOUT stage=tsc` を出す。
  - log: `A64 TIMER CAL BEGIN` の後に `A64 TIMER CAL source=tsc hz=<TSC Hz> window=<TSC count>` か `A64 TIMER CAL source=pit` を 1 行。`WINDOW n elapsed=`・`READY ticks=`・`TIMEOUT`・`INVALID` の行の形は不変。
  - `timecounter.c`/`.h`: `amd64_timecounter_bsp_candidate_frequency()`（完成した BSP の候補の TSC の Hz を返す、HAL の内部）。
  - `timecounter-policy.c`/`.h`: 純粋な `amd64_tsc_window_ticks()`（TSC の Hz → 1 窓の count、端数は切り上げ、1 MHz〜10 GHz の外と 0 を拒む）。
- PIT の timeout の後に TSC で較正し直す fallback は入れていない: TSC が READY なら PIT を使わないので要らず、NEEDS_PIT・UNAVAILABLE では TSC の Hz が分からないので TSC で測れない。
- 確かめ（host、QEMU・実機は未実施）:
  - `make ZEDBSD_CONFIG=config/ci/config-amd64.mk build/amd64/vmunix -j16`（worktree の `build/amd64/`、`build/llvm`・`build/NoctLang` は main の symlink）: exit 0、warning 0（374 個の compile が `-Wall -Wextra -Werror`）、kernel include check PASS、amd64 vmunix check PASS。vmunix に `A64 TIMER CAL source=tsc hz=%llu window=%llu` と `source=pit` の文字列がある。
  - host 試験（scratchpad の使い捨て、git に入れない）: `timecounter-policy.c` を host の gcc（`-Wall -Wextra -Werror`）で build し 9 項目 PASS: 13400F の CPUID（crystal 38400000、130/2）→ READY 2496000000 Hz、10 ms の窓 = 24960000、端数の切り上げ、上限・下限・0・NULL の拒否。
  - `git diff --check` 問題なし。

### 試験の依頼（Q1 → T1、QEMU）

- image: main に merge された commit（fc31f6ebe を含む tree）で `config/ci/config-amd64.mk` の image を作る。
- 流す: `plan/tools/boot-test.sh` を 2 回、(1) 既定（KVM、`-cpu host`。policy は NEEDS_PIT で PIT の経路）、(2) `QEMU_NO_KVM=1`（TCG、`-cpu max`。CPUID 0x15・invariant TSC の有無で経路が変わる、多くは UNAVAILABLE で PIT）。
- 合否: 両方で login prompt の PNG が撮れる。画面に `A64 TIMER CAL source=` の行が見えれば、どちらの経路だったかを結果に書く（見えなければ「未確認」でよい、serial/console log では判定しない）。
- 見る点: この QEMU の 2 回は PIT の経路が変わっていないこと（回帰）の確かめで、TSC の経路は通らない見込み。TSC の経路は実機で確かめる。

### 確かめの依頼（ユーザー、実機）
