# BUG-295: Pi 4 の FAT（/boot/boot0、SD の boot 区画）への 8MB の書き込みに数分かかる

- 状態: reproduced（Pi 4 の実機、2026-10-13） / resolved（2026-10-13 ユーザー「解決済みです。」、実機で確かめ済み）
- 発見: 2026-10-13 Q1 が SSH で vmunix（8.1MB）を /boot/boot0/vmunix.new へ cp し sync した時、約 4.7MB まで 1〜2 分、全部で数分かかった（ユーザー「カーネルのコピーに時間がかかりすぎです」）。同じ前に vmunix の .bak（8.2MB）の cp も同様に遅かった。root の UFS（mmcblk0p2）との比べは未測定。
- 影響: Pi の kernel の差し替え・更新が遅い、更新の途中の電源断の危険が長くなる。
- 候補（推測）: FAT の driver の cluster の割り当て・FAT の表の書き戻しが 1 cluster ごと、sync の度の全体の flush、SDHCI の小さな転送、cache を通らない書き込み。
- 次: 同じ大きさの UFS と FAT への dd の時間を比べ、FAT の driver（src/drivers/fs/ の fat）と mmc の転送の大きさを見る。

## 解析（2026-10-13 bug-analyzer、source だけ、Pi は未測定）

- 主因（確度 高）: Pi 4 の SD driver（src/drivers/platform/rpi4/rpi4-sdhci.c）が `d_max_transfer_blocks = 1`（:197）で全要求を 1 block の bio に割り、`transfer_block`（:683-755）が単一 block の CMD24/CMD17 を PIO で出し、block ごとに INT_TRANSFER_COMPLETE を polling で待つ（:749、card の program 遅延を 512B ごとに払う）。DMA・多 block（CMD18/CMD25）・High Speed は未使用、clock 25 MHz（:381）。
- FAT の書き込みの増幅: buffer cache が FAT では write-through（UFS は DISK_WRITE_CACHED を立てる、FAT は立てない、src/kern/buf.c:2942）、line の一部の書き換えは 4KiB の line を読んで 8 block 全部を書き戻す（buf.c:758-872、:3221-3260）。FAT は割り当てた cluster を書く前に 0 埋め（fat.c:5006-5100、:1424-1470）し、62 sector の run が line に揃わず 0 埋めの chunk ごとに 2 line を書く。FAT 表は mirror 2 つ（:3581-3680）。8MB で CMD24 約 5 万・CMD17 約 1.6 万 → 100〜250 秒の見積り。
- 直す案: (1) SD を多 block（CMD25/CMD18、BLOCK_COUNT、auto-CMD12、d_max_transfer_blocks 128）、次に ADMA2 と High Speed。(2) FAT で同じ write が丸ごと上書きする cluster の 0 埋めを省く（crash の時に古い内容が見える可能性、ユーザーの判断）。(3) 0 埋めの chunk を 4KiB line に揃える、または writeback_line_whole を dirty の範囲だけに。(4) FAT_BATCH_ENTRIES 32→128。(5) FAT にも DISK_WRITE_CACHED（設計の確認が要る、後回し）。
- Pi で測る手順: `sysctl hw.diskstats` の前後（mmcblk0 の write_ops・write_ns）、`time dd if=/dev/zero of=/boot/boot0/t8m bs=64k count=128; time sync` と UFS の同じ、`sysctl vfs.io.stats` の前後。

## 直し（2026-10-13 P4、b200ebb02。Q1 の判断で案 (1)(3)(4) を入れ、(2)(5) は入れない）

- (1) SD を多 block に（`src/drivers/platform/rpi4/rpi4-sdhci.c`）: `transfer_block` を `transfer_blocks(write, block, count, buffer)` にし、2 block 以上は CMD18/CMD25、transfer mode に multi-block・block-count-enable・auto-CMD12（SD Host Controller Simplified Specification の DMA 無しの手順）。PIO のまま、block ごとに BUFFER_READ_READY / BUFFER_WRITE_READY を待って 128 word を動かし、TRANSFER_COMPLETE（write の busy と auto-CMD12 の後）を 1 run に 1 回待つ。`d_max_transfer_blocks` は 1 → 128（`SD_RUN_BLOCKS`、KERN_IO_BATCH_MAX の 64 KiB）。clock 25 MHz・4 bit は変えない。ACMD23/CMD23 は使わない。
  - error と recovery: run の失敗（command・buffer の待ち・auto-CMD12 の error）は、どの prefix が動いたか分からないので、報告（interrupt status・Auto CMD Error Status 0x3c・present state）→ `restore_card`（今の `recover_card` = CMD/DATA line の reset、CMD13 で状態を見て DATA/RCV なら CMD12、PRG は待つ → 駄目なら `controller_init` → それも駄目なら `unit.failed`）→ run の全 block を今の `transfer_block_recovering`（単一 block、3 回の試行）で順に動かし直す。同じ block の再書き込み・再読み出しは無害。`transfer_block_recovering` の扱いは前と同じ（recovery の部分を `restore_card` に括り出しただけ）。
  - `sd_submit` は bio を最大 128 block の run に分けて順に動かす（disk 層が 128 で割るので通常 1 run）。
- (3) FAT の 0 埋め（`src/drivers/fs/fat.c` の `fat_engine_zero_run`）: chunk を leaf disk の 4 KiB line の境界で切る（`disk_resolve_range` で leaf の block 番号を得る。解けなければ前と同じ切り方）。中の chunk は line 丸ごと（読まずに書く）、端だけ部分の line。`FAT_ZERO_SECTORS` は `KERN_PAGE_SIZE / 512`（値は 8 のまま）。書く中身は同じ。
- (4) `FAT_BATCH_ENTRIES` 32 → 128。意味は変わらない: 1 transaction が触る FAT の sector は `FAT_BATCH_SECTORS`（8）で今まで通り縛られ、超える batch は書く前に E2BIG で割る（`fat_raw_free_chain` の半分割り・単一への fallback は前のまま）。`fat_raw_allocate_run` の上限は min(64 KiB / cluster, 128 − tail) で、同じ FAT の sector に入る entry だけを束ねる規則・0 埋め → durable → tail の link の順は変わらない。1 KiB cluster なら 1 transaction が 31 → 64 cluster、512 B cluster なら 31 → 127（SYNC の回数がそれぞれ約 1/2・1/4）。
  - 代わりに stack が増える（arm64 の `-fstack-usage`）: `fat_raw_allocate_run` 512 → 1664 B、`fat_raw_free_chain` 368 → 1136 B（allocate_run の rollback で両方が重なると +1.9 KiB）。arm64・amd64 の kernel stack は 16 KiB で、fat.c には既に 4 KiB 級の frame（mount・identify）と 1.1〜1.5 KiB の frame（insert_entry・set_cluster）がある。**x68k（m68k、kernel stack 8 KiB、fat.c を含む）は未計測**（共有の LLVM に m68k の target が無い）。
- 入れない（ユーザーの判断・設計の確認が要る）: (2) 同じ write が丸ごと上書きする cluster の 0 埋めを省く（crash の時に古い中身が見えうる）、(5) FAT に DISK_WRITE_CACHED。
- 次の段（未着手）: ADMA2（DMA）と High Speed（50 MHz、CMD6 の switch）。PIO 25 MHz・4 bit の上限は約 12.5 MB/s。

### 確かめた事（host と build だけ。QEMU・Pi の実機は未実施）

- 新しい host 試験 `tests/rpi4-sdhci-host-test.c`（`make -o …/.zedbsd-sysroot-complete ZEDBSD_CONFIG=config/ci/config-rpi4.mk rpi4-sdhci-host-test`、規則は `platform/arm64/vmunix.mk`）: driver の写し（include を除き、generic timer の 2 つの `mrs` を偽の時計に置き換え）を偽の controller・card に対して動かす。128 block の write/read が CMD25/CMD18 1 つ（arg・count 128・mode 0x26/0x36）と auto-CMD12、1 block は CMD24/CMD17（multi の bit 無し）、flush は command 無し、200 block は 128 + 72 の 2 run、CMD25 の 6 block 目の error → CMD13・CMD12 の recovery → 16 個の CMD24 を順に（CMD25 は再試行しない）、CMD18 の先頭の error → 8 個の CMD17、毎回失敗する card → 先頭の block だけ 3 回試して request は EIO・`unit.failed` は立たない。結果 `rpi4-sdhci-host-test: PASS`。変異（auto-CMD12 の bit を外す・fallback を read にする・run を 129 にする）でそれぞれ FAIL することを確かめた。

- `plan/tools/style-check.py`: rpi4-sdhci.c・fat.c は直す前と同じ件数（新しい指摘なし）、試験は 0。`git diff --check` 問題なし。
- FAT の (3)(4) に host 試験は無い（fat.c の kernel driver の host 試験が無い）。読みで確かめた。

### Pi で測る手順と危険

- 危険: SD の書き込みの driver を変えたので、誤りがあると boot 区画・root の UFS を壊しうる。置く前に元の vmunix を残す（例 /boot/boot0/vmunix.bug295-bak、または config.txt の kernel= で切り替え）。戻し方: 起動しない・書き込みが壊れる時は SD を別の機械に挿して boot 区画の vmunix を元に戻す。root の UFS が壊れた時は fsck か書き直し。
- 手順: `sysctl hw.diskstats`（mmcblk0 の write_ops・write_ns）と `sysctl vfs.io.stats` の前後、`time dd if=/dev/zero of=/boot/boot0/t8m bs=64k count=128; time sync`、同じを root の UFS に、`cp vmunix /boot/boot0/vmunix.new; sync` の時間と `cksum` の一致、umount・再 mount の後の `cksum`、log の `sdhci:` の失敗の行が無いこと。
