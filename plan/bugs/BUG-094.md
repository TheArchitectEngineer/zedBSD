# BUG-094: i915 の capture の image で compositor が始まらない（HAL の起動時の時間の測定が vCPU の停止で狂う: APIC timer の較正、AP の timecounter の probe）

Bug ID: `BUG-094`
Reproduction: reproduced（5330 の passthrough: p015 の e6-1、2026-09-28 の再開の e5-1・e6-2・e5-2。p006 の r6 も同じ形）
Disposition: resolved（2026-09-29、ws075-p009: ws075-p015 の修正の後、実機の passthrough で再現なし。下の「確認」）
Date: 2026-09-28
Source: ws075-p015（BUG-085 の再試験）
Owner: WS075

## 観測

BUG-091 の修正を含む kernel（main 06abe378）の egltest6 の capture の image で、compositor が始まらなかった。kernel の log は
`resident: GPU node published; serving` で終わり、guest の disk に zdesktop 等の log が無い。約 180 秒後の gdbstub: 4 つの CPU が全て
`sched_idle`、kernel の tick は進む、`next_pid` は 6。service の連鎖の最初の `sleep 45`（vkwait1）が終わらなかったか、init が終わりを見なかった。
**最初の gdb の attach（数秒の VM の停止）がその `sleep 45` の間にあった**ので、attach が原因の可能性を否定できない。

## 次の手

gdb を stall の印の前に attach しない、きれいな run（`plan/ws075/tests/bug085-hw.sh`）を 5 回以上。再び出れば、sleep の timer（BUG-091 で
`kern_usleep_range` を irqsave にした変更を含む）と init の子の回収を調べる。証拠: `build/ws075-b085-evidence/e6-1/`。

## 原因（2026-09-28、ws075-p015 の再開、gdbstub）

**local APIC timer の較正の誤り**（gdb の attach の影響ではない）。main 06abe378 系の egltest6・p005 の image（worktree の
`build/b085-e6`・`build/b085-e5`）の 3 回の run のうち 2 回（e5-1・e6-2）で起きた:

| run | `A64 TIMER CAL READY ticks=` | 結果 |
| --- | --- | --- |
| e6-1 | 62755（正常、1 kHz） | compositor は最後まで動いた |
| e5-1 | 1069954（17 倍） | 180 秒で capture の frame 0。gdbstub: 4 CPU とも `sched_idle`、`kernel_ticks` は壁時計 5 秒で 296（約 59 Hz）、起動から 8 分で 28 秒分 |
| e6-2 | 875803（14 倍） | watcher が較正の行で打ち切り |

kernel の tick が 14〜17 倍遅いので、service の連鎖の `sleep 45` が 10 分以上かかる（p015 の e6-1 の「180 秒で tick 0x3aa2〜0x4779」も
同じ: 約 18 秒分）。`src/hal/amd64/bsp-pcat/lapic.c` の `amd64_lapic_timer_start()` は APIC timer の free-running の count を
`pit_wait_10ms()` の**前**に始め、PIT の gate の窓（10 ms）の後に読むので、窓の前の準備（port 0x61・0x43・0x42 の I/O と OUT の low の
待ち。KVM では port I/O ごとに VM exit）の時間も数える。host が vCPU をその間に止めると窓が長く測られる。TSC の較正は gate の縁で
括っているので正しかった（悪い run でも `PIT READY hz=0:2496981131`）。

## 修正（ws075-p015、`src/hal/amd64/bsp-pcat/lapic.c`、hal.h は不変 = 承認不要の HAL の実装の変更）

APIC timer の count を TSC と同じく gate を上げる直前と OUT の high を見た直後で読み（`pit_wait_10ms()` の `lapic_start`・`lapic_end`）、
窓を 3 回測って最短（遅れは窓を長くするだけ）を TSC の組と一緒に使う。各窓を `A64 TIMER CAL WINDOW n elapsed=` で log する。
検証: [ws075-p015](../ws075/phase015/phase.md)。

## 2 つ目の形: AP の timecounter の probe の期限切れ（e5-2）

e5-2（較正は正常 62770）は `A64 TIMECOUNTER AP FAIL cpu=2 reason=ready-timeout` → 全 CPU の `TIMECOUNTER READ ... unavailable` →
`TIMECOUNTER UNAVAILABLE ... reason=cpu-set-invalid` → i915 の start が `time_base_anomaly: 5`（`drv_i915_time_base_ok()` が
`kern_rtc_read_counter()` の不在で EIO）→ GPU の node が無く compositor は `ZWL EXIT frames=0 error=6`。p006 の r6（「host の電源の入れ直しの
直後」と書かれた）も同じ形。e6-2 も較正の誤りに加えて同じ UNAVAILABLE だった。`src/hal/amd64/bsp-pcat/timecounter.c` の
`wait_probe_value()` は AP の準備を `pause` の 1000 万回で待つ（実機で約 0.5 秒）。vCPU が host に止められると AP は後から動く
（gdb では CPU2 も後に `sched_idle` にいた）。

修正: 同じ file で、poll の数に加え、TSC の rate が分かっていれば TSC で最低 2 秒（`TIMECOUNTER_PROBE_SECONDS`）待つ（4096 poll ごとに TSC を見る）。

## vCPU が止まる理由（推定）

5330 の capture の harness（`plan/ws031/tests/i915-capture.py` の `scan_for_area()`）は起動の直後から guest の 2 GiB を 64 MiB ずつ
QMP の `pmemsave` で読み続ける（capture の領域を探す）。QEMU の `pmemsave` は BQL を持ったまま file に書くので、BQL の要る vCPU の exit
（port I/O の 0x61・0x42・0x43、AP の SIPI の処理）が待たされる。H4（`h4-ctl.py splash` の 250 ms ごとの screendump）も同じ性質。
実機（bare metal）では同じ形の遅れは SMI などで起きうる。harness の側は変えていない（`i915-capture.py` は WS031 の共有の道具）。

## 確認（2026-09-29、ws075-p009、WS075 の i915 の subagent）

- ws075-p015（cleared）: 修正の後の egltest6・p005 の capture の image の各 5 回で、較正の誤り・AP の probe の期限切れ・compositor の不始動は 0。
- ws075-p008・p009: デモの passthrough の image（`plan/ws075/demo/build-demo-image.sh ... passthrough`、H4 の harness が起動の直後から
  250 ms ごとに std VGA の screendump を取る = vCPU が止められる条件）の 5 回の起動（`build/ws075-p008/hw-base`・`hw-irq`、
  `build/ws075-p009/hw1`・`hw2`・`hw3`）で、全て desktop が出て描画が進んだ（PLANE_SURFLIVE の flip、画面）。
- 合わせて 15 回で再現なし。resolved とする。再発したら（compositor が始まらない、i915 の start が `time_base_anomaly`）開き直す。
