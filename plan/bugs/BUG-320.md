# BUG-320: Pi 4 で browser が起動しない

- 状態: reproduced（Pi 4 実機、ユーザー・P1）/ scheduled。(1) 時計と (2) shell は P1 が直した（T2 の実機の確かめ待ち）、(3) GPU の描き方は B1 へ（下の「B1 への引き継ぎ」）
- 発見: 2026-10-15 ユーザー「Piでブラウザが起動しませんでした。PiではなくQEMUで確認できますか？P1を割り当てます。」
- 環境: Pi 4（kei@10.0.30.2）、kernel main 5afbaa4d5（T2 の T1-657）、userland はユーザーの build（main 2597b86 の頃、Bluetooth の driver off）。
- 症状: 窓が出ずに 0.5 秒で終わる（下の P1 の切り分け）。
- 関連: WS074（browser・libbrowser、B1）、WS141（Pi の GPU）。

## P1 の切り分け（2026-10-15、Pi 実機を読むだけ・host）

Pi（kernel・userland はユーザーの 2597b86、`uname` も同じ）で ssh から `XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0 /bin/browser`:

- 引数無し: 0.5 秒で rc=1。stdout に `ZBROWSER ERROR load path=https://www.google.com/ error=Protocol error tls=handshake: certificate verify failed: certificate is not yet valid` だけ、stderr は空。dmesg に v3d の error は無い。
- `/tmp/t.html`（ローカルの小さな頁）: `ZBROWSER READY width=1024 height=600`・NAVIGATE・TITLEBAR の後 `browser: cannot draw a frame: vkCreateGraphicsPipelines failed (-8)`（VK_ERROR_FEATURE_NOT_PRESENT）で終わる。

原因は 3 つ重なる:

1. **時計**: Pi 4 は RTC が無く、`date -u` が `Thu Jan 1 00:10:30 UTC 2026`（boot からの経過）。`/etc/rc.conf` の ntpdate は `enabled: false`・`servers: ""`。既定の開始頁の証明書が「まだ有効でない」で TLS が失敗する。
2. **shell**: `userland/desktop/browser/shell/shell.c` の shell_run が、最初の頁（libbrowser は最初の頁を同期で読む）が失敗すると窓を開かずに `return 1` で終わる。利用者には何も見えない。
3. **Pi の GPU**: kernel の V3D の Vulkan（`src/drivers/gpu/bcm2711/`）が libbrowser の paint の pipeline を断る。host で bcm2711 の shader compiler を直に呼んだ probe（scratch、tree に入れない）と source の検査で:
   - frag の `gl_FragCoord`（`shader-analyze.c` input_interface、builtin の入力は未実装）。
   - frag の `texelFetch`（DRV_GPU_IR_TEXTURE。正規化 2D の SAMPLE だけ対応）。
   - 頁の item を `VK_VERTEX_INPUT_RATE_INSTANCE` で渡す（`vulkan-pipeline-state.c` は VERTEX だけ）。
   - blend の srcColor が `SRC_ALPHA`（straight alpha。driver は ONE/ONE_MINUS_SRC_ALPHA だけ）。
   `plan/ws141/tests/shader-host-test.c` でも "browser paint" の frag は refused と既知の扱い。→ Pi では browser は一度も描けていない。
   試し: gl_FragCoord を noperspective の varying に、texelFetch を nearest の sampler の `texture()`（atlas 2048 の texel の中心）に替えた frag は bcm2711 の compiler が受け付けた（144 word）。

QEMU: raspi4b（TCG）には V3D が無いので 3 は再現できない。3 は host で決定的に再現できる。

## 判断（2026-10-15 ユーザー、Q1 経由のクリック）と分担

- (3) は **A: browser の描き方を Pi の driver に合わせる** → libbrowser の paint の shader・pipeline の直しは **B1**（下の「B1 への引き継ぎ」）。
- (1) は **ntpdate を既定で有効に、server は pool.ntp.org、Pi の image だけ** → P1（下の「P1 の直し」）。
- (2) shell の直し → P1。
- C（CPU で描いて写す fallback）は guardrail の「画像の処理は GPU で」（2026-10-12 ユーザー）に反するので作らない。

## B1 への引き継ぎ（(3)、libbrowser の paint を Pi の V3D の範囲に）

Pi の kernel の Vulkan（`src/drivers/gpu/bcm2711/`、main 0882d4576 で確認）が今の `userland/desktop/libbrowser/paint/vulkan.c` と `paint/shaders/display.{vert,frag}` を断る所は 5 つ。どれか 1 つでも残ると `vkCreateGraphicsPipelines` が -8（VK_ERROR_FEATURE_NOT_PRESENT、`vulkan-pipeline.c` の pipeline_status で ENOTSUP/E2BIG → -8）か、draw の記録の失敗になる。

1. **frag の `gl_FragCoord`**: SPIR-V の frontend は `DRV_GPU_SHADER_LOCATION_FRAG_COORD`（`src/drivers/gpu/compiler/spirv.c:2304`）の入力にするが、`src/drivers/gpu/bcm2711/shader-analyze.c:115` input_interface が location 16 以上の入力（builtin）を ENOTSUP で断る。→ vert で `layout(location = 5) noperspective out vec2 item_pixel; item_pixel = position;`（position は vert の quad の画素の座標）、frag で `vec2 pixel = floor(item_pixel);`。画素の中心で補間されるので floor は元の `floor(gl_FragCoord.xy)` と同じ画素になる。
2. **frag の `texelFetch`**: DRV_GPU_IR_TEXTURE は `shader-analyze.c:213` の instruction_shape で "operation has no native graphics lowering"。正規化座標の 2D の `texture()`（DRV_GPU_IR_SAMPLE）だけ受ける。→ atlas は `PAINT_GPU_ATLAS_SIZE` 2048 の正方形で sampler は NEAREST・CLAMP_TO_EDGE（vulkan.c:699-704）なので、`texture(glyphs, (floor(place) + 0.5) / 2048.0)` は元の `texelFetch(glyphs, ivec2(place), 0)` と同じ texel（2048 は 2 の冪で除算は厳密）。ivec2() の切り捨ては place が非負なので floor() と同じ。横倒しの glyph は `offset = floor(pixel - item_source.xy)`、`place = floor(item_atlas.xy) + vec2(offset.y, floor(item_source.z) - 1.0 - offset.x)`。
3. **instance の頂点入力**: `vulkan.c:1048` の `bindings[1].inputRate = VK_VERTEX_INPUT_RATE_INSTANCE` を `src/drivers/gpu/bcm2711/vulkan-pipeline-state.c:128` が断る（VERTEX だけ）。
4. **instance の draw**: `vulkan.c:1818` の `vkCmdDraw(commands, GPU_CORNERS, count, 0, 0)` は instanceCount が 1 を超えると `src/drivers/gpu/bcm2711/vulkan-record-validate.c:73`（`words[1] > 1 || words[3] != 0`）で ENOTSUP。→ 3 と 4 は、item ごとに 6 頂点（2 つの三角形）を作り、各頂点に corner と item の 5 つの vec4 を持たせる（binding 1 つ、6 属性、stride 96 byte ≦ 2048、offset ≦ 2047、R32G32B32A32_SFLOAT は受ける）。draw は `vkCmdDraw(commands, 6 * count, 1, 0, 0)`。
5. **blend**: `vulkan.c:1092` の srcColor = `SRC_ALPHA`（straight alpha）を `vulkan-pipeline-state.c:234` が断る（src ONE・dst ONE_MINUS_SRC_ALPHA・ADD だけ、alpha も同じ）。→ frag が premultiplied を出す（`color = vec4(rgb * a, a)`、a は alpha×coverage）にして blend を ONE/ONE_MINUS_SRC_ALPHA に。target は不透明で結果の色は同じ（丸めの差は B1 の pixel 一致の基準で確かめる）。

その他は受ける形: dynamic state は viewport・scissor の 2 つ（vulkan.c と一致）、topology TRIANGLE_LIST、cull NONE、1 sample、color の attachment 1 つで write mask は RGBA、atlas は B8G8R8A8_UNORM・LINEAR・SAMPLED。push constant は vert の vec4。

確かめ方（host、QEMU も実機も要らない）:
- 1 と 2 は scratch で shader を書き換え、`regenerate.py`（glslc・spirv-val）で作った SPIR-V を、`bcm2711_shader_compile()` を直に呼ぶ小さな host の probe（`src/drivers/gpu/compiler/{spirv,optimize}.c`・`src/drivers/gpu/bcm2711/{shader,shader-analyze,shader-lower,shader-output,shader-schedule,qpu}.c` を cc で link、`kern_calloc`/`kern_malloc`/`kern_realloc`/`kern_free` は libc に写す）に通し、frag 144 word・vert 255 word・coord 170 word で受けることを確かめた（P1、2026-10-15）。元の shader は frag が ENOTSUP。
- 直したら `plan/ws141/tests/shader-host-test.c` の "browser paint" の行の `fragment_refused` を 0 にして QPU の模擬の bit 一致に入れる（mesa の oracle `plan/ws141/temp/mesa` が要る。無ければ上の probe で compile が通るところまで）。
- pipeline の状態（3〜5）は `vulkan-pipeline-state.c` の検査を読めば決まる。実機は Pi で `/bin/browser /usr/share/browser/start.html` が `cannot draw a frame` を出さずに FRAME を出すこと（T2、Q1 経由）。

## P1 の直し（(1)(2)、2026-10-15）

- (2) `userland/desktop/browser/shell/shell.c`: 最初の頁が読めない時（TLS・offline・無い file）、窓を開かずに終わるのをやめ、理由を示す頁（data: の HTML: location、`strerror` と libbrowser の理由、「Try again」の link）を最初の頁の代わりに出して窓を開く。その間 titlebar は失敗した location を出し（data: の URL は titlebar の 1023 byte の上限を超えるので）、reload はその location を command line と同じ解決で読み直す。その頁も出せない時だけ従来どおり rc=1（stderr に `browser: cannot open ...`）。
- (1) `userland/base/ntpdate/main.c`: `-w` を足した（server が答えるまで 10 秒ごと、60 回まで、途中の失敗は黙って、最後だけ報告）。`-w` 無しの動きは変えていない。新しい package `userland/base/netclock/`（data だけ、`/etc/service.d/netclock`: `type=daemon`・`command=/sbin/ntpdate`・`arguments=-w pool.ntp.org`・`after=networking`・`restart=no`）。daemon なので init は待たず、network が無い boot は遅れない。既定では選ばれず、`config/ci/config-rpi4.mk` の ZEDBSD_USER_PROGRAMS で選ぶ（bootlog と同じ形）。`userland/base/etc/rc.conf` に `netclock: enabled: true, optional: true`（service の無い image では何も言わない）。ntpdate の service（rc.conf の ntpdate、`enabled: false`・servers ""）は変えていない。

## T2 の実機（T1-659、2026-10-15、B1 の p238 の libbrowser、kernel main 5afbaa4d5）

- windowed（`/bin/browser file:///home/kei/t1-659.html`、20 秒）: READY・NAVIGATE・TITLEBAR・FRAME が出て、`cannot draw a frame`・`vkCreateGraphicsPipelines failed`・`v3d: EIO` は無い。shell に CPU の描画の道は無い（P1 の調べ、案 C は作っていない）ので、FRAME は GPU で描いた frame と Q1 は読む。画面の目視・撮影は未実施。→ Q1 の判定: (3) の pipeline の拒否は解けた。
