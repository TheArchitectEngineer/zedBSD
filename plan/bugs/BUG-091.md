# BUG-091: i915 の timer の thread が spin lock を持ったまま別の CPU へ移り、spin_unlock で kernel が止まる

Bug ID: `BUG-091`
Reproduction: reproduced（1 回、5330 の i915 の VFIO passthrough、ws075-p013 の run5-apps、Notes の起動の約 2 秒後）
Disposition: resolved（2026-09-28、ws075-p014。実機の passthrough で Notes・PDF Viewer の起動 48 回で fault なし）
Date: 2026-09-28
Source: ws075-p013（H4）
Owner: WS075

## 観測

`amd64 fault v=6` at `spin_unlock+0x35`（`ud2`）→ `unhandled amd64 fault`。gdbstub の backtrace: `i915_timer_thread` → `waitq_sleep` →
`sched_sleep_locked` → `spin_unlock`。lock（`timers->lock`）は `held=1 owner_cpu=0` だが CPU1 が離した。30 分の Terminal の run では出なかった。

## 推定（2026-09-28 の ticket の作成時、未確認）

timer の thread が割り込みを許したまま `timers->lock` を持ち、`spin_lock` が preempt を止めないため、lock を持ったまま thread が別の CPU へ移った。
BUG-085（i915 の compositor の停止）との関係は未確認。

## 次の手

spin lock の保持中の preempt の扱い（`spin_lock` が preempt を止めるか、irqsave を使うべき所か）を調べ、i915 の timer の lock の取り方を直す。
実機で Notes の起動を繰り返して確かめる。証拠: `build/ws075-h4-evidence/run5-apps/`、`build/ws075-shots/hdmi-h4-notes-launch-kernel-fault.png`。

## 原因（2026-09-28、ws075-p014）

- kernel の `spin_lock()`（`src/kern/lock.c`）は割込みも preemption も止めない。持ち主の CPU を記録し、別の CPU の解放と同じ CPU の再取得を
  `__builtin_trap()`（`ud2`）で止める設計。clock の tick は quantum の尽きた kernel thread も `sched_yield()` で preempt し
  （`sched_clock_cpu()`）、暇な CPU は run queue の thread を盗む。したがって割込みを許したまま spin lock を持つ thread は、preempt されて
  別の CPU で続きを走り得て、その解放が trap する。
- `sched_sleep_locked()`（`waitq_sleep()` の下）の契約は「IRQ-safe の condition lock」（`include/kern/sched.h`）: 割込みを止めてから
  sleep を公開し lock を離す。lock を割込み許可で取った呼び手では、lock から `sched_sleep_locked()` の `hal_irq_disable()` までの間が
  preempt の窓になる。kernel の他の全ての `waitq_sleep()`・`sched_sleep_locked()` の呼び手（94 箇所を機械的に照合）は `spin_lock_irqsave()`。
  **kernel の sleep の経路は正しく、i915 の driver が契約を破っていた**（と kernel の `kern_usleep_range()` の 1 箇所）。
- `i915_timer_thread()`（`src/drivers/gpu/i915/workqueue.c`）は `timers->lock` を `spin_lock()`（割込み許可）で取り、loop の間（期限の
  計算、`waitq_sleep()` の手前）持つ。file の注記は「thread からだけ取るので普通の spinlock でよい」だったが、preemption を考えていない。
  Notes は delayed work を増やしたきっかけと見られる（run3 の 30 分の Terminal では出ていない）。

## 修正（ws075-p014）

- i915: 割込み許可のまま thread の文脈で `spin_lock()` を取っていた全ての所を `spin_lock_irqsave()`/`spin_unlock_irqrestore()` に:
  `workqueue.c` の timer queue の lock（6 関数）、`device.c` の start registry の lock（5 関数）、`request-queue.c` の
  `drv_i915_request_complete_list()` の `device->irq_lock`（retire の度に通る。IRQ lock を割込み許可で取っていた）、`sync.c` の
  `i915_wait_reg_slow()` の局所の lock の 1 tick の sleep、`tests/execution/ktest-sync.c` の K0。`display/hotplug.c` の 2 箇所は割込みの
  handler の中（割込み禁止）なので変えない。
- kernel: `kern_usleep_range()`（`src/kern/clock.c`、i915 の PCODE 等が使う）の局所の lock も同じ形だったので `spin_lock_irqsave()` に。
  `spin_lock()` と `waitq_sleep()` の注記に、thread は割込み禁止の所でだけ `spin_lock()` を使い、condition lock は `spin_lock_irqsave()` で
  取ることを書いた。sched・lock の実装と HAL は変えていない。

## 確認

  （毎回 mouse で 4 本の stroke を描いて Ctrl+W）、PDF Viewer を 24 回（Ctrl+W）、合計 48 回の起動。kernel の log（debugcon の全 record）に
  `amd64 fault`・`fatal`・`unhandled` は 0。lease 1〜3 は `ended PASS ... first anomaly: none`（lease 3 は shutdown の前に QEMU を止めた）。
  証拠: worktree の `build/b091-run1/`（`kernel.log`、`guest-logs.txt`、`shots/c2..c24-{notes,pdf,empty}-{A,B}.png`）、
  `build/ws075-shots/bug091-*.png`。
- host: `src/drivers/gpu/i915/tests/contracts/run.sh sync`（sync.c と workqueue.c）42 checks 0 failures（通常と ASan/UBSan）。
- QEMU: GPU の無い boot test（`plan/tools/boot-test.sh`、同じ image）PASS。
- 再現の率は元々未測定（H4 で 1 回）なので、48 回の無事は「直った」の証明ではなく、原因の除去（コードの読みで確定）と再現しないことの証拠。
