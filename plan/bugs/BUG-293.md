# BUG-293: DHCP が失敗して 169.254.x.x（link-local）になった後、`net down en0` などをしても 169.254 の address が外れない

- 状態: unknown（実機で未再現、source から原因を特定） / scheduled（修正を実装、2026-10-12 P1、実機の確認待ち）
- 発見: 2026-10-12 ユーザー（Pi 4、place23 以降の image）:「net down en0してもなにしても、DHCPの割り当て失敗の169.*.*.*が解除されないバグに遭遇」。
- 関係する source（Q1 の見当）: networkd が DHCP の失敗の後に link-local を割り当てる（`userland/base/networkd/managed-lan.c` の `networkd_lan_link_local`）。`net`（`userland/base/net/main.c:2225` 付近で 169.254.0.0/16 を「自分の address が無い」と扱う）、dhcpc、ifconfig。
- 期待: `net down en0` で address が外れ、`net up`・DHCP の再試行で 169.254 が DHCP の address に置き換わる。
- 観察: 169.254 が残り、解除されない。
- 再現の条件・手順・環境: 未記録（ユーザーに確かめる。Pi 4 の genet（en0）か USB か、DHCP の server の有無）。
- 次: bug-analyzer が source を読んで原因の候補を出す。Pi の SSH が戻ったら networkd の log と ifconfig の出力で確かめる。

## 解析（2026-10-12 bug-analyzer、要点）

- (A) `networkd/main.c` の `lan_assign_link_local` が `networkd_lan_link_local` に `sizeof(request.ifr_hwaddr)`（8）を渡していた。kernel の SIOCGIFHWADDR は 8 byte の field に 6 byte の MAC を入れて残りを 0 にする（`include/uapi/netif.h`、`src/kern/net/inet-socket.c` の SIOCGIFHWADDR）ので、host 部が padding の 0 から作られ、全機で 169.254.1.0 になる。
- (B) `net down en0`（NETWORKD_OP_DOWN）は DHCPv6 の返却と `ifconfig down` だけで IPv4 の address を消さない。genet は close で carrier を落とし、networkd の wired policy は down の後に RAISE（`ifconfig up`）し、carrier が戻ると DHCP を試し、失敗で 169.254 を付け直す。
- (C) UNCONFIGURED の再試行は cable の抜き差しだけで、`net up` では DHCP が再試行されない。
- (D) `net dhcp` の EIO は子の非 0 終了を一律 EIO にするだけで、dhcpc の失敗の段階は /dev/console にしか出なかった。
- 2026-10-12 Q1 追記: Pi の dmesg に `ufs: mmcblk0p2: the volume refuses writes ...`（BUG-294）。root が書けず dhcpc が /etc/resolv.conf を書けないと lease 全体が rollback されて EIO になる見込み。書き込みの失敗を DHCP の失敗と分けて出す。

## 修正（2026-10-12 P1、worktree p1 branch agent/p1）

- (A) `lan_assign_link_local` は `LAN_HARDWARE_ADDRESS_LENGTH`（6）を渡す。割り当て・失敗を syslog に書く。
- (B) wired policy に `held_down`（管理者の down）を足した（`managed-lan.[ch]` の `networkd_lan_hold_down`・`networkd_lan_release`）。held の間は RAISE も CONFIGURE もせず、CARRIER_UP は何も決めない。NETWORKD_OP_DOWN が成功したら `lan_hold_down`（hold、`lan_clear_address`、lease の route を取り下げ、syslog）。radio・loopback（policy の表に無い）は対象外。
- (C) NETWORKD_OP_UP が成功したら `lan_release`: held を外し、cable があり CONFIGURED でなければ PENDING（DHCP の再試行）、cable が無ければ RAISE に戻す。CONFIGURED はそのまま。
- (D) dhcpc は失敗の行（段階・rollback・socket・interface 選択）を console に加えて stderr にも書く（`report_failure`。進捗の行は stderr に書かない: networkd の diagnostic は 384 byte で、進捗が段階を押し出すため）。networkd の diagnostic と `net dhcp` の応答の stage にその行が乗る。/etc/resolv.conf を書けない失敗は段階 `lease obtained, but /etc/resolv.conf could not be written` として DHCP の失敗と分ける。networkd は DHCP の失敗（自分の configure と `net dhcp`）、link-local の割り当て、管理者の down/up、/etc/resolv.conf の書き込みの失敗を syslog（ident は既定の `zedbsd`、本文の先頭に `networkd:`）に書く。
- `net show`（SHOW）の 2 語目: 169.254.0.0/16 の address は `link-local`（それ以外は従来どおり `static`/`unconfigured`）。追従: `plan/ws033/tests/ssh-host-to-guest.py` の regex。desktop の `libkeiland-backend-zedbsd/network-zedbsd.c` は `static` だけを有線の接続と見るので、link-local の interface は有線の接続と見なされなくなる（コードの変更なし、header の注記は未更新）。
- 試験: `make managed-lan-host-test`（MLAN-T001）に場面を追加（padded 8 byte の field と 6 byte、hold の後に RAISE・CONFIGURE しない、CARRIER_UP が何も決めない、release で CONFIGURE、UNCONFIGURED の up で CONFIGURE、CONFIGURED の up で何もしない、cable の無い release で RAISE）。PASS。
- build: amd64・rpi4 の networkd・dhcpc・net が warning 0。
- 未確認: QEMU・実機（Pi 4）の確認は未実施。Pi で DHCPv4 が失敗する根本の理由は未確定（BUG-294 の root の書き込み拒否が候補）。
- 再調査の契機: Pi の SSH が戻ったら、`net down en0` で address が外れること、`net up en0` で DHCP が再試行されること、/var/log/messages の `networkd:` の行と `net dhcp en0` の stage を見る。
