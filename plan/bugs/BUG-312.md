# BUG-312: 起動の時に root の UFS が壊れていると read-only で mount され、fsck して rw にしない

- 状態: reproduced（実機、ユーザー）/ scheduled（2026-10-14 Q1、P2）
- 発見: 2026-10-14 夜、Pi 4（10.0.30.2）で WS236 の試験の kernel が止まった後、電源を入れ直すと root が RO で mount されていた。ユーザー「Pi4はイメージが壊れてROマウントになっていたので、書き直して起動しました。」「RO mountは動作中に壊れたらRO remountならわかりますが、ブート時にROなのは使いづらいです。fsckしてRWにするべき、というバグフィックスはできそうですか？」
- 期待: 起動の時に root（と他の UFS）が clean でなければ、mount の前に fsck（または journal の replay と修復）をして、直せたら rw で mount する。直せない時だけ RO にして、理由と回復の手順を画面と log に出す。
- 関連: BUG-307・BUG-308（UFS の journal）、WS072（UFS の format の lease）。
- 追加（2026-10-14 ユーザー）: 「しかも、ジャーナリングFSを書き込み途中で電源断したところで、修復できずにROマウントなのは、明らかにバグです。」→ 起動の時の fsck に加えて、電源断の後に journal の replay で直らず RO になった原因そのものを直す。壊れた image はユーザーが書き直したので証拠は無く、QEMU の電源断の繰り返しで再現する。
- 役割の分担（2026-10-14 ユーザー）: 「journal replayはカーネルの役目、それでもROマウントになったら/sbin/fsck (これはstatic link)して、re remountするのがinitの役目、という感じですね。」

## 調べた結果（source の読み、P2 2026-10-14）

壊れた image が無いので、確定ではなく source から見た経路。

### 起動の道（Pi 4）

- Pi の cmdline.txt は `login=...` だけで root を名指ししないので、kernel は **legacy autoroot**（`src/kern/vfs.c` `vfs_mount_legacy_root`）を使う。
- legacy autoroot は、boot partition の隣の partition を 1 つずつ **read-only の private mount** で開いて、`etc/zedbsd-root` の marker を読む（`ufs_root_marker_matches`）。
  - その mount が `EINVAL`・`EROFS`・`EOPNOTSUPP` で失敗すると、何も log に出さずに「root ではない」と扱う。
  - root が見つからないと、ARM の image overlay（FAT の `/rootfs.img`、UFS root の image には無い）を試し、それも無いと **FAT の boot partition を root にする**。
- 見つかった UFS root は rw で mount する（`mount_root_create("auto", 0, ...)`）。kernel が root を RO で mount し直す道は無い。rw の mount が失敗すると起動が止まる。
- amd64 は `rootpart=` の native root で、marker の probe が無い。WS063 の `plan/tools/ufs/root-crash.sh`（電源断と replay の試験）は amd64 の native root だけを試しているので、Pi の道は試されていない。

### 見つけた不具合（確実なもの）

1. **v3 の journal の volume は、read-only の mount で summary が group の数とずれていると EINVAL で失敗する**（`ufs_mount_impl`）。
   - 「journal の無い volume は clean のはず」という検査が `ms->journal_enabled`（v2 の tail journal）しか見ない。
   - v3（batched journal）の volume は `journal_enabled` が 0 で、write cached の rw の mount（root）だけが免除されている。
   - write cached の root は、電源断で summary が group の数より遅れる（同じ関数の注記「a crash can leave the totals behind the groups' own counts」）。
   - よって **電源断の後の Pi では、marker の probe（read-only）が EINVAL で失敗し、UFS root が「無い」ことになる**。
2. **marker の probe の失敗が log に出ない**。UFS の superblock がある partition が mount できなくても黙って飛ばす。
3. **v3 の replay は、最新の commit の descriptor・payload の checksum が合わないと EINVAL で mount 全体を失敗させる**（`j3_replay` → `j3_replay_slot` → `j3_payload_apply`）。
   - 「record は durable、payload は未完」の commit は、完了しなかった commit なので捨てて、前の commit（もう一方の slot）に戻すべき。
   - BUG-307 の bec395969 の注記は、修正の前の kernel にこの窓（record が payload より先に durable）があったと書いている。Pi の kernel はその前の build の可能性がある。
4. ufs の mount の失敗（metadata の領域の free の bit、root inode が無い、summary、replay）の理由が log に出ない。`j3_load` の EINVAL（journal を作り直す）も黙っている。

### 走っている時の RO

`stop_writing`（ufs.c の 43 か所）は、走っている時の失敗で volume の書き込みを止め（`EROFS`）、log に「the volume refuses writes until it is mounted again」と理由を出す。
ユーザーの見た「RO」がこれだった可能性も残る（次の mount では書ける）。

### fsck と remount

- userland に fsck は無い（`userland/base` に無く、`mount` に remount（`MNT_UPDATE`）も無い）。
- kernel にも RO → RW の remount は無い。
- host の検査（`tools/build/check-ufs-image.py`、298 行の python）は到達性・block の所有・bitmap・link の数・summary・directory を検査するが、直さない。

## 直しの案（P2、2026-10-14）

役割の分担はユーザーの 2026-10-14 の指示のとおり。kernel は replay と、直せる不整合の修復。init は RO の root に fsck。

| # | 内容 | 見積もり |
| --- | --- | --- |
| K1 | `ufs_mount_impl`: summary のずれは、v3 の journal・write cached・read-only の mount では group の数から作り直す（read-only では memory の中だけ、書かない）。log に出す | 0.2 LW |
| K2 | ufs の mount の失敗の理由（free の bit、root inode、replay の各検査、`j3_load` の作り直し）を全部 log に出す。marker の probe も、UFS の partition が mount できない時は log に出す | 0.2 LW |
| K3 | `j3_replay`: 最新の commit の descriptor・payload の checksum が合わない（未完の commit）時は捨てて log に出し、もう一方の slot が未適用なら適用する。I/O の error は今までどおり失敗 | 0.3 LW |
| K4 | root が rw で mount できず read-only なら mount できる時（orphan の scan・summary の書き戻し・clean の flag の失敗など）は、read-only で mount して理由を console に出す（起動を止めない） | 0.3 LW |
| I1 | init: root が read-only なら `/sbin/fsck -y <root の device>` を流す。直せたら（下の決定に従い）reboot か remount。直せない時は RO のまま、理由と回復の手順を console に出す | 0.5 LW |
| F1 | `/sbin/fsck`（static）: superblock・cg・inode・間接 block・directory を読み、block の重複と範囲外、directory の entry（`.`・`..`・未確保の inode）、到達性（lost+found）、link の数、cg の bitmap と数、summary、clean の flag を直す。v3 の journal は kernel の replay の後を前提とする（未適用の commit があれば適用か拒否）。host の image を壊す試験を含む | 3.5〜4 LW |
| R1 | （選択）kernel の root の RO → RW の remount（UFS の mount の状態を rw にする、cache の捨て直し）。代わりに fsck の後の reboot なら不要 | 1.5〜2 LW |
| T | 再現の手順（T1）: Pi か arm64 の QEMU で、UFS root を書き続けながら電源断を繰り返す。log の判断の行を見る | 0.3 LW |

K1〜K4 は小さく、BUG-312 の直接の原因（電源断の後に Pi の root が見つからない、replay の失敗で mount 全体が失敗する）に当たるので、先に実装する。
F1・I1・R1 は大きいので、Q1 とユーザーの判断を待つ。決めることは 2 つ。

1. fsck の後は remount（R1、FreeBSD の `mount -u` に当たる）か、reboot（FreeBSD の rc の「FILE SYSTEM WAS MODIFIED」の後の reboot と同じ）か。
2. F1 をベータ 2 に入れるか。
