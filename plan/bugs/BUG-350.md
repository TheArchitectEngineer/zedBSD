# BUG-350: VF2 で usb_hub_worker（USB hub の kernel thread）が 1 つの CPU を常に 100 % 使う

- 状態: fixed（確かめ: VF2・QEMU、2026-10-29 P3、commit f3d89900a）。旧: open（2026-10-29 Q1 が登録、P3 が WS221 の q1664 の中で直す）
- 発見: 2026-10-29 P3（q1664、VF2 の TCP の計測）。sched の tick で kernel thread の入口を数える一時の差分で、5 秒ごとに 5000/5000 tick が `usb_hub_worker`（`src/drivers/usb/usb-hub.c`）。
- 観測: idle の時も同じ。main の kernel でも 1 CPU が常に system 100 %。TCP の計測でも 1 CPU が取られる。
- 期待: hub の変化が無い時、usb_hub_worker は眠る（CPU を使わない）。

## 原因（2026-10-29 P3）

`usb_hub_worker` の loop（`src/drivers/usb/usb-hub.c`）は hub の status change endpoint を `drv_usb_interrupt(..., USB_HUB_POLL_MS = 250, ...)` で待つ。この同期の転送の待ちは USB の core の `drv_usb_urb_wait`（`src/drivers/usb/usb.c`）で、URB が終わるまで `sched_yield()` を呼び続ける作りだった。他に走る thread の無い CPU では yield がすぐ戻るので、hub の 250 ms の待ちの間ずっと CPU を 100 % 使う（hub は変化が無い限り待ち続けるので常に 100 %）。hub の driver ではなく core の同期待ちの問題なので、全 platform（xHCI・EHCI・UHCI の同期の転送）で同じ形。

## 直し（f3d89900a）

`drv_usb_urb_wait` の未完了の間の `sched_yield()` を `urb_sync_sleep()` に替えた: 1 つの wait queue（`usb_sync_waitq`、condition lock `usb_sync_lock` は `LOCK_RANK_POLL`）で眠り、URB の終端の状態を公開する所（`atomic_raw_store_release(&urb->status, status)` の直後）で `urb_sync_wake()` が待ち手のいる時だけ全員を起こす（各自が自分の URB を見直す）。待ち手の数と状態の公開の間は両側の full fence で取りこぼさない。保険として 1 回の sleep は 10 ms（`USB_SYNC_SLEEP_MAX_MS`）か転送の deadline までで見直す。

## 確かめ

- VF2 実機（2026-10-29、kernel は f3d89900a を含む build）: idle の 10 秒の `hw.cputimes` で各 CPU の busy が 0.1〜0.3 %（直す前は 1 つの CPU が system 100 %、idle の tick 1273 のまま増えない）。hub 2109:3431 は直した後も `lsusb` に出る。
- QEMU（`plan/ws221/tests/qemu-usb-idle.sh`: xHCI に usb-hub、その後ろに usb-mouse）: `qemu-usb-idle: PASS`、busy cpu0=0.3 % cpu1=0.0 % cpu2=0.4 % cpu3=0.1 %。`lsusb` に hub 0409:55aa と mouse。直す前の QEMU の値は測っていない（未実施）。
