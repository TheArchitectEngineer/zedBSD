# BUG-353: RTX 2070 で mview をゲームの表示（mailbox）で一度動かすと、同じ起動の中で後から開いた mview の window が画面に写らない

- 状態: reproduced（実機） / fixed（2026-10-29 WS309 p012、branch `agent/p1-ws309i` 799e52d4c、main に未 merge）
- 発見: 2026-10-29 P2（q1670-i04、WS291 p010a の実機、10.0.10.3 の RTX 2070、nvrtx）。
- 再現: 起動 → mview の shot（fifo）→ 出る。続けて mview の spin（mailbox、ゲームの表示）→ その後の mview の shot（fifo）→ window が写らず Settings の Welcome だけ（`plan/ws291/tests/rtx-mview-order.sh`、出力 o1 の a は出る、c・e・f は出ない）。
- 観測: GPU の error・fault は無い。depth の有無と無関係（depth は動く、WS291 p010a）。
- 期待: ゲームの表示を返した後も、window の表示が元どおりに出る。
- 範囲の見込み: ゲームの表示（VK_KHR_display・display の取り返し）の後の compositor の出力の戻し。WS309（Keiland の thread の整理、ゲームモード）と関係するかは未調べ。RDNA・i915 で起きるかは未確かめ。
- 2026-10-29 P1（q1662-i06、読みだけ）: 再現の道は compositor のゲームモード（`scanout.c` の enter/leave、backend `scanout-zedbsd.c` の claim・present・release、leave の後に window の mode が swapchain を開き直す）。WS309 の p001〜p008 はこの経路に触れていない（最後の変更は WS309 の前の 5f9ec7f08）ので WS309 が原因ではない。原因は未調べ（nvrtx の release の後の再 import か、leave の後の window の状態か）。
- Q1 の判断（2026-10-29）: WS309 の p012（display thread: claim・release・swapchain の作り直し）がこの enter/leave を書き直すので、p012 の受け入れに RTX の再現の試験（`plan/ws291/tests/rtx-mview-order.sh`）を入れ、p012 の中で直す（10.0.10.3 の枠は Q1 が割り当てる）。
- 2026-10-29 P1（q1662-i09、WS309 p012）: 原因と直し。
  - 原因: GPU・nvrtx の誤りではない。基点の compositor では、ゲームモードの leave の後に main が window mode を開き直し（2 s）、続けて glass maps 6 枚を作り直した
    （約 3.9 s。nvrtx では memory の確保が大きさに比例して遅く、8 MB で約 0.5 s）。その間 main が塞がれ、mview の最初の commit が試験の写し（mview の起動から 6 s）より後になった。
    window は後の frame で描かれていた（基点の run `build/ws309/rtx/r1c-base/c-shot1-session.log` の frame 928）。
  - 直し: 開き直しを display の thread へ（p012 の T3）、出力の let-go で glass maps と層の絵を保ち同じ大きさなら使い直す（55ef19028・799e52d4c）。
  - 確かめ: RTX `plan/ws309/tests/rtx-bug353-pair.sh`（2026-10-29 22:39〜22:48）で a・c・f の over15 が全て 2、PASS。main の塞がりは最長 270 ms（take）。
    基点の run（16:56）は c=2073252 で再現していた。
- 2026-10-30 P5（q1677-i02、WS243 p006、10.0.10.3 の RTX 2070）: 「nvrtx では memory の確保が大きさに比例して遅い」の原因と直し（Q1 の指示で記録）。
  - 原因: nvrtx の blob の作成（`node.c` → `nvrtx_bo_clear`）が新しい VRAM を CPU で register window（PRAMIN）越しに 4 byte ずつ消していた。
    実機の計測（一時の log、commit しない）: 約 31.7 MB/s。8294400 byte（1920x1080x4）で 254〜266 ms、16588800 byte で 508 ms、3133440 byte で 99 ms
    （`build/ws243/p006-hw2/tmp-clear.txt`、P5 の worktree）。上の「8 MB で約 0.5 s」と同じ桁。
  - 直し（WS243 p006、branch `agent/p5-ws243`）: 256 KiB 以上の blob は driver の work channel の copy engine の fill（128 KiB の行の多行、`nvrtx_work_clear`）で消す。
    driver の channel の copy object は nvrtx.video の有無に関わらず作る。fill の submit の失敗・fence の時間切れでは以後 CPU（PRAMIN）の消しに戻り、時間切れの VRAM は返さず別の VRAM を CPU で消して作成は成功させる。
  - 効果（実機、nvrtx.video=1）: Video Player の 1080p60 全画面の開始の止まり 2.4 s → 最初の CLOCK まで 114 ms、late 148 → 8。
    glass maps の作り直し（このチケットの再現）の時間は未計測（`plan/ws309/tests/rtx-bug353-pair.sh` は未実施）。
