# BUG-291: libc の memcpy・memmove・memset が 1 byte ずつの loop で遅い（uncached の map で 12 MB/s）

- 状態: reproduced（Pi 4 の実機の計測、2026-10-12 P3） / scheduled（P2、修正を commit 済み、Pi での効果の確かめ待ち）
- 発見: 2026-10-12 P3（ws141-p013）。Pi 4 で Settings の title bar の hover が重い件の内訳: libkeiland の present-copy.c が canvas の行を map した memory へ memcpy する所で 1180x800x4＝3.8 MB に 305 ms（約 12 MB/s）。
- 原因（source）: `src/libc/string.c` の `memcpy`・`memmove`・`memset` が 1 byte ずつの loop。canvas の map は Normal non-cacheable（`render-device.c` の render_map → `DRV_GPU_MAPPING_UNCACHED_RAM`）なので 1 byte ごとに uncached の store になる。kernel の `kern_memcpy` は word 単位で別。
- 影響: 全 platform の全 userland の memcpy・memset・memmove（特に uncached・write-combined の map への写し）。
- 直す案: word（できれば 16 byte）単位の memcpy・memmove・memset（alignment の前後の端を byte で、重なりの向き、`-fno-builtin` の下で compiler が自分を呼ばない形）。amd64・arm64（i386 は今は build しない、guardrail）。host の試験（長さ・alignment の組み合わせ、重なり）と速さの比較。

## 修正（2026-10-12 P2、branch agent/p2-bug291、base 08ce47169、commit cfd4dfbe7）

- 範囲: `src/libc/string.c` の `memcpy`・`memmove`・`memset` だけ（`bzero`・`bcopy`・`mempcpy`・`explicit_bzero` は委譲なので同じく速くなる）。`memcmp`・`memchr`・`str*`・rtld の `src/rtld/string.c`・kernel の `kern_memcpy` は変えない。
- 方式: 長さが 2 word 以上なら、destination が word（`unsigned long`、amd64・arm64 で 8 byte）の境界に揃うまで byte、その後は 1 pass に 4 word（32 byte）の word の写し、残りを byte。store は常に揃った word。source が揃わない時は `__aligned__(1)` の型で読む（amd64・arm64 は 1 命令の unaligned load、m68k・sparcv9 は compiler が byte の load にする）。型は `__may_alias__`（arm64・amd64 の libc.so は `-fno-strict-aliasing` 無しで build される）。`memmove` は destination が source より下か重ならない時は前から、上から重なる時は後ろから（どちらも 1 pass の 4 word を全部読んでから書く）。
- 生成 code: target の clang（-Os -fno-builtin）で arm64 は `ldp q0, q1` / `stp q0, q1`（16 byte の store）、amd64 は `movups` の 2 本。memcpy・memset の呼び出しへの書き換え（自分を呼ぶ形）は無い（clang の arm64・amd64、host の gcc・clang、m68k-linux-gnu-gcc -m68000 で確かめた。GCC 14 は `-fno-builtin` か `-ffreestanding` があれば書き換えない。無い時は書き換えるので、この file は libc の flag（`-fno-builtin`）で build する前提）。
- host の試験: `sh plan/tools/libc-string-host-test.sh`（新規、ASan・UBSan、clang・gcc の -Os・-O2）。長さ 0〜300 × source・destination の offset 0〜15 の全部の組、memmove は長さ 0〜160 × 同じ buffer の中の 40×40 の配置（前・後の重なり）、大きな block（4095〜3.8 MB+7）、memset は値 0・0xff・0x5a・-1・0x1234（下位 byte だけ）。結果を byte の参照と memcmp で比べ、前後の guard も確かめる。結果 4 通り全部 PASS（358813 checks）。故意の誤り（後ろ向きの順序・方向の判定・末尾の 1 byte 多い・unaligned の読み違い）を入れた版で FAIL になることを確かめた。既存の `plan/ws001/tests/strerror-host-test.py` も PASS。
- 速さ（参考、host の amd64、cache あり、3.8 MB、-Os -fno-builtin）: memcpy 1.59 → 0.28 ms（揃い）、1.41 → 0.28 ms（source +3）、memmove（後ろ向きの重なり）1.38 → 0.14 ms、memset 6.54 → 0.16 ms。Pi 4 の uncached の map での効果は未計測（Q1 経由で P3 の計測を待つ）。
- build: `make -j8 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug291-amd64 build/bug291-amd64/dynamic/libc.so build/bug291-amd64/dynamic/libkeiland.so build/bug291-amd64/bin/settings` と同じ target の `ZEDBSD_CONFIG=config/ci/config-rpi4.mk BUILD=build/bug291-rpi4`、両方 rc=0・warning 0（worktree の sysroot の libc.o も作り直された）。Linux の keiland は zedBSD の libc を使わないので build していない。
- 未実施: QEMU・実機の確認（Pi 4 の present-copy の時間、全体の回帰）。

## 2026-10-12 直しを main から外した

Pi 4 で、直しの libc（cfd4dfbe7）に置き換えて起動すると、compositor が `glass.c` の `tiles_create`（Normal non-cacheable の map の先頭への大きな memset と icon の decode・縮小、CPU だけ）で CPU を使い続けて止まった（P3 の切り分け、kernel のせいではない、libc を元に戻すと起動）。新しい word 単位の経路（memset か memcpy・memmove）の無限 loop の見込み。Q1 が `src/libc/string.c` を merge の前（9f1e501c1）に戻した。host の試験（plan/tools/libc-string-host-test.*）は残す（新しい直しで使う）。P2 が直し直す。状態は scheduled に戻す。
