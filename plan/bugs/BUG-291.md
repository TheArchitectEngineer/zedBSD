# BUG-291: libc の memcpy・memmove・memset が 1 byte ずつの loop で遅い（uncached の map で 12 MB/s）

- 状態: reproduced（Pi 4 の実機の計測、2026-10-12 P3） / resolved（2026-10-13 ユーザー「解決済みです。」、実機で確かめ済み）
- 発見: 2026-10-12 P3（ws141-p013）。Pi 4 で Settings の title bar の hover が重い件の内訳: libkeiland の present-copy.c が canvas の行を map した memory へ memcpy する所で 1180x800x4＝3.8 MB に 305 ms（約 12 MB/s）。
- 原因（source）: `src/libc/string.c` の `memcpy`・`memmove`・`memset` が 1 byte ずつの loop。canvas の map は Normal non-cacheable（`render-device.c` の render_map → `DRV_GPU_MAPPING_UNCACHED_RAM`）なので 1 byte ごとに uncached の store になる。kernel の `kern_memcpy` は word 単位で別。
- 影響: 全 platform の全 userland の memcpy・memset・memmove（特に uncached・write-combined の map への写し）。
- 直す案: word（できれば 16 byte）単位の memcpy・memmove・memset（alignment の前後の端を byte で、重なりの向き、`-fno-builtin` の下で compiler が自分を呼ばない形）。amd64・arm64（i386 は今は build しない、guardrail）。host の試験（長さ・alignment の組み合わせ、重なり）と速さの比較。

## 修正（2026-10-12 P2、branch agent/p2-bug291、base 08ce47169、commit cfd4dfbe7）

- 範囲: `src/libc/string.c` の `memcpy`・`memmove`・`memset` だけ（`bzero`・`bcopy`・`mempcpy`・`explicit_bzero` は委譲なので同じく速くなる）。`memcmp`・`memchr`・`str*`・rtld の `src/rtld/string.c`・kernel の `kern_memcpy` は変えない。
- 方式: 長さが 2 word 以上なら、destination が word（`unsigned long`、amd64・arm64 で 8 byte）の境界に揃うまで byte、その後は 1 pass に 4 word（32 byte）の word の写し、残りを byte。store は常に揃った word。source が揃わない時は `__aligned__(1)` の型で読む（amd64・arm64 は 1 命令の unaligned load、m68k・sparcv9 は compiler が byte の load にする）。型は `__may_alias__`（arm64・amd64 の libc.so は `-fno-strict-aliasing` 無しで build される）。`memmove` は destination が source より下か重ならない時は前から、上から重なる時は後ろから（どちらも 1 pass の 4 word を全部読んでから書く）。
- 生成 code: target の clang（-Os -fno-builtin）で arm64 は `ldp q0, q1` / `stp q0, q1`（16 byte の store）、amd64 は `movups` の 2 本。memcpy・memset の呼び出しへの書き換え（自分を呼ぶ形）は無い（clang の arm64・amd64、host の gcc・clang、m68k-linux-gnu-gcc -m68000 で確かめた。GCC 14 は `-fno-builtin` か `-ffreestanding` があれば書き換えない。無い時は書き換えるので、この file は libc の flag（`-fno-builtin`）で build する前提）。
- host の試験: `sh plan/tools/libc-string-host-test.sh`（新規、ASan・UBSan、clang・gcc の -Os・-O2）。長さ 0〜300 × source・destination の offset 0〜15 の全部の組、memmove は長さ 0〜160 × 同じ buffer の中の 40×40 の配置（前・後の重なり）、大きな block（4095〜3.8 MB+7）、memset は値 0・0xff・0x5a・-1・0x1234（下位 byte だけ）。結果を byte の参照と memcmp で比べ、前後の guard も確かめる。結果 4 通り全部 PASS（358813 checks）。故意の誤り（後ろ向きの順序・方向の判定・末尾の 1 byte 多い・unaligned の読み違い）を入れた版で FAIL になることを確かめた。既存の `plan/ws001/tests/strerror-host-test.py` も PASS。
- 速さ（参考、host の amd64、cache あり、3.8 MB、-Os -fno-builtin）: memcpy 1.59 → 0.28 ms（揃い）、1.41 → 0.28 ms（source +3）、memmove（後ろ向きの重なり）1.38 → 0.14 ms、memset 6.54 → 0.16 ms。Pi 4 の uncached の map での効果は未計測（Q1 経由で P3 の計測を待つ）。
- build: `make -j8 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug291-amd64 build/bug291-amd64/dynamic/libc.so build/bug291-amd64/dynamic/libkeiland.so build/bug291-amd64/bin/settings` と同じ target の `ZEDBSD_CONFIG=config/ci/config-rpi4.mk BUILD=build/bug291-rpi4`、両方 rc=0・warning 0（worktree の sysroot の libc.o も作り直された）。Linux の keiland は zedBSD の libc を使わないので build していない。
- 未実施: QEMU・実機の確認（Pi 4 の present-copy の時間、全体の回帰）。

## 2026-10-12 直し直し（P2 第 4 generation、branch agent/p2-bug291b、base e6b98d824、commit 689e0f911）

### 原因（source と target の objdump で確定、Pi の実機では未観察）

libc の word の直し（cfd4dfbe7）の codegen は正しい。arm64 の target の clang（-Os -ffreestanding -fno-builtin -fPIC）の object と libc.so を objdump した: memset・memcpy・memmove は自分（や PLT）を呼ばず、loop の終わりの条件も正しい（`build/bug291b-rpi4/dynamic/libc.so`）。止まったのは arm64 の HAL の実装の 2 つの不具合の組み合わせ:

1. `src/hal/arm64/space.c` の `leaf_flags`（user の page の属性）が `HAL_SPACE_NOCACHE`（`HAL_SPACE_DEVICE` 無し）を `PTE_ATTR(2)`、つまり MAIR の Attr2＝**Device-nGnRnE** にしていた。kernel の同じ RAM の view（`hal_pmem_map_uncached`）は Attr3＝Normal non-cacheable で、`src/kern/vm-device.c` の注記も「Managed uncached RAM uses Normal memory attributes, preserving unaligned byte access」。user の Vulkan の map（`DRV_GPU_MAPPING_UNCACHED_RAM` → `VM_DEVICE_UNCACHED_RAM` → `HAL_SPACE_NOCACHE`）だけが Device だった。Device memory では揃わない access（揃わない source の 8 byte の load、8 byte 揃いで 16 byte 揃いでない destination への `stp q0, q1`）が alignment fault になる。`kwl_icon_tile`（`userland/desktop/wayland/icons.c`）は tile の各行を `memset(argb + row * stride, 0, pixels * 4)` で消すので、pen_x の位置で 8 mod 16 の destination になる。旧 libc は byte の store なので fault しなかった。最初の 12 MB/s も Device-nGnRnE（1 store ごとに完了を待つ）で説明が付く。
2. `src/hal/arm64/int.c` の `arm64_classify` が EC 0x24/0x25（data abort）を fault status（ESR の DFSC）を見ずに全部 page fault にしていた。alignment fault（DFSC 0x21）も `kernel_user_fault_handler` → `vmspace_fault` に渡り、page はあって書けるので 0（解決済み）が返り、同じ命令に戻って永久に fault する。compositor が CPU を使い続けて止まった症状そのもの。

### 直し

- `src/hal/arm64/space.c`: `leaf_flags` の `HAL_SPACE_NOCACHE` を `PTE_ATTR(ARM64_ATTR_NORMAL_NC)`（Attr3）に（1 行と注記）。`HAL_SPACE_DEVICE` は Attr1（Device-nGnRE）のまま。hal.h・API は不変（src/hal/ の実装の修正、Q1 の許可 2026-10-12）。
- `src/hal/arm64/int.c`: EC 0x24/0x25 で DFSC 0x21 なら `HAL_TRAP_CAUSE_ALIGNMENT`（user は SIGBUS・BUS_ADRALN）、EC 0x20/0x21/0x24/0x25 で DFSC が translation・access flag・permission（0x04〜0x0f）以外なら `HAL_TRAP_CAUSE_OTHER`（SIGBUS）。それ以外は従来どおり page fault。kernel の fault（vector 0）は `kernel_sys_fault_handler` が cause に関係なく fatal にするので、kernel の挙動は変わらない（arm64 の HAL に copyin の fixup は無い）。
- `src/libc/string.c`: cfd4dfbe7 と同じ word 単位の memcpy・memmove・memset（変更なし）。
- `plan/tools/libc-string-host-test.{c,sh}`: (a) page 境界に揃えた 1040×4 byte の pitch × 600 行の image の全体の memset と、pixel の列 0〜15（4 byte 刻み、8 mod 16 を含む）・大きさ 1〜64 の tile の各行の memset と揃わない source からの memcpy（tiles_create と kwl_icon_tile の形）、(b) arm64 の pass: 木の LLVM の clang で `--target=aarch64-linux-gnu -march=armv8-a -Os -ffreestanding -fno-builtin -fPIC`（ldp/stp q が出る target と同じ codegen）で string.c を build し、`aarch64-linux-gnu-gcc -static` の harness と link して `qemu-aarch64`（user mode）で走らせる。道具が無ければその pass を skip と書く。

### 影響の確認（grep）

- `leaf_flags` は user の map（`hal_space_map`・`hal_space_prot_query`）だけで使われる。`hal_space_map` は managed RAM しか受けない（`p < hal_pmem_get_total_size()`）。kernel の device の map（`hal_space_map_device`、`kern_device_map`・ACPI・Type-C・PCI の BAR）は別の経路で変わらない。
- user の map で `HAL_SPACE_NOCACHE` を付けるのは `vm_device_page_attributes` だけで、`VM_DEVICE_UNCACHED_RAM` を作るのは `src/drivers/gpu/gpu.c`（`DRV_GPU_MAPPING_UNCACHED_RAM`）だけ。それを使うのは bcm2711 の render-device（V3D の buffer）と display-device（scanout）。どちらも snoop しない DMA が読む RAM で、kernel の view は既に Normal NC。MMIO（`VM_DEVICE_MMIO`）は `HAL_SPACE_DEVICE | HAL_SPACE_NOCACHE` で Attr1 のまま。
- Normal NC は store が write buffer に溜まりうる。GPU の job の開始の前に kernel が `kern_io_write_barrier()`（`dmb oshst`）を打つ（`v3d-hardware.c`）。同じ CPU の EL0 の store も program order で順序付けられる。arm64 は今 1 CPU（WS208 の SMP は未統合）。SMP では、user の store と別の CPU の kernel の doorbell の間の順序を WS208 側で確かめる要がある（残課題）。
- amd64・i386・m68k・sparcv9 の HAL は変えていない（amd64 の libc.so の build で確かめ）。
