# BUG-288: Raspberry Pi 4 で reboot の後に戻らない・前の起動で書いた file が消える・root が read-only に見える

- 状態: unknown（実機で 2 回の不通と 1 回の file の消失、原因は未確定） / scheduled（q938 P2: 直しを実装、試験待ち）
- 発見: 2026-10-11 P3（ws141-p013）とユーザー。kernel を /boot0 に置いて `reboot` → ping 不通（2 回、電源の入れ直しで復帰）。1 回は /var/backups と /boot0 に置いた file が消えていた。ユーザー「ファイルシステムがreadonlyになってるみたい」「たぶんrootfsがcorruptしてるのでは」。`sync` → `umount /boot/boot0` → `reboot` の回は約 50 秒で戻り file も残った（1 回目の reboot は umount 無しでも戻った）。
- 2026-10-11 Q1 の確認: 焼き直した後の起動の kernel の log に `sdhci:` の error は無い、`/` と `/boot/boot0` は rw。

## 解析（2026-10-11 bug-analyzer、source だけ、未確認の推測を含む）

- 経路: reboot・halt・poweroff は同じ program → init の `shutdown_system()`（service の停止 → `sync()` → `/dev/system` の ioctl。失敗は 5 秒ごとに永久に再試行、message は console だけ）→ kernel の `system_shutdown_prepare()`（`mount_sync_all` → `net_shutdown_for_boot`（ここで ping が止まる、完了まで無限 loop）→ USB・PCI の shutdown）→ rpi4 の `hal_reset`（watchdog の full reset）。unmount はしない。UFS の clean の印は unmount の時だけ書くので、正常な reboot でも次の起動は unclean（j3 の replay と orphan scan で回復する設計）。FAT の dirty bit は扱わない。
- **halt と reboot の耐久性は同じ**（同じ prepare を通り、最後が WFI か reset かだけ）。Pi 4 の halt・poweroff は CPU を止めるだけで電源は切れない。
- 候補（順位）: (1) SD（`src/drivers/platform/rpi4/rpi4-sdhci.c`）の write の error・2 秒の時間切れの後に SDHCI の error recovery（CMD・DAT の software reset、CMD13）が無く、以後の書き込みが失敗し続ける → buffer が dirty のまま、UFS は無音で read-only（`ms->writable = 0`、log 無し）、shutdown の sync も失敗して init が再試行の loop に入る → 電源を切ると消える。ただし ping 不通と両立しにくい。(2) sync の成功の後の net・USB・PCI の shutdown の無限 loop で止まる（data は disk にある）。/boot0 の bind を外した回だけ戻ったことから、`fat_sync_mount` が Pi の /boot0 で失敗・停止する可能性。(3) sync の後に service でない process が書いた物が消える。
- 直す案: SD の error recovery と時間切れの延長、UFS が read-only になる時の kern log、shutdown の各段の失敗の kern log と net・USB の loop の上限、init の再試行の上限（強制の扱いはユーザーの判断）。
- 試験の案: QEMU raspi4b の SDHCI で write の EIO の注入の後の回復と reboot、実機で reboot 10 回と cksum。

## 当面の安全な止め方

`dmesg | grep -i sdhci` に error が無いことを見る → 置いた file を cmp・cksum で読み直す → `sync` を 2 回 → `umount /boot/boot0` → `reboot`。戻らない時は電源を切る前に画面の console に `init: final system action failed` が出ていないかを見る。

## 直し（2026-10-11 q938 P2、base main 384908e71、commit 26b85eb57・3c53fd059、未試験）

source を読んだ見立て: networkd の停止（`retire_managed_policy` が interface を down）で ping はどの reboot でも sync より前に止まる。よって「ping 不通＋file の消失」は、止まった所が networkd の停止の後・sync（`mount_sync_all`）の完了の前と読むのが一番合う。SD の driver は error の後に CMD/DAT の reset が無く、DAT inhibit が残ると以後の全 command が 2 秒の時間切れ×block 数で進まず、sync が実質止まる（候補 1）。init の `stop_service` も SIGKILL の後の `waitpid` が無期限だった。FAT の /boot0 は private の mount の bind で、`mount_sync_target` が private の source を sync するので sync から漏れてはいない（`fat_sync_mount` に止まる所も見えない）。

- `src/drivers/platform/rpi4/rpi4-sdhci.c`: block ごとに最大 3 回、失敗の間に recovery（CMD・DAT の software reset、CMD13 で card が tran かつ READY_FOR_DATA になるまで最大 10 秒、data・rcv なら CMD12 を最大 3 回、prg は待つ）。recovery が駄目なら controller と card を初期化し直し、それも駄目なら `failed` にして以後の I/O を即 EIO（無限に時間切れを待たない）。write の完了（transfer complete＝card の busy の解放）の待ちを 2 秒から 10 秒に。失敗の log は消す前の interrupt status と present state を出す（前は clear 後の status を出していた）。TIMEOUT_CONTROL は 0x0e（最大）のまま。
- `src/drivers/fs/ufs.c`: read-only になる 41 か所を `stop_writing(mount, 理由, errno)` に集め、mount ごとに最初の遷移を `ufs: <disk>: the volume refuses writes until it is mounted again: <理由> (error N)` で kern log に出す（revoked の unmount の 1 か所は error でないので除く）。
- `src/kern/mount.c`: `mount_sync_all` で失敗した mount を path・型・errno で log。
- `src/kern/shutdown.c`: 各段の失敗を log、`the volumes are synced; stopping the network`・`the devices are quiet` の進みの log。`src/kern/net/core.c` の `net_shutdown_for_boot` の 2 つの barrier の再試行に合わせて 10 秒の上限（int を返す、`include/kern/net.h`）。上限を超えたら USB・PCI の teardown を飛ばして reset へ（producer が USB・PCI の memory に残りうるので。data は sync 済み）。`drv_usb_shutdown` の中の class driver の停止そのものは上限なし（残り）。
- `src/drivers/generic/system-device.c`: halt・power-off・reboot の prepare の失敗を log。
- `userland/base/init/main.c`: service の停止は SIGTERM → 5 秒 → SIGKILL → 5 秒で、それでも終わらなければ log して先へ（前は SIGKILL 後の waitpid が無期限）。service でない process（login の shell など）を `KERN_SYSTEM_GET_PROCESS` で列挙して SIGTERM → 5 秒 → SIGKILL → 5 秒（`kill(-1)` は init 自身に届くので使わない）、その後 sync。最終の動作の再試行は 5 秒ごと 12 回の後に警告を出し、以後 60 秒ごと（毎回 sync し直す）。**reset・halt の強制はしない**（ユーザーの判断、案は Q1 へ）。

確かめ: rpi4 の vmunix（`config/ci/config-rpi4.mk`、`build/bug288-rpi4/vmunix`）・amd64 の vmunix（`config/ci/config-amd64.mk`）・init（amd64・arm64）の build、rc 0・warning 0。host 試験は無し（変えた所は hardware と kernel の中で、短い host 試験を作れない）。QEMU raspi4b での error の注入と reboot、実機の reboot の繰り返しは未実施（T1・Q1 へ依頼）。

## 2026-10-11 ユーザー「全部承認です。」（Q1 が示した推しを全て承認）

init の最終動作が上限を超えても通らない時は **案 A: 強制しない**（警告を出し 60 秒ごとに sync して再試行）。
