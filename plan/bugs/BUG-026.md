# BUG-026: リンカの出力が通常ファイルへは全ゼロで届く

Bug ID: `BUG-026`
Reproduction: reproduced
Disposition: resolved（ws073-p018、2026-09-27、kernel の原因を修正。QEMU で確認、実機は未実施。toolchain の workaround は残っている）
Date: 2026-09-22
Source: WS032 p008（ターゲット上の clang の受け入れ）で観測。agent による再現・切り分け実施済み、原因未特定。
Owner: none（未割当）
Queue: none。workaround は現行のツールチェーンに入っているが、原因は未解明のまま残る。

## 期待と観測・影響

ターゲット上で `clang hello.c -o hello` が、**正しいサイズで中身が全部ゼロ**の実行ファイルを作る。できたファイルは exec には成功するが main に到達せず、何も出力せずに終了コード 1 になる。診断メッセージは一切出ない。

10104 バイトの全ゼロは `cksum` で `2187828017 10104` であり、ホストで `head -c 10104 /dev/zero | cksum` と一致することで確認した。

ld.lld はこのバージョンでは既定で出力をマップせず（`mmap_output_file` の既定値が false）、無名マッピングに像を組み立てて最後に書き出す `FileOutputBuffer` の `InMemoryBuffer` 経路を通る。その経路だけが失われる。

## 切り分け（実施済み）

- **バッファの中身は正しい。** 同じ `--no-mmap-output-file` で `-o -` にすると、lld は `commit()` を通らず同じバッファを標準出力へ流す。得られたのは正常な ELF（DYN、entry 0x1000、program header 9、section 17）。失われるのは書き出しだけである。
- **宛先の種別で結果が変わる。** 同じ `commit()` でも、FIFO 宛ては非ゼロの内容が届き、通常ファイル宛ては全ゼロになる。
- **ファイルシステムには依存しない。** tmpfs（`/tmp`）と UFS オーバーレイ（`/root`）で同じ。
- **読み込み側は正常。** ターゲットの `llvm-readelf` は `/lib/libc.so`、`/usr/lib/crt1.o`、clang が生成した `.o` をいずれも正しく解釈する。
- **リンク行の問題ではない。** ホスト側で、ドライバ既定のリンク行とリポジトリ既知良好のリンク行（`-nostdlib ... -l:libc.so`）が生成する実行ファイルはバイト単位で一致する。
- **スレッドではない。** `--threads=1` でも全ゼロになる。
- **同じシステムコールの並びでは再現しない。** 無名 mmap を埋めて 1 回の 10104 バイト `write()`、および 4096 バイト分割の両方を同じディレクトリへ書く C プログラムは正しい内容を書く。256 MiB を別々のマッピングで確保して全ページ touch した後でも、4 スレッドを走らせながらでも再現しない。

## workaround

ZedBSD ツールチェーンのリンカ定義が `--mmap-output-file` を渡し、出力ファイルのマッピングに直接像を組み立てる経路を選ぶ。
`userland/packages/lang/clang/patches/0003-write-the-linked-image-through-the-output-file.patch`。
これで `clang hello.c -o hello` は動作し、受け入れテストは通る。

## 次の条件

原因は未特定であり、workaround を修正と呼ばない。通常ファイル宛てと FIFO 宛てで結果が分かれる点が最も鋭い手がかりで、ここから先はデバッガでリンカのプロセスを追うのが筋である。ptrace と lldb が入ったら、`InMemoryBuffer::commit()` の `write()` 直前でバッファの内容と渡しているポインタを直接観測して再開する。

**2026-09-23 追記**: その前提は整った。WS032 で lldb / lldb-server が実機に入り、ブレークポイント・ウォッチポイント・メモリ表示が動く（`plan/ws032/tests/lldb-target.sh`）。再開時は `ld.lld` を `--no-mmap-output-file` で走らせ、上記の位置で止めて観測する。ただしこのとき、LLVM 由来のプログラムは起動に 10〜30 秒かかる（[BUG-027](BUG-027.md)）。
[bug-board](../known-bugs.md)に索引を保持。

## 再調査（2026-09-27、WS073。QEMU、amd64、main の測定用 image に WS073 の vmunix）

症状が変わっている: `clang /tmp/h.c -o /tmp/h2 -Wl,--no-mmap-output-file` の出力は **`cksum`・`cmp`・`od` では正しい ELF**
（既定の `--mmap-output-file` の出力 h1 と byte 単位で同じ、10104 byte）だが、**exec が `Executable format error`（ENOEXEC）** になる
（sh は script として走らせようとする）。h1 は exec できる（終了 7）。

- `stat`: h1 は `Blocks: 24`、h2 は `Blocks: 0`。`sync` と 5 秒の後も 0。tmpfs（`/tmp`）と UFS（`/root`、`Blocks: 0`・ENOEXEC）で同じ。
- read（`cmp`）と共有の mapping（`plan/ws073/tests/map-compare.c`: `pread` と `mmap(MAP_SHARED)` の比較）は h2 でも同じ正しい中身を返す。
- 同じ中身を `cp`・`cat >`・`dd conv=notrunc`（`write`）で作った file は block を持ち exec できる。
- 無名の mapping から 1 回の `write` をして `munmap`・`_exit` する probe（`plan/ws073/tests/write-unmap.c`）は再現しない（block を持つ）。

見込み: lld の `--no-mmap-output-file` の書き方（どの system call かは未確認）が、file の中身を page cache（vm object）にだけ置き、
filesystem の block を割り当てない（`sync` でも書かれない）。read と mmap は page cache を見るので正しく、exec の ELF の読み込みは
filesystem から直接読むので 0（以前の kernel では read も 0 を見ていた）。電源断・再起動で中身が失われる恐れがある（未確認）。
次の手: guest の lldb で ld.lld の `InMemoryBuffer::commit()` から出る system call（`write`・`pwrite`・`ftruncate`・`fallocate` など）を
特定し、その経路の file の write-back を調べる。workaround（`--mmap-output-file`）は有効のまま。

## 原因と修正（2026-09-27、[ws073-p018](../ws073/phase018/phase.md)）

ld.lld は `--no-mmap-output-file` でも一時 file を `ftruncate`・`mmap(MAP_SHARED)` して像を書き、`munmap`・`rename` する（lldb で確認）。
kernel は共有の file の mapping を `munmap` と exit で外すとき hardware の dirty bit を見ず、object page が dirty にならないので中身が
filesystem へ書き戻されなかった（read・mmap は cache を見て正しく、exec は filesystem を読んで 0、`Blocks: 0`、再起動で消える）。
`src/kern/vmspace.c` の `object_mapping_note_dirty()` が、書ける共有の mapping の object page を外す前に dirty にする（commit 4ed71e36・31ffb324）。
確認: `plan/ws073/tests/map-write.c` の 4 つの mode を tmpfs・UFS で 8/8 exec でき block を持つ、`clang -Wl,--no-mmap-output-file` の出力が
tmpfs・UFS で動く、fork・vfork・posix_spawn の回帰 ALL OK、boot test PASS。
残り: clang の package の workaround（`--mmap-output-file`・patch 0003）を外すかは package の判断（main へ）。

workaround の扱い（2026-09-27、main の判断）: kernel の修正で `--mmap-output-file` の workaround（clang の package の patch 0003）は不要になった
（`-Wl,--no-mmap-output-file` の出力が tmpfs・UFS で動く）が、当面は残す。外す条件: 修正の入った kernel で package の clang の受け入れ
（WS032）を `--mmap-output-file` 無しで通すこと。
