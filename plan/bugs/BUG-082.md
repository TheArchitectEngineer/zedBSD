# BUG-082: sync と process の終了の競合で kernel panic（invalid shared VM reverse mapping）

Bug ID: `BUG-082`
Reproduction: reproduced（WS073 の agent、full guest image、QEMU）
Disposition: resolved（2026-09-28、ws073-p020 の 2 回目の試行。QEMU で 300/300、実機は未実施）
Date: 2026-09-28
Source: WS073（BUG-075 の試験中）
Owner: WS073

## 観測

full guest image の UFS root で、通常の dd・cat と `sync` を process の終了と競わせると
`fatal: src/kern/vmspace.c:742: invalid shared VM reverse mapping` で止まる。gdbstub の stack:
mount_sync_all → vm_object_sync_mount_buffer → sync_inode_buffer → vm_object_sync_range_buffer → vmspace_object_page_revoke。

## 原因（WS073 の解析）

sync は mount の object の map された page を全て revoke する。vmspace_destroy() は refcount が 0 になった後に region ごとに
mapping を外し、region の間で metadata の lock を離す。その間に revoke が vm_tryref に失敗する mapping を見つけて HAL_FATAL する。
BUG-075 の変更より前からある。

## 修正の方針

revoke は HAL_FATAL の代わりに lock を離して yield し、終わりかけの space が mapping を外すのを待って再試行する（vmspace.c）。
WS073 で検証中。

## 経過（2026-09-28、ws073-p020、wrap up）

- 再現: [sync-exit.sh](../ws073/tests/sync-exit.sh)（[bug082.sh](../ws073/tests/bug082.sh)）。修正前は 1 回目で上の fatal。
- 同じ競合の 2 つ目: copy-on-write の fault が予約（BUSY）した mapping を revoke が見て `vmspace.c:768 shared VM reverse mapping changed while pinned`。
  fault は writeback が持つ page を待つので、revoke が単に待つと相互に待つ。
- patch（未 commit、`BUG-082-wip.patch`）: 終わりかけの space を yield で待つ、BUSY の mapping を fault の wait queue で待つ、fault は page が
  writeback 中なら予約を返して pin で待つ、revoke の最後の vmspace の参照を reaper へ。fatal は消えたが 30 回中 27 回の後に sync と cat の hang。
- 次の手: phase020 の再開の手順（hang の thread の stack を gdbstub で読む）。

## 解決（2026-09-28、ws073-p020 の 2 回目の試行）

wip.patch の hang は 2 つの別の不具合だった（gdbstub で hang した thread の stack と VM の object を読んで特定、[phase](../ws073/phase020/phase.md)）。

1. **sync と読みの fill の待ち合い**: 読みの cache の miss（`object_cache_read_missing`）と fault の fill は page を BUSY（WRITEBACK なし）で公開してから
   backend を読むために `i_io_lock` を取る。sync（`vm_object_sync_range_buffer`）は `i_io_lock` を持ったまま BUSY の page を待っていた。
   修正: i_io_lock を持つ sync は fill の途中の page（BUSY で WRITEBACK なし。clean で mapping も無い）を待たずに飛ばす（`src/kern/vm.c`）。
2. **fork が他の thread の frame を子に写す**: amd64 の HAL の `running_task` の macro が per-CPU の 2 回の load で、preempt されて CPU を移ると前の
   CPU の task を読む。`hal_task_fork_current()` が他の thread の page fault の frame を子に写し、子は fault を繰り返した。修正: task.c の読みを
   `hal_task_get_current()` の 1 回の GS 相対の load に（`src/hal/amd64/task.c`、HAL の実装、hal.h は不変）。

wip.patch の中身（revoke は終わりかけの space と COW の fault の予約を待つ、COW の fault は writeback の page を予約を返して待つ、revoke の最後の
vmspace の参照を reaper へ）は source に入れ、patch の file は削除した。

検証（QEMU、KVM、4 vCPU。実機は未実施）: [bug082.sh](../ws073/tests/bug082.sh) 300/300 PASS（fatal・hang なし）、最後の kernel で
[bug075.sh](../ws073/tests/bug075.sh) 14/14 PASS、boot test PASS。

別の bug の候補（ID は main に依頼）: block された SIGSEGV を fault が生むと、kernel は pending にして同じ命令へ戻り、process は fault を永久に
繰り返す（2 つ目の hang の症状）。`AMD64_CURRENT_SPACE`（space.c）も 2 回の load で、使う所の preempt の可否は未確認。
