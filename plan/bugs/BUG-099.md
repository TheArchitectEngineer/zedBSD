## 観測

main の checkout（4e850cdd）の pen の image（`build/main-pen`、QEMU Venus、1280x800）で `plan/ws081/tests/p012-guest.sh build/main-pen build/main-ws081-p012b`
を流すと、段 3（page mode の左への flick）の `replay swipe.script` が「touchinject swipe.script: FAILED」になった。`replay` は guest で
`/bin/touchinject /tmp/swipe.script; echo replay=$?` を走らせ、SSH の出力に `replay=0` の行が無いと失敗にする。
同じ段の効果の検査（the finger swiped・the swipe turned forward・page 2 is shown）は全部 ok で、swipe は届いていた。
touchinject が非 0 で終わったのか、SSH の出力が失われたのか（`guest.py run` の timeout 等）は分からない。log: `build/main-ws081-p012b.log`。

## 調べたこと

- 同じ guest を起こし直し、同じ `swipe.script` を単独で 2 回: どちらも `replay=0`。
- 試験の全体をもう 1 回（`build/main-ws081-p012c.log`）: PASS。
- 未調査: touchinject の終わりの経路（`hold` の後の close、注入の device の teardown）の誤りの返し方、`guest.py run` の timeout と SSH の出力。

## 次の手

touchinject の各 exit の経路で理由を stderr に出す（どの段で非 0 か分かるように）、`replay` が `replay=` の行の無いときに SSH の rc と出力を残す。
再び出たらその出力で原因を決める。

## 診断の追加（ws081-p013、2026-09-29、WS081 の作業用サブエージェント）

再び出たときに原因を決められるように、次を入れた（再現はまだしていない。状態は unreproduced / tracking のまま）。

- `userland/base/tests/touchinject/main.c`
  - replay は、終わりに成功なら `touchinject: done lines=N` を stderr に出す。SSH の出力が失われたのか、touchinject が失敗したのかを区別するためである。
  - 途中で止まった時は、行の番号と理由を出す（`line N: bad command: …`、`the injector refused a write`、`the injector refused the frame`、`stopped at line N`）。
  - その他に理由を出す経路: script の読みの失敗、既定の screen の宣言の失敗、`close` の失敗（`perror`、非 0 で終わる）。
  - `-c`・`-s`・`-d`・`-t` が非 0 で終わる時も、どれが失敗したかを出す。
  - 確認（QEMU の guest）: 良い台本は `done lines=3`・rc 0。悪い台本は行 2 の理由と `stopped at line 2`・rc 1。`-c` 14/14、`-s` 15/15。
- `plan/ws081/tests/p012-guest.sh` の `replay` と、`p013-guest.sh` の `touches`・`pen`
  - 共通の `inject` を通す。guest では `/bin/touchinject SCRIPT 2>&1; echo replay=$?` を走らせる。
  - `replay=0` の行が無ければ、SSH の終了状態と出力の全部を `OUTDIR/SCRIPT.failed.log` に残し、末尾 5 行を試験の出力に出す。
  - 両方の試験は、build の touchinject を guest に置いてから走る。

次の手は変わらない: 再び出たら `SCRIPT.failed.log` の出力（touchinject の終わりの行の有無、SSH の状態）で、touchinject の失敗か出力の喪失かを決める。
