# BUG-302: emacs（REmacs）で SKK を起こすと辞書が見つからない

- 状態: unknown / scheduled（2026-10-14 Q1 登録、bug-analyzer へ）
- 発見: ユーザーの UAT（2026-10-14）「emacsコマンドでSKKを起動したとき、辞書がみつからなかったです。」
- 期待: `/bin/emacs` で SKK を on にすると、同梱の辞書（`/usr/share/remacs/skkjisyo.dic`、`userland/base/emacs/Makefile` が image に入れる）で変換できる。
- 観察: 辞書が見つからない（文言・環境（image の config・端末）は未確認）。
- 手がかり（Q1、source を読んだだけ）: `editor/skk.noct` の skkInit は `REMACS_SKK_DICT` → `/usr/share/remacs/skkjisyo.dic` → `dict/SKK-JISYO.remacs`（相対）の順。主の辞書は `~/SKK-JISYO.L`。辞書の file は emacs が `ZEDBSD_USER_PROGRAMS` にある時だけ image に入る。`config/current-uat.mk` に emacs は無い。
- 関連: WS129（emacs の取り込み、ベータ2）。

## 解析（bug-analyzer、2026-10-14）

修正は実装していない。main の checkout を読み、host の Noct（`build/NoctLang/build-static/noct`）で辞書の探索の関数を模した script を 1 回走らせただけ（script は scratchpad、tree には何も残していない）。QEMU・実機は未実施。

### 確かめたこと（事実）

- 辞書は image に入っている。`build/uat/arch-images/amd64-native-root-1024m.ufs` を `tools/build/check-ufs-image.py` の reader で読むと `/usr/share/remacs/skkjisyo.dic` は inode 1057、mode 0100664、root:root、86352 byte、md5 `0f6ae0f0…` で `userland/base/emacs/dict/SKK-JISYO.remacs` と同じ byte。`/usr/share/remacs` は 0755。`/bin/emacs` 0755、`/usr/bin/noct -> /bin/noct`。`build/uat/.rootfs-config` の files にも `--file /usr/share/remacs/skkjisyo.dic=…` がある（`config/current-uat.mk` は `config/release/config-amd64-beta2.mk` を include し、その 17 行目が emacs を `ZEDBSD_USER_PROGRAMS` に足す。ticket の「current-uat.mk に emacs は無い」は include 先に在るので誤り）。
- 探し方（`userland/base/emacs/editor/skk.noct`）: skkInit (31-39) は `REMACS_SKK_DICT` が空なら `/usr/share/remacs/skkjisyo.dic`、それも無ければ相対 `dict/SKK-JISYO.remacs`。skkLoadDicts (303-315) は `~/SKK-JISYO.L`（EUC-JP、readTextEucJp）→ bundled（readText）→ 無ければ `SkkDict = ""`。**どの file も無い時に何も言わない**（message は無く、変換は候補 0 → 「よみ (登録): 」の minibuffer に落ちる。745-746）。kernel は init の環境に `REMACS_SKK_DICT=/usr/share/remacs/skkjisyo.dic` を入れる（`src/kern/exec.c:1006`）が、`login`（`userland/base/login/main.c:129-137`）は環境を作り直すので session では空。どちらでも同じ path になる。
- Noct の API（`userland/base/noct/noct/src/api/api-file.c`）: checkFileExists (3081-3113) は `fopen(path,"rb")` の成否、readText (3653-3738) は fopen/fseek(END)/ftell/fread。zedBSD の libc（`userland/base/libc/posix.c` fopen 6040、fseek 6629、ftell 6700、fread 6350）と kernel の lseek（`src/kern/file.c:2265-2270`、whence 2 = i_size）を読んだ限り、この経路が target で失敗する理由は見つからない。`System.getEnv` は未設定で `""` を返す（api-system.c:506-510）ので skkInit の分岐は意図どおり。zedBSD の noct は `NOCT_TARGET_POSIX`（c89compat.h:28-33）。
- 辞書の書式と検索: `skkLookupIn` (346-384) は `"\n" + よみ + " /"` を String.indexOf で探す。host の Noct で同じ logic を `SKK-JISYO.remacs` に当てると かんじ→感じ(3)、かくにん→確認、にほんご→日本語、われr→割、かk→書(2)、きょう→今日(3) が引ける。書式（`;;` の見出し、UTF-8、`よみ /候補/`）と読み込みの食い違いは無い。EUC-JP は `~/SKK-JISYO.L` の時だけ readTextEucJp で読み、bundled は UTF-8 のまま。
- 辞書の大きさ: `SKK-JISYO.remacs` は okuri-nasi 3279 見出し（`SKK-JISYO.X` は 14116）。にほん・こんにちは・ありがとう・おはよう・てすと・ひらがな・かたかな・ほんじつ は **両方に無い**。IME は X と remacs の両方を `/usr/share/keiland/ime/skk/` に入れる（`userland/desktop/ime/main.c:40-41`）が、emacs は compact の remacs だけを使う。

### 原因の候補（確度つき）

1. **[高、推定 6 割] 末尾の「n」が SPC で捨てられ、ん で終わる語が引けない。** `skk.noct:433-435`: 読みの状態で SPC は `skkClearPending()` → `skkStartConversion()`。`skkClearPending` (239-245) は **buffer に見えている pending の romaji を消すだけ**で、ん に変換しない（`Skk.pending` も残る）。`skkStartConversion` (636-640) は buffer の文字列を読みにするので、`Henkan` SPC は「へんか」、`Nihon` SPC は「にほ」、`Kantan` SPC は「かんた」で検索し、候補 0 → 「へんか (登録): 」の prompt。romaji の表は `nn ん` (129) で、単独の `n` は `na/ni/…/nn` の prefix なので pending に留まる（`skkFeedRomaji` 261-290）。DDSKK は SPC の前の単独 n を ん にする。既存の試験は `Kakuninn` と nn を打つ（`tests/term/case_skk_bundled.py:21`）か母音で終わる語だけで、この経路を通らない。IME を試す人が最初に打つ「へんかん」「にほんご」のうち、へんかん・にほん・かんたん は全て ん 終わりなので、「辞書が見つからない」と見える。C-j（437-440）と q（442-449）も同じく pending を捨てる。
2. **[中、推定 2〜3 割] compact の辞書に語が無い＋辞書が無い時と語が無い時の区別が無い。** 上の表のとおり挨拶や てすと・ひらがな は無い。候補 0 の時は常に (登録) の prompt で、「辞書を読めていない」のか「見出しが無い」のかを利用者は区別できない。
3. **[低、1 割] target だけで file が開けない・読めない。** tree を読んだ限り根拠は無い（image に在る、mode 0664、libc・kernel の経路は正しそう）。実機で `ls -l /usr/share/remacs/skkjisyo.dic` と `emacs` → `C-x C-j` → `Kanji` SPC が ▼漢字 になるかを見れば即座に切り分けられる（漢字 は かんじ で ん が語中なので候補 1 の経路を通らず、compact にも在る）。readText が失敗すると Noct の error（"Cannot open file …" など）が echo area に出る（`boot.noct:172-176`）ので、黙って候補 0 にはならない。
4. **[低] UAT の stick の image がこの build（build/uat、2026-10-11）と違う。** 未確認。辞書の install は 2026-10-04（a8ab492c3）からあるので、emacs が入る image には必ず入る。

### 直し方の案（実装していない）

- 候補 1: `skk.noct` に「pending を確定する」関数を足し、SPC・C-j・q・送り仮名の開始（大文字）の前に呼ぶ。`Skk.pending == "n"` なら見えている n を消して `skkEmit("ん")`、それ以外は今の `skkClearPending` に加えて `Skk.pending = ""` にする（今は残った pending が次の入力に混ざる）。isearch の `skkComposeChar` (170-199) は別 state なので対象外。
- 候補 2: (a) `skkLoadDicts` で辞書を一つも読めなかった時に flag を立て、`skkStartConversion`/`skkOkuriConvert` で (登録) の前に `ed.echoMessage = "SKK: no dictionary (~/SKK-JISYO.L, /usr/share/remacs/skkjisyo.dic)"` のように一度知らせる。(b) `userland/base/emacs/Makefile:44-52` で `dict/SKK-JISYO.X`（tree に在り、license は同じ Zlib、387 KB）も `/usr/share/remacs/` に入れ、`skkLoadDicts` で compact の後に X も読む（または X を skkjisyo.dic にする）。indexOf の線形探索は 387 KB でも実用の範囲。挨拶などの語は辞書に足す。
- 候補 3 が実機で出たら別 ticket（libc/kernel）。
