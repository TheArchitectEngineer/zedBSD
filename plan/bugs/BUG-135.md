# BUG-135: stat() が数秒かかることがある（UFS、guest）

Reproduction: reproduced（P2 / q591 の診断 build、QEMU）
Disposition: resolved（ws073-p051、2026-10-04、QEMU。実機は未実施）
Discovery: ws099-p020 / q591（BUG-125 の原因調査）
Owner: 未配属

## 観測

compositor の event loop の `zwl_preferences_tick` が `stat(~/.config/keiland/desktop.conf)` を呼び、1 回で 0.7〜6.5 秒止まっていた（loop の step ごとの時間の診断 build）。compositor 側は watcher thread へ移して回避した（P2 f1af6cc7f）。stat 自体が遅い原因（kernel の UFS・lock・I/O の待ち）は未調査。他の app の file 操作にも影響しうる。

## 再調査の契機

ネットワーク・desktop の作業で同じ遅さが見えたとき、または kernel/UFS の Phase を選ぶとき。gdbstub で stat の待ちの場所を取る。

2026-10-02 ws099-p020: QEMU の guest で sshd が 5 秒以上応答しない stall（ssh の Connection timed out during banner exchange）が、直す前と直した後のどちらの compositor でも出た。p076 の 20 回のうち 9 回で retry が起きた。sshd-session の fork・exec と login が UFS を読むので、stat の遅さと同じ根の可能性があるが、未証明（evidence: plan/ws099/phase020/evidence/sshcmp/）。

2026-10-03 / ws073-p045（q624-i01、P1）: 再現と原因の特定。host の disk の負荷（flush が秒単位）の下で、cache に載った file の stat が 1〜5.8 秒
止まる（guest 全体の停止ではない）。gdbstub で、stat は `ufs_lookup` が volume 全体の `namespace_lock` を待ち、その持ち主の journal の周期の
commit（`j3_hook`）か名前の変更が、device の cache の flush（`bio_flush`）を lock を持ったまま待っていた。直し（`src/drivers/fs/ufs.c`）: 検索と
commit が namespace を共有し変更だけが排他、fsync の最後の flush を mount の lock の外へ。直す前 10 回 → 直した後 2 回（4 回ずつ）。詳細と残りは
[ws073-p045](../ws073/phase045/phase.md)。sshd の stall は guest の kernel の待ちではなかった（host の負荷の間、guest の thread は全て idle）。

2026-10-03 user（優先度と依存）: 優先。WS131 の libkeiland の整理と desktop の設定の libkeiland 経由の再実装（WS131 p005・p006）の後に再び取り組む（stat と関連）。

2026-10-04 / ws073-p051（q653-i01、P9）: 残る鎖は「名前の変更が `namespace_lock` を持ったまま `ms->lock` を待ち、`ms->lock` は fsync か
flusher の commit（`j3_commit_locked`）が持ったまま descriptor と commit record の 2 回の `disk_sync`（flush）を待つ」。直し: journal の
commit を閉じる段（lock の中、memory の複写）と書いて flush する段（lock の外）に分け、pin を transaction の sequence の tag に

100 ms 超 1 回。crash-test.sh（4 9）・root-crash.sh（6）は直した kernel で PASS（UFS OK）。T1・T2 の試験・実機は未実施（user の指示で
除外）。詳細は [ws073-p051](../ws073/phase051/phase.md)。
