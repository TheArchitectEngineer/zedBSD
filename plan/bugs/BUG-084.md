# BUG-084: header を動かした後の最初の image の build で、rootfs の複写が再生成中の sysroot を読んで失敗する

Bug ID: `BUG-084`
Reproduction: reproduced（main の host の build で 3 回、WS073 の worktree で `plan/ws073/tests/bug084.sh`）
Disposition: resolved（2026-09-28、ws073-p021）
Date: 2026-09-28
Source: main の検証（WS078 の改名、ws074-p019 の merge の後）
Owner: WS073

## 観測

`include/libc` の header を改名・移動した直後の `plan/ws035/tests/build-zdesktop-image.sh build/ws035-sq` が
`cp: cannot stat '.../build/amd64/sysroot/usr/include/zdesktop.h'`（WS078 の改名の後）・`.../compat/png.h`（p019 の merge の後）で
`build/ws035-sq/rootfs/.stamp`（platform/amd64/vmunix.mk の rootfs の rule、`ZEDBSD_ROOTFS_INSTALL_DEVELOPMENT` の `cp -R`）が失敗した。
同じ build でその前に sysroot の再生成と package（clang 等）の再 build が走っていた。もう一度走らせると成功する。

## 推定（未確認、2026-09-28 の main の記録）

rootfs の rule は `$(ZEDBSD_TARGET_SYSROOT)/.zedbsd-sysroot-complete` にしか依らず、並列の build で sysroot の header の置き換え
（古い file の削除）と rootfs の `cp -R` が重なる。

## 原因（2026-09-28、ws073-p021）

順序の問題ではなかった。rootfs の rule は sysroot を正しく待つ（`.zedbsd-sysroot-complete` と clang の package を通して）。失敗したのは
`cp -R` ではなく、その前の `--file` の複写（`cp -f`）である。

clang の package（`userland/packages/lang/clang/Makefile`）は、image の `/usr/include` に入れる C library の header の一覧を
`$(shell find $(ZEDBSD_EXTERNAL_SYSROOT)/usr/include -name '*.h')` で作り、`ZEDBSD_PACKAGE_FILES` の `--file /usr/include/X=<sysroot>/usr/include/X`
にしていた。rootfs の rule の recipe は `$(eval)` で作られるので、この一覧は make が Makefile を読む時に、**古い sysroot**から作られる。
header を改名した最初の build では、同じ make の中で sysroot の rule が sysroot を作り直して古い名前の file を消し、その後で rootfs の rule が
古い名前を `cp -f` して `cannot stat` で止まる。次の make は新しい sysroot から一覧を作るので成功する。

## 修正（ws073-p021）

- `toolchain/llvm/sysroot.mk`: `ZEDBSD_SYSROOT_INCLUDE_NAMES` — sysroot の header の manifest（`ZEDBSD_SYSROOT_PUBLIC_HEADERS`、source の
  `include/libc`・`include/uapi`）を sysroot の `usr/include` の中の名前に写したもの（sysroot の rule の header の loop と同じ写し方）。
- clang の Makefile: header の一覧を disk の sysroot ではなくこの名前から作る（`.h` だけ、従来どおり）。sysroot の rule はこの manifest から作るので、
  一覧は同じ make で作り直された後の sysroot と一致する。

## 検証（host、WS073 の worktree）

- [bug084.sh](../ws073/tests/bug084.sh)（guest の構成の rootfs を作る → `include/libc/fmtmsg.h` を `fmtmsg-renamed.h` に改名（`#include` も）→
  `-j32` で rootfs を作り直す → 戻す。package の build は対象外なので staged の package は `make -o` で古いまま使う）:
  - 修正前の Makefile: 2 回目の build が `cp: cannot stat '.../build/amd64/sysroot/usr/include/fmtmsg.h'`（`platform/amd64/vmunix.mk:1466`
    の `rootfs/.stamp`）で失敗。main の症状と同じ。
  - 修正後: 1 回目（直前の試験が名前を戻した後の build、逆向きの改名）・2 回目とも成功、rootfs に `fmtmsg-renamed.h` があり `fmtmsg.h` は無い。PASS。
- 改名なしの tree で、修正前の一覧（sysroot の `find`）と修正後の一覧（`make -n` の `--file /usr/include/...`）は 227 件で同一。

## 残り（別の bug の候補）

同じ種類の parse 時の一覧がもう 1 つある: clang の `ZEDBSD_CLANG_RESOURCE_HEADERS = $(wildcard <clang の stage>/lib/clang/23/include/*.h)`。
新しい checkout の最初の build では stage がまだ無いので一覧は空で、その image には clang の resource の header（`stddef.h` 等）が入らない
（rootfs の設定の stamp が次の make で変わるので、2 回目の build で入る）。stage の中の file が消える改版でも同じ失敗になりうる。未修正、未再現。
