# BUG-307: UFS の fsync が 1 つの file でなく volume 全体を書き出す（数秒かかることがある）

- 状態: unknown / scheduled（2026-10-14 ユーザー「ベータ2 で直す」、P2）。**修正済み・T1 の試験待ち**（P2、2026-10-14、commit は下の「修正」）。
- 発見: WS217 の回転の遅さの解析（P3、2026-10-14、BUG-306 の T1-613）。`ufs_file_sync`（src/drivers/fs/ufs.c）は file で止まらず `ufs_sync(mount)` を呼び、volume の全部の遅延書き込みと journal を書いて disk の flush を求める。QEMU（cache=writeback）では host の fdatasync になり、32 ms〜7.5 s と揺れた。compositor の displays.conf の保存はこれで main thread が止まっていた（P3 が別の thread に移した、777da859b）。
- 影響（推測）: fsync を使う全ての program（editor の保存、vi の保存、passkey・account の file の書き込みなど）が、他の file の書き込みの量に比例して遅くなる。O_SYNC・O_DSYNC の write も write ごとに `file_fsync` を呼ぶので同じ。
- 関連: WS217 p004、UFS（WS054、WS060・WS063 の batched journal、ws073-p045・p051・p053）。

## 原因（source の読み、P2 2026-10-14）

batched journal（v3、`ufs_j3`）の volume で、1 回の fsync が volume 全体の遅延書き込みを 4 回書き出し、device を 3 回 flush していた。

1. `ufs_file_sync` → `inode_sync`（inode を running transaction に入れる）→ `ufs_sync(mount)`。
2. `ufs_sync` の commit（`ufs_sync_commit` → `j3_finish_commit` → `j3_commit_seal`）。seal は slot を durable にする時と commit record を durable にする時の 2 回、`j3_durable` = `disk_sync` = **`buf_sync`（volume の全部の dirty の line）＋ `bio_flush`** を行う。home が owed なら commit がさらに最大 2 回。
3. commit の後、`ufs_sync` がもう一度 `buf_sync`（全体）、`buf_write_unjournaled`（全体）、`disk_sync`（全体の `buf_sync` ＋ flush）。

`buf_sync` は dirty の line が無くなるまで回る（`dirty_reference` は device の list を新しい方から探す）ので、他の file を書き続ける program があるとその書き込みを追いかけ続ける。各 flush は QEMU では host の fdatasync で、その間に書かれた分も flush する。

## journal の順序の不変条件（壊さない物）

- 新しく確保した block の中身（`zero_new_block` の 0、`allocation_write_run` の data）は、その block を到達可能にする commit より先に device に届く（ufs.c の `zero_new_block` の注記「they reach the device before the commit that makes the block reachable」、`allocation_write_run` の「Keeps grouped allocation private until initialized data is durable」）。write cached の volume ではこれを **seal の最初の `j3_durable` の全体の `buf_sync`** が満たしている。これを外すと、crash の後に file が前の持ち主（消された file）の中身を見せる。よって seal の最初の書き出しは変えない。
- journal は volume で 1 つの running transaction で、file ごとの commit は無い。file の fsync は transaction 全体（他の file の metadata も）を commit する。
- slot の再使用: commit N の home は N の finish で書かれ、N+1 の seal の最初の flush で durable になり、その後で N+2 が同じ slot を使う。seal の 2 回目（commit record の後）の全体の `buf_sync` はこの不変条件に要らない（record が封じる物は 1 回目で durable）。

## 修正（P2、2026-10-14、commit f9f7acba9、branch agent/p2-ws215）

- `src/drivers/fs/ufs.c` `ufs_file_sync`: batched journal の volume では、(1) `inode_sync`、(2) **その file の block だけ**を cache から書く（`file_writeback_locked`: inode の lock の下で direct と indirect の block の map を歩き、隣り合う block を 1 つの run にまとめ、新しい `buf_writeback_cached` で書く。indirect block は metadata で journal が運ぶので書かない。directory は block が metadata なので歩かない）、(3) commit（`ufs_sync` から切り出した `ufs_sync_journal`: commit と owed の間の再 commit）、(4) `bio_flush` だけ（全体の `buf_sync` をしない。commit の finish が seal の後に書く held の中身のため）。batched journal でない volume（`nojournal`、v2 の tail journal、read-only）は今までどおり `ufs_sync`（write through の volume では書く物はほぼ無い）。
- `j3_commit_seal`: commit record の後の durable を「record の line だけを書いて `bio_flush`」に（全体の `buf_sync` をやめる）。全ての commit（flusher の 1 秒ごとの hook、場所の無い時の in-place の commit、sync）が volume 全体の書き出しを 2 回から 1 回にする。
- `src/kern/buf.c`・`include/kern/buf.h`: `buf_writeback_cached(disk, block, count)` を追加。cache が持つ line だけを書く（無い line を作らない。大きな file の fsync が memory を取らない）。journal が pin した line は line 全体を残し、範囲の中の普通の write の block（`b_unjournaled`）だけを cache の下で書く（BUG-163 と同じ。line の start が揃わない volume で file の data が metadata の pin に引き止められない）。device は flush しない。
- 結果: fsync 1 回の volume 全体の書き出しは 4 回→1 回（seal の最初、順序の不変条件のため）、flush は 3 回のまま（seal の 2 回は record と slot、最後の 1 回は held の中身）。後の 2 回の flush の前に書く物は record の 1 line と seal の後の home だけ。

### 名前（directory の entry）と rename の保存の流れ

- vi（`userland/base/vi/file.c`）: 一時の file に書いて fsync → rename → directory を fsync（914 行）。account（`userland/base/common/account.c`）: fsync → rename → directory の fsync（670 行）。compositor の displays.conf（`userland/desktop/wayland/heads.c` 1802 行）と settings-store（`userland/desktop/wayland/settings-store.c` 1045 行）: fsync → rename、directory の fsync は無い。
- 前と今の差は無い: journal の transaction は volume で 1 つなので、file の fsync は fsync の前の名前の変更（mkstemp の名前を含む）を一緒に commit する（前も今も）。fsync の後の rename はその fsync では durable にならない（前も今も）。flusher の hook の commit（約 1 秒、`BUF_FLUSH_INTERVAL`）か、次の fsync・sync か、directory の fsync で durable になる。directory の fsync は `ufs_file_sync`（directory の fops）で commit と flush をするので rename を含む。rename は 1 つの transaction で、crash の後は古い file か新しい file のどちらか（新しい file の中身は rename の前の fsync で durable）。

## 残り

- seal の最初の全体の `buf_sync` は残る。他の program が大きな file を書いている時、fsync は前の commit（約 1 秒前、`BUF_DIRTY_LIMIT` 32 MiB まで）からの他の file の中身も書く（新しい block の中身を commit より先に、の不変条件のため）。もっと減らすには、transaction ごとに中身の write の範囲を記録して seal ではその範囲だけを書く（または遅延の確保）が要る。`buf_sync` の追いかけ（書いている間に dirty になった line も書く）も残る。T1 の計測で fsync がまだ遅ければ、Q1 が別の Phase か Future Work にする。
- QEMU の kill は guest の crash を模すが host の電源断ではない（QEMU が受けた write は host の page cache に残る）。fsync が guest の cache から device へ data と commit を出すことは確かめられるが、device の flush の順序は確かめられない。
