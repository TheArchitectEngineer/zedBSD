# BUG-315: OLED（Wacom 056a:8191）の multi-touch で compositor の edge の gesture が不安定

- 状態: reproduced（実機、ユーザー）/ scheduled（2026-10-15 P2: Y の対応の quirk を touch.c に。T1 の較正と動作の確認待ち）
- 発見: 2026-10-15 ユーザー（BUG-313 の 2 回目の直しの後、T1-649）「マルチタッチにはなったのですが、操作がかなり怪しいです。画面端のスワイプでなくても仮想デスクトップ送りができていますし、上端からのスワイプダウンが認識されないですし、なんだか不安定です。」
- 環境: Pi 4、1280x720、13.3 インチの OLED の USB の touch panel（contact-count-maximum=10、10 slots）、BUG-313 の 2 回目の kernel（2f072ff41）。
- 症状: (1) 端からでない swipe で仮想 desktop が切り替わる。(2) 上端からの swipe down（Wiseview、BUG-270）が効かない。(3) 全体に不安定。
- 候補（未確認）: (a) `userland/desktop/wayland/touch.c` の群の規則（KWL_EDGE_GROUP_MS 以内の 2 本以上で、外側の 1 本が KWL_EDGE_GROUP_BAND の中なら残りはどこでも edge の swipe、BUG-267）が、この panel の 2 本指の操作で誤って当たる。(b) touch の座標の範囲（abs の max）と画面の 1280x720 の対応が合わず、端の判定がずれる（panel の native は 1024x600 の可能性）。(c) BUG-313 の event4（keyboard の collection の main device）が残っている影響。
- 次: T1 が abs の範囲・`fingers down at once`・compositor の log を集める（T1-649 の続き）。それから担当を決める。
- 関連: BUG-313、BUG-267、BUG-270、WS079、WS217。
- 2026-10-15 ユーザーの追試: 「1本指スワイプで仮想デスクトップ送りができてしまいました。」（画面の中ほどからの 1 本指の短い swipe）→ 群の規則（a）では説明できない。端の判定に使う座標がずれている（b）の見込みが強い: 中ほどの指が端の band の中と判定されている。
- 2026-10-15 ユーザー（中央と四隅を tap、T1 が event4・event5 を od で記録中）:「タッチは正常にクリックとして認識されていないことがわかりました。状態を持つスワイプに化けています。」→ 指を離したこと（release）が compositor に届いていない見込み（kernel の tip switch・contact count・slot の解放、または compositor の up の扱い）。座標の範囲は X 0..16383、Y 0..9599（16:10）、画面は 1280x720（16:9）。
- 2026-10-15 P2（BUG-313 の 3 回目と同じ round、kernel の release の経路の確認、host だけ）:
  - 8191 の touch の report（13、54 byte）は Finger が 10 個と Contact Count で、1 report に 10 本。hybrid にはならない（[BUG-313](BUG-313.md) の 3 回目の解読、fixture `plan/bugs/BUG-313/wacom-8191-if0.rdesc`）。
  - kernel の state machine（`src/drivers/generic/hid-touch.c`）に、この descriptor で次の 3 つの終わり方を host で通した。どれも slot に `ABS_MT_TRACKING_ID -1` を出し、最後の指で `BTN_TOUCH 0` を出す。
    - Contact Count 1 で Tip Switch 0。
    - Contact Count 0 の frame。
    - 2 本のうち 1 本が Tip 0（残りは触ったまま）、次に残りが Tip 0。
  - これは `plan/ws143/tests/hid-input-host-test.sh` の `check_8191_release` として固定した（PASS）。
  - kernel の原因は見つからず、直しは無い。
  - 残る kernel の側の可能性は 2 つ。どちらも T1 の event5 の生の記録で判定する。
    - (1) panel が離した時の report（Tip 0 か Contact Count 0）を出さずに黙る。Linux の hid-multitouch は Win8 の device にこれを見込んで、100 ms で指を離す（MT_QUIRK_STICKY_FINGERS）。zedBSD には無い。
    - (2) Contact Count が report の Finger の数（10）より大きい値で来る。frame が閉じず、次の count>0 の report は lift なしで書かれる。
  - 記録の見方は 2 つ。
    - event5 に `ABS_MT_TRACKING_ID -1`（type 3 code 57 value -1）と `BTN_TOUCH 0`（type 1 code 330 value 0）が tap ごとに出ていれば、kernel は離しを出しており、原因は compositor（`userland/desktop/wayland/touch.c`）の側。
    - 出ていなければ、生の report（`usbhid.dump=1` の `usb-hid-report:` の行）で (1)・(2) を P2 が見る。
- 2026-10-15 T1-649 の event5 の解読（T1、results-20261015-t1-649-650.md）: 各 tap は ABS_MT_TRACKING_ID -1・BTN_TOUCH 0・SYN で終わる（kernel の release は正しい）。tap は 0.07〜0.15 s、slot 0・1。X は左右の端で 0・16383。**Y は宣言の最大 9599 に対し約 6446 を超えない**（下端の tap が 5000〜6445）、上端は 1〜78。→ 原因は compositor の側（`userland/desktop/wayland/touch.c`）の見込み: 短い tap の扱い（状態を持つ swipe に化ける）と、Y の範囲（画面の下 1/3 に届かない）。
- 2026-10-15 P2（compositor の側の解析と直し、host だけ。QEMU・実機は未実施）:
  - 読んだ所: `userland/desktop/wayland/touch.c`（report の取り込み・tap・title・edge の群・release）、`edge.h`、
    shell.c の押しの鎖（desktops の swipe `desktop_press`/`desktop_release`、上端の band、Wiseview の閾値 84 px）、
    `cursor-box.c` の `geometry_scale`、libkeiland の `kl_motion_device_time`。
  - touch.c の tap と release の後の状態: 短い tap（80 ms、1 px の震え）、真ん中の 1 本指の短い swipe、端の tap の直後の真ん中の指、
    端の 2 本の後の真ん中の指を host で通した（下の試験）。どれも release の後に group・title・shell の押しが残らず、
    次の指は client のもの。**touch.c の tap・群・release の state machine に誤りは見つからなかった。**
  - 原因（確か）: **Y の座標の対応。** この panel は Y 0..9599 を宣言するが、絵の下端の指は約 6450 まで（T1-649 の下の段の tap は
    5848〜6446、9599 に近い値は 1 つも無い）。宣言の最大で写すと、絵の下端は 482 px（720 の 67%）に落ち、指は全部、本当の
    位置より 1/3 上に当たる。下の 1/3（App Home の下端の帯、下の方の button）には届かない。tap が狙った物でなく上の物
    （title bar など）に当たると、click でなく drag・swipe に化ける見込み。
  - 一般の規則で直せるかを確かめた:
    - 宣言のまま（Linux・libinput の既定）: 482 px で届かない。
    - 縦横比を合わせる（X の px/単位を Y にも使う）: 6446 × 1279/16383 = 503 px で、やはり届かない。
    - 縦横比を出力に合わせて Y の最大を決める（16383 × 9/16 = 9215）: 同じく届かない。
    - 見えた最大を学ぶ: 広げる方向は害が無いが、この panel は宣言より狭いので、縮める方向は指が下端に来る前に決められない（安全でない）。
    → descriptor の数（logical・physical・縦横比）からは 6450 が出てこない。**この panel を特別に扱う**ことにした。
  - 直し（touch.c）: 宣言の範囲が指の届く範囲と違う panel の表 `touch_quirks`（USB の vendor・product と、X・Y の届く最大。0 は宣言のまま）。
    `read_axes` が範囲を読んだ後で `read_quirk` が `kl_backend_input_id` で引き、宣言の範囲の内側の値だけを採る。
    056a:8191 は Y 6450（X は宣言のまま 16383）。log は `KWL TOUCH quirk device=… vendor=056a product=8191 declared x=0..16383 y=0..9599`
    と、その後の `KWL TOUCH added … y=0..6450`。他の panel（5330 の、注入器）は何も変わらない。
  - 残る見込み（未確認、下の T の較正で確かめる）: **X の端の飽和。** T1-649 の上端からの 2 本指の swipe（232/233、234/235、236/237）は
    2 本とも X が 0 か 16383 ちょうどだった。横に並べた 2 本（約 2 cm 離れる）が両方とも飽和するなら、絵の左右の端から 2 cm ほどが
    panel の X の外にあり、端から離れた指が column 0・1279（desktops の swipe の 16 px の帯、上端なら角の launcher・Notes）に読まれる。
    「端でない 1 本指の swipe で desktop 送り」「上端の swipe down が効かない（角に当たる）」はこれで説明がつく。一方で下端の右角の tap は
    15751・15785 で飽和していない。較正の data なしでは X の対応を変えない。
  - 付記: この panel の MSC_TIMESTAMP は常に 0（650 report すべて）。libkeiland は 0.5 s ごとの検査で Scan Time を信じず host の時刻を使うので、
    compositor には害が無い（kernel の Scan Time の読みは別に見る価値がある）。
  - 試験（host）: `plan/bugs/BUG-267/tests/run-host-touch-group.sh` を直した（stand-in の `kwl_pointer_warp_to`・`kwl_output_absolute`
    を足し、`kl_backend_input_id` を足した）。BUG-315 の場面 5 つを追加: 真ん中の短い tap と次の tap、真ん中の 1 本指の短い swipe、
    右端の tap の後の真ん中の swipe、左端の 2 本の後の真ん中の指、OLED の範囲（2 台目の touch screen として 056a:8191 を宣言の範囲で
    足し、Y 6445 が最下段、3225 が中段、1 が最上段、X は宣言のまま）。`host-touch-group: ok (94 checks)`。
  - build: `make -j8 ZEDBSD_CONFIG=config/ci/config-rpi4.mk BUILD=build/bug315-rpi4 build/bug315-rpi4/bin/wayland` rc 0、warning 0。
  - T の手順（T1、Pi 4 の実機、ユーザーが触る）:
    1. 上の命令で `bin/wayland` を build し、Pi の `/bin/wayland` を `/root/wayland.orig-bug315` に退避して差し替える（cksum を照合、sync、reboot）。
       kernel は今のまま（BUG-313 の 2 回目以降）。
    2. 較正: `od -A d -t x1 -v /dev/input/event5 > /tmp/ev5-cal.txt` を回し、ユーザーに 1 本指で、絵の縁（bezel との境目）ちょうどを
       約 1 s ずつ、この順に押してもらう: 左上の角、上の中央、右上の角、右の中央、右下の角、下の中央、左下の角、左の中央、画面の中央。
       続けて、左の中央で 2 本を横に並べて 1 s、右の中央で同じく 1 s。T1 は contact ごとに最初・最後・最小・最大の X・Y を表にする。
       見る点: 下の 3 点の Y の最大（6300〜6600 なら表の 6450 で良い。外れたら値を P2 へ）、左右の中央の X（0・16383 に飽和するか）、

    3. 動作（ユーザーの目視、各 OK/NG と一言）:

       b. 窓（Files など）を開き、窓の下の方の物（一覧の下の項目、button）を tap → 指の所の物が反応する。窓の閉じる button を tap → 閉じる。
       c. desktop の真ん中で 1 本指の短い swipe を左右に → desktop は変わらない。
       d. 右端のぎりぎりから 1 本指で左へ swipe → 次の desktop に移る（設計どおり）。
       e. 上端の中央から 1 本指で下へ swipe、次に 2 本指で同じく → Wiseview が開く。
       f. 下端の中央から上へ swipe → App Home が開く。
       c と e の間は event5 の od も取り、NG の時に照らし合わせる。
    4. 合格: 2 の下の Y の最大が 6300〜6600、3 の a〜f がすべて OK。NG の項目は od の記録とともに P2 へ（X の飽和なら較正の data で X の対応を決める）。
    5. 戻しは不要（次の round で上書き）。元は `/root/wayland.orig-bug315`。
