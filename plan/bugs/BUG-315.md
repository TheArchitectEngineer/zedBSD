## 2026-10-17: X の生 report による較正（ユーザー）

- 機器は Wacom 056a:8191 の OLED touch panel。画面の左右の端まで指は届くが、X が変わるのは画面中央の約半分だけ。中央から左へ約 1/4 幅より外では X=0、右へ約 1/4 幅より外では X=16383 に張り付く。Y は動き、縦方向の同様の飽和は観察されない。
- interface 0 の input report ID 0x0D、54 byte の生値を取得。1 本指の drag では byte 0 が report ID 0x0D、byte 1 が 0x11（Tip と Contact ID 1）、byte 2–3 が X の little endian 16 bit、byte 4–5 が Y の little endian 16 bit。動いたのは byte 2–5 だけで、残りの byte はその drag 中に変化しなかった。ほかの領域に独立した全幅座標がある証拠はない。
- 左端から右端への順序: 左の帯の外で `00 00` が 60 report 以上、帯に入ると `7f 00`（127）→ `ca 01`（458）→ `12 03`（786）→ `55 04`（1109）→ … → `67 1f`（8039）→ `1e 21`（8478）→ … → `cb 3e`（16075）→ `ff 3f`（16383）、右の帯の外で `ff 3f` が 70 report 以上続いた。帯の中はおよそ 330–440/report で滑らかに増える。全 report で X は 0..0x3fff、0x4000 以上なし。
- この生 report の X は 0..0x3fff の非負値で、負数を表す 16 bit signed の中心原点座標という説明とは合わない。以前の画面上の `0x7fff` という表現は生 report の最大値ではなく、生値の最大は `0x3fff`。
- **結論と限界**: 左右の帯の外はデバイスから同一の X 値として届く。現在の input/compositor の座標変換を変えても、その位置の違いは復元できない。X の `touch_quirks` の範囲を縮めるだけでは直らない。原因が controller の設定・firmware・panel の組み合わせのどこにあるかは未確認。
- 次: report 0x0D を出す前のデバイス設定と Wacom 固有の制御経路を調べ、全幅の X を送らせる手段があるかを判断する。変える場合は、同じ物理点で設定前後の生 report を比較する。解決できなければ、左右の帯の外を使う edge gesture の誤検出を避ける暫定策を別に検討する。実装は承認済み Queue の範囲を確認してから行う。

## 2026-10-17: Linux 上流との比較（コード調査、実機 Linux は未実施）

- Linux の HID core は vendor `056a` を `HID_GROUP_WACOM` に分類する。Wacom の device ID 表には `0x8191` 固有の entry がなく、USB Wacom の wildcard `HID_ANY_ID` が `HID_GENERIC` を選ぶ。[hid-core.c](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-core.c)、[wacom_wac.c](https://github.com/torvalds/linux/blob/master/drivers/hid/wacom_wac.c)。この ID 専用の認識エリア設定は Linux 上流で見つからなかった。
- Linux の汎用 Wacom 経路は HID Digitizer Input Mode の feature field を 2 にして `SET_REPORT` を送る。[wacom_sys.c](https://github.com/torvalds/linux/blob/master/drivers/hid/wacom_sys.c) の `wacom_hid_set_device_mode()`。zedBSD の `usb_hid_set_device_mode()` も interface 0 に feature report `0x21`、Device Mode 2、3 byte を送って成功した記録がある（BUG-313）。送る mode の値は一致する。
- Linux は descriptor に宣言された Wacom 固有の sensor offset feature があれば `GET_REPORT` して evdev の範囲に反映する。これは受信した座標の解釈であり、panel に認識範囲を設定する `SET_REPORT` ではない。この機器の保存済み interface 0 descriptor（`BUG-313/wacom-8191-if0.rdesc`、946 byte）を HID item として走査すると feature は ID `0x0a`（Contact Count Maximum）と `0x21`（Device Mode・Device Identifier）だけで、sensor offset や認識エリアを設定する feature は宣言されていない。[wacom_sys.c](https://github.com/torvalds/linux/blob/master/drivers/hid/wacom_sys.c)。
- よって、**上流 Linux の既知の `056a:8191` 経路からは、zedBSD が欠かした全幅設定コマンドを特定できない**。Windows では標準 HID で全幅が使えるというユーザーの観察は重要だが、Windows が追加の制御転送を送るのか、Windows で panel と画面の位置の対応を設定しているのか、あるいは別の状態差かは未測定。interface 1（vendor 0xff00、zedBSD では parser が拒否）も未解析。
- 次の識別測定: 同じ機器を USB の電源断を挟んで Linux で起動し、report ID `0x0d` の生 X を端から端まで記録する。Linux でも飽和するなら上流に認識エリアの復旧処理は無い見込み。Linux で全幅なら `usbmon` で起動からの interface 0/1 の control・output report を記録し、zedBSD の送信列と比較する。Windows 側でも必要になれば USB の制御転送を採る。取得した未知の vendor command は実機へ推測で送らず、転送の内容と効果を照合してから設計する。
- Linux の複合 USB 機器の扱い（同日ユーザーの「interface 0 しか使っていないが Linux は？」への調査）: Linux HID は USB interface ごとに `hid_device` を作り、vendor `056a` の各 HID interface を Wacom group に分類し、Wacom driver の `wacom_probe()` が各々の descriptor を解析する。`wacom_parse_and_register()` は汎用 Wacom で pen/touch 等の device type が分からない interface を `-ENODEV` で無視する。したがって interface 1 を単に USB 上に持つだけで、Wacom driver がそこへ認識エリアの command を送るわけではない。[usbhid の interface ごとの probe](https://github.com/torvalds/linux/blob/master/drivers/hid/usbhid/hid-core.c)、[HID の Wacom group](https://github.com/torvalds/linux/blob/master/drivers/hid/hid-core.c)、[Wacom の probe と判定](https://github.com/torvalds/linux/blob/master/drivers/hid/wacom_sys.c)。この機器の interface 1 の descriptor 全体と Linux 実機の bind 結果は未採取なので、実際に無視されるか、hidraw 等から使えるかは未確認。zedBSD は interface 1（vendor 0xff00、63 byte の input/output report）の解析を拒否しており、ここは比較上の未調査差分。次は interface 1 の descriptor と、Linux の各 interface の bound driver・USB 転送を採る。
