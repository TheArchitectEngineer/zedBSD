# BUG-300: Video Player のスライダーが、再生の終わりで 50% くらいの位置に止まる

- 状態: reproduced（実機 5330、ユーザー） / tracking
- 発見: [ws202-p013](../ws202/ws.md) の 5330 の UAT（ユーザー、2026-10-13）。ユーザー「動画プレーヤーアプリのスライダーは、ビデオの再生が終わっても50%くらいの位置で、スケールあるいは認識されている再生時間がおかしいようでした。それは動画プレーヤーのバグかも。」
- 期待: 再生の終わりでスライダーが右端（100%）に来る。
- 観察: 再生は終わりまで進むが、スライダーは約 50% の位置。UAT の判定は OK（ユーザー）で、この不具合は p013 を止めない。
- 疑い（未調べ）: Video Player がスライダーの全長に使う長さ（container の duration・`end_us`、ws202-p004）と、表示に使う pts の単位・時刻の基準（D29 の空の entry の時刻の消費、edit list・trim）の食い違い。約 2 倍なので、timescale の取り違えや音と映像の track の長さの取り違えもありうる。
- 再現の材料: ws202-p013 の image（libavcodec 無しの `plan/ws202/tests/config-media.mk`）、どの file で見たかは未記録（ユーザーに聞くか、WS202 の試験の stream で全部見る）。
- 関連: [WS202](../ws202/ws.md)（p004 の `end_us`、p010 の時刻、p011 の Video Player）、WS122（動画の player）。

## 2026-10-13 夜: ユーザーの動画（Q1）

- ユーザーが再生位置がおかしかった動画を渡した（「著作権の関係で、コミットしないでください。」）。置き場所は git の外の `build/bug300/user-video.mp4`（main の checkout、build/ は ignore）。**commit しない・tests/ に入れない・T1 の image に入れる時も repo の外から。**
- container の値（Q1、box を読んだ）: mvhd timescale 90000・duration 562560（6.25 s）。音の track 2: mdhd 48000・300032（6.25 s）、elst (558750, 0)。映像の track 1: mdhd 24000・149000（6.208 s、149 frame、24 fps、1920x1080 H.264）、elst (558750, 1000)。
- 見立て（未確認）: 約 2 倍の長さは、音の長さ 300032 を映像の timescale 24000 で読む（12.5 s → 6.2/12.5 ≈ 50%）か、movie の長さ 562560 を 48000 で読む（11.7 s → 約 53%）かで出る。mediafile/mp4.c の mvhd・mdhd・elst の読みは timescale を取り違えていないように見えるので、Video Player の slider の長さの出所か、時刻の単位の換算を疑う。

## 2026-10-13 夜: 原因と直し（Q1、bug-analyzer の解析）

- 原因: `userland/desktop/videoplayer/main.c` の「終わり」の遷移で `VP_ENDED` にする時に clock の anchor（`media.clock_time`）を今の clock に固定していなかった。`vp_media_clock()`（media.c）は再生中でない時 anchor をそのまま返すので、終わった瞬間にスライダーと時刻が「最後に Play で再開した位置か seek した位置」（どちらも無ければ 0:00）へ戻る。途中で Pause→Play か seek をすると、その位置（約半分なら約 50%）に見える。libmedia の engine（engine.c の ENDED）と Music（play.c）は固定している。
- 調べで外れた候補: container の timescale（mediafile の duration 6.25 s・各 track の end_us は正しい）、AAC の長さ（298000 frame = 6.208 s）、clock の単位（48000）、映像の pts。ユーザーの動画で host の probe で確かめた。
- 直し（Q1、main の checkout）: ENDED にする前に anchor を終わりの clock（長さの方が大きければ長さ）にする。Video Player の amd64 の build（config/current-uat.mk、BUILD=build/q1-bug300）warning 0。host 試験は無し（UI の main.c だけ）。
- 未確認: ユーザーが UAT で途中に Pause・seek をしたか（していなければ症状は 0% のはずで、別の原因が残る）。QEMU・実機の確かめは T1（短い file で途中に Space 2 回 → 終わりでスライダーが右端・時刻が「長さ / 長さ」、触らずに終わり → 右端、ENDED の後の Left で終わり −10 s へ）。
- 状態: 直しを入れた、確かめ待ち（tracking のまま）。

## 2026-10-13 夜: ユーザーの答え（Q1）

ユーザー「再生の途中に一時停止か seek をしていないです。」→ 2a7e09cd9 の直した原因（終わりで anchor が最後の Play・seek の位置に戻る）だけでは、一時停止も seek も無い時は 0:00（0%）に戻るはずで、約 50% の説明にならない。別の原因が残る。2a7e09cd9 の直しは正しい直しとして残し、bug-analyzer が続きを調べる。

## 2026-10-13 夜: 2 回目の解析（bug-analyzer）

- 一時停止・seek 無しで「終わりで約 50%」になる決定的な経路は code からは見つからなかった。除外した候補: container の長さ・timescale、AAC の rate（AAC-LC 48000 Hz・298000 frame）、clock の単位（AUDIO_RATE 48000）、heard の単位（audiod の read_position は stream frame、delay も換算、device は stereo）、audiod の delay（約 85 ms）、映像の pts（ctts 有り）、mp4 の interleave、slider の描画（widgets.c:500-504）、Space が UI に渡る、resize・F11。clock が半分の速さなら映像も遅れて終わりでは 100% になるので、50% は「heard が約 3.1 s で止まる」か「anchor が 3.1 s」しか無い。
- 別の実在の不具合: audiod の heard は client が書き終わると read − delay で凍る（mix.c:296-305、10-12 の acfb78a27 からの退行）→ Video Player の clock が音の終わりの約 85 ms 手前で止まり、最後の picture が due にならず ENDED に到達しない（main.c:803-811）。device が 48000 でない時は補間が最後の 1 frame を消費せず played_out も偽。→ player の側の直しを bug-fixer に（audiod の直し: ring が空で draining でない間は heard を時刻で read まで進める、は案として残す）。
- 残る仮説（5330 でだけ起きる実行時の条件）: (1) 音が鳴っていなかった・stream が lost（AUDIO open error・AUDIO lost）(2) 5330 の GPU decode が遅く音の ring が枯れて heard が凍り、picture ring が満杯で reader が待ち音を書かない膠着 (3) 途中の Space。
- 切り分け: 調査用の CLOCK の log 行（time_ms・heard・written・consumed・pictures・late・eof・state、1 秒ごと）を足した Video Player を 5330 で、ユーザーの動画（repo の外の build/bug300/、5330 の kei の home に scp、image や tests/ には入れない）で何も押さずに最後まで再生し、log を回収する（T1）。
- ユーザーの許可（2026-10-13）: 動画を 5330 の kei の home に scp して使ってよい（repo・image・tests には入れない、試した後は 5330 から消す）。
