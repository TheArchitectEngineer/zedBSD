# BUG-059: host の高負荷の下の QEMU で、起動中の NVMe の I/O queue の回復の後に root の mount が ETIMEDOUT で失敗する

Bug ID: `BUG-059`
Reproduction: reproduced（1 回、QEMU。3 回中 1 回）
Disposition: resolved（ws072-p002、2026-09-27、QEMU。元の高負荷の boot の条件での再現は未実施）
Date: 2026-09-27
Source: WS036 の toolchain（zedbsd7）の merge 後の main の検証（`plan/tools/boot-test.sh build/ws035-sq/hdd-image.img`、
`build/main-zedbsd7-boot/login.png`）
Owner: [WS072](../ws072/ws.md)

## 期待と観測

期待: login prompt。観測（画面）: `nvme: I/O queue recovered epoch=2` の後に `vfs: mount rootpart failed (error 42)`（42 は ETIMEDOUT）、
`VFS initialization failed (42); entering idle.`。

## 条件

host の load average が約 35（7 つのサブエージェントの build と LLVM の build が並行）。同じ image の再実行 2 回は PASS
（`build/main-zedbsd7-boot1/`・`boot2/`、load average 約 7）。toolchain の違いではないと見る（同じ image が再実行で通る）。

## 見立て（未検証）

QEMU の NVMe の emulation が host の負荷で遅れ、driver の I/O timeout が queue を回復させたが、回復の前後の要求（root の superblock 等の読み）が
ETIMEDOUT で返り、VFS が再試行せずに root の mount を諦めた。実機でも遅い device や一時的な停止で同じことが起こりうる。

## 次の手

回復の後の再試行（NVMe の driver が回復した queue に未完了の要求を出し直すか、VFS の root の mount が一時的な誤りで何度か試すか）を調べる。
再現は host に負荷をかけた QEMU（例: `stress-ng` と並べて boot test を繰り返す）。

## 解決（ws072-p002、2026-09-27）

確かめた原因: NVMe の driver は timeout で走っている全 command を ETIMEDOUT で失敗させて queue を作り直すが、失敗した要求を出し直さない。
再現: 2 台目の NVMe を QMP で 2048 byte/秒に絞って `dd` を並べると、読みが `Connection timed out` で失敗し、その後 queue は回復している
（`plan/tools/nvme/timeout-retry.sh`）。

修正: `nvme_disk_submit` は ETIMEDOUT の要求を、回復した queue に入れ直して最大 3 回走らせ直す（`src/drivers/pci/pci-nvme.c`）。
同じ絞りで直す前は 4 つの読みが全部 ETIMEDOUT、直した後は全部成功。詳細は [ws072-p002](../ws072/phase002/phase.md)。
