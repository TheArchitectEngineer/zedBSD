# BUG-338: VF2 の実機で SMP が S7 の監視用の hart 0 を起こそうとして止まる

- 状態: reproduced（2026-10-20 ユーザーの VF2 の実機）/ scheduled
- 発見: ユーザーの VF2 の UAT（beta2 U27、U-Boot の prompt から `load mmc 1:1 ${kernel_addr_r} EFI/BOOT/BOOTRISCV64.EFI; bootefi ${kernel_addr_r} ${fdtcontroladdr}`）。ユーザーが貼った serial の log（判定には使わない、手がかり）: `RISCV64 SMP 5 CPUs (device tree 5 usable of 5, limit 8)` の後、`sbi_trap_error: hart0: … mcause=0x5 mtval=0x4003d068`、`RISCV64 SMP cpu 1 (hart 0) did not come up`、`fatal: src/hal/riscv64/smp.c:621`。
- 原因（見込み）: JH7110 の hart 0 は SiFive S7（rv64imac_zba_zbb、S-mode・F・D が無い監視用の core）。U-Boot の control の DTB（`${fdtcontroladdr}`）では hart 0 も mmu-type 付きで usable と数えられ（`src/hal/riscv64/fdt.c` の usable の判定は mmu-type と status だけ）、SBI の HSM で起こして OpenSBI が trap した。vendor の Linux の DT は cpu@0 が `sifive,s7`、`rv64imac_zba_zbb`。
- 同じ log で分かった良い事: 配布の U-Boot 2021.10 は bootefi で GOP（1920x1080、format 1、base 0xfe000000）を出し、zedBSD の loader が受け取った（`RV64 GOP handed over`、`RISCV64 FRAMEBUFFER 1920x1080 phys=fe000000`）。WS277 の D1（U-Boot の mode の引き継ぎ）の前提が成り立つ見込み。
- 関係: WS256（p004 の SMP・FDT）。
