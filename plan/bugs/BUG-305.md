# BUG-305: network が止まらない時に shutdown が PCI の shutdown（disk の cache の flush を含む）を丸ごと飛ばす疑い

- 状態: unreproduced / resolved（2026-10-14 P2 の結論、T1-610 の QEMU の証拠と source。Q1 の確定で close）。直しは commit 738edbe23。元の疑い（network が止まらない）は T1-610 では起きず（`drv_pci_shutdown` が呼ばれた）、直しで disk の flush は network の停止に依存しなくなった
- 発見: ws231-p001 の T1-609（AHCI、poweroff で QMP の flush_operations が増えない）と review-1 中 7。`src/kern/shutdown.c:157` の `if (network_stopped)` が偽なら `drv_pci_shutdown`（AHCI・NVMe の flush を含む）が呼ばれない。T1-610 で gdbstub で確かめる。
- 直し方の案: disk の flush を network の停止の前に行うか、network が止まらなくても disk の shutdown は行う。

## 直し（2026-10-14 P2、branch agent/p2-ws215、base main 078b388fd、commit 738edbe23）

- 順序の理由（`src/kern/shutdown.c` の注記と BUG-288 の直し）: network が 10 s で止まらない時は、driver の RX/TX の producer が USB・PCI の memory に残りうるので、USB と PCI の teardown（`drv_usb_shutdown`・`drv_pci_shutdown`）を丸ごと飛ばして reset に任せる。意図は「止まっていない producer の下で他の device を壊さない」ことで、disk の flush を飛ばす意図は無い。その結果 AHCI・NVMe の `shutdown` の hook の中の FLUSH も飛ぶ。mount された volume は `mount_sync_all()` で flush されるが、raw の write（`dd of=/dev/sdN` で close の flush の無い disk）や mount されていない disk の volatile な cache は network の停止に依存していた。
- 直し: `system_shutdown_prepare()` で `mount_sync_all()`・writeback の終わりの後、network を止める**前**に `shutdown_disks_flush()` を呼ぶ。disk の層の `disk_at()` で live の disk を順に見て、whole（`d_parent == NULL`、`DISK_PARTITION` で無い）・書ける（`DISK_READ_ONLY` で無い）・loop で無い（`DISK_FILE_BACKED` で無い、中身は sync 済みの volume の file）disk に `disk_sync()`（`buf_sync()` で dirty の line を書き、`bio_flush()` で BIO_FLUSH）を出す。disk はまだ通常に動いているので driver の普通の flush の経路（AHCI は FLUSH CACHE (EXT)、NVMe は Flush）。失敗は `shutdown: <disk>: the disk could not be flushed (error N)` を log して他の disk を続ける（ENXIO＝媒体が無い・消えた disk は log しない）。shutdown は止めない（driver の shutdown の flush と同じ扱い）。network が止まった時は、その後の PCI の shutdown で AHCI がもう一度 flush する（重複は無害）。進みの log は `the volumes are synced; flushing the disks` → `the disks are flushed; stopping the network`。
- 全部の block の driver（AHCI・NVMe・USB の storage・UAS・SDHCI・IDE など）は BIO_FLUSH を受ける（`grep BIO_FLUSH src/drivers`）。
- 確かめ（P2、host）: amd64 の vmunix の build（`BUILD=build/bug304`）rc 0、warning 0、`amd64 vmunix check: PASS`。host 試験は無し（shutdown の順序は kernel の中だけで、短い host 試験を作れない）。QEMU は未実施。network が本当に止まっていなかったか（元の疑い）は未確認のまま。

### T1 への確かめの依頼の文（T1-610 の AHCI の再試験・BUG-304 と一緒に流せる）

image・QEMU は BUG-304 の依頼と同じ（AHCI の sata0 と NVMe の nv1、`-action shutdown=pause` か `-no-shutdown`、`-gdb tcp::<port>`）。判定は QMP と gdbstub だけ。

1. **poweroff の flush（AHCI）**: BUG-304 の 1 の書き込みの後、QMP `query-blockstats` の sata0 の flush_operations を取り、guest で `poweroff`、VM が止まった（`query-status` が shutdown か paused）後にもう一度取る。合否: poweroff の後に 1 以上増える。
2. **poweroff の flush（NVMe）**: 同じ時に nv1 の flush_operations も取る。合否: 1 以上増える。
3. **経路**（1 か 2 が増えない時だけ、または T1-610 の gdbstub の確かめと一緒に）: `break shutdown_disks_flush`・`break net_shutdown_for_boot`・`break drv_pci_shutdown` を置いて poweroff し、止まった順、`net_shutdown_for_boot` の戻り値（`finish` の後の `$rax`、0 以外なら network が止まっていない＝元の疑いの確認）、`shutdown_disks_flush` で `break bio_flush` に何回止まるか（whole の書ける disk の数と同じはず）を記録。

## T1-610 の結果の解析（2026-10-14 P2）

T1-610（QEMU q35、sata0 の AHCI ＋ NVMe の nv1、main f41c0c12b、成果物 `/home/awe/zedBSD-worktrees/t1/build/review/t1-610/`）: AHCI は全 PASS（poweroff で sata0 の flush_operations が 4→6）。NVMe の nv1 は dd の後も poweroff の後も flush_operations が 0。

1. **NVMe の 0 は QEMU の数え方で、FAIL ではない。**
   - zedBSD の driver は VWC を見ずに常に NVMe Flush を出す（`src/drivers/pci/pci-nvme.c`: `nvme_disk_submit()` → `nvme_disk_run()` → `nvme_io_execute(controller, DRV_NVME_NVM_FLUSH, ...)`）。NVMe の disk は `DISK_FLUSH_PROOF` を立てない（立てるのは USB の storage と UAS だけ）ので、`bio_flush()` は毎回 BIO_FLUSH を driver に出す。VWC が無い controller への Flush は spec 上で成功の no-op なので、VWC を見ないのは正しい。
   - QEMU の nvme は VWC を持つと答える（`hw/nvme/ctrl.c` の `id->vwc = NVME_VWC_NSID_BROADCAST_SUPPORT | NVME_VWC_PRESENT`）が、Flush の経路（`nvme_flush()` → `nvme_do_flush()` → `blk_aio_flush()`）は `block_acct_start(..., BLOCK_ACCT_FLUSH)` を呼ばない。`blk_aio_flush()` も数えない。QMP `query-blockstats` の flush_operations は device の model が数えた物だけなので、NVMe の Flush は何回出しても 0 のまま。controller の shutdown（CC.SHN）の `nvme_ns_shutdown()` の `blk_flush()` も数えない。AHCI（`hw/ide/core.c` の `BLOCK_ACCT_FLUSH`）は数える。
   - 確かめた source: host の `/home/awe/qemu-pc98`（QEMU 11.0.93 の fork）。数えが消えたのは upstream の commit 38f4ac65ac「hw/nvme: reimplement flush to allow cancellation」（2021-06-17、QEMU 6.1 の開発期）。T1 が使う Debian の QEMU 10.0.11 の source は host に無く、同じと推定（6.1 より後で、後に数えを戻した commit は 11.0.93 の tree にも無い）。
   - NVMe の Flush を直に観るなら（任意）: gdbstub で `break nvme_io_execute`（この関数は Flush だけに使う。vmunix に symbol がある）を poweroff の前に置き、`net_shutdown_for_boot` より前に NVMe の whole の disk ごとに 1 回止まること。または host 側の QEMU の trace の `pci_nvme_flush_ns`。
2. **sata0 の +2 の内訳**（source と gdb.log の順序から）: `shutdown_disks_flush()` は `system_shutdown_prepare()` からだけ呼ばれる static 関数で、inline された（T1-610 の vmunix と同じ世代の vmunix に symbol が無く、`disk_sync`・`system_shutdown_prepare`・`nvme_io_execute` はある）。だから breakpoint が止まらなかった。gdb.log の順は `bio_flush #20` → `ahci_port_flush #2` → `net_shutdown_for_boot` → `drv_pci_shutdown` → `ahci_shutdown` → `ahci_port_flush #3` → `nvme_shutdown` ×2。network の停止の前の `ahci_port_flush` の呼び手は BIO_FLUSH（`pci-ahci.c` の `ahci_disk_submit`）と close（`ahci_disk_close`、`cache_dirty` の時だけ）だけで、poweroff は sata0 を close しないので、#2 は `shutdown_disks_flush()` の `disk_sync()` → `bio_flush()` の BIO_FLUSH（推定、#2 の `bt` は取っていない）。#3 は `ahci_shutdown()`。よって +2 ＝ `shutdown_disks_flush` の 1 ＋ `ahci_shutdown` の 1 で、直しの設計どおり。
3. 元の疑い（network が止まらず PCI の shutdown が飛ぶ）は T1-610 では起きていない（`drv_pci_shutdown` が呼ばれた。`net_shutdown_for_boot` の戻り値は DWARF が無く gdb が読めなかったが、0 以外なら `drv_pci_shutdown` は呼ばれない）。T1-609 の「poweroff で増えない」は最後の読みが VM の停止の前だった可能性もあり、原因は確定していない。直しの後は network の停止に関係なく flush する。
4. 結論: **resolved にしてよい**。コードの変更は無し（この解析では source を直していない）。NVMe の Flush の直の観察は未実施で、上の gdbstub の手順は任意。
5. 観察（BUG-305 の範囲の外、直していない）: NVMe の disk には AHCI の `ahci_disk_close` のような close の時の flush が無い（`nvme_disk_ops` は `.submit` だけ）。raw の dev への dd の後、NVMe の cache は次の BIO_FLUSH（fsync・sync・shutdown）まで flush されない。正しい shutdown では `shutdown_disks_flush()` と `nvme_shutdown()` の CC.SHN が書き戻す。
