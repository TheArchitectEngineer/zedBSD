# BUG-301: RTL8822BU の CCMP の解読が MAC header を 24 byte 固定で読み、QoS の data（26 byte）で外れる疑い

- 状態: unreproduced / resolved（2026-10-14 Q1 判定: 今の association は QoS を名乗らず AP は non-QoS の 24 byte の header を送るので外れない、QoS の data が来ても EILSEQ と core の PN の確かめで捨てられる。再調査の契機は HT・WMM・QoS を名乗る時）
- 発見: ws004-p039（P2、2026-10-13）の WLAN の driver の共通化の調べ。物理の試験は通っている。
- 観察: RTL8822BU の driver の CCMP の解読は header の長さを 24 byte 固定で扱う。QoS の data frame（QoS Control の 2 byte で 26、4 address で 32）では CCMP の header・PN の位置がずれ、解読か replay の確かめが外れるはず。AX211 は header の長さを計算している。core の wlan_l2_parse_data は RTL 式の MIC の trailer を前提にしている（AX211 は 8 byte を足して合わせている）。core に channel_frequency の写しが 2 つ。
- 疑問: 物理の試験（WPA2 の AP への接続・通信）は通っているので、hardware が解読しているか、受けの path で QoS の header を外しているか、QoS の AP で試していない可能性。
- 次: P2 が source で確かめ、外れるなら header の長さを計算する直し（AX211 と同じ）。
- 関連: [WS004](../ws004/ws.md) p039、RTL8822BU（userland の外、src/drivers）。

## 2026-10-14 P2（q965）: source での確かめ — 今の約束では外れない（close の提案）

- **受け取る frame は QoS でない**:
  - core の association request（`wlan-wpa2-codec.c` の assoc の組み立て）が載せる element は、SSID・Supported Rates・Extended Supported Rates・RSN だけ。HT Capabilities（0x2d）も WMM の vendor の element（00:50:f2）も QoS の capability も載せない。probe request も同じ（`wlan.c:4263`、rates だけ）。src/kern/net/wifi と include/kern/net/wlan.h に HT・WMM・QoS を名乗る code は無い（grep）。
  - 802.11 では、QoS を名乗らない station は non-QoS の station とみなされる。AP はその station に QoS Data を送らず、Data（subtype 0）を送る。AP から station への data は FromDS=1・ToDS=0 の 3 address。4 address（WDS）は station に来ない。
  - よって、今の RTL8822BU の station が受ける data の MAC header は 24 byte で、`rtl8822bu_rx_classify` の CCMP の位置（24〜31）は正しい。TX の側（`rtl8822bu_frame_transmit_private` の確かめ）も core が組む non-QoS の data なので同じ。物理の試験（WPA2 の接続・通信）が通っていることと合う。
- **もし QoS Data が来たら**（AP の誤り、または将来この station が HT・WMM を名乗った時）: offset 24 の読みは QoS Control の 2 byte を PN の一部として読むので、`payload[26] != 0` か ExtIV の bit の確かめで `EILSEQ`、すり抜けても core が自分の解析の PN と driver の PN の一致を求める（`wlan-l2.c:226-231`）。どちらでも frame は**捨てられる**。誤った frame を上に渡すことは無い（安全側に倒れる）。hardware の復号の結果（`encryption_type`・`icv_error`）は driver の offset と関係なく正しい。
- **結論**: 今の約束（core が QoS・HT・WMM を名乗らない）の下では外れない。直しは要らない。**close の提案**（Q1 の判断）。
- **再調査の契機**: core か driver が HT・VHT・WMM・QoS を association で名乗るようにする時（スループットの WS など）。その時は、RTL8822BU の RX の CCMP の解読と TX の確かめで header の長さを計算する（QoS で +2、Order bit つきの QoS で HT Control の +4、4 address で +6。AX211 の `intel-ax211-rx.c` の計算と同じ）。core の `wlan_l2_parse_data` の QoS の扱い（TID 0 だけ受ける）も、その時に見直す。
- 他の観察（p039 の記録）のうち、core の `wlan_l2_parse_data` の MIC の trailer の前提と、`channel_frequency` の 2 つの写しは、この ticket の範囲の外（直しは要らない、p039 の phase.md に記録）。
- 試験: source の変更が無いので無し。
