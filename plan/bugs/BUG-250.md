# BUG-250: 5330 で greeter が display を掴めない（`KWL VULKAN_ERROR operation=format result=-1000000000`、6 回で console へ）

- 状態: reproduced（実機 5330） / resolved（2026-10-07 da51e8609（constraints の照合）＋88833c9da（eDP の connected）。5330 の実機: ユーザーの目視「5330を再起動し、画面がでました！」、Q1 が SSH で kernel.log の `lease 1 claimed`・`picture up`・`first frame 1920x1080 ... shown on the 1920x1080 panel`、session.log の `lost operation` 0）
- 証拠: [kernel-5330.log](BUG-250/kernel-5330.log)・[greeter-sessiond-5330.log](BUG-250/greeter-sessiond-5330.log)（SSH kei@10.0.30.3、zedBSD）

## 観察

- greeter.log: `KWL DISPLAY device=zedBSD i915 (Gen12 Xe) width=1920 height=1080` の後、`KWL STARTUP step=output-display` → `KWL VULKAN_ERROR operation=format result=-1000000000`（VK_ERROR_SURFACE_LOST_KHR、vkGetPhysicalDeviceSurfaceFormatsKHR）→ `KWL MODE_ERROR errno=5` → `KWL EXIT frames=0 error=5`。6 回とも同じ。
- kernel.log: resident display の lease・claim の行が 1 つも無い（claim の前で止まる）。`the firmware display (1 active crtc) is left to the resident start's takeover (N1)`、hpd の `[CONNECTOR:2:HDMI-A-1]` の後。
- 5320 の main 173fa2115 の kernel（ws113-p011a の前）では greeter・session が動いた。

## 疑い（Q1、未確認）

- ws113-p011a（9036a7ad4）の display の ID の変更（resident も 0x100+connector、connector ごとの generation、hotplug で generation を進める）と、libvulkan の wsi（p003・p004a の display の扱い、compose.c の surface を `compose->display` に開く）の食い違い。起動の hpd の事象で generation が進み、列挙した display の ID・generation で format の問い合わせが ESTALE/ENXIO → SURFACE_LOST になっている可能性。

## 原因（P2、2026-10-07、source を読んで特定）

- ws113-p011a（9036a7ad4）で i915 の resident の display の ID が `0x100 + connector`、generation が connector の generation になり、display.c の query・mode・claim・power・refresh は `i915_display_which` で照合するように変わった。
- ところが `GPU_DISPLAY_CONSTRAINTS` の callback（`src/drivers/gpu/i915/display/scanout.c` の `i915_scanout_constraints`）だけが古い固定の ID 1 / generation 1 を照合したまま残り、query が返す ID（eDP の connector の `0x100+n`）に `ENOENT` を返した。
- libvulkan の `display_formats`（vkGetPhysicalDeviceSurfaceFormatsKHR）は format の前に constraints を問い合わせ、`display_error` が `ENOENT` を分類外として `VK_ERROR_SURFACE_LOST_KHR`（-1000000000）にする → `KWL VULKAN_ERROR operation=format`。claim の前で止まるので kernel.log に lease・claim の行が無い。
- QEMU で出ない理由: Venus の display（`src/drivers/gpu/venus/display.c`）は自分の constraints を持ち、i915 の scanout.c を通らない。5320 の 173fa2115 の kernel は p011a の前で、query も固定の ID 1 / generation 1 だったので一致していた。

## 修正（P2、2026-10-07）

- `i915_display_which` を `drv_i915_display_which`（display.h）として公開し、resident の node の constraints はこれで照合する（resident の output、または接続された別の connector。未接続は ENXIO、別の ID は ENOENT、別の generation は ESTALE）。
- capture の build（`I915_TEST_CAPTURE`、固定の ID 1 / generation 1 の capture display）には別の表 `drv_i915_capture_scanout_ops` を渡し、従来の固定の照合を保つ。
- 確認: `make ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug250 vmunix`（warning 0、include check・vmunix check PASS）、同じく `I915_TEST_CAPTURE=y`（warning 0、PASS）。QEMU・実機は未実施。

## 次

- 実機 5330 で、修正の kernel で greeter が起動し（`KWL VULKAN_ERROR operation=format` が出ず、kernel.log に `resident display: lease N claimed` が出る）、login 後の session も表示されること（Q1 経由でユーザーの承認の下で kernel を入れ替える）。

## 修正 1 の後の実機（2026-10-07 Q1、5330、da51e8609+9a42683c9 の kernel、userland は 2fe4a5019）

- 自動 login の session（greeter は出ない boot）。kernel: `resident display: lease N claimed` → `released after 0 frame(s)` を繰り返す（format の問い合わせは通った）。
- session.log: `KWL OUTPUT open width=1920 height=1080` の後 `KWL OUTPUT lost operation=acquire result=-1000000000`（VK_ERROR_SURFACE_LOST_KHR、vkAcquireNextImageKHR）→ reopen → また lost。p004a の output-switch が回り続ける。
- 疑い: acquire が使う native の口（GPU_DISPLAY_WAIT か present の側、`drv_i915_present_display_wait` など）がまだ固定の ID 1・generation 1 か、別の照合を持つ。
- 証拠: [kernel-5330-fix1.log](BUG-250/kernel-5330-fix1.log)・[session-5330-fix1.log](BUG-250/session-5330-fix1.log)。

## 修正 2（P2、2026-10-07、source を読んで特定）

- 原因: acquire の SURFACE_LOST は、先に queue した最初の present が worker で失敗し、その error が chain に残って次の acquire で見えたもの（kernel の `released after 0 frame(s)`、`0 presents`）。i915 の present（`present.c` の `drv_i915_present_display_present`）は ws113-p011a から resident の output の connector が `connected` かを確かめ、違えば ENXIO を返す。ところが hotplug path は eDP の connector を一度も detect しない（`output.c` の inventory は HDMI と DP だけを probe）ので、eDP の status は `connector_status_unknown` のまま、topology の `connected` は 0。resident の内蔵 panel が「抜かれた」扱いになり、全部の frame が ENXIO → libvulkan の `display_error` が SURFACE_LOST にしていた。query は CONNECTED を常に立てるので format・claim は通る。5320 の 173fa2115 は p011a の前で connected を見ていなかった。QEMU は Venus なのでこの経路を通らない。
- 直し: `drv_i915_display_resident_identity()`（display.c）で、resident の connector が eDP なら connected を 1 とする（内蔵 panel は node が駆動している限り繋がっている）。
- display の全ての ioctl の ID・generation の照合の洗い出し（i915 の resident の node）: QUERY（resident_identity）、MODE・CLAIM・POWER・REFRESH（`drv_i915_display_which`）、CONSTRAINTS（修正 1 で `drv_i915_display_which`）、PRESENT（resident の generation と connected、修正 2）、WAIT（入力の ID なし、resident の generation を返す）、RELEASE（lease だけ）、EVENTS（sequence だけ）。control.c・backlight.c に ID・generation の照合は無い。固定の ID 1 / generation 1 が残るのは capture の build の capture display だけ（その node の中で一貫）。
- 確認: `make ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug250 vmunix`（warning 0、include check・vmunix check PASS）、`build/bug250/vmunix` の cksum `3608876397 3143616`。実機は未実施。
- 残り（範囲外、記録だけ）: HDMI などに output が移った時、別の connector として列挙される eDP も connected 0 のまま（claim で panel に戻すと ENXIO）。firmware の output に戻る経路（`drv_i915_display_output_back`）は別にある。

## 残りの直し（P2、2026-10-07、q854-i01、plan/ws177/backlog-p2.md の行）

- 原因: hotplug の道は eDP の connector を detect せず EDID も読まないので、topology の eDP は connected 0・mode 0 のまま。修正 2 は resident の時だけ eDP を connected にしたので、HDMI などに output が移ると、別の connector として並ぶ eDP は query で CONNECTED が無く、mode の列挙は ENOENT（mode 0）、claim は ENXIO（`drv_i915_display_which` の connected 0、`drv_i915_display_output_prepare` の「not connected」）。蓋を開けて panel へ戻す claim（ws113-p011a、`kwl_output_use_internal`）と、p004a の「消えた output から内蔵の display へ」が通らない。
- 直し: `drv_i915_display_output_connector()`（`output.c`、宣言は `output.h`）: hotplug の道の connector を返し、eDP の時は node が panel の依存（`rctx.lcd`）と panel の mode を持つ限り connected 1、mode・refresh・大きさを panel の物（起動の時に EDID か VBT から読んだ物）にする。`display.c` の resident の identity（修正 2 の特例を置き換え）・別の connector の query・mode・照合（`i915_display_other_check`、claim・power・refresh が使う）と、`output.c` の claim の準備がこれを使う。HDMI・DP は今までどおり。
- 確かめ: kernel（`make -j16 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/bug250 vmunix`）warning 0、include check・vmunix check PASS、cksum `2877465438 3147864`（BUG-253 の直しも含む）。`I915_TEST_CAPTURE=y`（`BUILD=build/bug250-capture`）warning 0、PASS。host の `plan/ws075/tests/hdmi/host-output-test.sh` 80 checks、0 failures。実機（5330、HDMI）: 蓋を閉じて HDMI へ移った後、蓋を開けると `KWL LID internal: the desktop comes back to the panel errno=0`、kernel の `the output moves to connector N (eDP panel, Keiland's claim)`、panel に desktop が戻ること。未実施（BUG-253 の直しが要る）。
