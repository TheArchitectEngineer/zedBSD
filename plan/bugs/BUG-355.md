# BUG-355: native の UFS への大きい書き込みが約 1 MB/s と遅い（2 GiB の swap file の 0 書きに約 30 分）

- 状態: 修正済み・Q1 の判定待ち（2026-10-30 P4、q1688-i01、commit 6387b82a0。QEMU だけ、実機は未実施）
- 発見: 2026-10-29 P4（q1665-i07・i08、WS307 p009・p010 の QEMU、SATA の disk）。installer が UFS の root に swap file 2 GiB を作る段。
- 観測: 0 書きが約 1 MB/s。installer は 1 MiB の write と最後の fsync 1 回で書いており、installer の側に直す所は無い（P4 の読み）。WS307 p006 の制限（UFS の 16 MiB の dd が同じ桁）と同じ見込み。
- 期待: 媒体の速さに近い書き込み（少なくとも数十 MB/s）。
- 未確認: QEMU だけか実機（NVMe・SATA）でも同じか、FAT・block device への直の書き込みとの比べ、原因（UFS の block の割り当て・buffer cache・同期の書き込み・driver の queue の深さ）。


- 4096 byte の sector の disk で特に遅い件は [BUG-358](BUG-358.md) に分けた（2026-10-29 ユーザー「4096バイトセクタで遅いことはバグとして記録して、先に進んでほしい」）。

## 原因（2026-10-29 P4、q1688-i01）

- 遅いのは `mkfs -t ufs --profile=native` で作った volume だけ。image の root（`zedimage-host ufs` の既定の profile 0）は速い。
- `userland/base/mkfs/ufs-format.c` の `format_tail` は profile が 0 でなければ、volume の後ろに tail journal の locator（`ZUJ2`）と snapshot の record（`ZSL1`・`ZSN1`）を書く。native の profile（2）もそれを書いていた。superblock には batched journal（v3、`.ufs-journal`）の大きさの要求（`ZJ3R`）も書いている。
- kernel（`src/drivers/fs/ufs.c`）は mount のとき `journal_discover` で `ZUJ2` を見つけると、tail journal（v2）を `journal_enabled` にする。そうなると `write_cached_intended` が 0 を返し、batched journal は開かず、書き込みの遅延（write-cache）もしない。変更のたびに、tail journal に同期で redo を書いて flush（`drv_ufs_journal_publishv` と checkpoint、`order_barrier`）する。content も 64 KiB の allocation run ごとに、この同期の commit を通る。
- 測り（`plan/ws307/tests/ufs-speed.sh`、QEMU・KVM、2 GiB の NVMe、cache=unsafe で host の fsync を外した値。`build/ws307-test/ufs-speed.aeWMJv`）: 512 の disk で 32 MiB の dd が 19.7 MB/s。このとき device の flush 5702 回、driver の書き込み 14532 回・129 MB（4 倍）。4 KiB の file 300 個の `cp -R` は 244 KiB/s で、flush 14453 回（1 file に約 48 回）・driver に 129 MB。host の fdatasync は 0.5〜2 s かかる（2026-10-29 の host、負荷の高い時）ので、cache=writeback の QEMU では 1 MB/s 以下になる。WS299 の実機（5330）の 4 GiB 書き 7 MB/s（`IO_DRIVER_FLUSH` 728057 回）も同じ原因。
- 遅い間、guest の CPU は 98% が `sched_idle` だった（`plan/ws307/tests/rip-sample.py` で QMP から RIP を取った）。CPU ではなく、flush と同期の書き込みを待つ時間が律速。

## 直し（commit 6387b82a0）

- `mkfs -t ufs --profile=native` は tail journal と snapshot の record を書かない。前の format が残した 3 つの record（`ZUJ2` の sector と `ZSL1`・`ZSN1` の 2 sector）は 0 で消す（`format_tail`）。tail の予約（`FORMAT_TAIL_BYTES`）・geometry・`--check-size` の値は変えていない。mount した kernel は image の root と同じ道を取る: batched journal（superblock の `ZJ3R` の大きさで、最初の書ける mount で `.ufs-journal` を作る）と、cache での書き込みの遅延。README（`userland/base/mkfs/README.md`）にこの形を書いた。
- 4096 byte の sector の disk では、batched journal の道に別の不具合があった（[BUG-358](BUG-358.md) の 2 つ目の原因）。同じ commit で直した。
- WS299 の「mkfs で作った native の UFS の write-through」（2026-10-28 ユーザー「さきほどの「mkfs で作った native の UFS が write-through になり、4 GiB の書きが 7 MB/s しか出ない件」は、P1に依頼します。」）も、この直しで扱った（2026-10-29 Q1 の承認で q1688 に含めた。WS299 の ws.md は Q1 が直す）。WS299 の実機（5330）での測り直しは未実施。

## 保証（tail journal から batched journal に変えて同じか）

- crash の後の整合: batched journal は metadata を transaction にまとめる。commit は slot に書いて flush し、commit record で封をする。mount の時は、封をした最新の transaction を replay する（`j3_replay`）。tail journal と同じく、crash の後も mount できる整合した volume が残る。image の root は既にこの形で、`plan/tools/ufs/crash-test.sh` の既定（v3）で試されている。
- fsync: batched journal の volume の `ufs_file_sync` は、その file の block を書き、走っている transaction を commit する（BUG-307 の直し）。fsync が返った時点で、その file の内容・inode・block の割り当て・それより前の名前の変更が durable。tail journal の時と同じ保証。
- 違う所: fsync も sync もしていない変更は、flusher の間隔（`BUF_FLUSH_INTERVAL` 1 s・`BUF_FLUSH_AGE` 2 s）の間 cache に残り、その間に電源が落ちると失われうる（失われるのは最後の変更で、整合は保つ）。tail journal では、変更のたびに同期で書いていた。この違いは image の root と同じで、普通の遅延書き込みの file system と同じ。
- snapshot: native の volume では使えなくなる（`ZSL1` が無い）。kernel の `KERN_SNAPSHOT_CREATE` を呼ぶ userland の program は無い（libc の包みだけ）。
- 既にある tail journal の volume（前の mkfs、前の installer が作った物）: kernel は今までどおり tail journal の道で mount する（遅いまま）。下の crash 試験の `tail-journal-volume` で、mount・書き込み・読み戻しを確かめた。

## 確かめた事（2026-10-29〜30 P4、QEMU だけ）

- 直した後の測り（`build/ws307-test/ufs-speed.6skEyw`、同じ条件）: 512 の 32 MiB の dd は flush 6 回・driver の書き込み 83 回・33.9 MB。4 KiB の file 300 個は flush 3 回・61 回・3.07 MB で 13.5 MB/s（前は 244 KiB/s）。直す前の値は上の「原因」。もう一度 mount した後の読み戻し（`cksum`・`diff -r`）は一致し、host の `check-volume.py` も OK。大きい file の時間は host の負荷で揺れた（同じ回の raw の dd も 1343 ms と遅かった）。locator だけを消した実験の回（`ufs-speed.cdKU6v`）では 182 MB/s。
- crash（`plan/ws307/tests/ufs-crash.sh`、`build/ws307-test/ufs-crash.rtSJPR`、cache=writeback、512 と 4096 の disk で 3 s と 20 s）: fsync した 256 KiB の file が切った後も同じ。replay の mount・名前に穴が無い（HOLDS = PREFIX）・その後の書き込みと読み戻し・512 の host の検査が全て ok。前の mkfs（`build/ws307n-img/bin/mkfs`）で作った tail journal の volume も、mount・書き込み・読み戻しが ok。512 の 20 s の回は 3182 個の名前で `No space left on device` になった。directory が 12 の direct block（約 96 KiB）の上限に達したため（`plan/tools/ufs/dir-grow.sh` の上限と同じ、既存の制限）。
- host: `sh plan/ws307/tests/host/mkfs-ufs-native-test.sh` PASS（native の 512 の 5 つの大きさは、旧の出力から tail の 3 つの record を消した物と byte で同じ。512・4096 の 8 つの大きさで verify・decode・tail の record 無し・loader の reader の mount）。
- build: amd64 の vmunix・mkfs rc 0・warning 0。他の platform の vmunix（pcat・armv7-virt・m68k-virt・ppc32-mac99・ppc64-pseries・riscv32-virt・riscv64-virt・rpi4・rpi5・visionfive2・zybo・odroid-c5・pc98・intelmac。各 `BUILD=build/q1688-k-<名>`）は全て rc 0・warning 0。
- 未実施: 実機（5330 の WS299 の測り、4Kn の実機）。installer の通しの導入（WS307 p011 で流し直す）。
