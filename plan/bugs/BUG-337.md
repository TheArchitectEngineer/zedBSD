# BUG-337: sun4u で Xzed の起動の後に zwm・zterm・zshell が出ず、text の console にも戻らない

- 状態: reproduced（QEMU、T1-746・T1-747）/ tracking（2026-10-19 22:22 ユーザー「sun4uはバグの原因がわからなければBUGチケットに積んでいったんやめます。」で WS275 を止めた）
- 発見: [WS275](../ws275/ws.md) p006（sun4u の /dev/graphics と Xzed）の T1-746 (2)。tree は P1 の branch（WS275 p002〜p005 と 19c6aee06・4aa7a753d、main には未 merge）。
- 期待: `plan/ws275/tests/config-sun4u-x11.mk` の image（QEMU sun4u、-g 1024x768x32）で login して startx（または Xzed と client を手で起動）すると、zwm・zterm・zshell の window と wallpaper が出る。
- 観察（QEMU のみ、実機は未実施）:
  - T1-746: startx の後 約 120 秒、Xzed の root window の地色（x32 で (32,48,64) = xzed の 0x203040、R・B の順は正しい）と arrow の cursor だけ。x8・既定も同じ。PNG: `/home/awe/zedBSD-worktrees/t1/build/t746x/{r2-x8,r3-n,r3-x32}/login-after.png`。
  - T1-747: startx を使わず `Xzed --size 800x600 -- /bin/sh -c '/bin/zwm /bin/zterm >/tmp/zwm.out 2>&1 & /bin/zshell >/tmp/zshell.out 2>&1; …' & sleep 30; ls …; kill %1; …; echo DONE` を serial で打った。256 MiB でも 1024 MiB（BOOT_MEMORY）でも同じく地色と cursor だけで、`kill %1` の後も text の console に戻らず、DONE 以降（/tmp の一覧、client の出力、meminfo、dmesg）は読めなかった。メモリの大きさで挙動は変わらない（メモリ不足の証拠は無いが、否定もできていない）。PNG: `/home/awe/zedBSD-worktrees/t1/build/t747/{m256d,m1024}/login-after.png`。
  - gdbstub（1024 MiB、symbol 付き、log `/home/awe/zedBSD-worktrees/t1/build/t747/g1024-{1,2}.txt`）: 2 回とも kernel が sparcv9 の TLB miss の解決の中。1 回目 pc `write_entry+220`（`membar #Sync`）← `sparcv9_resolve_miss`、2 回目 pc `find_mapping.isra.0+16` ← `resolve_user_locked.isra`。256 MiB の 1 回目も `write_entry` 付近。kernel は止まっておらず走っている。
- code で確かめた事（P1、q1325）: libX11 は setup で 'l' を名乗り request・reply・event を byte ごとに LE で詰める。Xzed は 'B'/'l' を見て rd/wr を順に従う。protocol の byte 順の誤りは見当たらない。
- 疑い（未確認）: (a) user の TLB miss が解決されず同じ miss を繰り返す（livelock、gdb の 2 点はこれと矛盾しない）、(b) client の XOpenDisplay の失敗、(c) Xzed の poll の loop が accept に戻らない、(d) client が sparcv9 で落ちる、(e) Xzedrc が実行されない。kill の後に text に戻らないのは、Xzed が終わらないか、console が再描画されないか、kernel が user の miss で回り続けているか、を判別できていない。
- 次に調べる時: gdbstub で `sparcv9_resolve_miss` に break して、miss の VA・context・task を数回読み、同じ VA を繰り返すかを見る。serial で `kill` の後に `echo` を打って shell が生きているか。`ps` は 27fe21770 で sparc64 の gcc で build できるようになった（config に足す）。
- 試験の道具の制約（T1-747）: `keys:` は `&` を打てない（`type:` を使う）、`then-expect` の待ちは boot-test.py の 120 秒の固定、QMP を別の client で同時に使うと boot-test の QMP が壊れる。
- 関係: WS275 p006（uncleared）。
