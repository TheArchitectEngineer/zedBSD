# BUG-356: Venus の desktop が動く時、networkd の競合で ue0 が設定されず SSH が上がらない（最初の見立て: ある disk の組で起動が止まる）

- 状態: open（2026-10-29 Q1 が登録）
- 発見: 2026-10-29 P4（q1665-i08、WS307 p011 の QEMU）。installer の image（main 630b76a12 の kernel、`BUILD=build/ws307l-img`）を Venus の GPU 付きの QEMU で USB から起動。
- 観測（1 回ずつ順に）: 空の NVMe 512 だけ → 起動（88 s）。NVMe 512＋SATA（ESP と Basic data の GPT）→ 起動。4096 の NVMe だけ → 止まる。NVMe 512＋4096 → 止まる。空の GPT の USB（2 つ目の qemu-xhci）だけ → 止まる。SATA の 3 partition（1 つを乱数で埋めた）だけ → 止まる。MBR と zedbsd.cfg の FAT の 2 台（別の ahci、並列の時）→ 止まる。止まった時は boot の splash のまま、gdbstub で全 CPU が sched_idle（何かを待つ）。
- 比べ: WS307 p009（Venus 無し、std VGA）では 4096 の NVMe・2 つ目の xhci の USB を付けて起動していた。
- 見込み（未確定）: kernel の起動の待ち（boot0 の FAT を探す時の disk の調べ）、Venus との組み合わせ、または p009 の後に main に入った kernel の変更。
- 期待: どの disk の組でも起動する（関係の無い disk は無視する）。
- 再現の script（P4、2026-10-29）: `/home/awe/zedBSD-worktrees/p4-ws307l/build/tmp/bug356-repro.py`（worktree の root で `python3 build/tmp/bug356-repro.py <dir> <SET>`、SET は nvme・k4・other・usb・tiny・zcfg・mbr の組）。disk の file と止まった回の image の写し（boot.img）は `/home/awe/zedBSD-worktrees/p4-ws307l/build/ws307-test/p011.vq3t9c4w/`。

## 解析（2026-10-29 bug-analyzer、source は変えていない）

- 結論: Venus でも disk の種類でもなく、2026-10-03 の 846464d1e から main にある 2 つの別の不具合（p009 の後の回帰ではない）。Venus の構成で device 無しの screendump は std VGA を写し、正常に起動した guest でも splash のままなので、「splash のまま」と「全 CPU が sched_idle」は止まった証拠にならない。
- **原因 A（この BUG-356 で扱う、Venus の desktop が動く時だけ）**: networkd の競合で ue0 が一度も設定されない。`userland/base/networkd/main.c` の `receive_wait_request()`（pump の経路）が全ての request に `decode_request()` をかけ、`NETWORKD_FIELD_OUTPUT` を受けず EINVAL → `send_error()` が予約の組（request_id 1、SHOW）で返す → net の LAN_ENABLE（request_id 3）が `net: mismatched networkd response` で失敗 → `init: oneshot networking failed`。pump の経路に入るのは、desktop の SUBSCRIBE が write 側を閉じず `control_inputs` に最大 5 秒残り、その間 main loop が新しい client を pump の経路で受けるため。起動した guest で `net watch` の loop と `net lan enable` を並べると 3/30〜29/40 で再現。
  - 直す方針: pump の経路の request の読みを `read_request()` と同じ規則に（LAN_ENABLE・LAN_DISABLE は decode を通さない）、pump の経路で SUBSCRIBE を受けたら EOF を待たず `accept_subscriber` へ、必要なら net の側で mismatch・EBUSY の時に一度やり直す。
  - 確かめる試験: Venus の guest で `net watch`・`net up lo0` の loop と `net lan enable` を 40 回ずつ流し mismatch 0。Venus 付きの単独の disk を 6 台同時に起動し全台で SSH と ue0 の address。
- **原因 B（Venus に関係なく起きる）は BUG-357 に分けた**。
- 解析の道具: `build/bug356/`（`run.py`・`threads.py`・`klog.py`・`net.py`、各回の出力と kernel の log。大きな disk・dump は消した）。

## 修正（2026-10-29 fix-bug356、状態の判定は Q1）

- 直した事（commit 8000e2484、branch agent/fix-bug356、基点 main 2b29b5f84）:
  - request の読みの規則を `userland/base/networkd/request-frame.[ch]` の一つにした: 閉じを待つ要求（SUBSCRIBE 以外）、field を decode する要求（SUBSCRIBE・LAN_ENABLE・LAN_DISABLE 以外）、受けた bytes が要求として揃ったかの判定。`read_request()`（event loop）と `receive_wait_request()`（pump）の両方が `decode_request_fields()` を通る。
  - pump の経路は SUBSCRIBE を frame が揃った時点で `accept_subscriber()` へ渡す（EOF を待たない）。watcher が 5 秒 slot に残り、その間の client が pump の経路へ回る状態は無くなった。
  - `net lan enable` は networkd が EBUSY（retry）を返した時だけ 1 秒後に 1 回やり直す（`userland/base/net/main.c` の `lan_send_policy()`）。mismatch ではやり直さない。
- 確かめた事:
  - host: `tests/networkd-request-host-test.c`（ASan・UBSan、command は file の頭）PASS（14 件: SUBSCRIBE は閉じ無しで揃う、他は閉じを待つ、1 byte ずつの SUBSCRIBE、OUTPUT の record を持つ LAN_ENABLE は decode しない、切れた header・payload・余りの bytes）。
  - build: amd64 の vmunix・networkd・net rc 0・warning 0。試験の image は今の tree から `make ZEDBSD_CONFIG=plan/ws307/tests/config-amd64-p010.mk BUILD=build/bug356-img … installer-image` rc 0。
