# BUG-294: Pi 4 の root の UFS（mmcblk0p2）が起動のたびに書き込みを止める（an indirect block could not be truncated (error 5)）

- 状態: reproduced（Pi 4 の実機、再起動しても毎回） / tracking
- 発見: 2026-10-12 ユーザー（Pi 4、写真で dmesg）:「再起動してもだめです。UFSがリードオンリー？」。dmesg: `ufs: mmcblk0p2: the volume refuses writes until it is mounted again: an indirect block could not be truncated (error 5)`（src/drivers/fs/ufs.c:9184 の stop_writing、truncate の中の write_block・order_barrier・free_block のどれかが EIO）。同じ dmesg に `vfs: scan mmcblk0 geometry error=21: 4 entries`、`v3d: job failed kind=0 error=42`。
- 影響: root が書けないので dhcpc が lease・resolv.conf を書けず IPv4 の DHCP が EIO（BUG-293 の「net dhcp en0 の Input/Output error」の主な原因と見る）、log も残らない。
- 経緯（推測）: 2026-10-12 は束の置き換え（/bin・/lib・/boot の書き換え）と電源の入れ直し・再起動が多かった。どの時点で volume が壊れたかは不明。zedBSD に fsck は無い（host の plan/tools/ufs/check-volume.py は image を検査できる）。
- 次: (1) 壊れた SD の volume を host に写して check-volume.py で調べる（ユーザーが可能なら）、(2) 原因（電源断の途中の truncate と journal の replay、free_block の bitmap の食い違い、mmc の書き込みの失敗）を bug-analyzer、(3) 当面の回避は image の焼き直し。

## 再発（2026-10-16 ユーザー）

- ユーザー:「PiがRead-onlyになったケースのエラーメッセージを捉えました。」`ufs: mmcblk0p2: the volume refuses writes until it is mounted again: an indirect block could not be truncated (error 5)`（今は src/drivers/fs/ufs.c:9205）。
- 時期: T2 の T1-668 で main 1872c0d84 の kernel（ws236-p010 の depth の直し）を入れて reboot した後、Pi が ping・ssh とも戻らなかった（10 分以上）。Q1 の見立て（未確認）: root が書けなくなると dhcpc が lease を書けず IPv4 が付かない（この ticket の「影響」）ので、kernel が起動していても network に出てこない。ws236-p010 の kernel が原因とは限らない。
- 最近の UFS の変更: BUG-307 の fsync（f9f7acba9・bec395969、10-14）、3d99cdb06（10-14）、6ec8ca8f7（10-15、ufs.c 7 行・vfs.c 1 行）。
- 状態: reproduced / scheduled（2026-10-16 Q1、解析の担当を立てる）。
- 2026-10-16 ユーザー: 同じ boot で `vfs: scan mmcblk0 geometry error=21: 4 entries`。Q1: src/kern/vfs.c:1455、21 は EOPNOTSUPP（SD の driver が geometry の ioctl に答えない）、partition は 4 つ見えている。RTX の guest の nvme0n1 でも同じ行が出るので、read-only とは無関係の見込み。
