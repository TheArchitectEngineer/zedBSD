# BUG-294: Pi 4 の root の UFS（mmcblk0p2）が起動のたびに書き込みを止める（an indirect block could not be truncated (error 5)）

- 状態: reproduced（Pi 4 の実機、再起動しても毎回） / tracking
- 発見: 2026-10-12 ユーザー（Pi 4、写真で dmesg）:「再起動してもだめです。UFSがリードオンリー？」。dmesg: `ufs: mmcblk0p2: the volume refuses writes until it is mounted again: an indirect block could not be truncated (error 5)`（src/drivers/fs/ufs.c:9184 の stop_writing、truncate の中の write_block・order_barrier・free_block のどれかが EIO）。同じ dmesg に `vfs: scan mmcblk0 geometry error=21: 4 entries`、`v3d: job failed kind=0 error=42`。
- 影響: root が書けないので dhcpc が lease・resolv.conf を書けず IPv4 の DHCP が EIO（BUG-293 の「net dhcp en0 の Input/Output error」の主な原因と見る）、log も残らない。
- 経緯（推測）: 2026-10-12 は束の置き換え（/bin・/lib・/boot の書き換え）と電源の入れ直し・再起動が多かった。どの時点で volume が壊れたかは不明。zedBSD に fsck は無い（host の plan/tools/ufs/check-volume.py は image を検査できる）。
- 次: (1) 壊れた SD の volume を host に写して check-volume.py で調べる（ユーザーが可能なら）、(2) 原因（電源断の途中の truncate と journal の replay、free_block の bitmap の食い違い、mmc の書き込みの失敗）を bug-analyzer、(3) 当面の回避は image の焼き直し。

## 原因（P4、2026-10-15、SD の写しの解析と source の読み）

- 証拠: ユーザーの SD の UFS の写し（`build/q1/bug294/sd-p2-ufs.img`、214 MiB、P4 は複写 `build/bug294/root.img` を読んだだけ）。読みの scratch は P4 の worktree の `build/bug294/scan.py`・`ino.py`。
- 壊れているのは **journal の file `/.ufs-journal`（inode 785）だけ**。size 0、direct は全部 0、single indirect = block 8752、blocks = 16 sector（indirect block 1 つ分）。block 8752 の entry 0 は 0、**entry 1〜1023 は arm64 の機械語**（消した実行 file の中身）で、block 番号として volume の外（`13348738739040420361` など）。他の inode・directory・bitmap は整合（host の `fsck -n` が見つけたのは inode 785 とそれに伴う数だけ）。
- superblock の locator は古い journal（10 MiB、header 96888、nonce 5a2965a7…、applied 178、slot の seq 178・177）を名指しのまま。その block は今は free。
- 仕組み（`src/drivers/fs/ufs.c`）:
  1. `j3_open` は mount ごとに journal の大きさ（`j3_wanted_sectors`、空きの 1/8 を MiB で丸め）を計り、前と違うと `j3_make` で作り直す。214 MiB の Pi の root は空きが減る（/root への vmunix の退避の複写など）と 10 MiB → 8 MiB に変わる。
  2. `j3_make` → `j3_allocate` は古い file を `ufs_truncate(0)` で切り（ここは成功）、`j3_file_fill` で block を取り直す。この間 `j3.creating` が立ち、`zero_new_block` は journal の block を **0 で埋めない**。data block はそれでよいが、**`bmap_ensure` が取る indirect block も埋めない**。
  3. 新しい indirect block（8752、前は実行 file の data）の古い中身の entry を `bmap_ensure` が「既にある block」として辿り、journal の block として返した。block が飛び飛びなので extent が header の上限（508）を超え、`j3_file_fill` が ENOSPC。`j3_open` の失敗は log に出ず、その mount は **journal なしの write cached** で走った。
  4. 次の mount からは毎回、`j3_make` が inode 785 を切る途中で entry 1 のでたらめな block を `free_block` に渡し（どの group にも無い → EIO）、`truncate_indirect` が `stop_writing("an indirect block could not be truncated", 5)`。これが毎回の起動で RO になる理由。
- 同じ boot の `vfs: scan mmcblk0 geometry error=21: 4 entries` は無関係（Q1 の見立てと同じ、SD の driver が geometry の ioctl に EOPNOTSUPP）。SD の driver・電源断・journal の replay は今回の原因ではない（replay は slot の seq ≤ applied で何もしていない）。

## 直し（P4、2026-10-15、agent/p4-bug294）

- `src/drivers/fs/ufs.c`:
  - `allocate_indirect_block`（新）: `bmap_ensure` の indirect block（root と中間の段）は、journal を埋めている間も 0 で埋める（`zero_block` を `zero_new_block` から分けた）。journal の data block は今までどおり埋めない。
  - `bmap_ensure`: indirect block の entry が volume の外を指すなら辿らず EIO と log（inode・indirect block・entry・block）。
  - `j3_make`: 古い file を切る前に locator を消して durable にする（`j3_locator_erase`）。作り直しの失敗で、free の block を名指す locator が残らない。
  - `j3_open`: 大きさが同じでも、`.ufs-journal` が在り、最初の block が header で、size が journal と同じ時だけ使い続ける（`j3_file_matches`）。上の失敗や fsck が file を消した後に、free の block の上で journal を使い直さない。
  - 診断: `truncate_indirect` の失敗で inode・indirect block・entry・block・error を log、`write_cached_start` で `j3_open` の失敗（ENOENT 以外）を log。
- `userland/base/fsck/check.c`: 最後の group の尾（volume の外）で `owned` の map の外を読んでいた（ASan の heap-buffer-overflow、この SD の写しで発見）。`local < fragments` の時だけ読む。動作は同じ（尾は is_free が常に 0）。
- 確認:
  - build: rpi4 `build/bug294-rpi4/vmunix`（`arm64 vmunix check: PASS`）、amd64 `build/bug294-amd64/vmunix`（`amd64 vmunix check: PASS`）、どちらも rc=0・warning 0。rpi4 の static `bin/fsck` rc=0・warning 0。`git diff --check` ok。`plan/tools/style-check.py` は ufs.c・check.c で新しい指摘 0（既存 528 件は同じ）。
  - host: 直した fsck（ASan つき）で SD の写しの複写に `-n` → 8（inode 785 の block が data の領域の外・`.ufs-journal` の entry・group 0/3 の数・superblock の数の 6 件）、`-y` → 4、もう一度 `-n` → 0、`check-volume.py` → `UFS OK`。`plan/tools/ufs/fsck-host-test.py` → 77 checks, 0 failures。
  - kernel の変更の host の試験は無い（kernel の ufs.c を host で動かす harness が無い）。QEMU・実機は未実施（T への依頼）。
