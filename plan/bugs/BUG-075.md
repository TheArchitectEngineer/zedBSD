# BUG-075: FAT で読んだ後に消した file の cluster が rm と sync の後も解放されない

Bug ID: `BUG-075`
Reproduction: reproduced（QEMU、FAT32 の 512 B・4 KiB cluster の試験の volume、swap・loop なし、WS073 の agent）
Disposition: tracking（WS073 の後の Phase）
Date: 2026-09-27
Source: ws073-p015（hybrid の試験で /boot/boot0 から走らせた script）
Owner: WS073

## 期待と観測

期待: `rm` と `sync` の後に file の FAT の chain が解放され、そこで強制終了しても `fsck.fat` が誤りを出さない。

観測: 読んだ（cat、sh で実行した）file を消すと、directory の entry は消えるが FAT の chain が解放されず、`sync` の後に強制終了すると
`fsck.fat` が "Reclaimed N unused clusters" と FSInfo の空き数の誤りを出す。読まずに消した file、強制終了の前に unmount した場合は正しく解放される。

## 見込み

FAT は cache の inode が離されたときに chain を解放し、`sync` はそれを済ませない（開いた後の inode の参照が残る）。

## 次の手

WS073 で p015 の後の Phase。p015 の試験は script を FAT に置いたまま避ける。

## 調査（2026-09-27、WS073。修正は未着手）

- guest（QEMU、amd64、512 B cluster の FAT32 の試験の volume）で `df -k`: 16 KiB の file を作ると使用 17 KiB、`cat` で読んでから `rm` しても
  17 KiB のまま（`sync` の後も）。読まずに消した file はすぐ 1 KiB に戻る。on-disk だけでなく mount の中でも chain が解放されていない。
- 原因の見込み（コードで確認した範囲）: `read()` の page cache の object（`cache_only`、`src/kern/vm.c` の object の作成）は同じ inode に自分の
  読みの handle（`object->file`）を開いて持つ。そのため unlink の後も inode の参照が残り、FAT の orphan の chain は inode が消える
  （cache の object が追い出される、または unmount）まで `fat_reclaim()` で解放されない。unmount で直るのはこのため。
- 修正の案: unlink で inode が最後の link を失い DEAD になったとき、その inode の cache だけの object（mapping なし・clean）を捨てる
  （unmount が使う `vm_object_discard_mount_refs(mount, inode, &refs)` と同じ扱い）。mapping のある object は従来どおり最後の munmap まで待つ。
  VM の object の寿命に触れるので、別の Phase で設計してから行う。
