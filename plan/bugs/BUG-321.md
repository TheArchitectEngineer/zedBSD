## P1 の調べ（2026-10-15、host だけ）

- 写真の番地の断片を host にある候補の kernel（`build/amd64/vmunix` 02:40、`build/uat/sv7-gen9/vmunix` 01:11、`build/uat/main-amd64/vmunix`）で引くと 3 つとも同じ: `ffffffff8021955c` = hal_task_context_switch+0xc1、`ffffffff80218f89` = irq_handler+0x447、`ffffffff80205368` = overlay_pread_internal+0x19。`ffffffff8901358` は桁が欠け text（…8040f000 まで）の外。HAL の早い所なので版の差が出ず、kern_free を呼んだ関数は分からない。
- 写真の行が混ざる理由: amd64 の hal_fatal の `fatal: caller … stack …` の行は fatal_trace が番地ごとに hal_printf を呼んで作るので、その合間に他の CPU の log の record が入る。
- 読んだ範囲（5330 で PASS した T1-606 の頃の a25b73a3f → 647d43d37）: i915 の共有の道（i915.c の Gen9 の既定 on・D0 の suspend、irq.c、device.c の interim の display irq、display.c の bootfb の bind・fini・session_close、vbt.c の test VBT の削除、takeover.c）は Gen12 では graphics_ver==9 か display==NULL の判定で外れ、Gen12 の初期化に新しい確保・解放は見当たらない。DMC（dmc.c・firmware.c）は 10-05 以降不変。kern_free の大きな確保の header の探し方（4d3d7eddf、10-12）は T1-606 に含まれる。kernel の他の変更（buf.c BUG-307、vfs.c WS238 の /boot/efi、devfs BUG-304、shutdown、pcat の TSC）にも明らかな誤った解放は見当たらない。WS237 の安全化 63d0532b0 は Gen9 の file だけ。
- 診断の改善（commit 0270e7973・394d73682、branch agent/p1-bug321）: hal_fatal の報告を console の所有を握ったまま出す（他の CPU の出力に割られない）、kern_free の未知の pointer で `kern_free: <pointer> is not a kernel allocation (freed from <caller>)` を出す。
- 再開の条件: ユーザーの kernel の版（`uname -v` か build の場所）と fatal の行の読める写真、または診断の入った main の image での 5330 の再現（T、Q1 経由）。
- 2026-10-15 ユーザー（クリック）: 止まった kernel は `build/amd64/vmunix`（02:40、647d43d37 と 63d0532b0 の間）。P1 の調べ: 写真の番地の断片はその kernel でも HAL の早い所（hal_task_context_switch・irq_handler・overlay_pread_internal）に当たり、どこで free したかは分からない。i915 の Gen12 の道に新しい誤った解放は見当たらない。→ 診断の改善（f3b7d66e3 → main）: hal_fatal の 2 行を console の所有を握って出す（他の CPU の出力に割られない）、kern_free の不正の前に `kern_free: <pointer> is not a kernel allocation (freed from <caller>)`。再開の条件: この診断の入った main の amd64 image で 5330 を素に起動して再現し、`kern_free:` と `fatal:` の行の写真と、その image の vmunix を保存（ユーザーの試験の一覧）。

## P1 の原因と直し（2026-10-16、branch agent/p1-bug321b）

### 原因（host の解析、実機での確証は未）

- **解放されたのは task の record ではなく kernel stack**: U6 の vmunix で hal_task_destroy を逆アセンブルすると、`freed from ffffffff80219753` は 1 つ目の `kern_free(task->sys_stack_allocation)` の戻り番地（2 つ目の `kernel_free(task)` は tail jump で、戻り番地は thread_wait になる）。`ffff80010b8b7030` の page の中の位置 0x30 は大きな確保の隠れた header（`struct kernel_large_allocation` 48 bytes）の直後で、kernel stack（16 KiB + 15、page に裏打ちされた確保）の先頭として正しい形。kern_free が拒んだのは、その header の magic か pointer が壊れていたから。
- **header は stack の底のすぐ下にある**: stack は下へ伸び、底（page+0x30）を越えると header の memory.size（+0x28）・paddr（+0x20）・magic（+0x18）・pointer（+0x10）を上書きする。0x18 bytes 以上越えると magic が壊れ、その thread を wait で刈った時に `kern_free: … is not a kernel allocation` になる。越え方が浅いと memory だけが壊れて pmem の解放が誤る（無言の破壊）。さらに深いと前の物理 page（別の確保）を壊す（10-15 の最初の写真の別の場所の fatal と整合）。
- **16 KiB を越える道がある**: U6 の vmunix の逆アセンブルから関数ごとの frame（push と `sub rsp`）と直接の呼び出しを辿った静的な見積もり（間接呼び出しは追えないので下限）:
  - user の GPU command の submit: syscall の入口（hardware frame・`amd64_common_interrupt` の 15 push・int_handler 144）+ kernel_syscall_handler 2256 + file_ioctl 112 + cdev_ioctl_file 16 + gpu_ioctl 160 + gpu_submit_ioctl 128 ≈ 3.0 KiB、その下の i915_command_submit → i915_command_render → drv_i915_render_dispatch → drv_i915_gfx_rec_dispatch（1632）→ drv_i915_gfx_resolve → drv_i915_gfx_rect_prepare（2176）→ i915_blit_compile → drv_i915_shader_compile_gen（4544）→ i915_compile_instruction（1392）→ … → i915_eu_reserve ≈ 12.4 KiB、kern_calloc → hal_pmem_alloc まで ≈ 12.9 KiB。合わせて約 15.9 KiB。
  - 割り込みは同じ stack に積まれる（IST は #DF と NMI だけ）。shader の compile の最中の割り込みで、入口と irq_handler（1264）と handler が加わり 16 KiB（16384）を越える。
  - 以前の kernel（q1-amd64k 10-12、q1-bug300 10-14）でも同じ道は 12.4〜12.6 KiB で、余裕が少しずつ減っていた（WS237・i915 の compiler の 10-14 の変更の頃に 12.9 KiB）。他にも exec・fs・ax211 の firmware の読み込み・fat の mount などが 10〜12 KiB（直接の呼び出しだけ）。
  - 静的な見積もりで、実機でどの thread が越えたかは見ていない（実機の確証は下の high water の行で取る）。

### 直し

- `src/hal/amd64/task.h`・`src/hal/arm64/task.h`: 作った task の kernel stack を 16 KiB → **32 KiB**（HAL の実装の定数。`include/hal/hal.h` は不変）。
- `src/hal/amd64/task.c`・`src/hal/arm64/task.c`: 
  - hal_task_create で stack を 0xa5 で埋める。
  - hal_task_context_switch で、去る task の stack の底の 128 bytes（guard）が埋めたままかを確かめ、壊れていれば `HAL_FATAL("amd64 kernel stack overflow")`（arm64 も同じ）。越えた後の無言の破壊を、その場の明示の停止に変える。
  - hal_task_destroy で guard を確かめ、stack が使った最も深い所を測って、起動からの最高を更新し、それが stack の半分（= 以前の 16 KiB）を越えたら `amd64: kernel stack high water <bytes> of 32768 bytes` を console に 1 行出す（最高の更新の時だけ）。
- `src/kern/thread.c`・`src/kern/process.c`（同じ道の潜在の二重の destroy）: thread_fork が失敗の時に task を destroy する道（prepare_created_thread と attach_thread の失敗）としない道（calloc・reserve_tid・EINVAL）が混ざり、呼んだ fork_process の `fail:` がもう一度 hal_task_destroy していた（prepare・attach の失敗で同じ stack を二度解放）。thread_fork は失敗の全部の道で task を destroy する（所有を常に受け取る）に揃え、fork_process は呼んだ直後に `task = NULL` にする。今回の fatal（thread_wait の道）とは別で、ENOMEM の時だけの潜在の不具合。
