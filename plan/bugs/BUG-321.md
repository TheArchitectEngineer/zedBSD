# BUG-321: Latitude 5330 で i915 の初期化の途中に kernel が止まる（`invalid kernel allocation free`、回帰）

- 状態: reproduced（ユーザー、5330 実機、2026-10-15）/ scheduled（P1、BUG-320 の後）
- 発見: 2026-10-15 ユーザー「5330でi915がフリーズするリグレッションを確認しました。P1でPiの修正が終わったらi915をP1で修正してください。」（画面の写真、chat。image の版は未確認＝ユーザーに聞く）
- 画面（写真から Q1 が読んだ）: login prompt の後に i915 の P3 の行が続く: `xc step=D0 DMC load queued (path=i915/adlp_dmc.bin, work_submitted=1)`、`i915: firmware /lib/firmware/i915/adlp_dmc.bin: loaded (79088 bytes)`、`i915: P3 modeset/flip workqueues: modeset=1 flip=1`、`i915: dmc worker: proceeding to load`、`i915: Forcing SAGV disable: mask 0x10b`、`i915: P3 intel_bw_init: obj=3 sagv_forced=1 qgv=0x4 psf=0x6 mask=0x10b pcode=0 sagv_status=1`、`i915: PCIID cached: ven=0x8086 dev=0x46a8 rev=0x0c subsys=1028:0b02 | live: …`、`i915: P3 intel_init_quirks: dev=0x46a8 subsys=1028:0b02 quirk_mask=0x0 hooks=0 …`。その後、複数の CPU の出力が混ざった行に `…rn/entry.c:269: invalid ker…`（= `src/kern/entry.c:269` の `HAL_FATAL("invalid kernel allocation free")`、kernel の大きな確保の free に確保されていない pointer が渡った）と `fault`・`call`・`ffffffff8…` の stack の番地（読み取れる断片: `ffffffff8901358`、`ffffffff80219…155c`、`80218f89`、`…8205368`）。
- 読み（未確認）: i915 の初期化（DMC の worker・modeset/flip の workqueue・bw_init・quirks の頃）か並行する仕事で、kernel_free の二重の解放か誤った pointer。最近の i915 の変更（WS237 の Gen9 の安全化 63d0532b0 は Gen9 だけの道、5330 は Gen12 の ADL-P）や他の main の変更との関係は未調査。
- 関連: WS237（Gen9、別の世代）、WS075（i915）、BUG-244（i915 の use-after-free、過去）。
- 2026-10-15 ユーザー:「テストしたカーネルは、さきほどSV7で動かしたものです。安全策が入る前のものです。」→ 同じ kernel が SV7（第 8 世代、Gen9.5）では display controller の制御で Keiland まで動き、5330（第 12 世代 ADL-P、Gen12）では i915 の初期化の途中で止まる。WS237 の安全化（63d0532b0）より前の main（Gen9 の既定 full 647d43d37 以降、ユーザーの build）。正確な commit は未確認（uname の版の文字列で分かる）。

## P1 の調べ（2026-10-15、host だけ）

- 写真の番地の断片を host にある候補の kernel（`build/amd64/vmunix` 02:40、`build/uat/sv7-gen9/vmunix` 01:11、`build/uat/main-amd64/vmunix`）で引くと 3 つとも同じ: `ffffffff8021955c` = hal_task_context_switch+0xc1、`ffffffff80218f89` = irq_handler+0x447、`ffffffff80205368` = overlay_pread_internal+0x19。`ffffffff8901358` は桁が欠け text（…8040f000 まで）の外。HAL の早い所なので版の差が出ず、kern_free を呼んだ関数は分からない。
- 写真の行が混ざる理由: amd64 の hal_fatal の `fatal: caller … stack …` の行は fatal_trace が番地ごとに hal_printf を呼んで作るので、その合間に他の CPU の log の record が入る。
- 読んだ範囲（5330 で PASS した T1-606 の頃の a25b73a3f → 647d43d37）: i915 の共有の道（i915.c の Gen9 の既定 on・D0 の suspend、irq.c、device.c の interim の display irq、display.c の bootfb の bind・fini・session_close、vbt.c の test VBT の削除、takeover.c）は Gen12 では graphics_ver==9 か display==NULL の判定で外れ、Gen12 の初期化に新しい確保・解放は見当たらない。DMC（dmc.c・firmware.c）は 10-05 以降不変。kern_free の大きな確保の header の探し方（4d3d7eddf、10-12）は T1-606 に含まれる。kernel の他の変更（buf.c BUG-307、vfs.c WS238 の /boot/efi、devfs BUG-304、shutdown、pcat の TSC）にも明らかな誤った解放は見当たらない。WS237 の安全化 63d0532b0 は Gen9 の file だけ。
- 診断の改善（commit 0270e7973・394d73682、branch agent/p1-bug321）: hal_fatal の報告を console の所有を握ったまま出す（他の CPU の出力に割られない）、kern_free の未知の pointer で `kern_free: <pointer> is not a kernel allocation (freed from <caller>)` を出す。
- 再開の条件: ユーザーの kernel の版（`uname -v` か build の場所）と fatal の行の読める写真、または診断の入った main の image での 5330 の再現（T、Q1 経由）。
- 2026-10-15 ユーザー（クリック）: 止まった kernel は `build/amd64/vmunix`（02:40、647d43d37 と 63d0532b0 の間）。P1 の調べ: 写真の番地の断片はその kernel でも HAL の早い所（hal_task_context_switch・irq_handler・overlay_pread_internal）に当たり、どこで free したかは分からない。i915 の Gen12 の道に新しい誤った解放は見当たらない。→ 診断の改善（f3b7d66e3 → main）: hal_fatal の 2 行を console の所有を握って出す（他の CPU の出力に割られない）、kern_free の不正の前に `kern_free: <pointer> is not a kernel allocation (freed from <caller>)`。再開の条件: この診断の入った main の amd64 image で 5330 を素に起動して再現し、`kern_free:` と `fatal:` の行の写真と、その image の vmunix を保存（ユーザーの試験の一覧）。
