# BUG-296: Notes がピンチ操作で拡大すると落ちる（5330）

- 状態: reproduced（ユーザーの 5330 の実機、2026-10-13） / resolved（2026-10-13 ユーザー「解決済みです。」、実機で確かめ済み）
- 発見: 2026-10-13 ユーザーの UAT「Notesアプリは、ピンチ操作で拡大すると落ちます。5330で確認。」
- 影響: 5330（i915）で Notes の頁を指で大きく拡大すると Notes が終わる（窓が消える）。
- 担当: P3（Q1 の依頼、2026-10-13）。Notes の source は `userland/desktop/notes/`（WS079・WS081 の p013 の指の操作）。

## 調べた事（2026-10-13 P3）

- 5330（10.0.30.3）は ping・SSH が届かず（ARP INCOMPLETE、電源が切れているか別の起動）、core・session.log・dmesg は読めなかった。原因は source の読みで決めた。5330 の log での裏付けは**未実施**。
- 原因（確度 高、source の読み）: i915 の executor の 1 つの allocation は最大 16 MiB（`src/drivers/gpu/i915/memory.h` の `I915_MAX_RESOURCE_BYTES`、連続した session object）。libvulkan は host-visible の memory（i915 の唯一の memory type）で `max_resource_bytes` を超える `vkAllocateMemory` を `VK_ERROR_OUT_OF_DEVICE_MEMORY` で断る（`userland/desktop/libvulkan/memory.c` の `native_bytes > max_resource_bytes`）。一方で heap は 1 GiB と報告され（`src/drivers/gpu/i915/render/instance.c`）、Vulkan 1.0 の app には 1 つの allocation の上限が見えない（`VK_KHR_maintenance3` は無い）。
- Notes は指の拡大が止まった時に頁の絵（色の image と stencil buffer。i915 の image.c は D24S8 を持たないので D32_SFLOAT_S8_UINT になると読んだ）をその倍率で作り直す（`notes_renderer_page`）。拡大の上限は 4 倍と 1 辺 4096 px だけで、5330 の窓（1920×1048、A4）では 4 倍で 2680×3792、色だけで約 40 MiB、stencil は約 51 MiB。16 MiB を超えて `vkAllocateMemory` が -2 を返し、Notes は「notes: vkAllocateMemory failed (-2)」で終わっていた（`main.c` の `app_draw`）。Venus（QEMU）と Pi 4 は上限 256 MiB なので出ない。
- 附随: `notes_renderer_page` は途中で失敗すると作りかけの image を残していた（次の frame で別の大きさを頼めば消えるが、失敗の後の描画が残りを見る余地があった）。

## 直し（2026-10-13 P3、agent/p3）

- `userland/desktop/notes/touch.c`・`touch.h`: `notes_touch_picture_limit(touch, pixels)` を足した。device が断った絵より小さい画素数を持ち、拡大の上限（`touch_zoom_max`）は 4 倍・1 辺 4096 px に加えて「頁の絵がその画素数に収まる倍率」で抑える（全頁より下げない）。上限は下げるだけ。`notes_touch_layout` の後半（倍率の抑え・scroll の端・置き場）を `touch_fit` に括り出して両方で使う（layout の動作は同じ）。
- `userland/desktop/notes/main.c`: 頁の絵を作る所を `app_picture` にした。`VK_ERROR_OUT_OF_DEVICE_MEMORY`・`OUT_OF_HOST_MEMORY` で断られたら、断られた絵の画素の 3/4 を上限に倍率を下げ、置き場を取り直して作り直す（最大 8 回、倍率が下げられない＝全頁なら前と同じく終わる）。断りは `NOTES PICTURE refused size=WxH error=E`、上限は `NOTES TOUCH picture limit pixels=N zoom=Z` の行で log に出る。絵の作り直しを place の log・`app->view` の前へ移し、下げた倍率がその frame の入力・描画の置き場になるようにした（stretch の判定も前へ移しただけで同じ）。
- `userland/desktop/notes/render.c`: `notes_renderer_page` の作る部分を `render_page_make` に分け、失敗したら作りかけを全部放す（絵の無い状態、texture の draw は飛ばされる）。
- 5330 での見込み: 最初の 4 倍への拡大は指を離した時に 4 回断られて約 2.25 倍に戻る（host の模型で 3.46 → 3.00 → 2.60 → 2.25）。以後のピンチは 2.25 倍で止まる。i915 の 16 MiB の上限が残る限り、5330 の Notes の拡大は約 2.25 倍まで（4 倍には戻らない）。

### 確かめた事（host と build だけ。QEMU・5330 の実機は未実施）

- 新しい host 試験 `plan/ws079/tests/host-notes-zoom-limit.c`（`sh plan/ws079/tests/run-notes-zoom-limit.sh`、plain・ASan・UBSan）: 本物の touch.c を 5330 の窓で動かし、i915 の executor の layout（image.c: 色は 4 byte の linear、D32S8 は Y tile の depth の面と次の page からの stencil の面）で 16 MiB を超える allocation を断る device の模型と、`app_picture` と同じ手順（3/4、8 回）で確かめる。遠いピンチが 4 倍・2680×3792 で device が断る（不具合の条件）→ 4 回の断りの後 2.252 倍・1508×2133 で作れる、頁は端の内、全頁へ戻した後の遠いピンチは 2.252 倍で止まり断り無し、大きい上限は何も変えない、全頁より下の上限は全頁のまま。結果 `run-notes-zoom-limit: PASS`（15 checks × 3）。変異（`touch_zoom_max` の画素数の抑えを外す）で 6 件 FAIL。
- 既存の `plan/ws081/tests/host-notestouch.c` は main の時点で古い（`notes_touch_take_tap` の第 4 引数、ws177-p012 で頁の tap も積む）ため build できない。scratch の写しで引数だけ足し、main の touch.c と直した touch.c の両方で ASan・UBSan で流した: どちらも同じ 3 件（tap の意味の変化）だけ FAIL、他の 49 件（ピンチの 4 倍・全頁・scroll・double tap・palm・指の書き込み）は PASS で、退行は無い。この試験の直しは WS081 の範囲（Q1 に報告）。
- build: amd64（`make -j16 ZEDBSD_CONFIG=config/current-uat.mk BUILD=build/amd64 build/amd64/bin/notes`）・rpi4（`make -j16 ZEDBSD_CONFIG=config/ci/config-rpi4.mk BUILD=build/arm64 build/arm64/bin/notes`）とも exit 0・warning 0（-Wall -Wextra -Werror）。`plan/tools/style-check.py` は直した 4 file・試験とも 0 件、`git diff --check` 問題なし。

### 実機（5330）で見る点

- Notes を最大化し、2 本の指で頁を大きく広げて離す: Notes が終わらず、頁が約 2.25 倍で鮮明に描き直される。session.log（runtime directory の `session.log`）に `NOTES PICTURE refused size=...` が数行と `NOTES TOUCH picture limit pixels=... zoom=2.2..` が出て、`notes: vkAllocateMemory failed` が無い。
- 続けてピンチで広げても約 2.25 倍で止まり、絵が鮮明（伸ばしたぼけが残らない）。全頁へ戻す・double tap・1 本指の scroll・ペンの書き込みが拡大の状態で正しい所に書ける。PDF の上に書く notebook（背景のある頁）でも同じく背景が出る。

### 残り（範囲外、Q1 へ）

- 根: i915 の 1 allocation 16 MiB（連続の session object）。拡大を 4 倍に戻すには i915 の GEM object を非連続にして上限を上げるか、libvulkan が `VK_KHR_maintenance3` の `maxMemoryAllocationSize` を報告して app が前もって知れるようにする（後者は Notes の「断られてから下げる」を不要にする）。どちらも kernel・libvulkan の別の WS。
- 同じ上限は 5330 の他の app（PDF Viewer・Image Viewer の拡大、4K の画面の swapchain など）にも当たりうる。未調査。
