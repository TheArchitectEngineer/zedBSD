# BUG-158: 操作中・放置中にフリーズし、電源ボタンの長押しが要る

Reproduction: reproduced（S1（2026-10-03、Latitude 5330、素の USB 起動、ユーザー、[結果](../ws133/s1-results.md)）、2 回）
Disposition: tracking（WS004（AX211）。原因は確定: 2026-10-04 P4 の節。修正 (1)(2)(4) を q684-i03（P3 gen9）で実装、q697 の console 10分確認 PASS、実機 UAT と残る SW_ERROR の解析待ち）

## 読みでの原因の候補（2026-10-03、q638、P1。実装していない）

読みで 1 つに絞れる証拠は無い。候補と S2 で分ける方法:

1. **AX211 の自動の探索の経路で kernel の thread が長く回り続ける。** WiFi 未接続の間、networkd は保存済みの network を探して scan・join を
   繰り返す。AX211 の driver には `sched_yield()` で待つ loop（`ax211_pci_operations_join_locked`、`ax211_pci_station_close_wait`、
   `intel-ax211-pci-mmio.c` の時間待ち）と、TX の timeout からの recovery（`ax211_pci_recovery_latch_locked` → `recovery_run_locked`、
   session stop・quarantine）がある。network の worker と利用者の thread は同じ優先度（`SCHED_PRIORITY_DEFAULT` 8）なので完全な飢餓には
   ならない見込みだが、recovery の繰り返し・interrupt の嵐・spinlock を持ったままの長い待ちがあれば画面ごと止まる。
2. **GPU（i915）の停止。** 画面と cursor が止まり入力も効かないように見える症状は、kernel が生きていても compositor の present が戻らなければ同じ。
   S1 ではバッテリーで GPU が遅くなった観察もある。WiFi との相関は偶然の可能性。
3. **入力の経路（xHCI・HID の M650 と PS/2 の touchpad）。** 1 回目は M650 を挿して放置、2 回目は M650 を抜いて touchpad で窓を移動中。両方とも
   pointer の入力に関わる。`ps2-8042.c` は controller_lock（spinlock、irqsave）を持ったまま input の emit をする所がある。

S2 で分ける方法: SSH をつないだまま（有線の USB LAN で）再現させ、(a) SSH が答えるか（kernel 全体か compositor だけか）、(b) 答えるなら
`ps`・zdesktop の log・kernel log（`intel-ax211: recovery`、`i915` の hang、input）を読む、(c) 答えなければ WiFi を off にして同じ放置で再現するか
（WiFi の経路の切り分け）。gdbstub が使えない実機なので、kernel log を serial や SSH で外へ逃がすのが要る。

## 解析（2026-10-04、P3 / q684-i01。読みだけ。実装していない）

対象: WiFi の policy が on で保存済みの profile が無い（または見えない）間に約 1 分で起きる「kernel のフリーズ」。実機の log は取れていないので、
code から (a) 症状の見え方、(b) WiFi 未接続の間だけ動く経路、(c) そこで kernel 全体を止め得る点、(d) 実機・QEMU で 1 つに絞る手順、を出した。

### 結論の要約（確度）

1. **確定（code）: graphical の session では kernel panic・`__builtin_trap`・`HAL_FATAL` が画面に出ず、「フリーズ」と見分けが付かない。**
   `__libc_panic`/`kern_fatal`（`src/kern/panic.c:50-80`）は `kern_text_reveal()` の後に全 CPU を止める（`hal_fatal`、`src/hal/amd64/lib.c:362-390`、
   `panic_in_progress` で他 CPU も `hlt`）。`kern_text_reveal` → `drv_pcat_text_reveal`（`src/drivers/platform/pcat/graphics/text.c:878-906`）は
   `text_ready` が立っている時だけ framebuffer を黒く塗って文字を描くが、i915 が display を取った時に `drv_pcat_text_suspend`（同 `:803-816`）が
   `text_ready = 0` にしており、`draw_cell_locked`（同 `:278`）も `!text_ready` で何も描かない。`__builtin_trap`（ud2）も `src/hal/amd64/int.c:395`
   「unhandled amd64 fault」→ `HAL_FATAL` で同じ。kernel log は ring（`src/kern/klog.c`、`klog_buffer`）だけで disk に残らない
   （`userland/base/syslogd` は socket の受信だけ。`messages.txt` に kernel の行が無いのはこのため）。debug console は `HAL_PCAT_DEBUGCON`
   の 0xe9 だけ（`src/kern/platform/pcat.c:398`）。→ 実機で「画面と pointer が止まり電源長押し」は、(i) panic/trap、(ii) IRQ 禁止のまま
   spinlock で止まる deadlock、(iii) MSI/IOAPIC を全部受ける BSP（`src/hal/amd64/irq.c:63-65, 711, 812`: MSI は BSP 宛て、I/O APIC も BSP）
   が止まる、のどれでも同じに見える。**まず (i) かどうかを分けるのが先**（下の「分ける手順」）。
2. **確定（code）: WiFi 未接続の間だけ、kernel の network worker（1 thread、`src/kern/net/core.c:547-620`、ue0 の入力・TCP timer・WLAN timer・
   device poll を全部ここで回す）が AX211 の scan を連続で回す。** networkd は AUTO_SEARCHING で 5 秒ごと（`NETWORKD_WLAN_RESCAN_SECONDS`、
   `userland/base/networkd/main.c:62`）に `run_automatic_work`（同 `:2388-2456`）→ `prepare_wlan_radio`（同 `:5985-6034`）が
   `wifi search-start` を出す（前の snapshot は `collect_profile_radios`（同 `:6691-6760`）が automatic な profile が無くても consume するので、
   毎回新しい scan になる）。kernel 側は `ioctl_scan`（`src/kern/net/wifi/wlan.c:4110-4240`）→ `station_scan_timer`（同 `:5179-5400`）が
   51 channel（`ax211_pci_runtime_scan_profile`、`src/drivers/wifi/intel-ax211/intel-ax211.c:3935-3970`、全部 `OFFLOADED_DWELL`）を 1 channel ずつ
   `scan_channel_start`（SCAN_REQ_UMAC を 1 本、同 `:7187-7280`）→ firmware の SCAN_COMPLETE → `scan_stop`（同 `:7282-7434`）で進める。
   その間の beacon/probe response は全部 RX_MPDU として host に届き `ax211_pci_rx_dispatch`（同 `:4255-4340`）→ `wlan_station_report_scan_frame`
   で処理する。接続中はこの経路（scan の command 列・大量の RX_MPDU・per-channel の stop）が動かない。これがユーザーの観察「未接続の時だけ」と合う。
3. **確定（code）、機能の不具合（フリーズそのものではない）: scan の command が 1 回でも timeout すると AX211 の command transaction は
   永久に poisoned になり、次の `scan_stop` が network worker の中で firmware を全停止し、WiFi off→on まで復帰しない。**
   `drv_intel_ax211_command_timeout_oldest`（`intel-ax211-command.c:519-566`）・`_cancel`（同 `:473-517`）は `poisoned = 1` にし、以後
   `command_submit`（同 `:139-260`）は `POISONED`。`scan_session_begin_channel`（`intel-ax211-scan-session.c:148-230`）は
   `pending_count != 0 || is_poisoned` で `SESSION_COMMAND`（EIO）。`ax211_radio_scan_stop` は TERMINAL の結果が COMMAND/TIMEOUT だと
   「expired or failed command」分岐（`intel-ax211.c:7420-7430`）で `ax211_pci_session_stop`（同 `:2939-3077`: assoc rollback → runtime stop
   （`intel-ax211-runtime-start.c:533-650`: interrupt_drain → transport quiesce → `drv_intel_ax211_mmio_stop`（`intel-ax211-mmio.c:357-434`）
   → DMA release）→ MSI-X の disestablish（`src/drivers/pci/pci.c:1587-1710` → `hal_irq_unregister_msi` → `irq_set_handler(NULL)` の
   drain spin、`src/hal/amd64/irq.c:174-254`）→ bus master off）を行う。stop の後は `runtime_active = 0` のまま net_device は open で
   station は `administrative_up` のままなので、`scan_channel_start`/`connect_start` は ENETDOWN（`intel-ax211.c:7216, 7483`）。
   `ops->open` は `open_count == 0` の時だけ（`src/kern/net/net-device.c:853-873`）なので、networkd の `up` では再開せず、down→up（WiFi
   off→on）だけが戻す。S1 の「Could not join (Network is down)」、今回の C5「off→on で 8 秒で再接続」、BUG-176 の「Network service is not…」
   はこの形と合う。timeout の源は firmware の ack 1 秒（`INTEL_AX211_SCAN_ACK_TIMEOUT_US`、`intel-ax211-scan.h:88`）・channel の watchdog 5 秒
   （同 `:89`）・common の 1 channel 1 秒（`WLAN_SCAN_OFFLOAD_DEADLINE_TICKS`、`include/kern/net/wlan.h:22`）・scan 全体 15 秒（同 `:16`）。
   **つまり実機では「scan の失敗 → network worker の中で firmware 全停止 → MSI-X 解除 → bus master off」という重い経路が、未接続の間に
   実際に通っている**（S1 の ENETDOWN が証拠）。フリーズの候補はこの経路に集中させる。
4. **フリーズの直接の原因は読みで 1 つに絞れていない（確度 中〜低の候補、下）。** 読んだ範囲で「IRQ を止めたまま待つ」「spinlock を持ったまま
   mutex/yield」「IRQ handler の loop」の形は見つからなかった: AX211 の MSI-X handler は latch と `net_device_schedule_poll` だけ
   （`intel-ax211.c:3144-3172`）、vector は automask（`transport.c:674-700` の rearm）、`interrupt_lock`/`registry_lock` の区間は短い、
   `station_scan_timer` は `station->lock` を外してから driver の op を呼ぶ、`sched_yield` の busy wait（`intel-ax211-pci-mmio.c:528-545`、
   `intel-ax211.c:2699-2745`）は mutex を外して回す、i8042 の handler は EOI の後に lock 内で emit するが IRQ 禁止のまま入れ子にはならない
   （`src/drivers/platform/pcat/ps2-8042.c:1104-1141`）。P1 の候補 1（driver の yield loop での飢餓）は 12 CPU の実機で画面と pointer を止める
   説明にならない。

### フリーズの候補（確度順。どれも「3. の stop 経路」か「panic が見えない」ことを前提にする）

- **H1（中）: 3. の stop/再開の経路のどこかで trap/HAL_FATAL が起き、1. により見えない。** 候補の trap: `mutex_check_owner`/再帰 lock
  （`src/kern/lock.c:300-305, 543-560`）、`ax211_pci_operation_leave_locked`（`intel-ax211.c:2693`）、`station_leave`/`station_control_leave`
  （`wlan.c:3690, 3760`）、`net_device_poll` の `poll_active`（`net-device.c:1265`）、`wlan_station_quiesce_end`（`wlan.c:1551`）。
  これらは stop・recovery・close の入れ子（`ax211_pci_close_locked` が lifecycle_lock を一度外して `station_close_wait` を回す、
  `recovery_run_locked` が lock を外して `report_link_loss` を呼ぶ）で順序が崩れた時に踏む。読みでは踏む具体の順序を特定できていない。
- **H2（中）: scan 中の firmware stop で `drv_intel_ax211_mmio_stop` の bus-master 停止（100 µs、timeout は警告扱い `intel-ax211-mmio.c:395-408`）
  が間に合わないまま `CSR_RESET SW_RESET` と DMA release（`runtime-start.c` の `drv_intel_ax211_dma_release`）に進み、firmware の残りの DMA
  が解放済みの page に書く → kernel の heap が壊れて後で任意の場所で落ちる（1. により見えない）。** 「約 1 分」が scan の失敗の頻度で決まるなら
  合う。runtime-start の順（interrupt_drain で bus master off → quiesce → mmio_stop → release）自体は正しいので確度は中。
- **H3（低〜中）: BSP が止まる。** MSI/IOAPIC は全部 BSP に来る。stop 経路の `irq_set_handler(NULL)` の drain（`irq.c:214-224`）は MSI では
  `hardware_mask` が no-op（同 `:973-979`）で、PCI 層の MSI-X table の mask（`pci.c:1668-1671`）が `CSR_RESET SW_RESET` の後の device に
  対する書き込みになる。device の reset で table の mask が効かない/`in_flight` が立ったまま（handler 側で `service_lock` 待ち）になると
  worker が永久に `pause` で回る。worker は BSP 以外でも回り得るので単独では全停止にならないが、`lifecycle_lock` を持ったまま止まるので
  networkd・`wlan_retirement_worker`・`net_shutdown_for_boot`（`core.c:262-290` の無限 retry）が巻き込まれる。
- **H4（低）: 大量の RX_MPDU（scan 中の beacon）に対する ring の処理。** `rx_refresh` の 12 bit mask と 512 entry の wrap、`rx_tail` の
  wrap、credit の 8 単位（`transport.c:792-1010`）は読みでは正しい。完了が順序通りに来ない時（buffer_id ≠ 完了位置）は STALE で tail が止まり
  scan が死ぬだけで、kernel は止まらない。
- 除外に近い: i915（接続中は起きないので相関が説明できない）、入力（同じ）、P1 候補 1 の飢餓。

### 実機・QEMU で 1 つに絞る手順（T1 / Q1 への依頼の形）

A. **QEMU + vfio passthrough で gdbstub（最優先、QEMU の debug 機能で直接見る）**。試験 host の 5330（10.0.30.3）で iwlwifi を blacklist
   （ticket 上の 2026-10-04 ユーザー指示）し、`plan/ws004/tests/run-intel-ax211-vfio-qemu.sh`（`AX211_VFIO_GDB_PORT=<port>`、
   できれば `AX211_VFIO_IGPU_BDF` で iGPU も渡して実機と同じ i915+AX211 の組）で UAT の image（保存 profile 無し、WiFi は起動で on）を起動し、
   desktop まで出たら **何もせず 5 分**待つ。止まったら host の `gdb vmunix -ex 'target remote :<port>'` で
   `info threads` / `thread apply all bt` / `x/20s klog_buffer`（`src/kern/klog.c:47`、512 KiB の ring。`klog_oldest`・`klog_used` も読む）、
   必要なら `plan/ws004/tests/ax211-gdb-threads.py` の `zthreads`（DWARF 付きの調査 build が要る）。判定:
   - 全 CPU が `hal_fatal`/`asm_hlt`（`panic_in_progress == 1`）→ panic。`klog_buffer` の末尾と `hal_fatal` の引数（file:line）が原因そのもの。
   - どれかの CPU が `spin_lock`/`service_lock`/`irq_set_handler` の `pause` で回る → deadlock。bt で保持者を読む。
   - kernel が生きている（worker が `sched_sleep_locked`、idle thread）→ 全停止ではなく display/入力の問題。i915・i8042 へ。
   monitor でも `info registers -a`（全 CPU の RIP）、`xp` で `klog_buffer` を読める（`-d guest_errors`）。
B. **実機で panic を見えるようにする最短の方法**: boot の行から `login=graphical` と `kmsg=quiet` を外し（`logo=` も）、text の console のまま
   `net wifi enable`（profile 無し）で 5 分放置。panic なら文字が残る（`text_ready` が落ちないので）。画面が凍るだけなら deadlock/停止側。
C. 原因が scan の失敗経路なら、同じ放置を「WiFi off」「有効 + 保存 profile あり（AP 在圏）」で比べると、3. の stop 経路が通る時だけ起きるはず。

### 直し方の案（P4 が実装できる形。原因が 1 つに決まる前でも価値のあるもの）

1. **panic を graphical でも見える・残るようにする（診断の前提、小さい）**
   - `kern_fatal`/`__libc_panic`（`src/kern/panic.c`）: `hal_fatal` の前に `kern_logf("fatal: %s:%d: %s")` で ring にも残す（今は `hal_printf` で
     console だけ）。gdb/`xp` で `klog_buffer` を読めば原因が分かる。
   - `drv_pcat_text_reveal`（`text.c:878-906`）: `text_hidden` の分岐の外でも、`text_surface == FRAMEBUFFER && text_pixels != NULL` なら
     `text_ready = 1` に戻してから `redraw_locked()` を呼ぶ（suspend で落とした `text_ready` を panic では無視する）。i915 が scanout を
     別の surface に向けている間は見えないので、i915 側に「panic 時に firmware の plane（`PLANE_SURF` = firmware framebuffer の GGTT）へ戻す」
     hook（`kern_text_ops` に `reveal` の前段として `display_panic_restore` を足し、i915 の takeover が登録）を足すのが本筋。
     HAL は触らない（text-display と i915 の中で済む）。
   - kernel log の永続化: `syslogd` に `sysctl` の kernel log（`src/kern/sysctl.c:455-475`、`dmesg` と同じ）を 2 秒ごとに差分で
     `/var/log/kernel.log` へ追記して `fsync` する loop を足す（ring の `klog_oldest`/`klog_used` 相当の offset を覚える）。電源長押しの後も
     直前の `intel-ax211:` の行が残る。
2. **AX211: scan の command の 1 回の timeout で永久に poisoned にせず、scan の失敗で firmware を全停止しない（3. の修正。フリーズの
   trigger を減らす＋「Network is down」の直し）**
   - `ax211_radio_scan_stop`（`intel-ax211.c:7420-7430`）: TERMINAL が COMMAND/TIMEOUT の時に `ax211_pci_session_stop` を呼ぶのをやめ、
     `ax211_pci_recovery_latch_locked(controller, ETIMEDOUT)` で poll の recovery に回す（recovery は `recovery_run_locked` が join を
     待ってから stop する既存の経路。直後に scan を再開できるよう、recovery の後に `session_stopped` を見て `ax211_net_open` 相当の
     再 open を行う「`ax211_pci_reopen_locked`」を足す）。
   - 復帰: `ax211_pci_session_stop` の後に runtime が無い状態で `scan_channel_start`/`connect_start` が ENETDOWN を返し続ける
     （`:7216, 7483`）のを、`session_stopped && !quarantined && station_attached` なら `ax211_net_open` と同じ再起動を行ってから進める形に
     する（`ax211_net_open` の本体を `ax211_pci_open_locked` に切り出して両方から呼ぶ）。これで WiFi off→on なしに戻る。
   - command transaction: timeout した slot を `abandoned` にして `poisoned` にするのは transport の slot を再利用できないからなので、
     poisoned になった時点で recovery に回す（上と同じ経路）。`drv_intel_ax211_command_after_device_reset`（`command.c:596`）で解く。
   - 試験（host）: `plan/ws004/tests/intel-ax211-core-test.c` に「SCAN_REQ の ack が来ない → timeout → recovery → 再 open → 次の scan が
     通る」の table 試験を足す（fake transport は既にある）。QEMU/実機は T1: vfio の passthrough で保存 profile 無しの放置 10 分（A の手順）、
     次に profile ありで off→on なしに自動接続が続くこと。
3. **H2 の防御（小さい）**: `drv_intel_ax211_mmio_stop` で `master_disable_timed_out` が立った時は `ax211_runtime_start_stop_and_release`
   で DMA を release せず `STOP_REQUIRED` に留める（retained DMA の経路は既にある: `runtime-start.c:533-600` の NO_DMA/STOP_REQUIRED）。
   release は次の close/open で「bus master off を確認した後」に行う。
4. **H3 の防御（小さい）**: `irq_set_handler(NULL)` の drain（`src/hal/amd64/irq.c:214-224`）は HAL なので変えない。driver 側で
   `ax211_pci_interrupt_drain` を呼ぶ前に `drv_intel_ax211_transport_disable_interrupts`（CSR の mask）と MSI-X table の mask を

### 割り込みの観点（2026-10-04 user のヒントに答える。P3、読みだけ）

user「未接続で放置した時の AX211 の割り込みで、ハンドルされていないもの・ハンドルで deadlock するものが無いか」。結論: **割り込みの嵐と
ISR と driver の lock の deadlock は、読みでは起こせない。** 根拠:

- **経路の形**: AX211 は MSI-X 1 本だけ（`ax211_pci_transport_bind`、`intel-ax211.c:3275-3290`: `DRV_PCI_IRQ_ALLOW_MSIX` で 1 本、MSI-X
  でなければ EIO。INTx の level の経路は無い）。ISR `ax211_pci_irq`（同 `:3144-3172`）は MMIO に触らず、`interrupt_lock`（irqsave）の中で
  `irq_latched = 1` と「`receive_enabled && runtime_active && net_device`」の判定だけをして、`net_device_schedule_poll`（`net-device.c:1195`、
  `device_lock` は IRQ 禁止の spin `:1464-1476`）→ `net_worker_wakeup`（`input_lock` irqsave）→ `sched_wakeup`（`cpu->lock` irqsave）で
  network worker を起こす。原因の ack・mask の操作は全部 worker の `ax211_pci_receive_event`（`intel-ax211.c:3352-3550`）で行う。
- **ack と mask**: IVAR は全 cause を vector 0 に `NON_AUTO_CLEAR` で割り付け（`transport.c:2027-2075`）、vector は automask
  （fire で自動 mask、`drv_intel_ax211_transport_interrupt_rearm`（同 `:674-700`）の `CSR_MSIX_AUTOMASK_ST_AD` 書きで戻す）。
  `receive_event` は毎回 `interrupt_claim`（同 `:631-672`）で FH/HW の cause を**読んだ値のまま W1C**（`ax211_ack_raw`、同 `:2138-2170`。
  enabled でない bit も含めて全部 clear）し、RX を 1 つ取り出し、replenish の後に rearm する。RX が無ければ STALE → rearm → poll では
  deadline が `now` なので TIMEOUT で抜ける（busy wait は boot/direct command の時だけ）。MSI-X は message なので cause を残しても level の
  嵐にはならず、clear し損ねても「次が来ない」側に倒れる。
- **未接続・idle の間に firmware が上げ得る cause ごと**（runtime の enabled 集合 `AX211_HW_SUPPORTED`/`AX211_FH_SUPPORTED`、`transport.c:91-120`）:
  - RX（scan の SCAN_COMPLETE/ITERATION、beacon・probe response の RX_MPDU、MISSED_BEACONS などの通知、command の response）: FH Q0/Q1 →
    `runtime_event_dispatch`（`intel-ax211.c:4415-4515`）。知らない group/opcode は末尾の `return 0` で捨てる（連結せず、無視して抜ける）。
    `(queue & 0x80) == 0` の response は `scan_command_dispatch`（同 `:4105-4180`）で phase が WAIT_*_ACK の時だけ消費、それ以外は `return 0`。
  - FH_ERROR・SW_ERROR(_V2)・HW_ERROR（firmware の assert/error）: `receive_event` が log を出して IO を返す（同 `:3410-3420`）→ poll が
    `recovery_latch` → `recovery_run_locked`（worker の文脈、`:2776-2885`）。rearm しないので vector は automask のまま → 嵐にならない。
  - RF_KILL・CT_KILL・WAKEUP・RESET_DONE・PERIODIC・SCD・FH_TX・HAP・ALIVE（runtime 中）: enabled だが専用の処理は無い。ack（W1C）されて
    RX 無しなら STALE → rearm で抜ける（無視して抜ける形）。RF-kill の状態は読まないので、rfkill が立つと command が timeout → 3. の poisoned
    → stop の経路に入るだけで kernel は止まらない。power save・D0i3 は driver が有効にしない（`ax211_pci_mac_power_configure` は接続時のみ）。
  - RX queue の満杯: host の credit（`rx_replenish`、`transport.c:919-1010`）が進まない間 firmware は RBD 不足で止まるだけ。host 側に
    cause は無い。
  - `runtime_active == 0`／`receive_enabled == 0` の間（session_stop の途中、open の前）の割り込み: ISR は latch だけで poll を起こさず、
    cause は unack のまま vector は automask → 以後来ない。次の open の `enable_firmware_interrupts`（`transport.c:445-545`）が `CSR_INT`
    と両 cause を clear して始める。HAL 側は consumer 無しの MSI 到着を EOI で捨てる（`irq.c:596-599`、`hardware_mask` は MSI では no-op）。
- **lock の取り合い**: ISR が取るのは `interrupt_lock`・`device_guard`・`input_lock`・`cpu->lock` で、全部 IRQ 禁止の spin。他の取り手も
  全部 irqsave（`interrupt_lock` の 11 か所は全て irqsave で短く、中で他の lock・MMIO・待ちをしない: `:2979, 3156, 3187, 3236, 3308, 3338,
  3386, 3617, 3657, 6693, 7074`）。`lifecycle_lock`（mutex）・`station->lock` は ISR では取らない。join（`:2699-2718`）・close_wait
  （`:2722-2745`）・recovery（`:2776`）・`irq_set_handler(NULL)` の drain（`irq.c:214-224`）は spinlock を持たずに回る（join は mutex を外して
  yield）。同じ CPU での再入は irqsave で塞がれる。→ ISR 起点の deadlock の形は無い。
- **残る穴（kernel を止めるものではないが直す価値がある）**: (a) ISR が cause を ack しないので、worker が長く走れない時（ue0 の大量入力、
  `NET_WORK_BUDGET` の yield）は RX の処理が遅れ、scan の 1 秒の ack 期限（`INTEL_AX211_SCAN_ACK_TIMEOUT_US`）を踏んで 3. の poisoned に入る。
  (b) RF-kill・CT-kill・PERIODIC を読まない。(c) `recovery_run_locked` の中の `session_stop` は worker を最長 5 秒（`AX211_LIFECYCLE_JOIN_TICKS`）
  ＋ mmio_stop の待ち（最大 150 ms 級）止めるので、その間 ue0 の受信・TCP timer も止まる（desktop の「一瞬固まる」には見えるが戻る）。

この観点からの直し方（P4 向け、2. の案に足す）: ISR で `interrupt_claim`（cause の読み出し＋W1C）まで行って `controller->pending_fh/hw_causes`
に OR で溜め、worker の `receive_event` はそれを消費する形にすると、ack の遅れが無くなり firmware 側の timeout（RX の待ち）に強くなる。
ISR から MMIO に触るので `interrupt_lock` の中で `transport.msix_configured && interrupts_enabled` を確かめ、stop の `interrupt_drain` は
`receive_enabled = 0` の後に `disable_interrupts`（mask）する今の順を保つ。RF_KILL の cause を見たら `kern_logf` と `recovery_latch(ENETDOWN)`。
これはフリーズの直接の修正ではないので、A/B の手順で原因が決まるまでは 1.（panic の可視化）と 2. を先にする。

### 静的解析（user 指示: 未接続で scan を続ける間の割り込み・event の経路。file:line）

Linux の iwlwifi（torvalds master `drivers/net/wireless/intel/iwlwifi/`、`pcie/gen1_2/trans.c`・`trans-gen2.c`・`rx.c`・`cfg/ax210.c`・`fw/init.c`）と突き合わせた。

- **C1（候補、中）: driver は AX211 を「非 integrated（discrete）」として扱う。** `ax211_pci_profile`（`src/drivers/wifi/intel-ax211/intel-ax211.c:2029-2047`）は `integrated` を 0 のままにし、`ax211_profile_valid`（`intel-ax211-mmio.c:799`）と transport（`intel-ax211-transport.c:1885`）は `integrated != 0` を拒否する。Linux は 8086:51f0 を `iwl_so_long_latency_mac_cfg`（`cfg/ax210.c:103-110`: `integrated = true`、`low_latency_xtal`、`xtal_latency 12000`、`ltr_delay 2500us`）とする。SOC_CONFIGURATION（`intel-ax211-runtime.h:109-110`: flags 0x0a、xtal 12000）は integrated の値で Linux と一致している。違うのは host 側の LTR: `intel-ax211-mmio.c:741-760`（UMAC 起動の直前、nic_lock 下）が `CSR_LTR_LONG_VAL_AD`（0x0d4）に 250 µs の bootstrap を書く（注記「non-integrated SO/GF bootstrap latency contract」）。Linux の `iwl_pcie_set_ltr`（`trans-gen2.c:420-460`）は integrated の AX210 ではこれを**書かず**、「ROM の bug は装置側にもあるが hardware security のため host から設定できない。IML 完了の割り込みを poll して CPU と装置を busy に保つ」と注記して `iwl_pcie_spin_for_iml` に回る。CNVi（PCH 内蔵）の LTR は PCH の電源管理（PMC）の入力なので、discrete 用の値を書くのは platform 側に影響し得る。hang との因果は未証明。
- **C2（候補、実機のみ）: MSI-X を使う間も INTx を disable していない。** `src/drivers/pci/pci.c:33` の `PCI_COMMAND_INTX_DISABLE` は定義だけで使用箇所が無い（`establish_msix` は command register に触れない）。Linux（`pci_intx_for_msi`）・OpenBSD は MSI/MSI-X 有効化で INTx disable を立てる。共有 INTx の dispatcher `pci_intx_dispatch`（`pci.c`）は line 上の全 handler を呼び、誰も claim しなくても `kern_irq_send_eoi` する。level の INTA# が張られたままなら IOAPIC の line（全部 BSP 宛て、`src/hal/amd64/irq.c`）が即座に再発火し BSP が割り込みの嵐で止まる＝画面・pointer・全部が止まる。実機では AX211 の INTA は IRQ16 で HDA・SMBus・thermal・TBT DMA と共有（ws004-p051 の記録）なので、HDA が IRQ16 を unmask している間に AX211 が INTx を上げれば嵐になる。装置が MSI-X 有効のまま INTx を上げる条件（firmware の RF-kill 等の legacy 割り込み）が要るので確度は中〜低。passthrough では host の Linux が物理の INTx を disable する（vfio の MSI-X 有効化で `pci_intx_for_msi`）ので host hang の説明にはならない。直すのは安全側: MSI/MSI-X を立てる時に INTX_DISABLE を立てる（PCI 層、HAL ではない）。
- **C3（P3 の H2/H3 と同じ経路、確度 中）: 未接続の scan 中に command が timeout すると stop（`ax211_pci_session_stop` → `ax211_runtime_start_stop_and_release`（`intel-ax211-runtime-start.c:533-660`）→ interrupt_drain → `drv_intel_ax211_transport_quiesce`（`intel-ax211-transport.c:1728-1830`: mask・ack、nic_lock 下で `RFH_RXF_DMA_CFG=0` と `RXF_DMA_IDLE` の 10 ms poll）→ `drv_intel_ax211_mmio_stop`（`intel-ax211-mmio.c:357-434`: MAC_ACCESS_REQ clear → link-power preamble → STOP_MASTER 100 µs（timeout は警告）→ INIT_DONE clear → SW_RESET 5 ms））が network worker の中で走る。** 列は Linux の `_iwl_trans_pcie_stop_device` → `iwl_pcie_apm_stop` → `iwl_pcie_apm_stop_master` → `iwl_trans_pcie_sw_reset`（`trans.c`）と同じ順。q590 run 4（`wifi wlan0 down`、同じ stop）で host は落ちていないので stop 単体は hang の原因ではない。違いは「scan で RX DMA が活発な最中に STOP_MASTER が間に合わないまま SW_RESET する」こと。
- **C4（読みでは成立、hang ではない）: RX ring の credit の向き。** `drv_intel_ax211_transport_rx_replenish`（`intel-ax211-transport.c:985-1000`）は `FRBDCB_WIDX` を「処理済み completion の tail − 1 を 8 で丸めた値」にする（初期 8 → 最初の completion で 0 → 8 → 16 …）。Linux（`iwl_pcie_rxmq_restock`/`iwl_pcie_rxq_inc_wr_ptr`、`rx.c`）は free RBD の write index を read index の**前**に置く。zedBSD の形は firmware の read index の 1〜8 後ろを追うので、firmware から見た空き数は modular に 504〜511 となり事実上 credit で止まらない。全 512 slot が常に有効な buffer を指し、host は `rx_published` の bitmap で再利用を検出するので壊れないが、設計意図（8 単位の credit）とは逆。hang の原因ではない見込み。
- **C5: 時間の決まる経路。** scan は 51 channel × 1 command（SCAN_REQ_UMAC、`ax211_radio_scan_channel_start`、`intel-ax211.c:7187-7280`）、channel ごとに firmware の SCAN_COMPLETE を待つ（common の 1 channel 1 s、全体 15 s、`include/kern/net/wlan.h:16,22`）。1 scan ≈ 5〜10 s、networkd は結果の 5 s 後に次の scan（`NETWORKD_WLAN_RESCAN_SECONDS`、`userland/base/networkd/main.c:62`）。走っている scan への `search-start` は何もしない（`ioctl_scan`、`src/kern/net/wifi/wlan.c:4110-4240`: RUNNING なら 0 を返す）ので abort の経路は通らない。1 分で 4〜6 scan ＝ command ring（256 slot、`intel-ax211-internal.h:95`、context info の CB size 5 = 256 で一致）が約 5 scan で 1 周、RX ring（512、CB size 9 で一致）が 2〜3 scan で 1 周する。ring の wrap の算術（`drv_intel_ax211_ring_reserve/complete`（`intel-ax211.c:1080-1127`）、`rx_tail`/`rx_head` の 12 bit mask（`transport.c:826-830`））は読みでは正しい。byte count table は command では更新しない（Linux の gen2 の host command も更新しないので同じ）。
- **MAC の sleep との関係**: DEVICE_POWER_CMD（0x77、`intel-ax211-runtime.c:237-243`）の payload は 0（power save 無効、CAM）なので firmware は idle でも MAC を眠らせない。PRPH の access（`transport.c:230,1792,2384`、`intel-ax211.c:3558-3597`、`4933-5136`）は全部 `drv_intel_ax211_mmio_nic_lock`（MAC_ACCESS_REQ → MAC_CLOCK_READY の poll、`intel-ax211-mmio.c:436-510`）の中。doorbell（`HBUS_TARG_WRPTR 0x460`）と `FRBDCB_WIDX_TRG`（0x1c80）は CSR で、Linux も shadow register（`cfg/ax210.c:40`、zedBSD は `CSR_MAC_SHADOW_REG_CTRL` を `transport.c:420-440` で有効化）があれば nic access 無しに書く。→「眠った MAC の register を読んで PCH ごと止まる」経路は読みでは無い。

### 原因の見立てと直し方（run 3 の時点の下書き。run 4〜6 で a) は除外、b) が確定。確定版は下の「原因（確定）」と「修正の計画」）

**原因（確度 高、passthrough の証拠）**: 未接続で scan を続けると約 1 分で poll の受信/配送が EIO を返し、最初の recovery が走る。その stop 列の
`ax211_pci_interrupt_drain` が、firmware が error 状態の AX211 に対して「MSI-X の cause mask → MSI-X table の mask → **MSI-X capability の enable を落とす**
（`drv_pci_device_disestablish_irq_checked`、`pci.c:1659-1705`）→ bus master off」を行い、この途中で platform（CNVi を含む PCH）が止まる。
Linux の iwlwifi は runtime の stop で MSI-X capability/table に触らず、INTx は MSI-X を立てた時に disable している。zedBSD は MSI-X を立てる時に
`PCI_COMMAND_INTX_DISABLE` を立てず（`pci.c:33`、使用箇所 0）、stop ごとに MSI-X を解放する。MSI-X を落とした瞬間、pending の cause は legacy の INTA#
に切り替わる（PCI の規則: MSI-X disable で INTx が有効なら INTx で通知）。実機では INTA#＝IRQ16（HDA・SMBus・thermal・TBT と共有）が level で張られ、
`pci_intx_dispatch`（`pci.c`）は誰も claim しなくても EOI するので BSP が割り込みの嵐で止まる（画面・pointer・全部）。passthrough では QEMU の
`vfio_msix_disable`（`hw/vfio/pci.c`）が `vfio_intx_enable` を呼び、host kernel が実機の INTx を有効にして host の IRQ16（host の HDA 等と共有）に
handler を付ける＝host 側でも「error 状態の CNVi の legacy 割り込み」を受ける形になる。host の hard hang の最終の機構（INTx の嵐か、MSI-X table/
capability への access の無応答か）は run 4 で絞る。

**直し方（P3 向け、HAL は触らない）**:
1. **PCI 層: MSI/MSI-X を establish する時に `PCI_COMMAND_INTX_DISABLE` を立て、INTx に戻す時だけ落とす**（`src/drivers/pci/pci.c` の `establish_msi`/
   `establish_msix`、`disestablish`）。Linux の `pci_intx_for_msi`、OpenBSD の `pci_intr_establish` と同じ。これだけで「MSI-X を落とした瞬間の INTA#」が
   止まる。実機・passthrough の両方に効く。
2. **AX211: runtime の stop（recovery・scan 失敗・close）で MSI-X を解放しない。** vector は attach（または最初の open）で 1 回だけ allocate/establish し、
   detach で解放する。stop では `drv_intel_ax211_transport_disable_interrupts`（cause の mask）と `ax211_pci_irq` の latch の無効化（`receive_enabled = 0`）
   だけにし、次の start で `drv_intel_ax211_transport_configure_msix`（IVAR と automask の再設定、Linux の `iwl_pcie_conf_msix_hw` に相当）を行う。
   `ax211_pci_interrupt_drain`（`intel-ax211.c`）から `drv_pci_device_disestablish_irq_checked`/`drv_pci_device_free_irqs` を外し、`ax211_pci_transport_bind`
   （`intel-ax211.c:3275-3340`）の allocate/establish を「未確立なら行う」に変える。`irq_established` を見る他の場所（`:3032, 3099, 3198, 3240, 3627`）を合わせる。
3. **順序を Linux に合わせる**: recovery の stop は「cause mask → RX/TX DMA の停止（quiesce）→ apm stop（STOP_MASTER）→ SW_RESET → INIT_DONE clear →
   IVAR 再設定 → cause mask の再 ack」。bus master off は firmware の DMA が止まった後（quiesce の後）に行う（今は drain の中で quiesce の前）。
4. **診断**: recovery の引き金（EIO の中身）を `kern_logf` に残すのは既にある（"runtime receive failed"/"runtime dispatch failed"/"fatal firmware interrupt"）。
   run 4 の klog で確かめる。
5. P3 の `7e2225a`（recovery → restart）は 2. の後なら安全に働く（restart は MSI-X を再確立せず configure_msix だけ）。

### 原因（確定。passthrough の証拠。実機は同じ経路なので同じ原因と判断するが、実機での確認は修正の後に T1/ユーザー）

未接続で scan を続ける間に firmware が assert（SW_ERROR）し、poll が recovery に入る。recovery の stop 列 `ax211_runtime_start_stop_and_release`
（`src/drivers/wifi/intel-ax211/intel-ax211-runtime-start.c:608-610`）は `interrupt_drain` → `transport_quiesce` → `mmio_stop` の順で、`interrupt_drain`
（`src/drivers/wifi/intel-ax211/intel-ax211.c:3605-3668`）の末尾（`:3652-3655`）が `drv_pci_device_set_bus_master(controller->device, false)` で
**PCI の Bus Master Enable を落とす。この時点では firmware の RX DMA（scan 中の beacon・probe response、RFH の RX ring の書き込み）がまだ動いている**
（RFH を止める `drv_intel_ax211_transport_quiesce` と STOP_MASTER を出す `drv_intel_ax211_mmio_stop` は drain の後）。AX211 の PCI function は PCH 内蔵の
CNVi（RCiEP、IOSF 経由）で、DMA 進行中に BME を落とすと PCH の fabric が止まり、OS に何も出さずに platform 全体が止まる（実機: 画面・pointer・全部。
passthrough: host の Linux ごと hard hang、journal に 1 行も残らない）。

証拠の整理:
- run 4・5: drain の中の access 単位の trace で、hang の直前の access は PCI_COMMAND への書き（bus master off）。MSI-X enable の clear（0x82）は 46〜53 ms 前に完了している。
- run 5: guest が `PCI_COMMAND_INTX_DISABLE` を立てていても同じ所で hang → legacy INTx の嵐（候補 a）は機構ではない。
- run 6: bus master off を外すだけで drain・quiesce・mmio_stop が通り、host も guest も生きている → 候補 b) が原因。
- 健全な `wifi wlan0 down`（2026-10-02 q590 run 4、scan 無し・DMA 無し）で同じ drain が通ったことと整合。
- Linux の iwlwifi は runtime の stop（`_iwl_trans_pcie_stop_device`）で bus master に触らず、`iwl_pcie_apm_stop_master`（CSR_RESET の STOP_MASTER、100 µs）→
  `iwl_trans_pcie_sw_reset` で device 側で DMA を止める。`pci_clear_master` は remove の時だけ。

  同じ device で先に立っている組み合わせは今は無い）。

### 残課題（この Phase では直さない）

## 修正の実装（2026-10-04、P3 generation9 / q684-i03）

計画の (1)・(2)・(4) を実装した。(3)（stop で MSI-X を解放しない）は計画どおり任意として入れていない（(1) の後は必須でない。必要なら別の Phase）。
記録の正本は [ws005-p032](../ws005/phase032/phase.md) の「q684-i03」節。

- (1) `ax211_pci_interrupt_drain` から bus master off を外し、boot ops に `bus_master_disable` を足した。runtime（`ax211_runtime_start_stop_and_release`）と
  boot（`ax211_boot_stop_and_release`）の stop は drain → quiesce → `mmio_stop`（STOP_MASTER・SW_RESET）が成功した**後**に bus master を落とし、その後に DMA を
  release する。drain・reset が失敗した時、master-disable の表示が timeout した最初の stop、bus master off が失敗した時は bus master と DMA を残して
  STOP_REQUIRED（次の cleanup で reset → bus master off → release）。session_stop の「coordinator の居ない IRQ の drain」（firmware が走っていない）だけは
  drain の後に bus master off を続ける（前と同じ）。quarantine・attach・detach・bind の巻き戻しの bus master off は firmware 未起動か reset 後なので変えていない。
- (4) recovery の stop の EIO: quiesce が `TRANSPORT_FAILED`（RX DMA は idle、command が残っていた）を返した時は stop の失敗にしない。reset の後の
  `command_after_device_reset` が残った command を捨てる。これで run 6 の「global stop deferred error=5」→ 遅れた close を経ずに `session_stopped` になり、
  7e2225a の restart（`ax211_pci_reopen_request_locked`）がすぐ働く。quiesce の他の失敗（RX DMA が idle にならない等）は従来どおり TRANSPORT を返す
  （reset が barrier なので DMA は解放する。解放の前に bus master は落ちている）。
- (2) PCI 層: `drv_pci_device_establish_irq` が MSI/MSI-X を立てた後に、INTx Disable が立っていなければ立て、cookie に印を残す。その cookie の
  disestablish（capability を戻した後）で戻す。前から立っていた bit には触らない。config の access の失敗は guard を飛ばすだけ（message の配送は
  この bit に依らない）。hda（MSI|INTX）・nvme（MSIX|MSI）・xhci（MSIX|MSI|INTX）・venus（MSIX|INTX）・AX211（MSIX）: INTx に fallback した時は立てないので
  挙動は変わらない。全部 1 vector で、disestablish は capability を establish 前の値に戻すので、複数 vector の時の数え方は要らない。
- 試験（host）: `run-intel-ax211-boot-test.sh`（`M` の順: reset の後・release の前、reset/drain 失敗では出ない、bus master off の失敗で DMA を残し cleanup で戻る）、
  新しい `run-intel-ax211-runtime-start-test.sh`（stop の table 7 行: 健全・command の残り・RX 非 idle・drain 失敗・reset 失敗・master-disable の timeout・
  bus master off の失敗）、`run-pci-msi-test.sh`（stale だった `pci-msi-test.c` を kern_* に直し、INTx Disable の立て・戻し・既存 bit の保持を assert）。全部 PASS。
- 未実施: QEMU の passthrough（計画 (5)、Q1 に依頼）、実機（UAT）。
