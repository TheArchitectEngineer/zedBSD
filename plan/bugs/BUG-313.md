# BUG-313: 13.3 インチの OLED の touch panel（USB、Wacom 056a:8191）が touch でなく mouse として動く

- 状態: reproduced（実機、ユーザー）/ scheduled（2026-10-15 Q1）
- 発見: 2026-10-15 ユーザー「このOLEDはタッチパネルがついてますが、マウスとして認識されてしまっているようです。タッチのファンクションを認識できるようにしてほしいです。」（Pi 4、image a9f0765）
- 観察（Pi 4 の dmesg、Q1 が ssh で）: `usb0: device 5 port 1 056a:8191`。interface 0: `usb-hid: … device-mode=2 report=33 bytes=3 error=0`（touch の mode に切り替えた）、`/dev/input/event4: HIDTOUCH` と `/dev/input/event5: HIDTOUCH Touchscreen`、report 54 byte。interface 1（vendor 0xff00、report 63 byte の in/out）は `refused error=3 stage=parse item=0x000f prefix=0x81`。interface 2 は `/dev/input/event6: HIDTOUCH`（report 7 byte、mouse の emulation の疑い）。
- 推測: Wacom の touch の device は、mouse の emulation の interface（2）と multi-touch の digitizer（0）を両方出す。compositor が event6（相対・絶対の mouse）を pointer として使っている、または event5 の touch が compositor に届いていない。
- 次: どの event が compositor に使われているか（KWL の input の log）、event5 の report の解読（contact の数・座標の範囲・tip switch）、event6 を touch の device として扱わない（同じ device に touchscreen があれば mouse の emulation を無視する）か、mode の切り替え。
- 関連: WS217（画面の回転と touch の座標）、USB の touch screen の対応。

## 原因と直し（P2、2026-10-15、未試験）

### 原因（source から）

- compositor（`userland/desktop/wayland/input.c` の `kwl_input_probe`）の振り分け:
  - multitouch protocol B の node（event5 `HIDTOUCH Touchscreen`）→ touch。
  - ABS_X・ABS_Y の node → 絶対の pointer。
- Windows 向けの touch screen は、Device Mode を設定する前に使う「mouse の emulation」を、次の 2 つの形で declare する。
  - touch screen の interface の中の collection（interface 0 の main device = event4 `HIDTOUCH`）。
  - 別の interface（interface 2 = event6 `HIDTOUCH`、7 byte の report）。
- kernel は両方を evdev の pointer として公開していた。compositor はそれを mouse として使い、touch が mouse の動き・click として届いた。

### 直し

- `src/drivers/usb/usb-hid.c`:
  - Device Mode の設定が成功した（または Device Mode の field が無い）touch screen の interface に `fingers` を立てる。
  - 公開の時に `usb_hid_publish_flags()` を使う。対象は main device が pointer（MOUSE・TABLET の kind）の interface。keyboard と pen は残す。
    - その interface が `fingers` なら `HID_INPUT_TOUCH_ONLY`（touch screen だけを公開。i2c-hid と同じ）。
    - 同じ USB の device の別の interface が `fingers` なら、新しい `HID_INPUT_EMULATION`（何も公開せず、report は捨てる）。
  - interface は番号の順に probe され、公開はその後なので、前の interface の screen は分かっている。
- `src/drivers/generic/hid-input.c`・`include/drivers/generic/hid-input.h`:
  - `HID_INPUT_EMULATION` を受けて、log に `hid-input: <path> is a touch screen's mouse emulation; it is not published` を出して成功を返す。
  - `drv_hid_input_touch_screen()`（touch の device が INPUT_PROP_DIRECT か）を足す。
- Device Mode の設定が失敗した device は、今までどおり全部を公開する。mouse として動き続ける。

## 2026-10-15 P2: T1-644 の後（2 回目、未試験）

T1-644（T2、`plan/agents/T2/results-20261015-bug313.md`、dmesg の全文は同じ所の `-pi.txt`）:

- interface 2 は `is a touch screen's mouse emulation; it is not published` で消えた（1 回目の直しは効いた）。
- interface 0 から `event4: HIDTOUCH` と `event5: HIDTOUCH Touchscreen` が今も並んで出る。
- ユーザー（kernel 5281755c7）:「OLEDはタッチですが、マルチタッチではないかも？」「OLEDはマルチタッチを実装してるけど、ドライバはシングルタッチで認識してるっぽいです。」1 本指の touch としては動く。

### 読み

- Pi の dmesg には interface 0 の descriptor が無い（dump は parse の失敗か `usbhid.dump=1` の時だけだった）。
  同じ Wacom の 5330 の内蔵の touch（056a:5131、BUG-267 の [touchscreen-if0.rdesc](BUG-267/touchscreen-if0.rdesc)）を host で今の parser に通した:
  - touch の report 0x0c: 1 report に Finger の collection 5 つと Contact Count・Scan Time。Contact Count Maximum（feature report 0x0c、8 bit）がある。
  - 同じ interface の vendor の collection（usage page 0xff11、input report 3、39 byte）が main device になる。kind は KEYBOARD（ABS_X も REL_X も pen も無いので）で、keyboard の key は無い。
- 1 回目の直しの `usb_hid_publish_flags()` は main device が MOUSE・TABLET の kind の時だけ見ていたので、この vendor の main device（event4）は残った。
- 8191 の report は 54 byte で、5131 と同じ形なら 1 byte（ID）+ 1（固定）+ 1（Contact Count）+ 7 × 7（finger）+ 2（Scan Time）= 54、1 report に 7 本。
  そうなら kernel の slot は 10（Contact Count があれば最小 10）で、multi-touch は kernel までは出ている見込み。ただし実機の descriptor で未確認。
- compositor（`userland/desktop/wayland/touch.c`）は 2 本目以降の指を wl_touch を持つ client にだけ渡す。wl_touch の無い client
  では最初の指が pointer の左 button になり、2 本指の scroll・pinch は compositor では作らない（「a pinch or a scroll stays theirs」）。
  kernel が 2 本以上を出していても、多くの app では single touch に見える。これは kernel の外（Keiland の WS079 の範囲）。

### 直し

- `src/drivers/usb/usb-hid.c`:
  - `usb_hid_publish_flags()`: 指を報告する touch screen の interface は、残りが pen か、keyboard の key（button でない EV_KEY）を持つ keyboard の時だけ
    main device を公開する。それ以外（今回の vendor の collection）は `HID_INPUT_TOUCH_ONLY`。pen はどこでも残す。
  - Contact Count Maximum を読む（`usb_hid_contact_maximum()`、GET_REPORT の feature）。Linux の hid-multitouch と同じく、その数まで slot を増やす
    （最大 16）。log: `usb-hid: usbB device D interface I contact-count-maximum=N report=R fingers-per-report=F error=E`。
  - touch screen・pad の interface の descriptor を常に log に出す（`usb-hid-rdesc:` の行、attach の時に 1 回）。
- `src/drivers/generic/hid-input.c`・`include/drivers/generic/hid-input.h`:
  - `drv_hid_input_has_keys()`、`drv_hid_input_touch_slots()` を足す。
  - 公開の時の log: `hid-input: <path> touch screen: N slots`、main device が何かを宣言していれば
    `hid-input: <path> main device published|dropped (the touch device alone): keys K, rel R, abs A, other O`。
  - 同時に触れた指の数が今までより増えた時に 1 行: `hid-input: <path> touch: N fingers down at once (of S slots)`（最大で slot の数の行数）。
    kernel が何本まで slot に出しているかが log で分かる。

### T への依頼（2 回目、Pi 4、kei@10.0.30.2、OLED の touch を挿したまま）

1. この commit を含む main の `config/ci/config-rpi4.mk` の vmunix に差し替えて reboot する（1 回目と同じ手順）。
2. `dmesg | grep -e usb-hid -e hid-input -e 'input/event'` の全行を取る。期待:
   - interface 0 の `usb-hid-rdesc:` の行（descriptor の全部）。報告にそのまま入れる（P2 が host の試験に起こす）。
   - `contact-count-maximum=N ... error=0`（N は 10 前後の見込み）。
   - `hid-input: usb0/port1/device5/interface0 touch screen: N slots`（N ≥ 2）。
   - `hid-input: ... main device dropped (the touch device alone): ...`。
   - `event` の node は interface 0 から `HIDTOUCH Touchscreen` の 1 つだけ（`HIDTOUCH` だけの名前の node が無い）。
3. ユーザーに画面を 1 本、2 本、3 本の指で同時に触ってもらい、その後でもう一度 `dmesg | grep 'fingers down at once'` を取る。
   - `2 fingers down at once` 以上が出れば、kernel は multi-touch を出している。
   - 1 本しか出なければ kernel の側の問題（descriptor と合わせて P2 が見る）。
4. 合格: 2 の event の node が 1 つ、3 で 2 本以上。2 本指の scroll・pinch が app で効かないのは、kernel が 2 本以上を出していれば compositor・app の側
   （wl_touch の無い client には最初の指だけが pointer として届く）で、この bug とは分けて Q1 に報告する。
5. 戻しは不要。
