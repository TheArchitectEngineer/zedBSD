# BUG-313: 13.3 インチの OLED の touch panel（USB、Wacom 056a:8191）が touch でなく mouse として動く

- 状態: reproduced（実機、ユーザー）/ scheduled（2026-10-15 Q1）
- 発見: 2026-10-15 ユーザー「このOLEDはタッチパネルがついてますが、マウスとして認識されてしまっているようです。タッチのファンクションを認識できるようにしてほしいです。」（Pi 4、image a9f0765）
- 観察（Pi 4 の dmesg、Q1 が ssh で）: `usb0: device 5 port 1 056a:8191`。interface 0: `usb-hid: … device-mode=2 report=33 bytes=3 error=0`（touch の mode に切り替えた）、`/dev/input/event4: HIDTOUCH` と `/dev/input/event5: HIDTOUCH Touchscreen`、report 54 byte。interface 1（vendor 0xff00、report 63 byte の in/out）は `refused error=3 stage=parse item=0x000f prefix=0x81`。interface 2 は `/dev/input/event6: HIDTOUCH`（report 7 byte、mouse の emulation の疑い）。
- 推測: Wacom の touch の device は、mouse の emulation の interface（2）と multi-touch の digitizer（0）を両方出す。compositor が event6（相対・絶対の mouse）を pointer として使っている、または event5 の touch が compositor に届いていない。
- 次: どの event が compositor に使われているか（KWL の input の log）、event5 の report の解読（contact の数・座標の範囲・tip switch）、event6 を touch の device として扱わない（同じ device に touchscreen があれば mouse の emulation を無視する）か、mode の切り替え。
- 関連: WS217（画面の回転と touch の座標）、USB の touch screen の対応。

## 原因と直し（P2、2026-10-15、未試験）

### 原因（source から）

- compositor（`userland/desktop/wayland/input.c` の `kwl_input_probe`）の振り分け:
  - multitouch protocol B の node（event5 `HIDTOUCH Touchscreen`）→ touch。
  - ABS_X・ABS_Y の node → 絶対の pointer。
- Windows 向けの touch screen は、Device Mode を設定する前に使う「mouse の emulation」を、次の 2 つの形で declare する。
  - touch screen の interface の中の collection（interface 0 の main device = event4 `HIDTOUCH`）。
  - 別の interface（interface 2 = event6 `HIDTOUCH`、7 byte の report）。
- kernel は両方を evdev の pointer として公開していた。compositor はそれを mouse として使い、touch が mouse の動き・click として届いた。

### 直し

- `src/drivers/usb/usb-hid.c`:
  - Device Mode の設定が成功した（または Device Mode の field が無い）touch screen の interface に `fingers` を立てる。
  - 公開の時に `usb_hid_publish_flags()` を使う。対象は main device が pointer（MOUSE・TABLET の kind）の interface。keyboard と pen は残す。
    - その interface が `fingers` なら `HID_INPUT_TOUCH_ONLY`（touch screen だけを公開。i2c-hid と同じ）。
    - 同じ USB の device の別の interface が `fingers` なら、新しい `HID_INPUT_EMULATION`（何も公開せず、report は捨てる）。
  - interface は番号の順に probe され、公開はその後なので、前の interface の screen は分かっている。
- `src/drivers/generic/hid-input.c`・`include/drivers/generic/hid-input.h`:
  - `HID_INPUT_EMULATION` を受けて、log に `hid-input: <path> is a touch screen's mouse emulation; it is not published` を出して成功を返す。
  - `drv_hid_input_touch_screen()`（touch の device が INPUT_PROP_DIRECT か）を足す。
- Device Mode の設定が失敗した device は、今までどおり全部を公開する。mouse として動き続ける。

### T1 への依頼（Pi 4、kei@10.0.30.2、OLED の touch を挿したまま）

1. この commit を含む main の `config/ci/config-rpi4.mk` の vmunix に差し替えて reboot する（BUG-311 と同じ手順）。
2. 次を取る。
   - `dmesg | grep -e usb-hid -e hid-input -e 'input/event'` の全行。期待は次の 3 つ。
     - interface 0 の `device-mode=2 ... error=0`。
     - `hid-input: usb0/port1/device5/interface2 is a touch screen's mouse emulation; it is not published`（番号は違ってよい）。
     - event の node は `HIDTOUCH Touchscreen` だけになり、`HIDTOUCH` の pointer の node が無い。
   - `ls /dev/input`。
3. desktop で compositor の log（`KWL INPUT device=... kind=touch abs=1` の行。無い時は compositor の起動の log）を取る。
4. 合格は次の 3 つ。指で触って確かめ、ユーザーにも頼む。
   - pointer の行が touch の device について出ない。
   - 指で icon を tap すると開く。
   - window を指で動かせる（mouse の cursor が指に付いて動くのではなく、touch として）。
