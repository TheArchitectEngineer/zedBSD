# BUG-202: 5330 の起動中の「scheduler queue underflow / idle thread sleeps」

Reproduction: reproduced（ユーザー、実機 5330、2026-10-05 夜、1 回）
Disposition: tracking（2026-10-06 Codex: idle上のdevice初期化を通常threadへ移す修正・amd64 build PASS、userの実機確認待ち）

## 観測

ユーザー「イメージを実機で起動したら、カーネルの起動の途中でpanicしたとみられますが、グラフィカルブートなのでわかりません。」QEMU の boot-test（T1-212 (2)）は PASS。

## 候補（未確認）

今日 main に入った kernel の変更で、QEMU では出ず実機で出る物: WS130 p002 の IPv6 の核（network の worker の 1 秒ごとの起床、装置の record）、WS168 p002 の syscall の入口の検め、WS161 の hidraw・smartcard、ACPI の BUG-195〜197 の直し、BUG-198 の overlay の inode の表。

## 2026-10-06 ユーザーの実機の結果（uat-0506b、Ctrl+Shift の safe boot）

画面の最後:
```
acpi: first SCI handled
fatal: src/kern/sched.c:1839: scheduler queue underflow
```

`queue_remove()` で count が 0 の queue から thread を外した（queue の整合が壊れた）。ACPI の SCI の thread（`src/drivers/acpi/acpi-kern.c` の event thread）が最初の SCI を処理した直後。QEMU では SCI が来ないか形が違うので出ない見込み。今日の SCI・GPE・EC・電源ボタンの変更（BUG-195〜197、WS049 p007、WS132 p008、WS052 p006 S0 idle）と、sched の変更（76282484 ほか 2026-10-05）が候補。Reproduction: reproduced（実機、safe boot で読めた）。

## 解析（2026-10-06）

解析だけ。source は変えていない（調査の build は scratchpad の `aml-host-lto` と `-fstack-usage` の object だけで、tree と共有の `build/` には何も残していない）。前回の「候補（未確認）」の WS130・WS168・WS161・BUG-198 は、画面の証拠（SCI の thread の最初の仕事の直後）で外れる。

### 確かめた事実

1. fatal は `src/kern/sched.c:1838-1839` の `queue_remove()`。thread の `sched.queue_kind`・`sched.priority`・`sched.cpu` が指す queue の `count` が 0 のときだけ出る。`queue_remove` は static で inline されるので、`hal_fatal`（`src/hal/amd64/lib.c:380`、file:line と message だけ、backtrace 無し）からは呼び手が分からない。呼び手は `pick_next_locked`（1873/1878）、`queue_remove_thread`（1852-1857; `sched_wakeup` 441・`sched_notify_task` 1101・`sched_exit_current` 814・`sched_unlink` 391・`take_stealable_locked` 2183・`sched_set_cpu` 1558）、tick の sleep の走査（890）のどれか。
2. sched.c の queue の出し入れは全部 `cpu->lock` の下で、入れる前に必ず外している（`sched_add` は `queue_kind == NONE` を検める 340-346、yield/preempt は RUNNING の thread だけ入れる、wake は sleep queue から外してから `wake_enqueue_locked`）。盗み（steal）は `hal_task_transfer` の `run_cpu >= 0 → BUSY`（`src/hal/amd64/task.c:796-806`、`run_cpu` は切替の前に立ち 576-580、次の context の `amd64_task_finish_switch` で下りる）で、まだ走っている thread を他の CPU が持って行けない。`sched_set_cpu`・`sched_unlink` は sched.c の外に呼び手が無い。通常の thread について、queue を壊す経路は見つからなかった。
3. **構造上の穴が 1 つ**: `switch_without_enqueue()`（1995-2007）は、current が `cpu->idle` で走れる thread が無いと、idle を RUNNING に戻して**切り替えずに返る**。だから idle thread が `sched_sleep`（1144）・`sched_sleep_locked`（1184）・`sched_sleep_locked_interruptible`（1223）・`sched_sleep_locked_notify`（1278）—— つまり `waitq_sleep`・`mutex_lock`・`kern_usleep_range`（`src/kern/clock.c:694-744`、「spin」ではなく tick まで `waitq_sleep` で眠る）—— のどれかに入ると、deadline 付きなら `cpu->sleep` に繋がれたまま返る。次に眠ると `queue_append` が同じ thread を二重に繋ぎ（`prev = next = 自分`、count +1）、tick の `queue_remove(&cpu->sleep)`（890）は prev/next が非 NULL なので head/tail を直せず stale のまま残し、idle を `woken[]` に入れる。その後 `pick_next_locked` が stale な head を外すと `count == 0` で**この fatal がそのまま出る**。`sched_wait_task` には idle の guard がある（1032-1035）が、sleep の 4 つの入口には無い。idle thread が実行するのは idle loop・`kern_sleep_idle`・steal と、その CPU で起きた割り込み/IPI の handler だけ。
4. SCI の経路の割り込み文脈で眠る物は見つからなかった: `sci_interrupt`（`src/drivers/acpi/acpi-kern.c:703-733`）は記録・mask・`waitq_wake_all` だけ、`intel-gpio` の `irq_interrupt`（`src/drivers/gpio/intel-gpio.c:558`）は pad の handler = `i2c-hid` の `line_interrupt`（wake だけ）、PCI の dispatch（xhci/nvme/hda/ax211）、klog の mirror（`src/kern/klog.c:364-391`、素の spin）、text console の backend（`src/drivers/platform/pcat/graphics/text.c`、`sched_sleep` は splash の kthread 1017 だけ）、`poll_notify`・`kern_random_tick`（wake だけ）。
5. 5330 では **SCI の経路が初めて動いた**: uat-0505c（ee2f8c7f）は DSDT が読めず `drv_acpi_attach` が `start_events()` の前に返っていた（`acpi-kern.c:202-207`、当時は `start_fixed_hardware` も無い）ので、SCI の handler も event thread も無かった。0505g 以降は 1eff1521 で namespace が揃い、最初の SCI で実機の `_Lxx`・EC・`_Q66` が初めて走る。QEMU では EC（PNP0C09）が無く、GPE の method も自発的には来ないので、この経路は boot-test で踏まれない。
6. 5330 の table（`plan/ws049/tests/latitude5330/`、iasl で読んだ）: `\_GPE` に `_L61`・`_L62`・`_L66`・`_L69`・`_L6F`（GPIO）・`_L72`・`_L73`・条件付き `_L6D`、SSDT に `_L18`（EC の event を `ECG7/ECG3/EV3` で処理）。EC の `_GPE` は eSPI なら 0x6E（eSPI でなければ **0** を返す）。EC の query method は `_Q66` 1 つ。EC の読み書きは `wait_status`（`src/drivers/acpi/acpi-ec.c:698-726`）→ `drv_acpi_os_stall(10)`（`acpi-kern.c:349-361`、comment は「spin」）→ `kern_usleep_range` → **1 byte ごとに tick 単位の sleep**。最初の SCI の時点で、event thread E は interpreter の mutex を boot_worker B（`drv_acpi_ec_attach`/`drv_acpi_power_attach` の最中）と初めて取り合い、power thread P は deadline 付きで sleep queue に居る。sleep queue と tick の wake、他 CPU からの `sched_wakeup`、idle CPU の steal がこの機械で初めて密に動く。
7. stack の見立て: kernel の thread の stack は 16 KiB（`AMD64_SYS_STACK_SIZE`、heap に first-fit で `struct thread` → `struct amd64_task` → stack の順、guard page 無し）。AML の予算は 1eff1521 で 8 → 10 KiB。kernel と同じ flag の LTO の host harness（scratchpad に build）で 5330 の table を読み、`--ec-query 66@6E`・`--gpe 0x18/0x69/0x6F/0x61/0x66/0x72`・`--power-button` の各経路の `stack deepest` は**全部 7184 byte**で、load + `_INI`（SCI の前に無事に走った）と同じ。ACPI の最大の frame は 584 byte（`-fstack-usage`）。最初の SCI の AML が stack を溢れさせた線は薄い（割り込みの frame を載せても 11 KiB 程度）。

### 最有力の原因（機構）と、まだ無い trigger

症状と一対一で合うのは事実 3 の機構（idle thread が sleep の入口に入る → `cpu->sleep` の二重連結 → `woken[]` の stale な head → `pick_next_locked` で underflow）。ただし、最初の SCI の経路からそこへ至る具体的な呼び出し（割り込み文脈で `kern_usleep_range`/`sched_sleep`/`mutex_lock` に入る物）は見つけていない。したがって「原因は X 行」とは断定できない。順位は次のとおり。

1. **idle thread の sleep**（上記）。trigger 未特定。sched.c:1995-2007 と sleep の入口に guard が無いこと自体は欠陥。
2. **memory の破壊**（`struct thread` の `sched`、または `scheduler_cpus` の `count`）: 実機の値で初めて走る interpreter/EC の経路（`_Q66`・`_L6F`・EC の region）が heap の隣を壊す。stack の溢れは事実 7 で薄い。heap は first-fit で ACPI の object が古い穴に入り得るので、thread の struct と隣り合う可能性は否定できない。
3. **sleep queue と tick/wake/steal の競合**: `sched_sleep_locked` の unlock と `switch_without_enqueue` の間に他 CPU が wake すると、走っている thread が自分の `woken[]` に入り、自分で自分を取り出す（整合する）。steal は `run_cpu` で守られる。読んだ限り整合しているので下位。
4. mutex（`src/kern/lock.c:291-395`、3 状態の futex 型）、klog、console、poll、random: 読んで問題無し。

### 修正の方針（未実装）

原因が 1 行に絞れていないので、まず**次の UAT で原因が読める build**（診断の変更、動作は変えない）を提案する。

- `src/kern/sched.c`: `sched_sleep`・`sched_sleep_locked`・`sched_sleep_locked_interruptible`・`sched_sleep_locked_notify` の入口に、`sched_wait_task`（1032-1035）と同じ `(thread->flags & THREAD_FLAG_IDLE) != 0 → HAL_FATAL("idle thread sleeps")` を足す。候補 1 なら fatal の場所がそこへ移り、trigger が分かる。
- `queue_remove`（1838）の fatal の前に、queue の種類（run/woken/sleep と priority）、CPU、`count`、thread の tid・state・flags・`queue_kind` を `kern_logf` で出す（inline された呼び手を見分ける）。`queue_remove_thread` と `pick_next_locked` と tick の走査で別の message にしてもよい。
- `src/hal/amd64/lib.c` の `hal_fatal`: `__builtin_return_address(0..3)` か frame pointer の backtrace を 1 行出す（vmunix は strip されていないので address から symbol が引ける）。
- 候補 2 の切り分けに、fatal 時に `kern_heap_validate()`（`src/kern/heap.c:316`）の結果を 1 行出す。

機能の修正としては、原因が確定した後に当てる。候補 1 なら「割り込み文脈/idle で眠る呼び出し」を thread へ移す（wake だけにする）のが直し。これと独立に、`drv_acpi_os_stall` は ACPI の Stall の意味（100 µs 以下、CPU を手放さない）どおり `kern_rtc_read_counter` で spin する実装に戻すべきで、EC の 1 byte ごとの tick sleep（Global Lock と interpreter の mutex を握ったまま）も無くなる。これは候補 1〜3 のどれでも無害な改善だが、BUG-202 の直しだと主張しない。

### 修正の確認

- 実機 5330: 診断 build の image を safe boot で起動し、fatal の直前の行（queue の種類・thread・backtrace）を写真で読む。ここで呼び手が確定する。
- QEMU（gdbstub）: EC は無いが SCI → event thread → `drv_acpi_events_process` の経路は踏める。`-smp 4 -S -gdb tcp::1234` で起動し `break hal_fatal`。QMP `system_powerdown` で PWRBTN_STS の固定事象（`power_button` → `kern_sleep_note_wake` → `kern_system_event_post`）、q35 の ACPI PCI hotplug（`device_add e1000`/`device_del`）で `\_GPE._E01` の method と Notify を event thread に走らせる。fatal が出れば `bt` と `info registers`、出なければ「QEMU では再現せず」と記録する（EC の `kern_usleep_range` の経路は QEMU では再現できない）。
- 直しの後は同じ手順で、5330 の boot-test（`plan/tools/boot-test.sh`）で login prompt まで、電源ボタン・蓋・AC の抜き差しで SCI を数回起こしても fatal が出ないことを確かめる。

### まだ確かめていない仮説

- `queue_remove` の実際の呼び手（上の診断で分かる）。
- 5330 で最初に来た SCI の種類（GPE 番号/固定事象）。`process_gpe` は失敗時しか log を出さない。
- AX211 と HD Audio の割り込み handler の本体（眠る呼び出しが無いか未読）。graphical boot の `kern_text_progress` の backend。
- EC の `_GPE` が eSPI でないとき 0 を返す件（GPE 0 を EC の handler が取る）。この fatal とは別の機能の問題の可能性。
- heap の隣接（`struct thread` の `sched` の前後に ACPI の object が来るか）は、fatal 時の `kern_heap_validate` で見る。

## 実装（2026-10-06 P1、agent/p1。Q1 の依頼: 解析の 1〜3 を最小の変更で）

- **(a) ACPI の Stall を spin に**（`src/drivers/acpi/acpi-kern.c` の `drv_acpi_os_stall`）: `kern_rtc_read_counter` で要求の µs（切り上げ、最大 1 秒）だけ CPU を保ったまま待つ。
  これまでは `kern_usleep_range` で 1 回ごとに次の tick まで眠り、EC の 1 byte ごと（Global Lock と interpreter の mutex を握ったまま）に tick の sleep が入っていた。
  EC の待ちの上限（`EC_POLLS` 50000 回 × 10 µs）は意図どおり約 0.5 s になる（これまでは tick 単位で実際には数分）。
- **(b) idle thread は眠らない**: `sched_sleep`・`sched_sleep_locked`・`sched_sleep_locked_interruptible`・`sched_sleep_locked_notify` の入口で、
  current が idle thread なら `sched: the idle thread of CPU N entered <入口> from <呼び手の address>` を出して `HAL_FATAL("idle thread sleeps")`。
  sleep queue の二重の連結に進む前に止め、呼び手を名指す。最初の SCI の周りで idle thread の上で眠る呼び出し（trigger）は今回も特定できなかった
  （IRQ の handler の hda・ax211・xhci・nvme・intel-gpio・SCI は眠る呼び出しを読んだ範囲で持たない）ので、根の直しではなく guard。
- **診断**: `queue_remove` を inline しない（呼び手の address が意味を持つ）。count 0 の時、fatal の前に
  `sched: underflow queue=<run|woken|sleep|foreign>[priority] cpu= count= head= tail= thread= tid= state= flags= kind= priority= on=<今の CPU> caller=<address>` を出す。
  `src/hal/amd64/lib.c` の `hal_fatal` は fatal の行の次に `fatal: caller <address> stack <address>…` を 1 行出す（hal_fatal の呼び手、
  stack pointer からその page の終わりまでの word のうち kernel の text を指す物を最大 12 個。frame pointer が無いので frame を辿らず、写像が確かな page の中だけを読む）。
  address は strip されていない vmunix で `addr2line -f -e vmunix <address>` で関数名になる。hal.h は変えていない。
- **未実施（3）**: fatal の時の `kern_heap_validate`。plain の validate は検めていない link を辿る（壊れた heap で fault・無限の walk になり得て、fatal の行と trace を失う）。
  bounded な `kern_heap_trace_validate` は heap trace の build（`KERN_KERNEL_HEAP_TRACE`）だけにある。候補 2（memory の破壊）を見るなら heap trace の build の image を別に作る。
- 確認: release の config（`config/release/config-amd64-beta1.mk`）の kernel（`build/p1-rel/vmunix`）の build、warning 0。sched の host 試験は無い。QEMU・実機は未実施。

## 写真からの原因確定と機能修正（2026-10-06、Codex）

userの依頼: ACPI/modern sleep追加後の起動停止を機能面だけで修正し、agentはbuildまで、実機試験はuserが行う。今回の写真は`idle thread sleeps`、`sched.c:1932`とcaller/stackを示す。[q779-i01](../agents/codex-bug202/queue.md)・[ws073-p055](../ws073/phase055/phase.md)に範囲と結果を記録する。

### 今回の証拠で訂正する点

以前の解析でACPI attachをboot_worker上とした説明は誤り。修正前の`kernel_entry`はCPU0のidle/bootstrap threadのまま`kern_platform_init`を呼び、PCI scan/attachとACPI attachを実行していた。`kernel_main`が作る通常のboot_workerはその後のVFS初期化からだった。写真で捕まったsleepはSCI割込みhandlerではなく、このPCI attach中のLPSS電源復帰待ちである。

写真のアドレスを、mainにある`build/uat-0506c/vmunix`（SHA256 `1ec7a53f08acb1aab3f5be140293e1bb43442f800499b20ba9e39bea96f49d94`）のsymbolと逆アセンブルに照合した。

| 写真のPC | ELFとの対応 |
| --- | --- |
| `ffffffff8033e685` / `ffffffff8033e6ed` | sched_sleep_locked内のidle拒否 |
| `ffffffff80338c80` | waitq_sleep |
| `ffffffff80335f94` | kern_usleep_rangeのwaitq_sleep call直後 |
| `ffffffff8032dabc` | lpss_attachのkern_usleep_range call直後。call直前の引数は`0x2710`（10000µs） |
| `ffffffff802499f4` | drv_pci_device_probe |

stackの列は本物のframe unwindではなくkernel textを指すwordの収集なので、他の全PCを呼出し列だとは扱わない。上のcall直後PCと命令、およびsourceの`lpss_power_on()`（`src/drivers/i2c/lpss-i2c.c:371`）が一致する。PMCSRがD1〜D3ならD0へ書き、10ms待つ。LPSSの追加に伴うこの経路はgit blameで`a0596c510`（2026-10-05）。QEMUでD0またはLPSS無しなら分岐を踏まない。

### 修正

Source WIP **`801393ad`**、base **`acbb7e4a`**、branch `codex/fix-bug202-boot-worker`、worktree `/tmp/zedbsd-bug202-codex`。

- `src/kern/entry.c`: platform discovery/refreshを外し、IRQを有効にしてkernel_mainへ渡す。core、secondary CPU、reaper、networkの初期化順は維持。
- `src/kern/main.c`: 既存boot_workerがPCI→ACPI→USB/WLAN refresh→i915 runtime→VFS→initの順を実行する。LPSSの10ms待ち、AML Sleep、mutex待ちは通常のschedulable threadで行う。boot device tableはstatic寿命のままmain.cに移した。
- `include/kern/kernel.h`: 唯一の呼び手に合わせkernel_mainの引数をhandoffだけにした。HAL APIの変更は無い。
- platform固有の拡張handoffは元のpointerをworkerの引数としてdiscoveryまで渡し、後続VFS/永続metadataには従来の共通snapshotを使う。PC-98の低位mappingとRPi4/sun4u/x68kの拡張部を失わない。
- idle sleep guardは残る。待ちを握り潰す変更や、LPSS/ACPI/modern standbyを無効にする変更はない。

機能レビューでは別CPUでのworker開始、IRQ/tick進行、handoff/device tableの寿命、reclaimの同期初期化と起動順を確認した。全文C規約の変更範囲のreview、clang-format19の編集範囲への適用、style-diffの変更行findings 0、git diff --check PASS。
