# BUG-346: sshd の listener が子の sshd-session [priv] を刈らずに残し、MaxStartups で新しい SSH の接続が banner の前に落ちる

- 状態: reproduced / resolved（2026-10-27 05:10 Q1: 7bdee4894、merge ae266e6fe。原因は kernel の unix の datagram の受信が送り手の待ちを起こさない事。VF2 で直す前 login 10 回・Timeout 16 回、直した後 141 回・0 回。10.0.10.3 の実機での再確認は未実施）
- 発見: 2026-10-27 04:08 WS291 p003（P2）。amdrdna の非同期の submit の試作 kernel で mview の game mode の FIFO を流した時、SSH の新しい接続が止まり、最後は banner で timeout。ping は返り、kernel・userland は動いていた（USB の FAT に書いた watcher の 333 回の記録）。
- 期待: sshd の listener が、終わった session の子（sshd-session [priv]、その子 sshd-auth）を待って刈り、新しい接続を受け続ける。
- 観測: listener が子の `sshd-session [priv]` を刈らずに残す（その子の sshd-auth は zombie）。数が MaxStartups（10）に近づくと新しい接続が落ちる。同期の kernel の回でも「[priv] が残る」は 2 個出て約 2 分後に刈られた。非同期の回は刈られずに残り続けた。GPU の driver の不具合の証拠は無い（P2 の code の読みで、GPU と無関係な process・signal・poll の起こしの側の見込み、負荷で起き方が変わる）。
- 証拠: P2 の worktree の build/ws291/measure/p003-repro/（watch/・fifo/）。
- 回避: WS291 の measure.sh は SSH の接続を 1 本に多重化（ControlMaster）。watchdog は 2026-10-27 04:13 ユーザー「watchdogは不要です。」でやめた。

## 再調査の条件

- 原因の候補: SIGCHLD の配送、waitpid・poll の起こし、sshd の privsep の子の終わり方。GPU に依らないので、SwitchBot で電源を入れ直せる VF2 か QEMU で再現を試すのがよい。
- 2026-10-27 04:10 ユーザー「VF2を使ってSSHの問題を修正してください。P1が空いていますか？AMD RDNAマシンでは、SSHの問題を回避しつつ、元の作業を継続してください。」 → P1 が VF2 で修正（q1607）。

## 原因（2026-10-27 P1、q1607-i01、VF2）

kernel の unix の datagram の受信が、待ち行列から datagram を取り出した時に送り手を起こしていなかった。
`src/kern/net/unix-socket.c` の `unix_socket_receive_commit()` は stream の時だけ `receive_space_waitq` を起こし、
datagram の時は起こさない（一般の socket の取り出し `socket.c` の受信は起こす）。datagram の待ち行列は 8 通
（`SOCKET_RECEIVE_MESSAGES_MAX`）で、満杯の間に `send()` した送り手は `socket_enqueue_packet_wait()` で
`receive_space_waitq` に寝る。受信側が読んで空きができても誰も起こさないので、送り手は signal が来るまで寝たまま。

sshd での現れ方: syslog() は `/run/log`（syslogd の datagram の socket）への blocking の `send()`。syslogd が 8 通遅れると
（負荷の高い時、10.0.10.3 では syslogd が CPU を食っていた）、log を書く process が寝る。

- `sshd-session [priv]`（monitor）は sshd-auth の log を syslog に流す所で寝て、sshd-auth の終わり（EOF）を読まない。
  LoginGraceTime（120 秒）の SIGALRM でやっと終わる（観測の「[priv] が約 2 分残る」「sshd-auth は zombie」「sshd-auth の log が出ない」）。
- listener は `child_reap` の log（"Timeout before authentication"、PerSourcePenalties の log）を SIGCHLD・SIGHUP・SIGTERM を
  block した区間で書くので、寝たら起こすものが無く永久に止まる。accept も reap もしなくなる（観測の「[priv] の zombie が刈られない」
  「startups の数が変わらない」「新しい接続が banner で timeout」）。
- `[postauth]` の monitor も "Disconnected" などの log で寝て、client が去った後も残る（観測の「[postauth] が残る」）。

GPU・SIGCHLD の配送・waitpid・ppoll は無関係（読んで確かめた範囲で POSIX どおり）。

## 修正（7bdee4894）

- `unix_socket_receive_commit()` で datagram の時も `receive_space_waitq` を起こす（stream と同じ）。
- guest 試験: `userland/tests/posix-r2.c` の `test_unix_dgram_space_wakeup()`（`unix-dgram-space-wake`）。datagram の
  socketpair の待ち行列を満たし、子が blocking の send で寝た後に親が 1 通読み、子が 5 秒以内に送り終えることを見る。
  POSIX-R2（`plan/tools/posix` の `console-posix-r2.sh`）の一部として流れる。

## 証拠（2026-10-27、VF2、10.0.30.2。QEMU は未実施）

- build: `config/ci/config-visionfive2.mk` の vmunix、`config/ci/config-amd64.mk` の vmunix と `POSIX-R2.ELF`、どれも warning 0。
- logger の試験（syslogd を SIGSTOP して `logger` を 400 本、5 秒後に SIGCONT、10 秒待つ）:
  - 直す前の main（eef49c12a、vmunix sha256 90da53c1…）: 233 本が send で寝て、CONT の 10 秒後も寝たまま。届いた行は 8。
  - 直した kernel（c66a43a1…）: 232 本が寝て、CONT の 10 秒後に 0 本。届いた行は 240（残りの 160 は寝た送り手が packet の
    buffer を持っている間の送りの失敗の見込み、下の残り）。
- sshd の試験（host から port 22 へ 180 秒、並行 6 本で login・中断の接続・banner 待ちで諦める接続、CPU 負荷 6 本、
  syslogd を 10 秒ごとに 3 秒止める）:
  - 直す前: 正常の login 10 回、sshd の log の `sshd[16]: Timeout before authentication`（[priv] が LoginGraceTime まで止まった数）14、
    client が去った後も `[postauth]` が 2 個残る。PerSourcePenalties で以後の接続も断られた。
  - 直した後（2 回、入れ直しを挟む）: 正常の login 132 回・141 回、"Timeout before authentication" 0・0、終了後の listener の子は
    [priv] 0・zombie 0、startups 0。logger の試験も 2 回目の起動で同じ結果（232 本 → 0 本、240 行）。
  - syslogd を止めない同じ負荷（直す前の kernel、login 503 回）では残りは 0 で、syslogd の遅れが条件だった。
- 再現の script（host 側）は P1 の scratchpad（repro.sh・lag.sh・logfill.sh）。回帰には上の guest 試験を使う。

## 残り

- amd64（10.0.10.3）での確認は未実施（WS291 の measure で ControlMaster を外した時に見る）。QEMU の POSIX-R2 は T1 に未依頼。
- datagram の待ち行列が 8 通と小さく、syslogd が少し遅れるだけで送り手が待つ。寝た送り手が packet の buffer を持つ間に
  他の送りが失敗する事がある（logger の試験で 400 本中 160 行が届かない）。どちらも本件の修正の外（必要なら別の ticket）。
- libc の `vsyslog()` は user space の spin lock を持ったまま blocking の send をする（signal handler から syslog() すると止まり得る）。本件の原因ではない。
