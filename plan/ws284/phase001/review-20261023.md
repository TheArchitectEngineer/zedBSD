## 確かめて正しかった事

- 構造: Focus の順（左上・左下・右上・右下、`network_blocks.py` 197〜209 行）、stem は BaseConv 3×3（12→16）、SPPBottleneck は depthwise でも BaseConv（122〜144 行）、CSPLayer の `cat((x_1, x_2))`（186〜187 行の forward）、Bottleneck の expansion 1.0 と `use_add`、PAFPN の cat の順（`yolo_pafpn.py` の forward）、head の obj が reg の特徴から出る事（`yolo_head.py` 159〜161 行）、decode（235〜253 行）、postprocess の `>=` の閾値・score = obj × cls・`torch.max` の最初の index（`boxes.py` 32〜76 行）、demo の conf 0.3・nms 0.3・`class_agnostic=True`（`tools/demo.py` 55〜56・162〜163 行）。
- 重み: `yolox_nano.pth` と `.onnx` の size と SHA-256 は §0 と一致した。0.1.1rc0 の Nano は legacy でない重み（legacy は `storage/releases/download/0.0.1`、`docs/updates_note.md` の Breaking changes、README 50・59 行）なので、正規化の無い前処理は正しい。
- **BN の eps 1e-3 を数値で確かめた**: torch を使わない制限 unpickler で pth を読み、BN のある 104 個の conv を eps 1e-3 で畳んだ重みと、ONNX の initializer（BN は畳まれていて BatchNormalization は 0 個）を比べた。最大の相対差は 1e-3 で 1.22e-7、1e-5 では 2.05。ONNX は同じ重みから作られている。ONNX の op は Conv 113・Add 7・MaxPool 3・Resize 2・Sigmoid 110（SiLU 104＋head 6）で、付録 A の数と合う。
- ZNET の header の offset（0〜255）は重なりも隙間も無い。concat の部分の channel 数は全て 16 の倍数なので、C4 の連続の区間になる。
- HAL の変更は要らない（設計の主張どおり）。

## 指摘

### F1 High: specialization constant は zedBSD の compiler で断られる。lavapipe の試験では見つからない

- 箇所: design §3.6 の `conv1x1.comp`（「画素 P 個（specialization constant、既定 4）」）、§3.6 の「必要なら後で specialization constant で tile を変える」、§3.7 の必要な機能の一覧。
- 根拠: 共有の前段 `src/drivers/gpu/compiler/spirv.c` に `OpSpecConstant*`（48〜52）の case が無い。module の段の switch の `default` は 1667〜1673 行で `"module-level instruction that is not interpreted"` として断る（定数は 1526 行の `OP_CONSTANT` と 1579 行の `OP_CONSTANT_COMPOSITE` だけ）。`spirv-compute.inc` 196〜212 行は spec constant の `LocalSizeId` も断る。bcm2711 の executor は graphics で `pSpecializationInfo != NULL` を `ENOTSUP` にする（`src/drivers/gpu/bcm2711/vk/vulkan-pipeline-build.c` 219 行）。WS283 の design §1.6 は「前段が既定値で畳む」と書くが、今の code とは合わない。
- 起こる事: 宣言しただけの spec constant（既定値で使う場合でも）が SPIR-V に入ると、Pi 5 で pipeline を作れない。T3〜T5 は lavapipe で流すので通り、最初に分かるのは p006 の T7。
- 修正案: shader に spec constant を使わない。P・活性化の有無・残差の有無・stride は `regenerate.py` で `glslc -DP=4` などの build 時の variant（shaders.h に複数の配列）にするか、push constant の uniform な分岐にする。§3.7 の一覧から specialization constant を外し、WS283 に「前段は OpSpecConstant を断る（§1.6 の記述の訂正）」を伝える。

### F2 High: 「command buffer を 1 回だけ記録」は、呼ぶたびに違う VkBuffer を受ける API と両立しない

- 箇所: design §3.6 の 280 行目付近（「command buffer は runner を作る時に 1 回記録し」）、§3.2 の `yolox_submit_buffer(runner, image, buffer, offset, wait)` と `yolox_detect`。
- 根拠: Vulkan 1.0 の core には `UPDATE_AFTER_BIND` が無い。記録済みの command buffer が bind した descriptor set を `vkUpdateDescriptorSets` で更新すると、その command buffer は invalid になる。`offset` も storage buffer の descriptor では `minStorageBufferOffsetAlignment` の倍数でなければならないが、API は任意の値を受ける。host の経路では staging の大きさが画像の大きさで変わる（1080p の RGBA で 8.3 MB）が、§3.5 は staging を数えていない。
- 起こる事: 2 回目の submit からは、無効な command buffer を submit する（未定義の動作）か、毎回の記録し直しになる（設計の前提と違う）。validation layer があればすぐに分かるが、§4 の試験は validation layer を使うと書いていない。
- 修正案: 入力の段を分ける。(a) submit ごとに小さな command buffer を記録する（入力の buffer を library が持つ buffer へ `vkCmdCopyBuffer` するか、submit ごとに使う descriptor set の ring を持つ）。その後に固定の graph の command buffer を semaphore か同じ submit で続ける。(b) `offset` は uniform で渡して binding の offset を 0 にするか、alignment を確かめて断る。staging は「大きさが変わった時だけ作り直し、入力の段だけ記録し直す」と書く。T3〜T5 を `VK_LAYER_KHRONOS_validation` 付きで流し、validation の error 0 を合格の条件に入れる。

### F3 Medium: WS283 は 1 dispatch を数 ms に収めるよう求めているが、stem と大きな 1×1 は収まらない

- 箇所: design §3.6（122 dispatch、層の分割無し）、§5。
- 根拠: WS283 design §2.3 の 5（121 行）「1 dispatch = 1 step。…WS284 の kernel は 1 dispatch を数 ms に収める（大きい層は分ける）」。§5 の前提（38.4 G MAC/s、効率 10〜25%）で計算すると、stem（74.8 MMAC）は 7.8〜19.5 ms、`dark5.1.conv2`（22.2 MMAC）は 2.3〜5.8 ms。効率 10% では 2 ms を越える dispatch が 20 個ある（graph.py の表から計算）。
- 起こる事: Keiland の compositor の step が待たされる。分けると dispatch の数が 122 より増え、§5 の固定の費用も増える。
- 修正案: graph の計画（`graph.c`）に「1 つの op を行の範囲で N 個の dispatch に分ける」を入れる（範囲は uniform か push constant）。§3.6 の数と §5 の固定の費用を分けた後の数で書き直す。

### F4 Medium: Focus を融合した stem の重みの配置が、C4 の入力と合わない

- 箇所: design §3.4（「stem は [co/4][ky][kx][ci/4] の mat4」）、§3.3 の融合 (5)、§3.6 の `stem.comp`。
- 根拠: Focus の 12 channel は patch×3＋色の順（§1.5）。C4 の入力は RGB0 の 4 channel（§3.4）。ci/4 = 3 の束は (p0R, p0G, p0B, p1R) のように patch をまたぐので、RGB0 の vec4 の読みと 1 対 1 にならない。
- 修正案: Focus＋3×3 は、元の画像に対する 6×6・stride 2・pad 2 の conv と同じである（出力 (y, x) は元の行 2y−2〜2y+3 を読む。focus の段の 0 の pad は元の画像の外の 0 と同じ）。library の load で stem を [co/4][6][6] の mat4（ci = RGB0、4 番目の列は 0）に並べ替えると決める。CPU の参照は Focus を明示したまま（独立性を保つ）。

### F5 Medium: 前処理の仕様が参照と一致する程には書かれていない

- 箇所: design §1.7、§3.6 の `preprocess.comp`、§4 の T5。
- 根拠: `data_augment.py` 142〜158 行。(a) `cv2.resize(...).astype(np.uint8)` なので、network への入力は 0〜255 の**整数**の値になる。(b) cv2 の縦横の倍率は src ÷ dst（dst = `int(w * r)`）で、1/r ではない。(c) r と `int(w * r)` は Python の float64 で計算される。高さが 5000 以下で `int(h * (416 / h))` が 415 になる値は 260 個ある（23・45・46・90・92・93・165…、host で計算した）。その時は参照の画像に 1 画素の 114 の帯が残る。(d) T5 の「1/255 以内」は、0〜255 の尺度で単位が分からない。
- 起こる事: GPU と CPU の C 版が小数の値を出すと、参照と系統的にずれる。float32 で r を計算すると、ある大きさで画像の幅が 1 画素違う。
- 修正案: §1.7 に次を書く。cv2 の INTER_LINEAR の写像（sx = (dx + 0.5)·(src/dst) − 0.5、端は clamp）、値を整数に丸める（cv2 の uint8 の丸め）、r と dst の大きさは double で `min(S/h, S/w)` と `(int)(w * r)` を Python と同じ順で計算する。T5 の許容差は「0〜255 の尺度で ±1」と書く。

### F6 Medium: T1・T2・T3 の比べる量と許容差の定義

- 箇所: design §4 の T1・T2・T3。
- 根拠: release の ONNX には Exp の op が無い（上の確かめ）。decode の前の出力（`export_onnx.py` 86 行の `decode_in_inference = args.decode_in_inference`、既定は False）である。PyTorch の既定は decode する（`yolo_head.py` 33・210〜211 行）。T2 の「生の出力の差の最大 ≤ 2e-3」は、decode した値なら w・h = exp(reg)×stride（数百 px）に対する絶対値の差で、厳しすぎて意味が定まらない。T3 の「相対 1e-4」は、0 に近い出力（打ち消しのある和）で破れる。
- 修正案: T1 は PyTorch を `decode_in_inference=False` で動かして ONNX と比べる。T2 と T4 は decode の前の 85 値（reg は生、obj と cls は sigmoid の後）を `|d| ≤ atol + rtol·|ref|` で比べる（例 atol 1e-3・rtol 1e-3）。T3 も atol と rtol の両方を置く。**T0 に「畳んだ重みを ONNX の initializer と比べる（相対 ≤ 1e-6）」を足す**（今回 1.22e-7 で一致した。torch が無くても converter の eps・畳み・並びを独立に確かめられる）。R4 の「ONNX で代える」が成り立つ事もこれで分かった。

### F7 Medium: debug の runner が、concat・add の融合と 7 つの shader と矛盾する

- 箇所: design §3.5 の最後（「tensor ごとに別の buffer で全部残し」）、§3.2 の `yolox_runner_read_tensor`、`yolox_runner_config`。
- 根拠: concat を別の buffer にすると concat の写しの shader が要り、残差を分けると add の shader が要るが、どちらも §3.6 の 7 つに無い。融合した後には、add の前の tensor と focus の tensor は存在しない。`yolox_runner_config` には debug を選ぶ field が無い。
- 修正案: debug の runner は「同じ融合の計画で、arena の再利用をしない（全ての buffer の生きる区間を全体にする）」と決める。存在しない tensor（add の前・focus・reg と obj の分かれた形）を read_tensor が error で返す事と、config の `debug` の field を書く。

### F8 Medium: Pi 5 の見積もりが既にある観測と WS283 の制約を反映していない

- 箇所: design §0（「未確認: Pi 5 の QPU の数と clock」）、§5、§8 U1。
- 根拠と問題:
  1. WS279 p002 の Pi 5 の実機の記録は V3D 7.1.10・12 QPU・1.15 GHz（`plan/ws279/ws.md` 36 行、`plan/ws279/phase002/phase.md` 42〜44 行）。§5 は 800 MHz（38.4 G MAC/s）、WS283 §3.3 は 1.15 GHz（110 GFLOPS = 55 G MAC/s）で、2 つの WS の前提が違う。
  2. 帯域: graph.py の表から、書き 40.4 MB、各入力を 1 回読む 53.1 MB で計 93 MB（§5 は 130 MB）。1×1 の conv が出力の束ごとに入力の全体を読み直し、cache に当たらなければ、入力の読みだけで 430 MB になる（Σ ⌈cout/4⌉ × 入力の byte）。WS279 design 169〜170 行により、job ごとに前で L2T を flush して slice の cache を無効化し、後で clean するので、dispatch をまたぐ再利用は無い。invocation と（画素、出力の束）の対応は設計に書かれていない。WS283 §1.3（63 行）の ldunifa で重みを読む形は「1 つの workgroup の lane は同じ出力の束」を要るので、入力の再利用と引き換えになる。
  3. WS283 の compiler の制約: IR は scalar で、vec4 の 1 回の読みは p008 まで 4 回の TMU の lookup になる（§1.3 59 行）。各 access に範囲の clamp が 2〜3 命令付く（62 行）。TMU の FIFO は thread あたり 16/threads 語（61 行）。spill は無く、register は 4 thread で 28 個、2 thread で 56 個（§1.5 87 行）。§3.6 の conv1x1（累積 16＋重み mat4 16＋入力 4 vec4 16 ＝ 約 48 個が同時に生きる）は 2 thread でぎりぎりで、断られる risk がある。
- 修正案: §5 を 1.15 GHz の観測で書き直し、WS283 §3.3 と数を揃える。invocation の対応（推し: workgroup の y を出力の束にし、lane は画素。重みは ldunifa、入力の再利用は L1T と L2T に任せる）と、その時の DRAM の量の上限・下限を書く。P を build 時の variant（1・2・4）にして、register に収まる最大を p006 で選ぶ（F1 と同じ仕組み）。「vec4 の TMU と ldunifa（WS283 p008）が無いと §5 の効率は出ない」と明記する。

### F9 Medium: WS283 への依存が曖昧で、Pi が無くても見つかる失敗を T7 まで見つけられない

- 箇所: design §6 の p006「WS283 の Pi 5 の compute」、ws.md の Phase の表。
- 根拠: WS284 の shader は loop（ci の束、class 80）を要る → WS283 p004。storage → p003。実行器 → p006。実機 → p007。§5 の速さ → p008。WS283 §4 は「WS284 は p006 の後に書き始められる」と書くが、p006 は p004 に依存していない（p003 だけ）。
- 修正案: p006 の依存を「WS283 p004・p006・p007 が cleared（速さの判定は p008）」と書く。p004（または p006 の最初）に、WS284 の全ての shader を host で bcm2711 の 7.1 の後段にかけて compile だけする確かめ（WS283 の `shader71-host-test` の形、WS283 p004 の後）を足す。F1（spec constant）と F8-3（register）の失敗を Pi 無しで見つけられる。

### F10 Medium: 変換した重みは firmware の repository の約束（upstream と byte が同じ、fallback あり、同意の問い）に合わない

- 箇所: design §2.4、§7 D1・D2。
- 根拠: `userland/firmware/zedbsd-firmware.mk` 1〜19 行。repository は各 file を「byte for byte」で保ち、fetch は upstream に fallback する（「where the bytes come from, never which bytes are accepted」）。ZNET は zedBSD が作る派生物で upstream が無い。production の firmware の package は同意の問いを必ず出す（例 `userland/firmware/i915/Makefile` 48 行の `override I915_FIRMWARE_LICENSE_PROMPT := y`。`n` は fixture だけ、29 行）。設計の「`LICENSE_PROMPT n` 相当」は production の前例が無い。revision は全ての package で 1 つ（`ZEDBSD_FIRMWARE_REPOSITORY_REVISION`）なので、file を足すと global の値を変える事になる（Q1 の操作）。
- 修正案: D1・D2 の問いに「firmware の repository の約束を、派生 file のために変える」事を明記して、ユーザーに決めてもらう。代案を並べる: 元の `.pth`（SHA `cd28f55f…`）を byte のまま mirror し（upstream の fallback あり）、build の中で標準 library だけの converter を動かして出力の SHA-256 を確かめる（T0 で決定的と確かめる）。設計が根拠にする「依頼の指示」（§2.4・§7 D1）の原文は見つけられなかった（推測: Q1 の依頼文）。引用して書く。

### F11 Medium: ZNET の load の確かめに抜けがある（外から来る data）

- 箇所: design §2.3 の最後の段落。
- 抜け: kernel・stride・groups の値の上限（conv の k ∈ {1, 3}、stride ∈ {1, 2}、groups ∈ {1, cin}、maxpool の k ∈ {5, 9, 13}）。各 tensor を作る op がちょうど 1 つである事、入力の tensor を書く op が無い事。u32 の積の溢れ（channel ≤ 4096 でも k に上限が無いと cout×cin×k×k が溢れる。64 bit で計算する）。予約の field が 0 である事。fp32 は 4 byte、fp16 は 2 byte の境界。fp16 の file で bias も fp16 か。入力の大きさの上限（S = 4096 なら最大の tensor 16×(S/2)²×4 B = 256 MiB で、`maxStorageBufferRange` の下限 128 MiB を越える）。§4 には壊れた ZNET の試験が無い。
- 修正案: 上を §2.3 に足し、上限は runner を作る時に device の limit と比べる。p003 に壊れた header・範囲の外の offset・循環・二重の生成の負の試験を足す。

### F12 Medium/Low: 非同期の API と device の共有の約束

- 箇所: design §3.2。
- 抜け: `vkQueueSubmit` は queue ごとに外から排他する決まりがある。app と library が同じ `VkQueue` に別の thread から submit すると race になる。他にも、wait semaphore の stage（COMPUTE_SHADER）、app の buffer が別の queue family の EXCLUSIVE の時の所有権の移転、library が自分で device を作った時に app の `VkBuffer`（別の device の物）を渡された時の拒否、`VK_ERROR_DEVICE_LOST` の後の runner の状態、`count` が `capacity` を越えた時の意味が書かれていない。公開の struct `yolox_runner_config` には大きさ・版の field が無いので、field を足すと ABI が壊れる。
- 修正案: 上を API の文に書く。config の先頭に `uint32_t struct_size`（または版）を置く。queue は「submit と collect を app と同じ thread で呼ぶ」と決めるか、lock の callback を受ける。

### F13 Low: memory の数「concat の別名で 6.60 → 4.62 MiB」は graph.py の数え方の産物

- 箇所: design §3.5（262 行目付近）、phase.md の記録、`graph.py` 100 行と 118 行。
- 根拠: 別名の無い方は `live | {"image"}` で入力の画像を最後まで生かす（100 行）。別名の方は `first = {"image": 0}` で、画像は op 0 だけ生きる（118 行）。1,730,560 − 519,168（3×416×416）＝ 1,211,392 で、別名の方の最大とちょうど同じ。つまり別名で最大は減っていない。さらに C4 の入力は 4 channel（692,224 要素）なので、入力と stem の出力が同時に生きる最大は 5.28 MiB になる。
- 修正案: 数を直す。concat の写しを無くす利点は、13 個の写しの dispatch と帯域を減らす事だと書く。

### F14 Low: dispatch の数が自分の融合と合わない

- 箇所: design §3.3 の (6)（reg と obj を 1 つの 1×1 にする）と §3.6 の「conv1x1 82、計 122」。
- 融合すると conv1x1 は 79、計 119 になる。decode を 1 つの dispatch にすれば 117。F3 の分割の後の数と一緒に直す。

### F15 Low: 残差の融合の順

- 箇所: design §3.3 の (1)（「残差の入力を足してから書く」）。
- 根拠: `Bottleneck.forward` は `y = conv2(conv1(x)); y = y + x` で、conv2 の pconv の SiLU の**後**に足す。
- 修正案: 「out = SiLU(acc + b) + residual」と式で書く（T2 で見つかるが、書き方で誤りを防ぐ）。

### F16 Low: barrier を graph の依存だけから決めると、arena の再利用の危険を逃す

- 箇所: design §3.6（「依存のある dispatch の間に compute→compute の memory barrier」）。
- arena の区間を再利用すると、graph では独立な dispatch（cls の枝と reg の枝）の間にも WAR・WAW の依存ができる。連続する全ての dispatch の間に barrier を置くか（graph はほぼ直列、V3D の executor は job ごとに完了を待つので費用は同じ）、memory の重なりから決める。access に SHADER_WRITE を含める。

### F17 Low: T1 の venv の package が足りない

- 根拠: `yolox/utils/__init__.py` が全ての utils を import し、`metric.py` が `psutil`、`exp` が `tabulate`、他に `packaging`・`loguru`・`cv2`・`torchvision` を import する（`requirements.txt` も参照）。§4 の T1 の一覧には psutil・tabulate・packaging が無い。
- 修正案: 一覧を足し、torch・torchvision・opencv の版を pin して、`pip freeze` を参照の data と一緒に記録する（cv2 の resize と torch の数値は版で少し変わる）。

### F18 Low: 試験が無い所

- 320 の参照が無い（§5 の fallback は 320 と 256）。T1 で 320 の参照も作り、T2・T4 を 320 でも流す。
- 入力の format（RGB8・RGBA8・BGRA8）と `row_bytes` の pad、非同期の submit・collect・timeout、device の共有の試験が無い。
- host の試験で lavapipe を選ぶ方法（`VK_DRIVER_FILES` などで ICD を固定する、または config で物理 device を選ぶ）が書かれていない。host に別の GPU があると T3〜T5 がそちらで動く。

### F19 Low: NMS の同点と class ごとの NMS

- torchvision の `batched_nms` は box が少ない時に座標を class × (max + 1) ずらす方法を使う。fp32 の丸めで IoU が少し変わる。sort の安定性も torchvision の版による（推測、版ごとには確かめていない）。
- 修正案: zedBSD の規則（score が同じなら anchor の番号が小さい方が先、class ごとに厳密に NMS）を書き、試験は同点と境の物を除く（§4 T2 の除外に同点を足す）。

### F20 Low: converter と試験の data の置き場所が、WS の完了で消える

- 根拠: AGENTS.md「WS が完了したら…Phase のディレクトリとその WS だけの試験を削除する」。§2.2 の converter は `plan/ws284/tools/`、§4 の data は `plan/ws284/tests/data/`。配る `.znet` の由来（manifest が script と commit を指す）と `yolox-test` の回帰の data は WS の後も要る。
- 修正案: converter は `userland/firmware/yolox-nano/` の下か `plan/tools/`（Master の Tools に登録）に置くと決める。D5 に「回帰の data として WS の後も残す場所」を含める。

### F21 Low/Info: license の表示

- NOTICE に COCO（注釈は CC BY 4.0）の attribution の 1 行も足しておくと、D4 の解釈がどちらでも条件を満たす（費用は無い）。試験の画像の license 7・8 の選び方は COCO の license の番号と合っている。

### F22 Info: camera の入力の分布（WS285 への伝達）

- 学習は sRGB の JPEG（gamma・white balance の済んだ物）。WS285 の debayer が ISP（AWB・CCM・gamma）無しの RAW から作る画像では検出の精度が落ちる見込みがある（推測）。WS284 の「参照と一致」の基準ではこれは分からないので、WS285 の設計に伝える。
