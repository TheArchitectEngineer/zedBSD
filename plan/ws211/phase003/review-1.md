# WS211 p003 review-1（design-reviewer、fe10ea668）
結論: 段 1（bind の省略）は M1・M2 を書き足せば条件付きで実装可、ただし効果は compositor の記録の時間だけ（H2）で段 1 の数を段 2 の判断に使わない。段 2 は H1・H2・M3〜M8 の後、まず床だけで試して Pi の数を測る。HAL・UAPI・kernel の変更は不要。

H1 種類ごとの順（2.3）の誤りを試験の参照が検出できない: KWL_BATCH=0 で並べ替えも戻すと書かれていない。今の順は icon ごと（home.c:2002-2073）、並べ替えは home.c:752-801 の作りの変更。2.3 の証明は横の隣だけで、行どうし（縦 152、home.c:159）、letter icon の影（quad ±60、縦 y-18〜y+102、home.c:2331-2345）、24 本の帯と rim と字（2383-2431）、選択の ring（2052-2062）、hover の白（glass.c:2440-2450、MODE_TEXT・tiles の set で tile と映り込みの間）、名前と印の交互（2069-2073、全部の名前→全部の印と明記）が抜け。被覆で考えれば重ならないことは示せる（光は ±65.6 で 0、letter の影の上端は上の行の名前の下 y+144 より下）、ただし幅の狭い出力（W 約 870 未満）でページを drag 中は隣のページの icon が重なり得る（home.c:1866、推測）。直し: 並べ替えも KWL_BATCH=0 で旧の順に戻す（または旧 binary の撮影を参照）、2.3 を被覆基準で全部の形・行・ページの drag まで、比べる場面に letter icon・hover・選択の ring・動作中の印・検索・2 ページの drag の途中・暗い外観。
H2 段 1 は Pi の kernel の draw ごとの準備に効かない: kernel は draw ごとに今の状態から作り直す（vulkan-prepared.c:213-233、snapshot_descriptors 246-287、vulkan-native-draw.c:76-170）、bind の command はポインタを置くだけ（vulkan-draw.c:161-166）。減るのは libvulkan の encode（commands-generated.inc:16-39、367-）、record の追加と retain（vulkan-record.c:150-206）、submit 時の bind の走査（vulkan-record.c:117-147、vulkan-prepared.c:338-377）だけで prep・rec・tex は不変。7 割減は bind の数で、1 draw の command 総数は約 37% 減。段 2 の損得は prep の減りと頂点の詰め直しの増え（uncached から 4 byte ずつ vulkan-native-draw.c:840-855、vulkan-memory.c:417、床 192 形で読み 2.3k→13.8k、減る draw 188×5〜20µs）で決まる。直し: 段 1 の目的を「compositor の記録（KWL LAT acquired→recorded）を減らす」に、段 2 は床だけ束ねて前後の rec・prep と記録の時間を Pi で測って決める、未決 3（133 行）を差し替え。

M1 段 1 の比較の鍵は (set, layout) の組: 同じ set が quad（compose->layout、push vertex 32B compose.c:1293-1300、2216-2218）と glass（panel_layout、push 96B compose.c:1327-1329、glass.c:1797-1799）で bind される（desktop.c:355 と 363、subsurface.c:782 と 793）、spare の set は handle ごと使い回し（compose.c:1980-2020）、Pi の kernel は互換の無い layout の set を乱し（vulkan-draw.c:231-251）draw で EINVAL（vulkan-draw-validate.c:106-117）。set だけで省くと Pi で EINVAL。消す所の一覧は誤り（bind は compose.c:2216-2217 と glass.c:1797-1798 の 2 か所だけ、backdrop・heads・cursor-plane・shot は bind しない）、記録の始めは compose.c:2341 と layer-cache.c:218 の 2 か所。state は render pass をまたいで残る（Pi vulkan-draw.c:138-191、i915 command.c:3603-3654）。直し: 鍵は pipeline と (set, layout)、2 つの vkBeginCommandBuffer と全部の vkCmdBeginRenderPass で消す、kwl_compose_set_put でも消す、layer-cache.c:571・612 の draw_counts のように保存・復元しない、host 試験に quad→同じ set の glass・spare の再利用・quiet frame。
M2 検証の数が実際の command を数えていない: draws= は形の数（compose.c:2869-2872）、pipelines=・sets= は前の draw と違う回数で pass で消えない（2163-2169）→ 実際の vkCmdDraw・BindPipeline・BindDescriptorSets・PushConstants を flush と bind の所で数える。
M3 面積の閾値の矛盾: 128×128 を超えない光（147.2×68=10,010）は面積なら束に入る、103 行の「光 12→12」と合わない、layer の拡大縮小（glass.c:1690-1700）で大きさが変わる → 「面積 16384 以下」か「幅も高さも 128 以下」かを決めて表を合わせる。
M4 束の pipeline layout: 別の layout（push 8B）だと set 0 の互換が切れる（vulkan-draw.c:231-251）、交互で set の bind し直し・screen.xy の push し直し。head の pass は view_width を pass の後に置く（heads.c:1251 の後、1277-1281）。直し: 束の pipeline も panel_layout、shader は panel.screen.xy（byte 80）、push し直しは flush の時に「最後に押した screen」と今の値を比べて。
M5 corners の bind し直しが quad の経路に無い: compose_quad_part も binding 0 の corners 前提（compose.c:2216-2219）、quad は cursor（compose.c:2553）・popup（popup.c:632）・IME（input-method.c:1932）・head の壁紙（heads.c:1271）。直し: binding 0 の状態を 1 つの helper で覚え両方の描く関数の前で保証、pass と記録の始めで corners に戻す。
M6 flush の一覧に layer-cache.c が無い（543・550・554・556・615 行の vkCmd）、glass.c の vkCmd は 1797-1800 の 1 組 → 一覧を今の source で作り直す。
M7 Pi の絵の比較が落ちている（p001 397 行）→ Pi でも shot.c で KWL_BATCH=0 と比べる、T1 の 1 回は KWL_BATCH_CHECK の build。
M8 16KiB の計算は正しい（kernel は宣言した入力の scalar 数×4×頂点数 vulkan-native-draw.c:832-838、1235）が、vert が mode ごとの入力だけを宣言する前提、coordinate と vertex の入力数の一致（822-830）→ vert も mode ごとの variant、host 試験で input_count×4×6×n ≤ 16384。

Low: L1 ws.md の Resume point と p002 の Status が古い。L2 0.28・0.23・662 コマの元の log を plan/ws211 に要約。L3 頂点の buffer は 1MiB 固定の HOST_COHERENT で常時 map（compose.c:1426 と同じ選び方）、Pi の 8MiB の連続確保の危険が消える。L4 並べ替えの後も kwl_hover_probe の順を保つ（home.c:1997）。L5 色を R32 に詰める案を採らない理由。L6 shader の host 試験は plan/ws141/tests/shader-host-test.sh 依存、Tools への登録を Q1 に。L7 i915 の native compiler が flat を扱うかは推測、host の compiler の試験で。
