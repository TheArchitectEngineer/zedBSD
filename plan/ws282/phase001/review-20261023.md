## 指摘

### H1（高）案 A の `drv_gpu_shared_backing` は Vulkan の export した memory に対して必ず ENOTSUP になる

- 場所: design §3.6 案 A、§6 D3、§11 p006、§10「案 A は GPU core に 1 関数で済む」。
- 根拠: `vkGetMemoryFdKHR` は `vulkan_memory_allocation_fd` → `GPU_ALLOCATION_EXPORT`（libvulkan/memory.c:207・660-697）で、allocation だけの共有を作る。bcm2711 の共有は image を渡された時だけ `has_image = true`（bcm2711/share.c:101-119）。design が呼ぶ `get_scanout_backing` は bcm2711 では `render_backing`（render-device.c:647-660、952）で、`bcm2711_shared_backing` は `if (!shared->has_image) return ENOTSUP;`（share.c:192-193、注記「Allocation-only exports cannot silently acquire a scanout layout」）。つまり gpu.c に 10〜20 行を足すだけでは、app の作った storage buffer の memory を camera が取り込めない。
- 起こる状況: p006 の `camvk` が `CAM_QUEUE_BUFFER` で常に失敗する。
- 修正案: (1) bcm2711 の share（WS279/WS141 の `share.c`・`render-device.c`）に allocation だけの共有から物理の run を返す別の op（例 `get_allocation_backing`、連続・page の列・cache の方針を返す）を足し、gpu.c の `drv_gpu_shared_backing` はそれを呼ぶ。gpu.c の import と同じく `handle->ops == gpu_shared_operations()` と `shared->allocation.version != 0` を確かめる（gpu.c:4703-4716）。(2) D3 の費用と p006 の依存（他 WS の source、Q1 経由）を書き直す。(3) `drv_gpu_scanout_backing` には cache の方針が無い（share.c:194-198 は flags に CONTIGUOUS だけ）ので H2 のために足す。

### H2（高）取り込んだ GPU の buffer に CPU の dirty な cache の line が残り、RP1 の DMA の書いた frame を上書きし得る

- 場所: §3.6 案 A の「cache: … camera が書く間 app は触らない契約」、§9 R5。
- 根拠: bcm2711 の buffer は確保の時に cached の direct map で 0 を書く（buffer.c:109・125 `kern_memset(buffer->address, 0, rounded)`、`kern_pmem_to_kernel` の alias）。RP1 の DMA は cache を覗かない（dtb に `dma-coherent` が無い、rp1.c:1521-1523 で `drv_fdt_dma_coherent`）。dirty な line は後で evict されると RAM に書き戻され、camera の書いた行を古い値で潰す。app が host-visible の cached な mapping に書いた場合も同じ。
- 起こる状況: frame の一部の行が 0 や古い値になる。evict の時期次第で、`camvk` と `camcap` の一致の試験（§7.3 p006）でたまにしか出ず、host の試験では検出できない。
- 修正案: 取り込みの時（最初の `QUEUE_BUFFER`）に run 全体を `hal_dcache_clean_invalidate_range` で掃除し、backing が cached の方針なら `QUEUE_BUFFER` のたびにも行う（または uncached の memory type だけを受け、cached なら `EXDEV`）。consumer が CPU なら FE の後・DEQUEUE の前に invalidate。V3D が読む前の V3D 自身の L2T/TMU cache の無効化が job の開始で行われる事を WS279/WS283 で確かめる（推測: 行われていない場合は前の frame が読める）。

### H3（高）`CAM_MEMORY_DEVICE` の buffer の kernel 側の alias と cache の掃除が定まっていない

- 場所: §3.4（`kern_pmem_alloc_limited` → `vm_device_create(..., VM_DEVICE_UNCACHED_RAM, PROT_READ)`、「kernel 側は direct map で触らない」）。
- 根拠: `vm_device_create` は kernel の `address` を受け、`vm_device_read`/`write`（ptrace・kernel の複写）はその alias で読む（kern/vm/device.c:46・vm_device_read の注記「Reads through the retained kernel alias」）。design は direct map を渡すのか uncached の alias を渡すのかを書いていない。新しく取った run には前の持ち主の dirty な line が direct map に残り得て、`hal_pmem_map_uncached` だけがそれを捨てる（hal.h:655-661）。既存の正しい型は `drv_dma_device_create_window` + `drv_dma_alloc_coherent`（rp1-ethernet.c:827-842、dma.c:997-1018 が non-coherent なら `kern_pmem_map_uncached` を使う）。
- 起こる状況: H2 と同じく、まれに古い値の行が混じる。R5 の「cached + invalidate に替える」も、確保の時の clean+invalidate が無いと同じ穴がある。
- 修正案: buffer は `drv_dma_alloc_coherent`（RP1 の window の device、bus address も得られる）か `kern_pmem_alloc_limited` + `kern_pmem_map_uncached` で確保し、その uncached の alias を `vm_device_create` に渡すと §3.4 に明記する。解放は mapping の release の後に `kern_pmem_unmap_uncached` → `kern_pmem_free`。

### M1（中・色が誤る）OV5647 の Bayer の並びの表が Linux と違う

- 場所: §3.3 末尾「既定 BGGR、hflip で GBRG、vflip で GRBG、両方で RGGB」、§4.6「全部 RAW10、BGGR（flip なし）」、§7.1 の flip と Bayer の試験。
- 根拠: `ov5647_get_mbus_code`（ov5647.c:838-852）は `index = hflip | (vflip << 1)`、表は `{GBRG, BGGR, RGGB, GRBG}`。HFLIP・VFLIP の control の既定は 0（ov5647.c:1310-1316）。よって既定は **GBRG**、hflip=1 で BGGR、vflip=1 で RGGB、両方で GRBG。mode の表の `SBGGR10` は `get_pad_fmt` が上書きする（ov5647.c:905-906）。
- 起こる状況: debayer の色が入れ替わる。host の試験は design の表をそのまま期待値にするので誤りを固める。
- 修正案: 表を Linux の通りに直し、host の試験の期待値も直す。p004 で color bars の色の順（白・黄・シアン・緑…）を目で確かめる手順を足す。

### M2（中・推測を含む）REMAP（16 bit unpacked）の値の位置が確かめられていない

- 場所: §3.3「unpacked は 16 bit little endian の下位に値」、D7（既定を unpacked）、§7.3 p004 の black level「16/1023」。
- 根拠: Linux は RAW10 の 16 bit 版を `V4L2_PIX_FMT_SBGGR16` にする（cfe_fmts.h:117 の `remap`）だけで、hardware が LSB 側に置くか MSB 側に寄せるかは rp1_cfe の source に書いていない。推測: Raspberry Pi の libcamera は CFE の unpacked を 16 bit の深さとして扱っており、MSB 寄せの可能性が高い（確かめていない）。
- 起こる状況: MSB 寄せなら値が 64 倍になり、`camcap` の black level・gain と WS285 の compute の正規化が全部ずれる。
- 修正案: ABI の `cam_format` に `sample_shift`（または `msb_aligned`）を持たせて driver が答える形にし、p004 で test pattern の最大値を読んで決める手順を §7.3 に足す。決まるまで「下位に値」を ABI の文書に書かない。

### M3（中）`kern_usleep_range` は busy wait でなく CPU を譲る

- 場所: §9 R1「zedBSD の待ちの実装（kern_usleep_range）が busy wait である事以外は同じ」、§4.4 の DPHY の 15/5/10 µs。
- 根拠: clock.h:197-201 の注記は busy delay と書くが、実装（clock.c:694-740）は次の tick（aarch64 は 1000 Hz、include/hal/arch/aarch64.h:16）まで `waitq_sleep` で譲る。WS278 の GEM の停止は spinlock を持ったまま `kern_usleep_range` で譲った事が原因だった（plan/ws278/tests/rpi5-hw-test.md:86）。
- 起こる状況: receiver の `prepare`/`start`/`stop` を `device->lock` の下で呼ぶ実装にすると同じ停止が起きる。DPHY の待ちは 1 ms 単位に延びる（DPHY には害は無い見込み）。
- 修正案: R1 を直し、§5 に「receiver の `prepare`・`start`・`stop` と DPHY の手順は mutex の下・spinlock の外でだけ呼ぶ。spinlock の下で呼ぶのは `set_buffer` と割り込みの処理だけ」と書く。µs の待ちが spinlock の下で要るなら GEM の直しと同じく単調 counter の busy wait にする。

### M4（中）停止の順序と FE_ACK の待ちが Linux と違い、割り込みとの競合が定まっていない

- 場所: §4.4 停止、§5「`STOPPING` で FE_ACK か 100 ms の timeout を待つ」。
- 根拠: Linux（cfe.c:1202-1240）は先に channel を止め（`csi2_stop_channel`: FORCE、ADDR0 に 0 を 2 回）、次に sensor の stream off、`csi2_close_rx`、INTE = 0、そのまま buffer を返す。FE_ACK は待たない。design は sensor を先に止める（途中の frame で lane が止まれば FE は来ない）ので、ほぼ毎回 100 ms の timeout を待つ。さらに、別の CPU で走る FS の割り込みが receiver の停止の後に `set_buffer` を呼べば ADDR0 の書き込みで channel を再び arm し得る（推測、hardware の挙動は未確認）。
- 起こる状況: stop/start 100 回の試験（§7.3 p005）が遅い。競合すると解放した buffer に DMA が書く。
- 修正案: (1) spinlock の下で状態を `STOPPING` にし、以後の割り込みは `set_buffer` を呼ばず buffer を動かさない。(2) receiver の停止（FORCE・ADDR0×2・IRQ_MASK = 0・INTE = 0）の後に register を 1 つ読み戻して PCIe の posted write を流す。(3) sensor の stream off。(4) FE_ACK は待たず、1 frame の時間（mode の fps から）を上限に DEBUG の line counter が止まった事を見てから buffer を返す。順序を Linux と同じにする理由を §4.4 に書く。

### M5（中）stream の所有者の規則に穴がある

- 場所: §3.1「`REQUEST_BUFFERS` を呼んだ open が所有者」「`SET_FORMAT` … は所有者だけ（他は EBUSY）」、§3.2 番号 5（buffer 確保中は EBUSY）。
- 根拠: `SET_FORMAT` は `IDLE`（buffer の確保前）でしか許されず、その時には所有者がいない。2 つの process が `SET_FORMAT` → `REQUEST_BUFFERS` の間に互いの format を書き換えられ、規則の「所有者だけ」は意味を持たない。
- 修正案: `SET_FORMAT` が所有を取る（所有者がいれば他は EBUSY）、または明示の `CAM_ACQUIRE`/`CAM_RELEASE`、または `REQUEST_BUFFERS` に format を含める。host の試験に「2 つ目の open の SET_FORMAT が EBUSY」を足す。

### M6（中）sensor の電源の状態機械と control の保持が無い

- 場所: §2.2 `power_on`/`power_off`、§4.1 手順 5（登録の後 `power_off` で待機）、§4.4 開始（`set_mode`/`start` だけで `power_on` が無い）、§3.2 番号 15（stream 中でも設定可）、§5 sensor の失敗（NACK 3 回で FAULT）。
- 根拠: Linux の `ov5647_power_off` は出力 enable を 0 にし（0x3000-0x3002 = 0）SW standby・regulator 断をする（ov5647.c:711-736）。開始は runtime resume で `ov5647_power_on`（regulator・20 ms・OE enable・stream off で LP-11）を通ってから `ov5647_stream_on`（ov5647.c:799-806 の `ov5647_s_stream`）。電源が無い時の control は hardware に書かず、stream の開始で書き直す（ov5647.c:1181 `pm_runtime_get_if_in_use`、626 行の `__v4l2_ctrl_handler_setup`）。
- 起こる状況: power_off のままの `STREAM_ON` で MIPI の出力が出ず、500 ms で FAULT。regulator を切った状態の `SET_CONTROL` は NACK になり FAULT の数に入る。
- 修正案: 枠組みに電源の状態を持たせる（例: `STREAM_ON` で `power_on` → `set_mode` → `start`、`STREAM_OFF` か最後の close で `power_off`）。control の値は枠組みが保持し、電源が無い間は保持だけ、`set_mode` の後に全部書き直す（design §4.4 手順 5 の「control の値を書き直す」の出所をこの保持にする）。

### M7（中）kernel の interface の欠け・矛盾

- 場所: §1・§2.1・§2.2・§5。
- 内容と修正案:
  1. §1 は「sensor の driver は枠組みが渡す電源の callback を使う」と書くが、`drv_cam_device_desc`・`drv_cam_sensor_ops` に電源の callback も I2C の bus と address の渡し口も無い。`ov5647.c` の作り方（例 `drv_ov5647_create(bus, address, const struct drv_cam_power *power, void **argument)`）を §2 に足す。
  2. `set_buffer(bus_address, …)` の bus address を誰が作るか: desc は `dma_physical_limit` だけで bus offset を持たない（§4.4 手順 2 は receiver が足すように読める）。desc に `dma_bus_offset` を足すか、「枠組みは物理 address を渡し receiver が変換する」と決める。
  3. `drv_cam_receiver_error` は §2.1 で「統計に足す」、§5 で「致命を告げた」。致命かどうかを引数で分ける。
  4. 「STREAM_ON の後 500 ms で FS が無ければ FAULT」の時計（timer か DEQUEUE の待ちの deadline か）が無い。DEQUEUE の待ちの deadline で判定するなら、誰も DEQUEUE しない時は FAULT にならない事を明記する。
  5. 待っている `DEQUEUE` は mutex を持たずに spinlock と waitq で眠る事、`STREAM_OFF`・FAULT・close で起こされ `EIO`/`EINVAL` で返る事を §5 に書く（mutex を持って眠れば `STREAM_OFF` が永久に待つ）。
  6. `QUEUE_BUFFER` で既に queue・DMA 中・完了列にある index を渡した時の答え（EBUSY）、`STREAM_OFF` で完了列にあって未 DEQUEUE の buffer の扱いを決める。

### M8（中）AEC/AGC を既定で on にすると metadata の露光・gain が嘘になる

- 場所: §3.5（frame start の時点の control の値を写す）、D6（既定で AEC/AGC on）。
- 根拠: AEC/AGC が on の間 sensor は 0x3500-0x3502・0x350a/b を自分で決め、control の値は使われない（Linux は既定で両方 manual、ov5647.c:1263-1270 と mode の表の `{0x3503, 0x03}`）。
- 修正案: auto が on の間は metadata に `CAM_METADATA_EXPOSURE_UNKNOWN` を立てる、または FE の後に thread（割り込みでなく）で register を読んで次の DEQUEUE に載せる。WS285 が露光を使わないなら前者で足りる。

### M9（中・推測）誤りの割り込みを開けると、buffer の枯渇のたびに割り込みが多発し得る

- 場所: §4.4 手順 4（IRQ_MASK を開けて OVERFLOW と DISCARD の 4 種を数える）、§5（DISCARD_INACTIVE は正常）。
- 根拠: Linux は既定で IRQ_MASK = 0（csi2.c:403-405、`track_csi2_errors` の時だけ）。DISCARD の register の amount は数（csi2.c:41-46）なので packet ごとに数えている見込みで、INACTIVE の割り込みが packet（行）ごとに来るなら 972 行 × 32 fps で毎秒約 3 万回（推測、未確認）。また IRQ_MASK の bit は STATUS の bit と位置が違う（IRQ_MASK は bit 0〜4、STATUS は bit 20〜24、csi2.c:49-58 と 80-84）ので取り違えに注意。
- 修正案: INACTIVE は開けない。OVERFLOW と他の DISCARD だけ開けるか、全部閉じて FS/FE の割り込みの中で `DISCARDS_*` を読んで 0 を書く。p004 で INACTIVE を開けた時の割り込みの数を一度測る。

### M10（中）試験の計画と Phase の順が合わない（node の権限）

- 場所: §7.3 p003「`/dev/cam0` が 0600 root で出る」、§11 p008（devfs の 0600 を Q1 に依頼）。
- 根拠: devfs の規則に無い名前は 0666（devfs.c:590）。p003〜p007 の間は誰でも camera を開ける image になり、p003 の期待値も満たせない。
- 修正案: devfs の `cam` の規則（小さな変更）は p002 か p003 で Q1 に依頼し、sessiond の seat は p008 のまま。p003 の期待値はそれに合わせる。

### M11（中）build の計画の欠け

- 場所: §4.1・§4.7・§7.1。
- 根拠: `i2c.c`・`lpss-i2c.c` は amd64 の build にだけ入る（platform/amd64/vmunix.mk:334-339）。rpi5 の driver の有無は `ARM64_BOARD_DEFINE_rpi5` の `-DCONFIG_DRIVER_RPI5_*=0/1` で C に渡す型（platform/arm64/vmunix.mk:20-22、rpi5.c:178 の `#if CONFIG_DRIVER_RPI5_FAN`）。§4.1 の手順に `drv_rp1_gpio_init()`（何度呼んでもよい、rp1-gpio.h）が無い。
- 修正案: p003 に「arm64（rpi5）の source に `src/drivers/i2c/i2c.c`（D2 (a) なら `dw-i2c-core.c` も）を足す」「`-DCONFIG_DRIVER_RPICAM` を `ARM64_BOARD_DEFINE_rpi5` に足し rpi5.c の呼び出しを `#if` で囲む」「probe で `drv_rp1_gpio_init()`・`drv_rp1_irq_init()` を呼ぶ」を書く。i2c.c の `drv_i2c_bus_find_acpi` は `#if CONFIG_DRIVER_ACPI`（i2c.c:24-26）なので arm64 で -Wundef の warning にならないか build で確かめる。

### L1（低）mmap の offset の式が曖昧で、重なり得る

- 場所: §3.2 番号 8「`index * image_bytes` を page に揃えた値」。
- 根拠: 例 1296×972 RAW10P の 1,586,304 byte（page の倍数でない）で、`roundup(index × image_bytes)` と `index × roundup(image_bytes)` は index 2 で 4096 byte ずれ、前者だと buffer 1 の範囲と buffer 2 の始まりが重なる。
- 修正案: `mmap_offset = index × roundup(image_bytes, PAGE)` と書き、2 つの buffer にまたがる mmap は EINVAL。

### L2（低）mapping が残る間は close が来ず、stream は止まらない

- 場所: §3.1「所有者が stream 中に close したら枠組みが stop」、§5 close。
- 根拠: `vm_device_create` は file を retain し（kern/vm/device.c:103）、最後の mapping の release の後に `file_close` する（同 vm_device_put）。fd を閉じても mmap が残れば cdev の close は呼ばれず、DMA と所有は続く。
- 修正案: この挙動を §3.1・§5 に書く（munmap か process の終了で止まる）。host の試験に「close 後も mapping が残る間は stream が続き、munmap で止まる」を足す。

### L3（低・推測）捨てた frame の sequence と INCOMPLETE の誤判定

- 場所: §3.5 sequence、§4.5 手順 3。
- 根拠: arm されていない channel（buffer が無い）が FS の割り込みを出すかは Linux の source から確定できない（`cfe_sof_isr_handler` は cur_frm が NULL でも動くが、来る保証ではない）。また Linux の「前の FE が無い」の処理は buffer を DONE で返す（cfe.c:797-807 → `cfe_eof_isr_handler`）。FE と次の FS+FE が 1 回の割り込みに重なった場合（Linux の case 3）は次の frame の FE が失われ、design では正常な frame が INCOMPLETE になる。
- 修正案: sequence は CSI2_CH_DEBUG の frame の field（bit 31:16）から作るか、それと照合して飛びを数える。INCOMPLETE は「FE を見ていない」の意味だと文書に書く。p004 で枯渇の時の FS の有無を確かめる。

### L4（低）I2C の所要時間の見積もりが小さい

- 場所: §10「1 mode 約 70 個…20〜30 ms で済む」、§4.1（boot の時の検出）。
- 根拠: `lpss_transfer` は transfer ごとに core を off/on し、待つたびに 1 tick 眠る（lpss-i2c.c:679・719・772-775、aarch64 は 1 tick = 1 ms）。1 書き込み 1〜3 ms で、common + mode + VC + control で約 100 回なら 0.1〜0.3 s/STREAM_ON。boot の検出は `kern_platform_refresh_devices` の中で同期に 2 connector × (20 ms + I2C) と、bus が low に張られた時の timeout がかかる。
- 修正案: 見積もりを直す（害は小さい）。boot を待たせないなら Wi-Fi・BT のように thread で検出する。

### L5（低）実機の前提: 22 pin の connector

- 場所: §6 D1、§9 R7。
- 根拠: Pi 5 の CAM/DISP は 22 pin の mini FPC。Camera Module v1（OV5647）の付属の 15 pin の cable は挿さらず、15→22 pin の変換 cable が要る（公開の事実、repository の外）。
- 修正案: D1 に「22 pin の cable があるか」を足す（p003 の板の試験の前提）。

### L6（低）Phase の依存と範囲

- p009（規約の全文）の依存が p006 だけ。p007（IMX219 の C）と p008 の後に置く（p007 が保留なら「p007 を除いて」と明記）。
- poll・`O_NONBLOCK` が p002（ws.md の p002 の内容）と p005（§11）の両方にある。どちらかに決める。
- p003 の依存が ws.md では p002、§11 では「並行可」。どちらかに揃える。
- p003 の受け入れ（§11）が「担当が SSH で kernel を入れ替える許可を得て」と、実機の試験は T1 という AGENTS.md の規則（「QEMU・実機の試験は … 試験の担当 T1 に依頼」）とずれる。Q1 の判断として D に足す。

### L7（低）その他の記述

- `CAM_EXPORT_BUFFER`（§3.2 番号 17）: 取り込む側が無いのに handle を作る所まで p002 で実装すると、使われない fd の経路（他の process へ uncached RAM の capability を渡せる）を保守する事になる。p002 では `ENOTTY` にして案 B の WS で実装する方がよい。
- `CAM_CONTROL_TEST_PATTERN` の値 1/2/3 と register の値 0x80/0x82/0x81（ov5647.c:154-159 `ov5647_test_pattern_val`）の対応を表に書く（host の試験の期待値）。
- Linux の `ov5647_write` は失敗しても 0 を返す（ov5647.c:488-509、`return 0;`）。値として引用する時にこの挙動は写さず、§5 の NACK の数え方が成り立つように誤りを返す。
- 640×480 の DPHY の rate は Linux の整数の割り算で 416（208,333,000 × 2 / 10⁶）。417 と書いてあるが同じ行なので害は無い。
- `kern_pmem_alloc_limited` の `max_address` に `dma_physical_limit` の「0 で制限なし」をそのまま渡さない（UINT64_MAX に読み替える）。
- 取り込む buffer の `QUEUE_BUFFER` で前と違う fd を渡した時の扱い、GPU の job が読み終える前に再び `QUEUE` しない契約（fence が無い）を §3.6 に書く。

## まとめ

- 高 3 件（H1 GPU の取り込みの経路が bcm2711 で ENOTSUP、H2・H3 RP1 の non-coherent DMA と dirty な cache の line）は p002/p006 の前に設計を直す必要がある。H1 は他 WS（WS279/WS141）の source の変更を伴い D3 の費用が変わる。
- 中 11 件のうち M1（Bayer の表）は事実の誤り、M2 は実機で決める事項、M3〜M7 は実装者が必ず当たる穴。
- 実機・QEMU の確認は未実施（設計の review）。M2・M9・L3 は推測を含み、p004 の板で確かめる。
