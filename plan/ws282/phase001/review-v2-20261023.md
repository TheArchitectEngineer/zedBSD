## 正しいと確かめた事（指摘なし）

- xHCI の isochronous の上限: encoder は `maximum_packet_size & 0xf800` が 0 でない endpoint と SuperSpeed を拒む（pci-xhci-control.h:164-180）。`xhci_isoch_enqueue` は packet の長さを `max_packet_size & 0x7ff` 以下に限る（pci-xhci.c:8160-8170）。よって HS で 1 interval 1024 byte = 8.192 MB/s が今の上限（design §4.7 の通り）。
- 64 KiB の境界: packet の DMA address が 64 KiB をまたぐと `EINVAL`（pci-xhci.c:8207-8215）。`drv_dma_alloc_coherent` は page に揃える（dma.c、`alignment < page_size` なら page）ので、4096 の stride なら 4096 以下の packet はまたがない。3072 を詰めると 22 番目（21 × 3072 = 64512、+3072 = 67584）でまたぐ計算も正しい。
- `xhci_isoch_finish` は staging から URB の buffer へ packet ごとに `kern_memcpy`（pci-xhci.c:8001-8011）→ class の buffer は CPU だけが書く（§3.4・R5 の「cache の操作は要らない」は uvc の buffer については正しい）。
- FIFO 4 要求 × 32 packet（pci-xhci-isoch.h:43-44）、ring 255 slot に 128 TD が入る。HS の 32 packet = 4 ms（bInterval 1 の時）。
- isoch の URB の契約（callback は wake だけ、1 本の cancel で endpoint の全部が終わる、EALREADY でも空になる）: usb.h:980-990。
- `drv_usb_interface_claim`・`drv_usb_host_interface_extra`・`drv_usb_device_get_string`・`drv_usb_control`・`drv_usb_urb_setup_isochronous`・`drv_usb_urb_iso_result`・`drv_usb_urb_drain`・`DRV_USB_URB_SHORT_OK` は usb.h にその名前である。`cdev_register_managed` と finalizer の規則（cdev.h:83-104）、`vm_device_create` が file を retain し最後の mapping の後に `file_close`（vm/device.c:103・145-149）、`kern_pmem_to_kernel`・`kern_pmem_map_uncached`（pmem.h:65・86）、`waitq_sleep(queue, spinlock, …)`（waitq.h:47）、`kern_rtc_read_counter`（clock.h:194）、devfs の既定 0666（devfs.c:583-589）、ioctl の group `'C'` は include/uapi で未使用。
- UVC の定数: VS の subtype（INPUT_HEADER 0x01、FORMAT_UNCOMPRESSED 0x04、FRAME_UNCOMPRESSED 0x05、FORMAT_MJPEG 0x06、FRAME_MJPEG 0x07、COLORFORMAT 0x0D、FRAME_BASED 0x10/0x11）、VC の subtype 0x01〜0x06、request の番号 0x01・0x81〜0x87、selector PROBE 0x01・COMMIT 0x02、PROBE の record の byte の並びと長さ 26/34/48（Linux uvc_video.c:276-284・338-360 と一致）、payload header の bit（FID 0、EOF 1、PTS 2、SCR 3、RES 4、STI 5、ERR 6、EOH 7）と PTS 4 byte・SCR 6 byte、YUY2/UYVY/NV12 の GUID の文字列。
- 帯域の数: 640×480×2×30 = 18.43 MB/s、1280×720×2×10 = 18.4 MB/s（3072 × 8000 = 24.6 MB/s に入る）、1080p の YUYV 4,147,200 byte。合計の見積もり 29〜40 LW（p010 を除き 27〜37）の足し算。

## 指摘

### H1（高）HS の isochronous IN の経路は実機で一度も動いていない。p004 はそれを確かめ済みの土台として扱い、p005 の回帰の基準（SCO）も存在しない

- 場所: design §4.3（「usb-bt の SCO と同じ作法」）、§9 R5（「non-coherent の板で xHCI の staging の扱いが正しい事は既存の USB の driver（storage・NCM）で通っている」）、§4.7 の 4（回帰「BT の SCO（T1）」）、§6.2 D10（「WS197 は完了の WS」）、§11 p004・p005。
- 根拠: WS197 p007 の記録（plan/ws197/phase007/phase.md:319）「X12 (b) の QEMU の ktest は作らない。…isoch の実地は p007a2 の最初の 5330 の HCI Local Loopback」、同 :365「xHCI の isoch の初めての実地（p007a1 の受け入れの続き）」、:383「5330 は新しい image の後」。L2 の結果の記録は無い。WS207 p003（UAC1）も planned（plan/ws207/ws.md:32）。SCO の実の利用は FS・8 packet・63 byte 以下の物（usb-bt.c:103-105、phase007:327）で、HS・1024 byte・32 packet の IN は誰も流していない。`xhci_isoch_finish` の packet ごとの複写は bulk の `xhci_completion_finish` とは別の code で、storage・NCM の実績は当たらない。WS197 は incomplete（plan/master.md:520、ws197/ws.md:6）で、p007 は in-progress（ベータ3）。
- 起こる状況: p004 の最初の板の試験が、uvc の誤りと xHCI の isoch の初めての不具合（TD の照合、skip の規則、BEI、IN の短い packet、Missed Service の扱い）の切り分けになり、5〜7 LW に入らない。p005 の受け入れ「SCO・HID の回帰 PASS」は、SCO が一度も PASS していないので比べる基準が無い。p005 の xHCI の変更は WS197 p007a2 が同じ file を直している最中に入る（衝突）。
- 修正案: (1) R5 と §4.3 の「既存の作法で通っている」を「isoch IN は未実地」に直す。(2) p004 の最初に「xHCI の HS isoch IN の実地」の段（低い帯域の webcam か HDMI capture の小さい alternate で、`hw.usb` の isoch の統計と URB ごとの packet の結果を SSH で読む）を置き、見積もりに 2〜3 LW を足す。(3) D10 を「WS197 は incomplete、p007 が同じ isoch の code を変えている」に直し、p005 の前提に「WS197 p007a2 の L2 が PASS して main にある事」と担当の調整（Q1）を足す。p005 の回帰の基準は L2 の結果を使う。

### H2（高）帯域の足りない alternate を選ぶ方針と D8 の「640x480 で約 13 fps」は UVC の device の振る舞いと合わない。p004 の受け入れは HDMI capture では満たせない見込み

- 場所: design §4.3 の alternate の選択（「無ければ受けられる中で最大の物を選び、log に…（device は fps を落とすか frame を欠く）」）、冒頭の要約・§6.2 D8（「p005 の拡張までは MJPEG と小さな YUYV（640x480 で約 13 fps）だけ」）、§11 p004 の受け入れ（「MJPEG と 640x480 の YUYV」「300 frame 連続で落ちなし」）。
- 根拠: isochronous は device が速さを決める。device は COMMIT した `dwFrameInterval` で frame を作り、host が選んだ alternate の packet の大きさまでしか 1 microframe に送れない。host が小さい alternate を選んでも device は fps を下げない（内部の FIFO が溢れて frame が欠けるか ERR が立つ）。Linux は帯域の足りる alternate が無ければ stream を始めない: uvc_video.c:2045-2085（`psize >= bandwidth` の最小、無ければ「No fast enough alt setting for requested bandwidth」で `-EIO`）。帯域を下げるのは PROBE で interval・質を変えてからで（uvc_video.c:441-487 の `uvc_probe_video`）、alternate の側ではない。13 fps の数（8.192 MB/s ÷ 614,400 byte、header 12 byte を引けば 13.2）は device がその interval を持つ時だけ意味がある。
- 推測: MS2109 級の YUYV の mode は USB 2.0 の最大（約 20 MB/s）に合わせた組（1080p 5 fps、720p 10 fps、640x480 30 fps など）で、どれも 1 microframe 2.3〜2.6 KB = 3072 の alternate を要る。そうなら p005 の前は YUYV の mode は 1 つも使えない。MJPEG も device は PROBE で 3072 前後を答える事が多い。p003 の dump で確かめるまで分からない。
- 起こる状況: p004 の板で YUYV の frame が上半分だけ・ERR・drop だらけになり、受け入れ「300 frame 落ちなし」を満たせない。MJPEG も pattern（§7.4 の 1 画素の市松は JPEG の最悪の入力）で 1080p の frame が数百 KB になり 8 MB/s を超えると同じになる（推測）。不具合が uvc の組み立てか帯域か区別できない。
- 修正案: (1) `set_mode`（と TRY）は COMMIT の P が今の xHCI の受ける alternate の容量を超えれば `ENOSPC` で拒む（Linux と同じ）。`start` も同じ検査。log だけで進めない。(2) `ENUM_MODE` の各 interval に「今の host で取れる」の flag を付けるか、TRY で分かる事を ABI に書く。(3) D8 の答えを「p005 までは、device が P ≤ 1024 の interval を持つ mode だけ。HDMI capture の YUYV は p005 の後の見込み（p003 の dump で確かめる）」に直す。(4) p004 の受け入れを「P ≤ 1024 の mode（webcam の 320x240/640x480 の低い fps、または capture の MJPEG の低い mode）で frame が正しい」にし、HDMI capture の YUYV と MJPEG 1080p は p005 の後（p006）へ。または p005 を p004 の板の受け入れの前に置く（§10 の「拡張を p004 の前に」をしない理由は、この見込みが正しければ崩れる）。(5) D12 の webcam を p004 の試験の device に勧める（多くの webcam は 128〜3072 の alternate と小さい YUYV の mode を持つ、推測）。

### H3（高）bulk の「endpoint に 4 本同時に出せる」は誤り。2 本目は EBUSY

- 場所: design §4.4「xHCI は `DRV_USB_HCD_CAP_CONCURRENT_URBS` を持つので endpoint に 4 本同時に出せる」。
- 根拠: usb.h:79「The HCD accepts one active URB per endpoint instead of one per controller.」。`xhci_urb_enqueue` は isoch でない endpoint で `ep->active != NULL` なら `EBUSY`（pci-xhci.c:4161-4172）。FIFO は isoch の endpoint だけ（pci-xhci.c:4139-4143、WS197 X1「bulk・interrupt・control は今の 1 つだけのまま」）。
- 追加の穴: (1) bulk の URB の大きさを `dwMaxPayloadTransferSize` にすると、frame 全体（数 MB）を言う device では `xhci_request_alloc` が投入のたびに数 MB の連続の coherent を取る（予約は 64 KiB まで、usb.h:85）。Linux は payload transfer が URB をまたぐ前提で組む（`uvc_video_decode_bulk`、header は payload の最初の URB だけ）。(2) bulk の URB の timeout（`drv_usb_urb_setup` の t）を書いていない。HDMI の信号が無い間 NAK が続く。(3) 手元の device（HDMI capture、買う webcam）が bulk か分からず、bulk の経路を試す device が計画に無い。
- 起こる状況: bulk の device で `start` の 2 本目の submit が `EBUSY` → `drv_cam_source_fault` か無限の再試行。1 本ずつなら完了と再投入の間に device の FIFO が溢れ得る。
- 修正案: bulk は 1 本を回す形にし（完了 → すぐ再投入、worker でなく可能なら完了の直後）、URB は 64 KiB 以下で `drv_usb_urb_reserve_transfer`、payload は URB をまたいで組む（header は payload の最初だけ、短い packet か累計 `dwMaxPayloadTransferSize` で payload の終わり）。複数本が要るなら xHCI の bulk の FIFO（WS197 の source、Q1）を別 Phase に。bulk の device が手元に無ければ p004 の範囲から外すか「未実地」と明記。

### H4（高）URB の完了を bit で受けると、1 回の wake で 2 本終わった時に順が入れ替わり frame が壊れる

- 場所: design §4.3「完了の callback は URB の番号の bit を立てて worker を起こすだけ（`usb_bt_sco_completion` の型）」、「完了した URB の packet を順に見て」。
- 根拠: usb-bt の型は bit を集めて番号の小さい順に処理する（usb-bt.c:1833-1860 の completion、1884-1905 の thread: `for (index = 0; index < USB_BT_SCO_IN_URBS; index++) if (work & (1U << index))`）。URB は 0→1→2→3→0 の順に終わるので、worker が 4 ms 以上遅れて URB 3 と URB 0 が同じ wake で見えると、0（新しい）→ 3（古い）の順に payload を解析する。
- 起こる状況: FID の判定（§4.5 の 1）が、新しい frame の payload の後に古い frame の payload を見て、frame を途中で `done`（INCOMPLETE）し、古い payload で新しい slot を取る。worker の遅れ（R3、WS285 の compute と同時）で起き、host の試験（§7.1 の uvc-payload-host-test は packet の列だけ）では出ない。
- 修正案: 投入の順の ring（`next_complete` の番号）を持ち、worker はその番号の URB が終わっている間だけ順に処理する（bit は「終わった」の印に使ってよいが、処理の順は ring）。host の試験に「2 本・3 本が同時に終わる」「wrap の直後」を足す（偽の URB の層）。注記: usb-bt の SCO も同じ形で、組み立て直しの resync で吸収しているが順の入れ替えは数えられていない（WS197 の範囲、別に報告する価値がある）。

### M1（中）128 KiB の URB は予約できず、投入のたびに連続の coherent を取り直す。non-coherent の板では毎秒 250 回の uncached の alias の作成と解放になる

- 場所: design §4.3「1 本 = 32 × 4096 = 128 KiB（staging も同じ大きさの連続の coherent の run。xHCI の `xhci_request_alloc` に大きさの上限は無い）」、§10「staging が 33% 増えるが 128 KiB」。
- 根拠: 予約（`drv_usb_urb_reserve_transfer`）は 64 KiB まで（usb.h:85、usb.c の `capacity > DRV_USB_TRANSFER_RESERVE_MAX_SIZE` で EMSGSIZE）。予約の無い URB は投入ごとに `kern_malloc` + `drv_dma_alloc_coherent(length, 64)`（pci-xhci.c:3746-3766）、完了で `drv_dma_free_coherent`（同 3797-3802）。non-coherent の板の coherent は page に丸めた run を uncached の alias で持つ（dma.c）。今の packet は 1024 以下なので、stride 4096 は不要（1024 は 64 KiB を割り、page に揃った staging では 1024 の stride でまたがない）。
- 起こる状況: Pi 4/5・VF2 で 4 ms ごとに 32 page の連続の確保、alias の map・unmap と cache の保守。断片化（§3.4 の 4 MB × 8 の buffer と同時）で途中の投入が `ENOMEM` になると、§4.3 の再投入の規則（EBUSY/EAGAIN は待つ、ENODEV は fault）に `ENOMEM` が無い。
- 修正案: 今は stride 1024（または packet の大きさ）× 32 = 32 KiB の URB にし、`start` で 4 本とも `drv_usb_urb_reserve_transfer(urb, 32 KiB)`（xhci_urb_reserve は 2 の冪に揃えるので 64 KiB をまたがない、pci-xhci.c:3984-3999）。p005 の 3072 では 64 KiB の予約に 21 packet を詰める（21 × 3072 = 64,512）か stride 4096 × 16 packet。再投入の `ENOMEM`・`EMSGSIZE` の扱いを書く。

### M2（中）frame の組み立て（§4.5）の状態の穴

- 場所: design §4.5 の 1〜5、§3.5 の `sequence`・`flags`、§9 R2。
- 根拠と穴:
  1. `fid` の初期値が無い。Linux は −1 で始め最初の payload で frame を始める（uvc_video.c:1213-1215）。
  2. EOF の後 `current = NULL` で、同じ FID の payload（EOF の後の header だけの payload や、遅れて来た同じ frame の残り）が来ると、1 の条件（FID が違う）に当たらず 2 の `current + offset` への複写に進む（NULL への書き込み、または未定義）。Linux は「ACTIVE でない buffer は FID が変わるまで payload を捨てる」（uvc_video.c:1296-1312）。
  3. R2 の「FID を反転しない device」への対処を「§4.5 に入れた」とするが、§4.5 に無い。そういう device では最初の EOF の後、FID が二度と変わらないので frame が 1 枚も出なくなる。Linux は `UVC_QUIRK_STREAM_NO_FID` で EOF の時に last_fid を反転する（uvc_video.c:1306-1308・1397-1403）。
  4. FID の変化で `done` する時に `offset == 0` の空の frame も返す。Linux は空の buffer を完了しない（uvc_video.c:1217-1225）。
  5. EOF を立てない device では全部の frame が `CAM_FRAME_INCOMPLETE` になる。Linux は FID の反転を正常な frame の終わりとして扱う（同 1209-1225）。一方、非圧縮の frame の長さが足りない事は検査していない: Linux は非圧縮で `bytesused != dwMaxVideoFrameSize` なら error（uvc_video.c:1535-1541 `uvc_video_validate_buffer`）。buffer は使い回すので、短い YUYV の frame の下の行は前の frame の画素のまま「正しい frame」として出る。
  6. MJPEG の「末尾の 2 byte が EOI でなければ ERROR」: EOI の後に詰め物の 0 を付ける device がある（推測、Linux は検査しない）。誤った ERROR になる。
  7. PTS/SCR の bit と `bHeaderLength` の整合（PTS なら ≥ 6、SCR も足して ≥ 12）を見ていない。header を越えて data を PTS として読む。
  8. sequence: 「take ごとに +1、drop でも +1」は、take が EAGAIN の時と、take の後の溢れ（discard + `dropped(OVERFLOW)`）で 2 回数え得る。`camcheck` の「飛びは drop の数と一致」が合わなくなる。
- 起こる状況: 2 は kernel の fault か壊れた frame、3 は stream が止まる、5 は壊れた画素が正しい frame として出る（WS285 の検出の入力が黙って壊れる）。
- 修正案: Linux の `uvc_video_decode_start/end` と同じ状態（last_fid = 無効で開始、ACTIVE でなければ FID が変わるまで捨てる、空の frame は完了しない、NO_FID の device は EOF で反転）を §4.5 に書く。`INCOMPLETE` は「非圧縮で used_bytes ≠ stride × 高さ」と「MJPEG で SOI が無い」だけにし、FID の反転は正常の終わり。EOI は末尾の一定の範囲（例 64 byte）で探す。header の長さを flag と照らす。sequence は「FID の変化 1 回に 1」と 1 か所で数える。全部を uvc-payload-host-test の case に。

### M3（中）COMMIT は SET_FORMAT の時だけ。STREAM_ON の度に COMMIT し直さず、他の open の TRY（PROBE）が間に入る

- 場所: design §2.2（`try_mode` = PROBE、`set_mode` = PROBE + COMMIT、`start` = alternate の選択）、§3.2 の 4〜6（TRY は所有を取らずどの open でもよい）、§7.3 p006「stop/start 100 回」。
- 根拠: UVC は COMMIT の後に alternate を選ぶ手順。Linux は stream の開始ごとに COMMIT する（`uvc_video_start_streaming` の uvc_video.c:2344-2347、resume の 2196 も同じ）。design では STREAM_OFF（alternate 0）→ STREAM_ON の時に COMMIT が無い。また所有者が SET_FORMAT した後・stream 中に、他の open の TRY_FORMAT が `SET_CUR(PROBE)` を device に送る。推測: 一部の device は最後の PROBE の値で stream する、または alternate 0 で COMMIT の状態を失う。
- 起こる状況: 2 回目以降の STREAM_ON で frame が来ない・別の大きさの frame が来て溢れる。p006 の stop/start 100 回で device ごとにたまに出る。
- 修正案: `start` の中で alternate の選択の直前に COMMIT（保存した PROBE の答え）を送り直す。所有者がいる間（BUFFERS・STREAMING）の他の open の TRY は device に送らず、保存した答えか `EBUSY` を返す。

### M4（中）抜去の時の停止が二重になり得る。close の路が admission に入っていない

- 場所: design §2.3（「source の detach の順（uvc）: streaming なら `stop` → `drv_cam_unregister`」、「進行中の ioctl の数（admission）: ioctl と mmap の入口で」）、§4.1「`quiesce` は worker の join と URB の drain」、§5 の close。
- 根拠: uvc の detach が自分で `stop` を呼ぶと、枠組みの `device->mutex` の外で、同時の `STREAM_OFF`・所有者の close（枠組みが mutex の下で source の `stop` を呼ぶ）と競る。worker の二重の join、URB の二重の cancel/drain、alternate 0 の二重の SET_INTERFACE になる。close（cdev の close op）は admission に数えられていないので、`drv_cam_unregister` が戻った後に close が source の `stop` を呼ぶ路が残る（その時 uvc の構造体は解放済み）。`quiesce`（usb.h:315-319「successful quiesce keeps the binding until reset」）の後、枠組みは STREAMING のまま worker がいない。
- 起こる状況: stream 中の抜去（§7.3 p006 の項目）と同時の close・STREAM_OFF で、join 済みの thread の再 join や解放後の参照。quiesce の後は DEQUEUE が永久に待つ（M5）。
- 修正案: 停止は枠組みだけが行う: `drv_cam_unregister` が mutex を取り、STREAMING なら source の `stop` を 1 回呼び、GONE にしてから admission の 0 を待つ。uvc の detach は `stop` を呼ばない（または uvc の `stop` を内部の flag で冪等に）。close・poll・mapping の release も mutex の下で GONE を見る（または admission に数える）。uvc の `quiesce` は `drv_cam_source_fault` を先に呼ぶ。

### M5（中）監視（watchdog）の定義が isochronous では働かず、HDMI の信号が無い時に DEQUEUE が永久に待つ

- 場所: design §5「FAULT（…または 2 s 間 frame が無い watchdog）」と「監視: …uvc の worker が自分で見る（URB の完了が 1 s 無い = device が止まった）」（2 つの定義が食い違う）、§3.2 の DEQUEUE（timeout 無し）。
- 根拠: isochronous の URB は device が何も送らなくても 32 packet 後に終わる（長さ 0 の packet、または Missed Service で MISSED、pci-xhci-isoch.h:16-21 の規則）。よって「URB の完了が 1 s 無い」は抜去以外でほぼ起きない。「2 s 間 frame が無い」を見る thread は枠組みに無い（§5・§10 で枠組みの thread を持たないと決めた）。bulk では逆に、信号の無い間の NAK で URB が終わらず 1 s で FAULT になる（正常な待ちを故障にする）。
- 起こる状況: HDMI の入力が無い・PC が画面を切った時、capture が frame を出さない device なら（推測）、`O_NONBLOCK` でない DEQUEUE が戻らない。quiesce の後（M4）も同じ。
- 修正案: worker の中で「最後に frame を `done` してから max(2 s, 4 × frame の間隔)」を見る（URB の完了とは別）。故障にするか counter と `POLLERR` 無しの印にするかを決める（信号無しは故障でない）。`cam_buffer` に DEQUEUE の timeout（ms）を足すか、`poll` を使う契約を明記。`waitq_sleep` は `WAITQ_INTERRUPTIBLE` で（signal で戻る）。

### M6（中）buffer を 0 で埋めていない。mmap で kernel の古い memory が user に見える

- 場所: design §3.4（`kern_pmem_alloc` → `vm_device_create(..., PROT_READ, ...)`）。
- 根拠: `kern_pmem_alloc` は中身を消さない（pmem.h・pmem.c に 0 埋めの記述が無い）。前例の audio.c は確保の直後に `kern_memset(stream->shadow_address, 0, AUDIO_RING_BYTES)`（audio.c:2048-2059）。MJPEG は `used_bytes` の後ろ、最初の frame の前は全体が古い中身のまま user に map される。
- 起こる状況: seat の user が他の process や file の page の残りを読める（情報の漏れ）。
- 修正案: `REQUEST_BUFFERS` で各 run を `kern_memset` 0（4 MB × 8 でも 1 回）。host の試験に「確保直後の buffer は 0」。

### M7（中）試験の計画が誤りを見逃す、または正しい物を FAIL にする

- 場所: design §7.3（p004〜p007 の表）、§7.4（`camcheck` と `pattern.html`）、§7.1。
- 根拠と穴:
  1. frame counter（`requestAnimationFrame` ごとに +1）: PC の出力は 60 Hz、capture は 30 fps 以下なので、正常でも 1 frame に 2 以上進む。browser の jank で rAF が飛ぶ、capture の frame の取り込みが入力の vsync と合わず上と下で違う値を写す（tearing、推測）。「飛びは drop の数と一致」は成り立たない。
  2. 色: capture の RGB → YCbCr が BT.601 か BT.709 か（と PC の出力の range）で 75% の patch の値が ±8/255 を超えて動く（cyan・magenta で約 10〜20/255、推測）。design は range だけ記録し matrix を記録しない。
  3. 1 画素の市松は JPEG の最悪の入力で、MJPEG の bit rate を上げ H2 の帯域の問題を pattern が自分で起こす。
  4. MJPEG の DHT: libjpeg-compat は DHT が無いと失敗する（marker.c の DHT だけで表を作る、error.c:43「Huffman or quantization table 0x%02x was not defined」）。design は `camcap` だけが標準の表を挿すとするが、`camcheck`（libjpeg-compat に link、§4.8）と WS285 の app も同じ補いが要る。
  5. 「stream 中の抜去と再挿入」は人の手が要る（zedBSD に software の port の切り離しの道具が無い、userland に lsusb だけ）。T1 は実行できない。「stop/start 100 回で leak なし」の測り方（どの counter）が無い。
  6. host の試験に、URB の順（H4）、帯域の不足（H2）、NO_FID・EOF 無し・空の payload（M2）の case が無い。
  7. bulk の経路を試す device が無い（H3）。
- 修正案: counter は「単調に増える」だけを合否にし、増分の分布を記録する（drop は `sequence` の飛びで別に数える）。色は最初の frame の白・黒・2 色で matrix と range を推定してから許容を当てるか、patch を 100% の原色と灰に限り matrix を記録。市松は MJPEG の試験では外す（別の pattern）。DHT の補いは userland の小さな共通の関数にして `camcap`・`camcheck`・WS285 で使う。抜去はユーザーの UAT の一覧（AGENTS.md の運用）に入れ、T1 には `stop` → USB の device の reset など software でできる代わりを。leak は `io_stats`（`IO_DMA_REQUEST` など、`hw.usb`）の前後の差で。推測: 試験する板自身の HDMI 出力（Pi 4/5）で pattern を出せば PC と人が要らない（zedBSD の HDMI の出力が使えるかは未確認）。

### M8（中）p005 の内容が足りず、見積もり 3〜4 LW は小さい

- 場所: design §4.7 の拡張の 1〜4、§9 R3、§11 p005。
- 根拠と穴:
  1. HS の high-bandwidth: §4.7 の 1 は context だけで、Isoch TRB の TBC/TLBPC を SS だけに書く。Linux の xHCI は xHCI 1.0 以上で HS でも TLBPC = TD の packet 数 − 1（TBC は 0）を入れる（`xhci_get_last_burst_packet_count`、記憶。今回 xhci-ring.c は取得していない、推測）。入れないと 3072 の TD が 1 packet として扱われる controller があり得る（推測）。
  2. SS の isoch: 1 TD = 1 TRB（pci-xhci.c の enqueue、WS197 X4）の作りでは、48 KiB の TD は 64 KiB の境界をまたがないよう 64 KiB の stride が要り、1 本 8 packet = 512 KiB（予約の上限 64 KiB を超え M1 の毎回の確保）。SS の ESIT は 125 µs なので 8 packet = 1 ms、FIFO 4 本で 4 ms の余裕しか無く、worker が 1 tick（1 ms、`HAL_TIMER_FREQUENCY` 1000）単位で眠る作りでは足りない。
  3. R3 の対策「本数は 4 のまま packet を増やす」は `DRV_XHCI_ISOCH_PACKETS_MAX` 32 と ring の 255 slot（4 × 32 = 128 の倍は入らない）で、WS197 の定数の変更になる。
  4. WS197 p007 が同じ code を変えている（H1）。
- 修正案: p005 を HS の high-bandwidth だけにし（TLBPC を含め、xHCI 1.2 §4.11.2.3・§6.4.1.3 を読んで決める）、SS の isoch（TRB の分割か 64 KiB の stride、FIFO の深さ、完了の直後の再投入）は別 Phase（後、USB 3 の device を買った時）に。R3 の対策を「FIFO と packet の定数の変更（WS197、Q1）」と書き直す。

### M9（中）MJPEG の format descriptor の形の誤り、GUID の byte 順、仕様の節の引用

- 場所: design §4.1 の 3（「VS_FORMAT_MJPEG（0x06: `bmFlags`、他は uncompressed と同じ）」）、§3.3（「UVC 1.1 §3.9.2.3 の GUID」「§3.9.2.5」）、§8 の表。
- 根拠: MJPEG の format descriptor には `guidFormat`（16 byte）と `bBitsPerPixel` が無く、`bNumFrameDescriptors` の次が `bmFlags`、続いて `bDefaultFrameIndex`・aspect・interlace・copy protect（全 11 byte。uncompressed は 27 byte）。uncompressed の offset で読むと `bDefaultFrameIndex` などを誤る。GUID の byte 列は Data1〜Data3 が little endian（YUY2 は `59 55 59 32 00 00 10 00 80 00 00 AA 00 38 9B 71`）。uncompressed の GUID と MJPEG の descriptor は UVC 1.1 の本体でなく別の payload の仕様（Uncompressed Payload・MJPEG Payload）にある（推測、仕様は手元に無い）。
- 起こる状況: MJPEG の既定の frame を取り違える。GUID の文字列を byte 順を考えずに比べると YUY2 を認識しない。License の注記の「Value(s) referenced」の節が違う。
- 修正案: MJPEG の format の field を別に書き、host の試験の descriptor に MJPEG を必ず入れる。GUID は byte 列で定義する。§8 と code の注記の出典を payload の仕様の名前と節に直す。

### M10（中）Phase の依存の誤り、suspend の影響の書き漏れ

- 場所: design §11、§5「shutdown・suspend は Future Work」。
- 根拠と穴:
  1. p008 の板の試験は「Pi 5 + capture」だが、Pi 5 の uvc の確認は p007。依存は「p004、WS279」だけ。
  2. p004 の YUYV の受け入れは p005 に依る（H2）。p005 は WS197 p007a2 に依る（H1）。
  3. xHCI は isoch が流れている間 system の suspend を拒む（pci-xhci.c:6675「An isochronous stream refuses the sleep before the gates close.」、WS197 X10: 2 秒待って失敗）。camera を開いて stream している app（camcap、WS285 の demo）が居る間、蓋を閉じても 5330 は眠らない。Future Work とするなら影響（suspend の失敗）と、suspend の前に stream を止める（FAULT にする）かを書く。
- 修正案: p008 の依存に p007（少なくとも Pi 5 の部分）を足す。H1・H2 の依存を §11 の表に入れる。§5 に suspend の振る舞いを 1 行。

### L1（低）PROBE/COMMIT の細部

- `GET_LEN` を優先する方針（§4.2）は Linux と違う。Linux は `bcdUVC` だけで長さを決め、GET_LEN を使わない（uvc_video.c:276-284）。GET_LEN が誤った長さを返す device では SET_CUR が stall する（推測）。版で決め、GET_CUR が短い長さで返った時に受ける形の方が安全。
- Linux の既知の修正が抜けている: `dwMaxPayloadTransferSize` の上位 16 bit が全部 1 の device（16 bit の値の符号拡張、uvc_video.c:221-227）、P が device 自身の最大の alternate を超える device の P の切り詰め（同 266-273）、非圧縮では `dwMaxVideoFrameSize` を frame descriptor の `dwMaxVideoFrameBufferSize` で置き換える（同 214-218）。`dwMaxPayloadTransferSize` 0 の見積もり（§4.2 の式）は Linux の FIX_BANDWIDTH の式（同 229-264、12 byte の header を足し 1024 を下限）に揃えると根拠が書ける（Guardrail の規則で「Value(s) referenced」）。

### L2（低）build の配管の抜け

- arm64 の `ARM64_USB_SOURCES` は列挙した CONFIG のどれかが y の時だけ `usb.c` を入れる（platform/arm64/vmunix.mk:213 の `filter`）。`CONFIG_DRIVER_USB_UVC` をその列に足さないと、uvc だけを y にした config で usb.c が入らない。
- driver の登録の場所は 5 つ: `src/kern/platform/pcat.c:283`、`src/drivers/platform/rpi4/rpi4-pcie.c:275`、`src/drivers/platform/rpi5/rp1-usb.c:731`、`src/drivers/platform/visionfive2/vf2-pcie.c:228`、`src/drivers/platform/riscv-virt/virt-pci.c:151`。§4.8 に列挙する。`cam.c` は USB に依らない（将来の CSI）ので `AMD64_USB_CLASS_SOURCES` でなく独立の knob が良い。

### L3（低）hotplug の event の class が決まっていない

- §2.3 は「hidraw と同じ経路」とするが、hidraw は `KERN_SYSTEM_EVENT_INPUT`（hidraw.c:733）で、sessiond の seat は `INPUT | USB` だけを受ける（seat.c:70）。camera を INPUT で出すと input の利用者が誤解し、新しい class なら `include/uapi/system.h` と seat の subscription の変更（p009）。どちらにするかを書く。

### L4（低）UAPI の細部

- record の layout（field の順・幅・padding・`size`）が無い。p002 で決めるなら、`_Static_assert` で大きさを固定し host の試験に入れる事を受け入れの条件に。`cam_buffer` に `cam_frame_metadata`（64 bit の field）を埋めるので明示の padding を。
- `intervals[8]`: UVC の離散の interval は 255 個まで持てる（`bFrameIntervalType`）。9 個目以降の扱い（切る・番号で引く）を書く。
- `QUERY_BUFFER` と `poll` を誰ができるかが無い（非所有者の poll は POLLIN で回り続ける）。`REQUEST_BUFFERS` を STREAMING の間に呼んだ時の答え（EBUSY）が無い。
- DEQUEUE の「close で EINVAL」は、同じ file で眠る thread が file を retain する間は close の op が来ないので起きない（同じ process の別 thread の close）。STREAM_OFF で起こす、と書き直す。

### L5（低）alternate の選び直しの順

- §4.3「endpoint の enable が encoder に拒まれると次に小さい alternate へ」: `drv_usb_interface_set_alternate` は device に SET_INTERFACE を送った後で host の endpoint を enable し、失敗すると SET_INTERFACE で戻す（usb.c:3412-3470）。拒まれる alternate を毎回 device に選ばせ、戻しの timeout は device の隔離（`device_quarantine_selection`）になる。encoder の検査（`drv_xhci_endpoint_context_encode` は inline の純粋な関数）と同じ条件で先に候補を絞る。

### L6（低、推測）usb-bt の型の thread の後始末の競合

- usb-bt は SCO の thread を `thread_wait` の後に `bt->sco_thread = NULL` を lock の外で書き（usb-bt.c:1648-1649）、completion は lock の下で `bt->sco_thread` を読んで起こす（同 1857-1861）。join と cancel の間に URB が終われば、回収済みの thread を起こし得る（`thread_wait` が thread を解放するかは未確認）。uvc は「NULL を lock の下で書いてから join」「join の前に cancel」の順を §4.3 に書く。

### L7（低、推測）hard IRQ の中の複写

- `xhci_isoch_drain` は `xhci_irq` から呼ばれ（pci-xhci.c:1488-1492・3189-3191）、`xhci_isoch_finish` の `kern_memcpy` は hard IRQ の中で走る。non-coherent の板では staging が uncached なので、p005 の 3072 × 32 = 96 KiB/4 ms を uncached から読む。Pi 4 の A72 での所要時間を p007 で測る（遅ければ xHCI の側で worker に移す、WS197 の source）。

### L8（低、推測）板の xHCI の isoch の個性

- Pi 4・VF2 の VL805 と Pi 5 の RP1（DWC3）は、Linux に isoch や ring の巻きに関わる quirk がある（VL805 の TRB の cache など、記憶。未確認）。isoch は ring を絶えず巻くので、p007 の前に Linux の `xhci-pci.c`・`xhci-ring.c` の該当の quirk を調べる段を置く。

## 推測と未確認のまとめ

- MS2109 の実の mode・alternate・isoch か bulk か・信号無しの振る舞い（H2・H3・M5）: p003 の dump で確かめる。
- Linux の xHCI の HS の TLBPC（M8 の 1）、VL805/DWC3 の quirk（L8）: xhci-ring.c・xhci-pci.c は今回取得していない。
- UVC 1.1/1.5 と payload の仕様の節番号（M9）: 仕様の PDF は手元に無く、Linux の実装と記憶で照合した。
- `thread_wait` の後の thread の寿命（L6）、uncached の読みの速さ（L7）、color matrix の差の大きさ（M7 の 2）。
