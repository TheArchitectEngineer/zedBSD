# WS213 compositor の thread 化: 設計の要約（ユーザーの review 用）

設計の本文は [phase.md](phase.md)（第 6 版）。この頁は、その要点を 1〜2 頁にまとめた物です。節の番号は本文の節です。2026-10-12 ユーザーが「この設計でよい」と確認。

## 何が問題か

compositor（`userland/desktop/wayland/`）は今 1 本の thread で動いています。1 コマを描く間（描く命令を作る、GPU に送る、表示を頼む）は、マウスの読み取りも cursor の表示も止まります。Pi 4 の記録では、普通のコマで 10〜20ms、App Home を開くような重いコマで 60〜120ms 止まっています。この間 cursor が引っかかります（1 節）。

## thread の分け方（3 節）

| thread | 受け持つ物 |
| --- | --- |
| **M**（main、今の thread） | Wayland の protocol（client との話）、窓への通知（マウスの motion・enter、key など）、hover と cursor の形の決定、画面の状態の全部、「描く物の一覧」を作る（今の描画のコードをそのまま歩く）、入力の device の開け閉め |
| **R**（描画、1 本） | 一覧を GPU の命令に直して送る、表示を頼む、GPU の終わりを待つ |
| **C**（cursor、1 本） | cursor の plane（cursor 専用の重ね合わせ）の表示。1 refresh（16.7ms）に 1 回まで |
| **I**（入力、1 本） | マウス・touchpad の読み取り、加速、画面をまたぐ位置の計算。位置を C の受け箱に直に書く。全部の入力を順番どおり M に渡す |
| **W**（作業、p005） | 文字の形（glyph）を描く、壁紙のぼかし、時計の大きな字 |

ユーザーの指示「ウィンドウへの通知の転送以外の処理はほとんどすべてスレッドに」に沿い、M に残るのは窓への通知と、画面の状態を持って描く物を決める所だけです。

## 渡し方（2・4・6 節）

- **描く物の一覧＋pull**（ユーザーの判断）: R が「描く画面の画像を取れた、描いてよい」と知らせ、M は今どおりの時（client の絵を少し待つなど）に一覧を 1 回作って渡します。画像を取れた後にしか一覧を作らないので、作った一覧は必ず描かれ、無駄や食い違いが出ません。M が一覧を作っている間、R は何もしないので、M は今のコードのまま GPU の物を作れます。
- **受け箱**: cursor の位置と形を入れる 1 組の箱です。I が位置を、M が形を書き、C が最新を読んで表示します。古い値は上書きされ、溜まりません。
- **FIFO（順番どおりの列）**: I→M の入力の列（押した・離したの順を崩さない）と、R→M の知らせの列（描き終わり、次を描いてよい）。lock は 3 つで、2 つを同時に持たない、lock を持ったまま GPU や待ちを呼ばない、という規則にしてあります（4.6）。
- **device の付け外し**（review-5）: マウスの device が抜けた・画面の切り替えで止まった時は、M が I に「外して」と頼み、I が外したと答えてから閉じます。閉じた番号を別の file が使い回しても、I が間違って読むことはありません。

## park（止めて変える、4.8）

出力の開け閉め・解像度の変更・画面の切り替え・sleep の時は、M が R と C を一度止め（park）、両方が「止まった」と答えてから変更し、また動かします。変更の間、cursor の plane は出しません。止まるのに時間がかかりすぎたら（GPU の中で固まった時）、後始末をせずに log を出して終わります（他の thread が GPU の中にいて後始末が呼べないため）。I は GPU を使わないので止めません。

## 何が速くなるか

- **cursor の位置**: I が M と関係なく受け箱に書くので、App Home の開閉や窓の drag で M が数十 ms 止まっても、cursor の位置は止まりません。この WS の必達は「マウスが動いた時刻から受け箱に書かれるまでの遅れ（box_lag）の p99 ≤ 16.7ms」です。最長も 16.7ms 以内を判定し、超えた原因が kernel の中の長い処理なら WS208（SMP）・kernel への依存として返します（6.4）。
- **入力の反応**: M は描く命令を GPU に送る・待つ仕事が無くなり、一覧を作るだけになるので、窓への通知（hover、click）の遅れが減ります。M の 1 回の仕事は最長 33.3ms（2 refresh）以内が目標です。
- **画面に映る cursor の 60fps** は、WS141 p016 (B) の速い経路（B-u、位置だけの表示が GPU を通らない）が入ってから判定します。分担は、WS141 が「main loop が止まらない時の入力→表示の依頼」、この WS が「マウスの入力→画面の cursor」の端から端です（6.3）。
- **コマの速さ（fps）** は、この WS では上がりません。CPU の量は同じだからです。fps は SMP（WS208）か描画の削減（WS211）で上がります。

## 段と閾値（8 節）

| 段 | 内容 | 次へ進む条件・受け入れ |
| --- | --- | --- |
| p002 | 測る＋cursor の表示の依頼を 1 refresh に 1 回に（実装済み） | Pi で cursor の表示が約 60 回/秒以下 |
| p003 | 描く物の一覧（まだ同じ thread で描く） | 一覧から描いた命令が今と同じ（host 試験）、画が同じ（T1）。p004 へ進む閾値: 一覧を作る時間が普通のコマで p90 ≤ 8ms・最長 ≤ 16.7ms、重いコマ（300 draw 以上）で p90 ≤ 16.7ms・最長 ≤ 25ms。満たさなければ WS211 の削減を先に |
| p004 | R・C・I の thread | 試験（1 歩ずつの host 試験、ThreadSanitizer）、box_lag の p99 ≤ 16.7ms（必達）と最長 ≤ 16.7ms、M の 1 回の最長 ≤ 33.3ms（pointer だけ・App Home の開閉・drag の場面で。app の起動は p99 を記録） |
| p005 | W（文字の形・壁紙） | 日本語の画面で一覧を作る最長が下がる、壁紙の変更の間も p004 と同じ条件 |
| p006 | 規約の見直し | build の warning 0、host 試験 PASS |

## Pi が 1 core であることの制限（10・11 節）

- 今の Pi の kernel は 1 core しか使いません（WS208 まで）。thread にしても同時には動かず、順番に動きます。
- それでも効くのは、マウスの入力が来た時に I が起き、描画中の M や R を横取りして先に位置を書けるからです（kernel は起きた thread を次の安全な点で切り替える。遅れは 1 tick 程度の見込み）。
- ただし R や C が kernel の中で長い処理（GPU の命令の解読、最大 11〜19ms）にいる間は、I も待ちます。box_lag の最長が 16.7ms を超えるとしたら主にこれで、その時は kernel の時刻の記録と並べて原因を確かめ、SMP（WS208）・kernel への依存として返します。
- Pi には入力の自動化が無いので、p004 の Pi の場面（pointer だけ 10 秒、App Home の開閉 5 回、drag 10 秒、app の起動）はユーザーか Q1 の手で行います。

## ユーザーに見てほしい点（2026-10-12 確認済み）

1. thread の分け方（M に窓への通知と描く物の決定を残し、他を R・C・I・W へ）。
2. 必達を「cursor の位置の遅れ（box_lag）の p99 ≤ 16.7ms」にし、画面の 60fps を WS141 と合わせて判定すること。
3. p003 で一覧を作る時間が閾値に届かなければ、WS211 の描画の削減を先にすること。
