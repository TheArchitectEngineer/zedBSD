# WS213 p001 review-1（design-reviewer、6a2d96c6d）— 要点
結論: S2 に進めない。M0 可（present の内訳と display 側の時刻を足す）、C0 条件付き可、S1 条件付き可（WS211 p003 段 2・p005・p006 の後、遅延作成と set の正規化を先に）、S2・S3 不可。
C1 画面に映る cursor の速さは C0・S2 では上がらない: libvulkan の present の worker は queue ごとに 1 本（wsi-swapchain.c:2664-2710、:2745 no later job can overtake）、各 job の GPU の fence を UINT64_MAX で待つ（:2776-2782）、cursor の plane と出力のコマは同じ compose->queue（cursor-plane.c:468,500、compose.c:2813,2831）。§8 の「C0 と S2 は B-u を前提にしない」は誤り。KWL CURSOR_PLANE present の時刻は M が呼んだ時刻（cursor-plane.c:509-510）で画面に出た時刻ではない。直し: 重いコマの間の cursor の 60fps の判定は WS141 p016 (B) の B-u の後への依存、測るのは display 側の時刻（kernel の CURSOR_SET・MOVE、B-u の event_us）。
C2 写しの置き換え・捨てで walk の時に確定した副作用が巻き戻らない: layer-cache.c:291-312（decided_anim・keys[HOME]）、:538-551（valid・inflight）、shot.c:335（SHOT_RECORDED → kwl_shot_complete shot.c:355-372 が書かれていない buffer）、import.c:229-242・compose.c:609（layout の list）、shm.c:604-619・622-631（damage の行だけ写し直後に release）、壁紙・ぼかし・glyph の staging の更新の依頼、heads.c:1272-1275・1313、compose.c:2525。世代の古い写しを R が捨てる経路も同じ。直し: (a) pull の形（R が次をくれと知らせ、M はその時に walk を 1 回だけ、H5 も解ける）を推す、(b) 一回きりの効果を写しの完了で確定・捨てられたら戻す。
H1 shm の画像の寿命と walk が読む値（compose.c:1986-1997、3004-3077、shm.c:187、575-590、walk の読み compose.c:2124-2128,2165、draw shm.c:599-601 → compose.c:2257）→ M が commit の時に import の記録と metadata を同期で作り R は Vulkan の object だけ、古い shm の画像は参照する全写しの完了で退役。
H2 M が呼ぶ Vulkan の列挙が足りない: cursor の形の画像（遅延作成 cursor.c:262-270,388、image_make cursor.c:722 → shm.c:784-788、vkQueueSubmit＋WaitIdle shm.c:877-882、compose->pool shm.c:842、set_get shm.c:801、host_images の list shm.c:796-797）、backdrop の作成（backdrop.c:69-79、395、459）、load pass（compose.c:2283）、大きな字（glass.c:2147-2152、greeter.c:1633、vkDeviceWaitIdle）、import の layout の溢れ（import.c:248-252、348、353）、import の descriptor set（import.c:258,276、compose.c:2005-2083）、shot の buffer（shot.c:445,472）→ 全部を表に、作成は open・park の時か R への同期の依頼、非同期の作成の結果で walk を分岐させない。
H3 cursor の present は queue_lock の trylock があっても R を待つ: vkQueuePresentKHR は queue->mutex（wsi-swapchain.c:557）、R は vkQueueSubmit の間それを持つ（queue.c:333、422-460）、present_record は context->mutex（context.c:496）の下で R の End の decode と競る、capacity の待ち（queue.c:362-366）→ zedBSD の libvulkan では compositor の queue_lock を使わない（Mesa の build だけ）、M0 で mutex の待ちを測る、本当の解決は B-u。
H4 park の deadlock と R の上限の無い待ち（acquire は UINT64_MAX compose.c:561、今は os_paused・sleep_hold で draw を呼ばない display.c:118,160-166、session の pause backend-host.c:46）→ R の acquire と W の待ちを上限付きの繰り返し、pause の予告を R に先に。
H5 置き換えの回数と 1 core と damage の履歴（約 125Hz の walk の捨て、KWL_DAMAGE_HISTORY 8 compose.h:270 を超えて全体 compose.c:2299-2300）→ pull の形、frame の番号は R が取った時に。
H6 ユーザーの合意（master.md:546「最新の画面の状態の写し」）からのずれ: display list で walk を M に残す → ユーザーに明示して確かめる、「ユーザー了承済み」は言い過ぎ。
M1 heads（heads.c:316-361,370-391、1274,1313、487-490）→ head ごとの条件付きの区間、R が結果を返し M が完了で確定。M2 submit の結果が server の状態を書き換える（compose.c:2829-2845 switch_proving・kwl_displays_move_settled、2848-2853 output_lost、heads の lost）→ 完了の記録に。M3 glyph（色の emoji の metrics glass.c:3199-3240、予備の font の途中の open 3105-3125、未着の job の番号、R は写しの番号までの W の結果だけ）。M4 game mode（scanout.c:90,284、display.c:174-186）を park の一覧に。M5 R が region を狭めるのは S2 ではしない（SetScissor shell.c 2 か所・backdrop.c:136、backdrop の end の全体の renderArea backdrop.c:128-131）。M6 「cursor の present 1 回約 3ms、main の 6 割」は推定 → C0 は M0 で確かめてから。M7 Phase を p002（M0＋C0）、p003（S1）、p004（S2）、p005（S3）、規約に分け、S5・S6 は Future Work。S1 は P3 の WS211 p005・p006 と衝突。M8 試験に置き換えの時の layer の焼き・shot・layout・shm の行・世代の古い写しの破棄・遅延作成、golden の比較で descriptor set の handle を正規化。M9 compose-bind.c:46-48 の鍵は VkDescriptorSet の値、kwl_compose_set_put は bind_forget（compose.c:2036-2038）→ 鍵を（import の pointer、種類、世代）に。
Low: C0 で plane の shown の切り替え（cursor-plane.c:165-168）は間引かない、間引きは「最初の動きは即時、最後の位置は周期の終わり」。compose->command を直に使う所（compose.c:2365〜、layer-cache.c:184）は型の違いで見つからない。KWL LAT・FIRST_FRAME の意味の定義し直し。retire（objects.c:739）と shm の写し（shm.c:146）は in_flight で止まり pipeline では飢える。
