## H1 specialization constant が無い（WS284 には blocker）

- 場所: design §0「前段は変えない」、§1.6「specialization constant: 前段が処理する（`OpSpecConstant*` は既定値で畳む …p003 で確かめる。YOLOX の kernel は push constant で足りる）」。
- 根拠:
  - Z `src/drivers/gpu/compiler/spirv.c` 116〜119 行は `OP_CONSTANT_TRUE/FALSE/CONSTANT/CONSTANT_COMPOSITE`（41〜44）だけを定義し、`OpSpecConstant*`（48〜52）を扱う code は frontend のどこにも無い（`grep -n "SpecConstant\|5[012]U" spirv.c` に該当なし）。`spirv-compute.inc` 197〜198 行は LocalSizeId の spec constant を明示で断る。
  - Z `vk/vulkan-pipeline-build.c` 219 行は `pSpecializationInfo != NULL` を断る。i915 `render/pipeline.c` 923 行、PowerVR `vk/vk-draw.c` 239 行、amdrdna `vk/vk-pipeline.c` 294・469 行も map entry のある specialization を断る。libvulkan（`codec.c` 3148〜3158 行）は送るだけ。
  - [WS284 design](../../ws284/design.md) §3.6 の `conv1x1.comp` は「画素 P 個（specialization constant、既定 4）」、§3.7 は「specialization constant」を WS283 に求め、§8 U2 で「通すか」を WS283 に問うている。
- 起こる事: WS284 の shader の SPIR-V は OpSpecConstant を持つので、bcm2711 の compile が断る（推測: 未知の opcode の refusal の経路）。既定値で畳むだけでも frontend の変更が要り、`pSpecializationInfo` の値を使うなら kernel の pipeline の decode も要る。frontend は i915・PowerVR・nvrtx・amdrdna と共有なので、所有と回帰の範囲が WS283 の外に広がる。
- 修正案: (a) WS284 の側で spec constant をやめ、P ごとに別の SPIR-V を作る（regenerate.py で #define を変える）か push constant にする、または (b) WS283 に「frontend: OpSpecConstant{True,False,,Composite,Op} を VkSpecializationInfo（無ければ既定値）で OpConstant に畳む」Phase を足し、共有の frontend を変える事を Q1 と他の GPU の WS に通す。どちらにするかを D6 として user／Q1 の判断に上げる。§0 と §1.6 の「前段は変えない／前段が処理する」を直す。

## H2 scheduler は fragment 専用（compute は詰められない）

- 場所: design §1.1「scheduler と register の割り当ては 1 つの直線の block だけを扱う」、§1.5「scheduler: 今は 1 block だけ。branch と loop の先頭を block の境にし、block ごとに詰める」、§3.3 の効率 30〜50%、§4 p004 8〜12 LW。
- 根拠: Z `compiler/shader.c` 560〜577 行「A program the scheduler refuses, and every vertex program, keeps one recorded operation per word in source order」、`if (compiler->binary->stage == BCM2711_SHADER_FRAGMENT) error = bcm2711_shader_schedule(compiler);`。`shader-schedule.c` 8〜20 行・`shader71-schedule.c` 9〜21 行は「Fragment program scheduling」で、tail（最後の switch の対、tile の書き込み、`schedule_tail`・`tile_nodes`）を前提にする。規則の外の transaction（TMU の一般の書き込み、ldunifa、SYNCB）があると黙って source 順に落ちる（同 18〜20 行）。
- 起こる事: compute の program は add と mul の対が無く、遅延は保守の NOP のまま。1 MAC = fmul＋fadd の 2 語、TMU の待ちも隠れない。§3.3 の「1×1 conv は peak の 30〜50%」「最初の素直な kernel で 3〜8 fps」は対になった語を前提にしており、scheduler を compute に広げない限り成り立たない（推測: さらに数倍遅い）。p004 は「block ごとの scheduler」を 1 行で持つが、実際の仕事は 4.2（2360 行、accumulator と promote あり）と 7.1（2068 行）の 2 つの scheduler に、(1) compute の終わり（tile 無し、TMUWT が最後の語でない）、(2) TMU の一般の access と FIFO、(3) SYNCB・BARRIERID・thrsw、(4) branch・遅延の slot・uniform の位置、(5) `verify()` の値の simulate を複数の block に、を足す事になる。
- 修正案: 「直線の compute の schedule（両版）」を p003 の後の独立の Phase（例 p003b、6〜10 LW）にし、branch の schedule は p004 に残す。§3.3 に「p007 の数字は schedule の有無で 2〜4 倍変わる」と明記し、p007 の R5 で scheduled/unscheduled（`binary->scheduled`）を記録する。

## H3 試験 R2 の supergroup の経路が誤り、supergroup・部分 batch を通る試験が無い

- 場所: design §3.2 R2「local size 256 と 48〈supergroup の経路〉」、§1.4・§2.4 の supergroup の選び方。
- 根拠: M `common/v3d_util.c` 45〜49 行「If the workgroup size is a multiple of 16 … return 1」。48 = 3 × 16 なので wgs_per_sg = 1。R0（32）・R1（64・256）・R2（256・48）・R3（conv、local size の記載無し、WS284 は 64）も全部 16 の倍数。
- 起こる事: CFG3 の wgs_per_sg・batches_per_sg、CFG4 の余りの式、wg_in_mem、supergroup の中の barrier（§1.4）、slice をまたぐ supergroup の可視性（risk R1）のどれも実機で一度も通らない。H3 の host の照合（M の式との一致）は式の写し誤りしか見ず、hardware の意味の誤りは見つからない。
- 修正案: R2 の 48 を 24・40（barrier あり／なし）に替え、さらに「1 workgroup だけ、wg_size 24」（部分 batch、supergroup も詰められない）と「wg_size 8 × 3 group」（余り）を足す。期待値に「範囲の外の word が書かれていない」（buffer の前後に canary）を入れる。

## H4 loop の branch が dispatch されていない lane を数える

- 場所: design §1.5 本文「QPU には channel ごとの実行の mask が無い（fragment の MSF は compute で使わない）」、手順 1「loop の前: active = 全 lane 真」、手順 3「どれかの lane が active なら先頭へ branch（ANYA）」。
- 根拠: M `compiler/nir_to_vir.c` 4565〜4569 行（loop）・4235〜4241 行（if）: `branch->qpu.branch.msfign = V3D_QPU_MSFIGN_P;`「Pixels that were not dispatched or have been discarded should not contribute to looping again」。同じ code が compute でも使われる（stage の分岐は無い）。
- 起こる事: batch の 16 lane が埋まらない時（wg_size が 16 の倍数でなく supergroup で埋まらない、余りの workgroup、H3 の場合）、dispatch されていない lane の active が真のまま残り、その lane の値（payload の残り、ゴミ）から作った loop の条件で余計に回る。最悪は止まらず、2 秒の hang の判定（L5）で GPU の全体の reset になり compositor も巻き込む。その lane の述語付きの TMU の access も address がゴミになる（H5 の clamp が無いと他の memory を読み書きする）。
- 修正案: loop と（将来の）SKIP の branch に msfign=P を付ける。「active の初期値 = dispatch された lane」（MSF から作る、または LocalInvocationIndex < wg_size）にする。CSD の batch で MSF がどう立つかは M の code からの推測なので、lane の model に「dispatch されていない lane」を入れ、H3 の部分 batch の実機の試験で確かめる。

## H5 shader の計算した address の clamp は隔離の要（全部の道で必須）

- 場所: design §1.3「範囲: … descriptor の範囲に clamp する（… Vulkan の robustBufferAccess と同じ振る舞い）」、§1.3 の ldunifa、§1.4 の共有 memory、p008 の vector の load・store。
- 根拠: Z `mmu.c` 9 行「V3D 4.2's single-level page table」、`v3d-job.c` 215〜227 行の compute の検査は code と uniform の span だけを見る（storage・shared の span は job に無い）。V3D の page table は 1 つで、全 session（Keiland の compositor の framebuffer を含む）の buffer が同じ VA の空間にある。
- 起こる事: clamp を「robustness」として最適化で省く・vector の道や shared・ldunifa で漏らすと、任意の app の compute shader が他の session の GPU の memory を読み書きできる（情報の漏れ、compositor の破壊、MMU の違反による全体の reset）。特に ldunifa は 1 回 address を書くと以後の読みが自動で進むので、loop の回数が push constant で決まる場合、読む語の数を compile の時に抑えられない。
- 修正案: (1) 「全ての shader の計算した address（storage・shared・ldunifa・vector・将来の atomic）は binding の範囲に clamp する。省く最適化はしない」を設計の不変条件に書く。(2) 実装は predicate＋0 の選択より、M の robust access と同じ address の clamp（`base + umin(offset, range − bytes)`）が安い: Vulkan の robustBufferAccess は範囲外の読みに buffer の中の任意の値、書きに buffer の中への書き込みを許すので、1 access に umin 1 つで済み、flag を使わず、M8 の「全 lane が無効の lookup」も減る。range < 4（空の binding）は dummy の page に向ける。(3) shared は `offset < shared_bytes` に clamp。(4) ldunifa は loop の各回で unifa を clamp 済みの address で書き直すか、読む語の数が静的に範囲に収まる時だけ使う。(5) 試験に「範囲外の store が隣の canary buffer を変えない」を入れる（L4）。

## H6 ldunifa の制約が設計に無い

- 場所: design §1.3 最後の段落「uniform の offset … の load は `ldunifa` … SSBO にも使う」「conv の重みはこれで読む」、§3.3、p008。
- 根拠: M `compiler/nir_to_vir.c` 3184〜3190 行「We can only use unifa with SSBOs if they are read-only. Otherwise ldunifa won't see the shader writes to that address (possibly because ldunifa doesn't read from the L2T cache)」、3163〜3180 行「the address that is used to write to the unifa register is taken from the first lane and if that lane is disabled by control flow then the value we read may be bogus and lead to invalid memory accesses」。Z `ir.h` の `LOAD_STORAGE` は access（NonWritable）の印を持たない（ir.h の LOAD_STORAGE の注記）。
- 起こる事: (1) IR だけでは「この binding は読みだけ」が分からず、frontend の変更が要る（H1 と同じく「前段は変えない」と矛盾）。(2) 同じ shader が書かない buffer でも、前の dispatch が TMU で書いた data（WS284 の活性化）を ldunifa で読むと、L2T の clean が済むまで古い値を読む。p008 の「連続の CSD の間の L2T の clean を省く」と組むと誤る。(3) 実行の mask の下（H4）で lane 0 が無効だと address がゴミ。(4) divergence の解析の材料（§1.3「定数・push・uniform・group id・uniform な loop の counter」）に `LocalInvocationId.y`（local size の y が 1 なら 0）が無く、WS284 の conv1x1 が出力の channel の束を `gl_GlobalInvocationID.y` から取る形（推測: WS284 §3.6 の 1 次元・2 次元の local size 64）では重みの offset を uniform と判定できない。
- 修正案: ldunifa を使う条件を「binding が NonWritable（IR に印を足す）かつ、その execution の中で前の dispatch が書いていない、または間に L2T の clean がある、かつ uniform な制御の中、かつ H5 の clamp」と書く。divergence の解析に local size が 1 の軸の LocalId を uniform とする規則を足す。WS284 に「重みの buffer を `readonly` で宣言する」を伝える。

## M1 register の数の誤りと loop 変数の合併

- 場所: design §1.5「4 thread は 1 thread あたり rf 28 個、2 thread は 56 個の expression の register」、R3（risk）。
- 根拠: Z `compiler/shader-private.h` 29〜31 行 `BCM2711_SHADER_FIRST_REGISTER 4U`・`REGISTER_END 60U`・`QUAD_REGISTER_END 28U` → 4 thread は rf4〜rf27 の **24**、2 thread は rf4〜rf59 の 56。さらに 42 行 `SCRATCH_RESERVE 4U`、45 行 `CONSTANT_RESERVE 12U` が実際に使える数を減らす。Z `ir.h` 冒頭: loop の変数は loop の前と終わりの `MOVE` で定義される。
- 起こる事: WS284 の conv1x1（出力 4 × 画素 4 = 16 個の和を loop の変数で持つ）では、§1.5 の「loop の中の読みを loop の終わりまで延ばす」と、終わりの `MOVE` の元（新しい和）と先（loop の変数）が別の register なら、loop の終わりに 16＋16 個が同時に生きる。入力 4 画素 × vec4 の 16 語、address、counter を足すと 56 を越える見込みで、spill が無いので断られる（推測: 実際の数は shader の形で変わる）。
- 修正案: §1.5 の数を 24／56 に直す。p004 に「loop の変数の MOVE の合併（新しい値の定義が古い値の最後の読みなら同じ register に置く）」を入れる。H2 の試験に WS284 の実際の `conv1x1.comp`（P=4）を入れ、2 thread で通る事を p004 の完了の条件にする。

## M2 TMU の FIFO と sequence の規則の欠け

- 場所: design §1.3 の load・store・FIFO の段落、p008 の vector の store。
- 根拠: M `compiler/nir_to_vir.c` 700〜705 行「Make sure we won't exceed the 16-entry TMU fifo if each thread is storing at the same time. while (tmu_writes > 16 / c->threads) c->threads /= 2;」（入力の FIFO、1 sequence の TMUD＋TMUA の数）。同 640〜690 行: 複数語の store は `num_components = tmu_writes − 1` から VEC2〜4 の config を作り TMUAU に書く（TMUA は既定の 32 bit・1 語だけ）。同 600〜609 行: 依存のある未受領の TMU の flush が sequence の途中に入るのは不可。同 4523〜4528 行: 「Always process pending TMU operations in the same block they were emitted」。
- 起こる事: (1) vec4 の store（TMUD 4＋TMUA 1 = 5）は 4 thread（上限 4）では不可で、2 thread に落とす必要がある。設計は出力の FIFO しか書いていない。(2) §1.3「data を TMUD に 1〜4 回書いてから TMUA に address（連続の 1〜4 語を書く）」は TMUA では 1 語しか書けない。(3) scheduler が TMUD … TMUA の間に別の ldtmu・thrsw を入れると不正な sequence になる。(4) branch を入れた後、block をまたいで ldtmu を残すと、未実行の側の FIFO の数が合わない。
- 修正案: §1.3 に入力の FIFO の上限と thread の数の選び方、TMUAU＋config の規則、sequence の不可分、block の終わり（branch の前）の flush を書き、lane の model の FIFO の検査に入力の FIFO も入れる。

## M3 branch・thrsw・unifa・MULTOP の hazard（試験で検出できない）

- 場所: design §1.5「最初は遅延の slot を NOP で埋め、後で詰める」、§3.1 H1（encoder の照合）。
- 根拠: M `compiler/qpu_schedule.c` 2375〜2390 行（遅延の slot に branch・thrsw・unifa の書き込み・uniform を読む命令を置かない）、2403〜2405 行（thrsw の後 2 語・branch の後 3 語の中に branch を置かない）、`qpu_validate.c` 138〜141 行（MULTOP と UMUL24 の間の thrsw は rtop を消す）、304〜305 行（branch の遅延の slot の thrsw）、376〜379 行（GFXH-1625）、445 行（program の終わりの THRSW）。
- 起こる事: 「後で詰める」時に uniform を読む命令（ldunif・push・定数の materialize）を遅延の slot に入れると、branch の `ub` の相対の巻き戻しの数がずれ、以後の uniform が全部 1 語ずれる。MULTOP/UMUL24 の間に scheduler が thrsw を入れると IMUL の結果が壊れる。H1 は単語の encode を M の packer と照合するだけで、H2 の lane の model も同じ作者の理解で書くので、規則の誤解は両方をすり抜ける。
- 修正案: scheduler に rtop を資源として持たせ、遅延の slot の規則を設計に列挙する。H1 に「M の qpu_validate の規則（上の列挙）を独自に書き直した host の検査器」を足し、H2 の全 binary と既存の graphics の binary に流す（M の file を写さず、規則の一覧から書く）。

## M4 shared の arena の分割と大きい dispatch

- 場所: design §1.4「上限を越える dispatch は workgroup の base の offset（CFG0〜2 の下位 16 bit、M `v3d_csd.h` WG_OFFSET）で複数の CSD job に分ける」、§2.3 手順 3、§2.4 CFG0〜2。
- 根拠: M `vulkan/v3dv_cmd_buffer.c` 4302〜4310 行は base を `job->csd.wg_base` に置くだけで CFG0〜2 の下位 16 bit を書かず、`v3dv_uniforms.c` 638〜640 行・`nir_to_vir.c` 3741〜3748 行で uniform（`QUNIFORM_WORK_GROUP_BASE`）として shader に渡す。M は WG_OFFSET を使わないので、その時の payload の WorkgroupId に offset が足されるか、wg_in_mem がどう数えられるかは M から分からない。M `nir_to_vir.c` 4806〜4818 行は wg_in_mem を (16 − b) bit に mask する。Z `v3d-job.c` 20〜21 行 `JOB_POLL_STEPS`・`JOB_PROGRESS_WINDOWS 4U`（500 ms × 4 = 1 job 2 秒の上限）。
- 起こる事: (1) WG_OFFSET の意味が想定と違えば、分けた後の job で WorkgroupId がずれる（結果の誤り）か、wg_in_mem が job の間で同じ slot を指す（推測）。(2) wg_in_mem が (16 − b) bit なら、同時に区別される slot は高々 2^(16−b) 個（b = 6 で 1024）で、M の「shared_bytes × workgroup の数」は大きい dispatch では過大（推測: hardware が slot を巡回させる）。分割しなくても arena は min(num_wgs, 2^(16−b)) × shared_bytes で足りる可能性がある。(3) maxComputeWorkGroupCount 65535³ では CFG4 の batch の数が 32 bit を越え、2 秒の上限も越えるので、arena と無関係に分割が要る。
- 修正案: 分割は M と同じく base を uniform で渡し（`LOAD_SYSTEM` の GROUP_ID に足す）、CFG0〜2 の WG_OFFSET は 0 のままにする。arena の大きさの規則（min の式）は実機の試験（shared を使う大きい dispatch で、各 workgroup が自分の slot の番号を書いて重なりを見る）で決めるまで M と同じ数を取る。CFG4 の溢れと 2 秒の上限による分割を §2.3 と H3・H4 に足す。

## M5 COMPUTE の queue flag を出すと他の component が compute を使い始める

- 場所: design §2.2 queue「1 つの family に `VK_QUEUE_COMPUTE_BIT` を足す」、§5 D4（atomic・storage image・subgroup は範囲外）。
- 根拠: Z `userland/desktop/libglesv2/gles.c` 2455〜2470 行: display の family が COMPUTE を持てば `state->compute = 1` で OpenGL ES 3.1 の compute を出す（同 1437〜1457 行の版の選択、2253〜2255 行）。`userland/base/noct/noct/src/accel/accel_vulkan.c` 1131〜1139 行は COMPUTE の family を選んで compute の accel を使う。`userland/tests/vkreset`・`vkcoherency` も compute を使う。Vulkan 1.0 は graphics の family に compute を要求するので、flag を出す事自体は正しい。
- 起こる事: WS283 の途中の段階（loop・shared・barrier が未完、atomic・image は D4 で範囲外）で flag を出すと、Pi 上の GL の app が GLES 3.1 を見て compute shader（atomic counter・image の load/store を含みうる）を作り、pipeline の作成で断られて描画が壊れる。noct の accel も compute の道に入る。WS283 の試験はこれらを流さない。
- 修正案: flag を出すのは p007 の R0〜R3 の後にし、その Phase の確かめに libglesv2 の 3.1 の compute の経路と noct の accel、`vkreset`・`vkcoherency` の Pi 5 での実行を足す。atomic・image が無い間は libglesv2 を bcm2711 で 3.0 に留めるか（libglesv2 の所有の WS と相談）、D4 の判断に「GLES 3.1 を Pi で出さない」を含める。

## M6 dispatch の往復の費用と WS284 の問い

- 場所: design §2.1「1 step = 1 native pass、session が順に 1 step ずつ回る」、§2.2 pipeline「code を GPU の memory に置く（graphics の shader の置き方 `native-shader.c`/`native71-shader.c` と同じ）」、§2.3 手順 5、§3.3「1 dispatch の往復を 30〜80 µs と置く」、§3.3 最後の段落、R2（risk）。
- 根拠:
  - Z `render-worker.c` 1900〜1908 行: executor は step を 1 つ終えるたびに `sched_yield()` する。
  - Z `vk/vulkan-native-draw.c` 321 行 → `native-storage.c` 228〜280 行: graphics は program を pass（step）ごとに `bcm2711_native_program_upload` で native storage に写して clean する（pipeline の作成の時ではない。view の cache で map の再利用はある）。設計の「作る時に置く、graphics と同じ」は今の code と食い違う。
  - Z `v3d-job.c` 504〜545 行・`v3d71-hardware.c` 439〜505 行: CSD の前に L2T の flush（FLM=0、待たない）と slice の無効化、後に TMUWCF の flush（待つ）と L2T の clean（FLM=2、待つ）。
  - [WS284 design](../../ws284/design.md) §3.7 最後の項・§8 R2・[ws284 phase001](../../ws284/phase001/phase.md) 32 行: 「同じ submit の中の CSD の job の間は clean を省けるか」を WS283 に問う。WS283 の design は p008 の候補に 1 行置くだけで答えていない。
- 起こる事: (1) 122 dispatch の各 step の後の yield で、同じ CPU に実行可能な thread（camera、demo の NMS、compositor）があると、その time slice（tick は 10 ms、`include/kern/clock.h`）を失いうる（推測: zedBSD の scheduler の yield の振る舞いによる）。R5 は空の dispatch を単独で測るので見えない。(2) 122 回の program の upload（分配・clean・retire）が往復に乗る。(3) WS284 の判断の材料が無い。
- 修正案: (1) 同じ execution の compute の event が続く時は、他の session が ready でなければ yield せずに続ける（または compute の連続を 1 step で回す）案を §2.1 に置き、R5 を「Keiland の desktop と CPU の負荷の下」でも測る。(2) compute の code は pipeline の作成の時に 1 回 native storage に置き、pipeline の破棄と実行中の job の retire まで持つ、uniform の流れは execution ごとの ring に置く、を明記する。(3) WS284 への答え（設計の案、実機で確かめる）: GPU → GPU の可視性に要るのは TMUWCF の flush と次の job の前の slice（L1T）の無効化で、L2T の clean（DRAM への書き戻し）は CPU が読む前（indirect の 3 語、UBO を uniform の流れに写す step、host の読み）と ldunifa で GPU の書いた data を読む前（H6）だけに要る（推測: 次の job の前の FLM=0 の flush が書き戻しも行う）。kernel の job に `clean_output` の様な選択を足せば execution の最後だけにできる。CFG3 の OVERLAP と CSD の queue への積み増しは、依存の無い dispatch の間だけ（依存のある間は cache の操作が入らないので不可）。(4) 費用の推定を確かめる安い手: 今ある V8 の診断の dispatch を N 回回して往復の時間を測る（p002 の前でもできる、T1 に依頼）。

## M7 整数の除算

- 場所: design §1.1 表「`UDIV`・`UMOD`・`IDIV`・`IREM` … 定数の除数だけで足りる（x・y の分解）。定数は乗算と shift」。
- 根拠: QPU の整数の乗算は MULTOP＋UMUL24 で下位 32 bit だけ（design 自身の §1.1、M `v3d_compiler.h` 1541〜1544 行）。M は `nir_opt_idiv_const`（mul-high を使う）の後に `lower_mul_high = true`（`vulkan/v3dv_pipeline.c` 200 行）で mul-high を複数の乗算に展開し、一般の除算は `nir_lower_idiv`（`compiler/vir.c` 1831〜1835 行、float の逆数＋補正）。
- 起こる事: magic number の除算は 32×32 の上位 32 bit を要するので「乗算と shift」では書けない（2 の冪は shift で書ける）。また WS284 の decode（anchor の index → grid の x・y、level の幅は push・UBO の値の可能性）や WS285 の debayer（幅で割る）は除数が実行の時の値になりうる。後段が断ると WS284・WS285 の shader が通らない。
- 修正案: 2 の冪は shift／and、それ以外は定数・変数を問わず「u2f、RECIP、乗算、f2u、整数の補正 2 回」（被除数 < 2^24 なら補正 1 回）の一般の形を p003 で入れる。WS284・WS285 の shader が使う除算の形を p003 の前に確かめる。

## M8 全 lane が無効の条件付きの TMU の lookup（推測の risk）

- 場所: design §1.3「述語（IR の `component` 1 と predicate の src）: TMUA の書き込みを条件付きにすると、条件の外の lane は access しない … load も store も同じ」。
- 根拠: Z `ir.h` 冒頭「Structured control flow is if-converted by the parser: both sides of a selection run for every channel」→ if の中の load・store は全部述語付きで、条件が batch の 16 lane 全部で偽の時も実行される。M は非一様な if・loop で active の lane が無い block を `ALLNA`・`ANYA` の branch で飛ばす（`nir_to_vir.c` 4235〜4241・4349・4565 行）ので、全 lane が無効の条件付きの lookup をほとんど出さない。
- 起こる事（推測）: 全 lane が無効の TMUA の書き込みが lookup を出さないなら、無条件に置いた ldtmu が来ない結果を待って thread が止まる、または FIFO の数がずれる。store なら TMUWT の待ちの意味が変わる。hardware の文書が無く、M からは安全とも危険とも言えない。
- 修正案: load は H5 の address の clamp で TMUA を無条件にし（範囲外・無効の lane は範囲の中の dummy の address、結果は捨てる）、store だけを条件付きにする。p007 に「16 lane 全部で述語が偽の load・store」の実機の試験を足す。branch ができた後は M と同じく「active の lane が無い時は block を飛ばす」を SKIP で使う。

## M9 Phase の分け方・依存・見込み

- 場所: design §1.6 最後、§4 の表、ws.md の Phase の表。
- 根拠と問題:
  1. §1.6「compute の lowering は 4.2 の `shader-compute.c` を作り、違いのある所だけ 7.1 の写し」なのに、受け入れと実機は Pi 5（7.1）で、p009「Pi 4（4.2）: host の H1〜H3 の 4.2 の版」2〜4 LW。p003〜p005 が両版を実装するならその LW は少なすぎ、7.1 だけなら p009 の 2〜4 LW で 4.2 の branch・schedule（accumulator・promote のある別の 2360 行）を足すのは無理。どちらかに決めていない。
  2. Z の 4.2 の `run_compute`（`v3d-job.c` 504 行）は呼ぶ所が無い（`BCM2711_V3D_JOB_COMPUTE` を作るのは `v3d71-diagnostic.c` 449 行だけ）。「4.2・7.1 とも既にあり」は「4.2 は一度も走っていない」と書くべき。
  3. lane の model（`plan/tools/v3d-qpu/qpu-machine.c` 1067 行・`plan/ws279/tests/qpu71-machine.c` 1131 行）に thread・barrier・TMU の memory と FIFO・branch・uniform の巻き戻し・dispatch の mask を足す仕事は H2 の前提だが、どの Phase の LW にも分けて数えていない。
  4. R1〜R5 の試験の program（C・GLSL・SPIR-V・`plan/ws283/tests/` の config.mk と個別の file の複写、AGENTS 2026-10-04 の規則）を作る仕事が無い。
  5. 最初の実機の確かめが p007（p005 の後）。CSD の構成・payload・TMU の store の誤りは、p003＋p006 だけで R0（fill）・R1（saxpy）で見つかる。p006 は p004・p005 と並べられるのだから、p006 の直後に R0・R1 の実機の確かめを置けば、p004・p005 の前に前提の誤りが分かる。
  6. §4 最後「WS284 は p006 の後 … 層の kernel を書き始められ」: WS284 の kernel は ci の loop（p004）と spec constant（H1）を要する。正しくは p004＋p006＋H1 の解決の後。
  7. p006 が p004・p005 と並行で `shader.h` の binary の形（uniform の種類、local size、shared bytes、barrier の有無）を同時に変える。
- 修正案: 7.1 を元にして 4.2 を写しにする（Pi 5 が唯一の実機と受け入れ）か、両版を同時に進めるかを決め、4.2 の port を現実の LW（推測: 8〜15）の Phase にする。lane の model の拡張（4〜6 LW 程度）と試験の program を Phase に入れる。p006 の後に「R0・R1 の実機（T1）」の小さい Phase を置く。binary の interface を p003 で先に決める。合計は 51〜77 LW の 1.5〜2 倍の見込み（推測）と明記する。

## M10 barrier を含む loop の deadlock

- 場所: design §1.5 手順 4「barrier を含む loop は前段が『全 invocation が入る loop』に限る」。
- 根拠: Z `ir.h` の `BARRIER` の注記「the parser refuses one after a return and one in a loop not every invocation enters」。回数が lane・thread ごとに違う loop（非一様な trip count）は断っていない。M `common/v3d_util.c` 61〜64 行: 「QPU threads will stall at TSY barriers until the entire supergroup reaches the barrier」。
- 起こる事: 全 invocation が入っても、thread（batch）ごとに回る回数が違えば、早く抜けた thread が barrier に来ず、supergroup が永久に待つ。2 秒で hang と判定され GPU の全体の reset になり、compositor の実行中の仕事も失う（Vulkan では app の UB だが、他の session に波及する）。
- 修正案: 設計に「barrier を含む loop の条件は uniform であること（divergence の解析で証明できなければ compile で断る）」を足すか、受け入れて hang からの回復を R4 で確かめる（`vkreset` の Pi 5 での実行）。

## L1 性能の見込みの不整合

- 場所: design §3.3。
- 根拠と問題: (1) peak は WS283 が 1.15 GHz で 110 GFLOPS、WS284 §5 が 800 MHz で 38.4 G MAC/s（76.8 GFLOPS）。WS279 ws.md 36 行は 1.15 GHz を記録したが、負荷の下でその clock を保つかは未確認。(2) 活性化の読み書きは WS283 が 40〜60 MB、WS284 §5 が約 130 MB。(3) 1×1 conv は出力の channel の束ごとに入力の tensor を読み直す（C_out/4 回、tensor は最大 2.8 MB で L2T より大きい、推測）が、どちらも数えていない。(4) TMU の lookup の速さ（slice あたり 1 clock に何語か）を数えていない。p008 の vector の load の前は 1 語 1 lookup。(5) 「最初の素直な kernel 3〜8 fps」は H2 の schedule を前提にする。
- 修正案: WS284 と同じ前提（clock、MAC・memory の量）に揃え、TMU の速さと読み直しの量を未知の項として明示する。R5 に「TMU の lookup の語 / clock」と「1×1 conv の L2T の miss」（性能 counter の TMU の access・miss、Z `v3d-job.h` 97〜103 行の counter）を入れる。

## L2 limit・descriptor・barrier の欠け

- design §2.2 の限界に `minStorageBufferOffsetAlignment`（M `vulkan/v3dv_device.c` 979 行は 32。WS284 §3.5 が使う）、`maxPerStageDescriptorStorageBuffers`・`maxDescriptorSetStorageBuffers`、`maxComputeWorkGroupSize` の device の報告値（frontend の 128・128・64 と一致させる）を書く。
- §2.4 CFG3 の `wg_size & 0xff` は 256 で 0 になる事を書く（H3 の照合の場合に 256 を入れる）。
- §1.1 の peripheral の一覧に UNIFA（waddr 9、M `qpu/qpu_instr.h` 105 行）が無い（ldunifa に要る）。
- §2.2 barrier の受け付けに HOST の stage・HOST_READ（WS284 の最後の compute → host）と、indirect の DRAW_INDIRECT・INDIRECT_COMMAND_READ を足す。indirect の group の数が 0・65535 を越える時の扱い（skip か clamp）と、indirect の時の arena・NumWorkgroups の uniform を step の時に作る事を書く。

## L3 ID の衝突

- 試験（§3.2 の R0〜R5）と risk（§6 の R1〜R5）が同じ接頭の R を使う。§1.4「（R1）」は risk R1 の意味だが試験 R1（saxpy）と読める。§6 R1「R2 で確かめる」、R2「R5 で測る」も紛らわしい。試験を HW0〜HW5 などに改名する。

## L4 試験の欠け（試験の計画で検出できない誤り）

- payload の y・z: R0〜R3 は 1 次元。local size 4×2×3 と group の数 (3, 5, 2) で、LocalInvocationId・WorkgroupId・NumWorkgroups・GlobalInvocationId を全部 buffer に書いて見る試験が要る（payload0 の上位 16 bit、payload1 の下位 16 bit、index の分解の誤りを検出）。
- 非一様な loop（lane ごとに回数が違う、例 `for (i = 0; i < gid % 7; i++)`）: R3 の conv の loop は一様なので、execute の mask・conditional な MOVE・ANYA の誤りが見えない。
- 2 thread の variant を強制する試験（design §1.5 で未確認と書いた CFG5 の THREADING=0）: どの試験も 2 thread になるとは限らない。
- 範囲外の store が隣の buffer を変えない（H5）、全 lane が無効の述語（M8）、大きい dispatch の分割（M4）、barrier を含む loop（M10）、既存の `vkreset`・`vkcoherency` の Pi 5 での実行。

## L5 payload の移しと hang の上限

- §1.2「program の最初に別の register へ移す」: Z は rf0〜rf3 を expression に使わない（`shader-private.h` 29 行、「Expression storage excludes fragment payload」）ので、4.2 の rf0・rf2、7.1 の rf3・rf2 は pinned のまま読める。移すと register と命令を 2 つずつ無駄にする（7.1 の rf0 は ldunif 等の暗黙の書き込み先なので、7.1 で payload を rf0 に置かない事だけ注意。今の payload は rf3・rf2 なので当たらない）。
- §2.3 手順 5「hang の判定は CURRENT_CFG4 が減らない時」: CFG4 は残りの batch の数なので、全 batch を配り終えた後の最後の batch が 500 ms × 2 の窓で動かないと見なされ、さらに `JOB_PROGRESS_WINDOWS 4U` で 1 job は進んでいても 2 秒が上限（Z `v3d-job.c` 20〜21・549〜660 行）。WS284 の「1 dispatch を数 ms」の根拠としてこの上限を明記する。

## L6 UAPI の注記

- `include/uapi/gpu-op.h` の `GPU_OP_CREATE_COMPUTE_PIPELINES`（956 行）・`GPU_OP_CMD_DISPATCH`（1454 行）・`_INDIRECT`（1462 行）の「bcm2711 has no route」を route を足す Phase で直す（layout の変更ではなく注記だけ。HAL ではない）。

## L7 その他の記述

- §0「storage buffer の load・store・atomic … loop は IR に出てくる。前段は変えない」: H1（spec constant）と H6（NonWritable の印）で前段の変更が要る。
- phase.md「確かめていない事」の「specialization constant の前段の扱い」は、この review で「前段に無い、全 driver が断る」と確かめた（H1）。

## 確かめていない事（この review の限界）

- V3D の hardware の意味（CSD の batch の MSF、WG_OFFSET の意味、wg_in_mem の巡回、全 lane が無効の TMU の lookup、L2T の FLM=0 が書き戻すか、TMU の lookup の速さ、yield の待ち）は M の code と注記からの推測で、文書・実機では確かめていない。各項に「推測」と書いた。
- WS284 の shader の source は未作成なので、除算・divergence・register の見積もりは WS284 design の文からの推測。
- build・host の試験・実機は流していない。
